# 말투 (한국어판)

판단 기준은 이 질문 하나다. **"내가 이 경험을 누군가에게 말로 설명한다면 이렇게 말할까?"** 문장은 내가 한 일을, 내가 겪은 순서대로, 내가 주어가 되어 쓴다. 영어판 말투는 [english.md](english.md)에 있다.

## 기본

| 항목 | 규칙 |
| --- | --- |
| 종결어미 | 한다체(~다), 존댓말 없음. `~다.`만 이어지면 단조롭다. `~었는데`, `~더라`, `~것 같다`, `~ㄹ까 싶었다`를 섞는다 |
| 인칭 | 겪은 일은 1인칭. 막힌 곳, 착각, 판단, 감정은 "나는", "내가"가 주어다. 무인칭은 개념을 설명하는 문단에만 쓴다 |
| 대시 `—` | 본문 1,000자당 1개 이하(제목 구분자는 세지 않는다). 인기 한국어 기술 글 14편은 0~1.2개였다. 정말 끼어드는 말에만 쓴다 |
| `**굵게**` | 1,000자당 4개 이하. 문장 전체를 굵게 하는 건 섹션당 1개까지. `<mark>`와 같은 문단에 겹쳐 쓰지 않는다. 목록 머리말을 굵게 해서 같은 모양으로 늘어놓지 않는다 |
| 영어 | 한국어판 본문에 영어 요약이나 영어 부제를 두지 않는다. 영어는 `GOMEMLIMIT`, `sync.Pool` 같은 식별자로만 들어간다. 영어로 쓴 글은 영어판 파일에 따로 있다 |
| 고객사 환경 | "온프레미스" 또는 "온프레"라고 쓴다. "폐쇄망"이라고 쓰지 않는다. 현장 글에서는 제품명을 일반화한다 |
| 학습 노트 | 가르쳐 주는 말투로 쓴다. 예: "먼저 이것부터 잡고 가자", "숫자로 확인해 보자" |

## 사람이 쓴 문장으로

| 쓰지 않는다 | 대신 |
| --- | --- |
| AI를 주어로 세운 협업 서술. 예: "Claude와 처음 한 일은 코드를 짜는 것이 아니었다" | 내가 주어가 되고, 이유를 먼저 쓴다. 예: "여기에 공고 찾기를 붙이고 싶어서 처음 한 일은 코드를 짜는 것이 아니었다" |
| 명사로 끊는 문장. 예: "A4 PDF가 나오는 스킬 하나." | 끝까지 맺는다. 예: "A4 PDF가 나오는 스킬 하나였다." |
| 요약형 머리말. 예: "한 줄로 답하면 이렇다.", "핵심은 ~다", "정리하면" | 답을 바로 쓴다. 예: "알고 보니 `settings.json` 235번째 줄의 쉼표 하나였다." 머리말 없이 쓴 짧은 답은 리드나 셋째 문단 안에 두면 좋다 |
| 절마다 다음 내용 예고. 예: "이제 ~를 살펴보자" | 리드에서 범위를 한두 문장으로 밝히는 것까지만 쓴다. 예: "온프레미스 3노드 환경에서 겪은 일이라 클라우드에서는 다를 수 있다." |
| 은유나 경구로 마무리. 예: "그 질문이 구조를 지켰다" | 실제로 달라진 것을 쓴다. 예: "구조가 크게 흐트러지지 않았다" |
| 격언처럼 단정하는 정리. 예: "LLM은 숫자를 판단하는 게 아니라 그럴듯한 숫자를 만든다" | 겪은 결과로 쓴다. 예: "점수를 매겨 달라고 하면 숫자는 나오지만, 왜 그 숫자인지는 남지 않는다" |
| 딱딱한 설계 용어나 비유. 예: "데이터 계약", "몸통" | 평소 쓰는 말로 쓴다. 예: "데이터 구조", "공고를 모으고 읽는 부분" |
| 과장된 평가. 예: "생각보다 컸다", "결정적 한 수였다" | 무엇이 어떻게 도움이 됐는지 쓴다 |
| 면접·채점 어휘. 예: "무조건 X는 감점이다", "🔑 답변 공식", "외울 것은 …", "Go는 객체지향 언어인가요?" | 평서문으로 쓴다. 예: "X라는 규칙은 두지 않는다", "확인할 것은 …", "객체지향 언어인지 묻는다면 '부분적으로'라고 답하겠다" |
| 시점을 구분하는 서술. 예: "현장에 없다", "엔지니어가 겪은 일이다" | 쓰지 않는다 |

이 기준은 캡션, `<Note>`, `<Summary>`, h2, `<Stats>` 라벨에도 똑같이 적용한다. 멋을 낸 한 줄보다 실제로 한 일 한 줄을 쓴다.

## AI가 다듬은 티 (티스토리 글 25편을 실측한 결과)

AI 편집을 많이 거친 9~10월 글은 직접 쓴 7월 글과 비교해 세 가지가 달랐다.

- 대시가 두 배였다: 천 자당 5.0개, 7월 글은 2.6개.
- 1인칭이 절반이었다: 천 자당 0.5개, 7월 글은 1.0개.
- 문장 길이 리듬이 일정했다: 표준편차 17~19, 7월 글은 25.

「AI를 쓸수록 커지던 회의감에 대해」가 기준점이다. 대시 1.8개, 1인칭 3.1개, 표준편차 39.

1. **매번 같은 뼈대.** 세 줄 요약 → 번호 설명 → 강조 → 정리 → 회고가 매번 반복된다.
   - `<Summary>`, `<Note>`, `<Stats>`, `<Bars>`, `<Compare>`, `<Carousel>`은 내용이 그 모양일 때만 쓴다. 같은 컴포넌트가 절마다 나오면 그것도 뼈대가 된다.
   - ①②③ 번호 목록은 순서나 개수가 실제로 의미 있을 때만, 글당 한 번 쓴다. "~는 셋이다."처럼 개수를 먼저 선언하지 않는다.
2. **대시와 뒤집기 문장.** 인기 글에서도 대시는 드물었다(한국어 천 자당 0~1.2, 영어 천 단어당 0~2.7).
   - 예고형 대시("X는 하나다 —", "답은 한 줄이다 —", "절반만 맞다 —")는 쓰지 않는다. 답을 그냥 말한다.
   - 대시를 지울 때는 문장을 둘로 나누거나, 쉼표나 괄호를 쓰거나, "그런데", "다만", "알고 보니"로 잇는다.
   - 예: "Go의 값 전달 규칙은 하나다 — 전부 복사된다." → "Go는 함수에 넘기는 값을 전부 복사한다. 헷갈렸던 건 무엇을 복사하느냐였다."
   - "A가 아니라 B다" 반전은 글당 한두 번까지. 남길 반전은 글의 주제문이어야 한다.
3. **절마다 격언처럼 매끈한 결론.**
   - 절은 마지막 사실, 마지막 수치, 내가 다음에 한 행동으로 끝나도 된다. 앞 내용을 다시 요약하는 문장을 붙이지 않는다.
   - 다음 절을 예고하는 문장을 쓰지 않는다. 다음 h2가 그 일을 한다.
   - 아래 꼴은 글 전체에서 3개 이하로 쓰고, 절의 마지막 문장에는 쓰지 않는다.
     - "A와 B는 다른 질문이다"
     - "X가 곧 Y다"
     - "~까지다" (글당 한 번)
     - 예고하는 "~가 필요하다."
     - "문제는 ~ 때 생긴다."
     - "정리하면 이렇다." 뒤에 대구를 붙이는 꼴
     - "얻은 건 ~ 하나였다"
     - "코드가 대신 말해 주지 않는다"
4. **다른 경험인데 같은 리듬.**
   - 겪은 일은 일어난 순서로 쓴다. 언제, 무엇을 하다가, 처음에 뭐라고 생각했고, 그게 왜 틀렸는지.
   - 착각, 막힘, 감정을 지우지 않는다. 예: "처음엔 ~인 줄 알았는데", "여기서 한참 헤맸다", "이건 아직 잘 모르겠다".
   - 실제로 본 구체적인 장면을 하나 넣는다. 인기 글은 첫 문단에 시각이나 장면을 뒀다(예: "새벽 1시가 넘은 시간이라", "OOMKilled 알림을 받았다").
   - 감정과 실수는 꾸미지 말고 사실 한 줄로 담담하게 쓴다(예: "그날은 꽤 창피한 채로 퇴근했다").
   - 모르는 것은 모른다고 쓴다(예: "이게 처음 쓰인 방식인지는 모르겠다", "틀린 데가 있으면 알려 주면 좋겠다").
   - 숫자를 하나씩 박는다. 회고와 후기도 기간, 비용, 개수 같은 수치가 있으면 읽힌다.
   - 문장 길이를 섞는다(표준편차 25 이상). 맺음도 섞는다. 비유는 글당 하나만 쓴다.

## 남의 말 인용

인터뷰·발표를 정리하거나, 문서와 다른 글을 인용할 때의 규칙이다.

- 인용은 `> 인용` 블록에 짧게(한국어 한두 문장, 영어 25단어 안팎) 담고, 바로 아래에 출처 링크를 단다. 영상이나 팟캐스트면 타임스탬프(`12:40`)도 단다.
- 인용 바로 뒤에는 내 반응을 쓴다: 동의, 의심, 내 경험과 대조. 인용만 이어 붙이지 않는다.
- 외국어 원문을 한국어판에 옮길 때는 내가 번역하고 원문 링크를 단다. 핵심 표현은 괄호에 원어를 남겨도 된다.
- 인터뷰이의 말투(해요체, 구어)는 인용 안에서 그대로 둔다. 본문만 한다체다.
- 인용 블록은 그때 내가 세운 가설(`> 처음엔 ~인 줄 알았다`), 흔한 오해, 에러 원문을 보여 줄 때도 쓴다([structure.md](structure.md) 트러블슈팅 2단계).

## 써도 되는 수사 (각각 글당 한 번까지)

한 글에서 아래 가운데 두세 개만 쓰고, 바로 앞 글에서 쓴 것은 피한다.

- "A가 아니라 B다"
- "절반만 맞았다", "필요조건이었지 충분조건이 아니었다"
- "실제로는 무엇인가"
- "전부 여기서 파생된다"
- 질문을 던지고 바로 답하기
- 번호를 매긴 함정(함정 ①②③④)

## 단정 대신 조건

- 배수를 결론으로 고정하지 않는다. "N배 빨라진다" 대신 "이번 실행에서는 이 방향으로 움직였다"라고 쓴다. `<Stats>`와 `<Bars>`의 `note`에 측정 조건을 단다.
- 실험이 증명하지 못하는 것도 같이 적는다. 다만 매번 같은 공식으로 적지 않는다.
- 문법 목록은 "확인할 후보"로 쓴다.

## 이모지

| 이모지 | 자리 |
| --- | --- |
| 🧪 | `<Lab>` 라벨(컴포넌트가 붙인다). h2에는 넣지 않는다 |
| ✓ ✕ | `<Side tone>`(컴포넌트가 붙인다). 코드 주석의 `// ✓` `// ✘`는 코드 펜스 안에서만 쓴다 |
| 💥 | 장애 상황. 드물게, 문단 앞에만 |

그 밖에는 이모지를 쓰지 않는다. `<Summary>`, `<Note>`, h2, 캡션, 문장 안도 마찬가지다(💡 📋 🔑 폐지).

## 고칠 때 순서

1. `npm run check:voice -- <id>`를 돌린다. 대시, 반전, 굵게, 1인칭, 문장 길이, 경구 문장, 같은 박자를 센다.
2. 경구로 닫힌 절 끝부터 지운다. 지워서 어색하면 내가 그다음에 한 일로 바꾼다.
3. 대시를 천 자당 1개 이하로 줄인다.
4. 무인칭으로 쓴 경험 문단을 1인칭으로 바꾼다. 착각하거나 막힌 곳 문장을 하나 이상 넣는다.
   - 원문에 있는 경험부터 살린다.
   - 원문에 없어서 지어 넣은 문장은 보고에 원문 그대로 적어 사용자가 확인하게 한다.
5. 소리 내어 읽어 본다. 같은 박자가 세 번 반복되면 하나를 길게 풀거나 짧게 끊는다.
   - 굵은 머리말 목록이 같은 꼴(예: "~지 ~가 아니다")로 늘어선 것도 같은 박자다.
