<Lead>
쿠버네티스 글을 쓸 때마다 파드가 이미 떠 있는 장면에서 시작했는데, 정작 `kubectl apply`를 친 뒤 파드가 뜨기까지 누가 무엇을 하는지는 그림으로만 알고 있었다. 그래서 그 사이를 실습 노드에서 밀리초 단위로 찍어 봤다. 컨트롤러를 30초 동안 꺼 둔 채 파드를 지우고 개수를 바꾼 뒤 다시 켜 보기도 했는데, 1초도 안 돼 원하는 개수로 돌아왔다.
</Lead>

<Note title="누구를 위한 글인가">
`kubectl`로 Deployment를 올려 본 적은 있지만 그 뒤에 무슨 일이 일어나는지는 그림으로만 본 사람을 기준으로 썼다. 글 끝 정리에는 단계마다 어느 글에서 더 깊이 들어가는지 표로 붙였다.
</Note>

## kubectl apply는 HTTP 요청을 보내는 일이다

쿠버네티스는 프로그램 몇 개가 일을 나눠 맡는다. 요청을 받는 API Server, 그 내용을 저장하는 etcd(키와 값을 저장하는 분산 저장소), 저장된 내용을 보고 일하는 컨트롤러와 스케줄러, 그리고 노드마다 컨테이너를 실제로 띄우는 kubelet이다. 앞의 넷을 묶어 컨트롤 플레인이라고 부른다.

컨트롤러도 스케줄러도 kubelet도 서로 직접 말하지 않고, 모두 API Server를 지켜보다가(watch) 할 일이 생기면 처리하고 결과를 다시 API Server에 쓴다. etcd를 직접 여는 건 API Server뿐이다.

kubectl도 이 그림의 바깥쪽 하나다. `-v=6`을 주면 kubectl이 보내는 HTTP 요청이 한 줄씩 찍힌다.

<Shot src="/img/34/apply.webp" w={1720} h={586} phone={{ src: '/img/34/apply-phone.webp', w: 1170, h: 1602 }} name="lab-node:/tmp/jd-k1" alt="kubectl apply -v=6 출력: OpenAPI 스키마를 받는 GET 세 번, Deployment web을 찾는 GET이 404, 네임스페이스 GET이 200, 마지막 POST가 201 Created로 30ms, 이어서 deployment.apps/web created" />

앞의 세 줄은 YAML을 검사하려고 스키마(OpenAPI)를 받는 요청이고, `GET`이 404를 받자 마지막 `POST`로 만들었다. 서버가 `201 Created`로 답하면 kubectl의 일은 끝난다. 이 순간 파드는 아직 하나도 없다.
</Lab>

kubectl과 API Server(`https://127.0.0.1:6443`) 사이는 TLS 연결이고, kubectl은 kubeconfig에 든 클라이언트 인증서로 자기가 누구인지 밝힌다. TLS가 상대를 확인하는 방식은 [TCP·TLS 편](/33)에서 다뤘다.

인증은 요청을 보낸 게 누구인지, 인가는 그 사람이 이 일을 해도 되는지 본다. Admission은 들어온 오브젝트를 고치거나(기본값 채우기) 정책에 맞지 않으면 막는 단계다.

통과한 오브젝트는 etcd에 키 하나로 적힌다. etcd 파드 안의 `etcdctl`로 키를 직접 읽어 봤다.

<Lab title="etcd에는 /registry 아래에 protobuf로 적혀 있었다">
<Shot src="/img/34/etcd.webp" w={1720} h={693} phone={{ src: '/img/34/etcd-phone.webp', w: 1170, h: 1272 }} name="lab-node:/tmp/jd-k1" alt="etcdctl get /registry --prefix --keys-only를 jd-k1로 거른 결과 키 여덟 개, 그리고 Deployment web 값의 앞 48바이트를 od -c로 본 결과가 k 8 s \0로 시작한다" />

키는 종류, 네임스페이스, 이름 순서로 이어진다. 값은 YAML이 아니라 `k8s` 세 글자와 0 한 바이트로 시작하는 protobuf다[^magic]. 그 뒤로 `apps/v1`, `Deployment`, `web`, `jd-k1` 같은 글자가 보인다.
</Lab>

그런데 내가 kubectl로 만든 건 네임스페이스와 Deployment 둘뿐인데, 키는 여덟 개였다.

## 컨트롤 플레인이 멈추면 무엇이 멈추나

> 기능은 레벨 기반(level-based)이어야 한다. 중간 상태 변화를 몇 번 놓쳤든 원하는 상태와 지금 관찰한 상태만으로 올바르게 동작해야 하고, 사건에 반응하는(edge-triggered) 동작은 최적화일 뿐이어야 한다.

## 실습에서 쓴 명령

실습에서 쓴 명령을 무엇을 보는 명령인지와 함께 모았다. `<…>`는 그때그때 바꿔 넣는 값이다.

```bash title="클러스터 안을 보는 명령"
# kubectl이 보내는 HTTP 요청을 본다. -v=6은 요청 줄만, -v=8은 본문까지
kubectl apply -f web.yaml -v=6

# 바뀔 때마다 한 줄씩 받는다. --output-watch-events가 ADDED·MODIFIED를 앞에 붙인다
kubectl get pod -w --output-watch-events -o jsonpath='{.type} {.object.metadata.name}{"\n"}'

# 원하는 필드만 표로 뽑는다. 주인(ownerReferences)을 보는 데 썼다
kubectl get pod,rs -o custom-columns=NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].name

# 컨트롤러가 남긴 기록. 무엇을 언제 만들었는지 남는다
kubectl get events --field-selector reason=SuccessfulCreate --sort-by=.lastTimestamp

# API Server의 상태 검사. verbose를 붙이면 항목마다 [+]·[-]로 나온다
kubectl get --raw '/readyz?verbose'
```

```bash title="노드에서 보는 명령"
# 컨테이너 런타임(CRI)에 직접 묻는다. -q는 id만 찍는다
crictl ps --name nginx -q
crictl inspect <컨테이너 id> | grep -m1 '"pid"'

# 프로세스를 나무로 본다. -s는 조상까지, -p는 PID까지 찍는다
pstree -sp <pid>

# etcd의 키 목록과 값. 값은 protobuf라 od -c로 바이트를 글자로 바꿔 본다
# 여기서 etcdctl은 etcd 파드 안의 etcdctl을 부르는 래퍼다(실습 환경 절)
etcdctl get /registry --prefix --keys-only
etcdctl get /registry/deployments/jd-k1/web --print-value-only | head -c 48 | od -c
```

```bash title="실습을 묶는 셸 도구"
date +%T.%3N                         # 밀리초까지 찍는 시각
timeout 15 <명령>                    # 15초 뒤 끝낸다. 배경 watch를 정리하는 데 썼다
nohup <명령> > log 2>&1 &            # 터미널과 떨어져 배경에서 돌린다
echo $! > x.pid; kill $(cat x.pid)   # 방금 띄운 프로세스 번호를 남겼다가 그것만 끈다
ss -ltn                              # 열려 있는 TCP 포트. 실습 포트가 비었는지 봤다
```

## 실습 환경과 한계

실습은 실습 서버(Rocky Linux 8.10, 커널 4.18, x86_64, 4 vCPU)에서 했다. RKE2 클러스터는 v1.28.2 단일 노드(containerd 내장, CNI는 Calico와 Flannel을 묶은 Canal)였고, kubectl도 v1.28.2였다. 컨트롤러와 etcd를 멈춘 실습은 같은 서버에 kube-apiserver·kube-controller-manager v1.37.2와 etcd v3.7.3을 127.0.0.1의 다른 포트로 띄워서 했다. 실측 화면은 서버에 화면이 없어서, 명령과 출력을 그대로 기록한 뒤 터미널 모양으로 그려 찍었다. 출력은 고치지 않았고 노드 이름만 `lab-node`로 바꿨다.

watch 실험은 화면에 실은 것을 포함해 네 번 돌렸다. Deployment가 생기고 첫 파드의 노드가 정해지기까지 52\~156ms, 첫 파드가 Ready가 되기까지 2.0\~2.8초였다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| watch 시각 | 단계 순서와 대략의 간격 | 이미지를 받아야 할 때의 시간. 이미지가 노드에 있었다 |
| 실습용 컨트롤 플레인 | 놓친 일을 따라잡는 것, etcd가 없을 때 API 응답 | 노드와 스케줄러가 있을 때 같은 실험 결과 |
| 프로세스 부모 | 컨테이너가 kubelet·API Server와 떨어져 도는 것 | etcd가 멈춘 동안 트래픽과 재시작. 멈추지 않았다 |

화면에 나온 스크립트와 래퍼는 아래가 전부다. Deployment는 nginx 하나짜리다.

```yaml title="/tmp/jd-k1/web.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: jd-k1
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: nginx
        image: docker.io/library/nginx:1.27-alpine
```

```bash title="/tmp/jd-k1/bin/etcdctl · etcd 파드 안의 etcdctl을 부르는 래퍼"
#!/bin/bash
# RKE2 etcd 파드 안의 etcdctl을 클라이언트 인증서와 함께 부른다
T=/var/lib/rancher/rke2/server/tls/etcd
exec kubectl -n kube-system exec etcd-$(hostname) -- etcdctl --cacert=$T/server-ca.crt --cert=$T/server-client.crt --key=$T/server-client.key "$@"
```

```bash title="/tmp/jd-k1/run.sh · 세 종류를 같이 watch"
#!/bin/bash
# apply 한 번에 Deployment·ReplicaSet·Pod가 바뀌는 시각을 밀리초까지 찍는다
ts(){ while IFS= read -r l; do echo "$(date +%T.%3N) $1 $l"; done; }
w(){ timeout 15 kubectl get "$1" -w --output-watch-events -o jsonpath="$2" 2>/dev/null | ts "$3" > "/tmp/jd-k1/$3.log" & }
w deploy "{.type} {.object.metadata.name} ready={.object.status.readyReplicas}{\"\n\"}" DEP
w rs "{.type} {.object.metadata.name} ready={.object.status.readyReplicas}{\"\n\"}" RS
w pod "{.type} {.object.metadata.name} node={.object.spec.nodeName} {.object.status.containerStatuses[0].state.waiting.reason} ready={.object.status.conditions[?(@.type==\"Ready\")].status}{\"\n\"}" POD
sleep 2; echo "$(date +%T.%3N) apply" > /tmp/jd-k1/APPLY.log; kubectl apply -f web.yaml >/dev/null
wait; sort /tmp/jd-k1/{APPLY,DEP,RS,POD}.log | sed "s/$(hostname)/lab-node/g"
```

```python title="/tmp/jd-k1/node-steps.py · containerd 로그에서 파드 하나의 단계 뽑기"
"""containerd 로그에서 파드 하나의 샌드박스 · 네트워크 · 컨테이너 단계를 시각 순으로 뽑는다"""
import re, sys
pod = sys.argv[1]
log = open("/var/lib/rancher/rke2/agent/containerd/containerd.log", errors="replace").read().splitlines()
def short(s):
    s = re.sub(r"&(PodSandbox|Container)Metadata\{Name:([^,]*),[^}]*\}", r"{Name:\2,…}", s.replace("\\\"", "\""))
    return re.sub(r"[0-9a-f]{64}", lambda m: m.group(0)[:12] + "…", s)
sb = cid = None
for l in log:
    if "PodSandboxMetadata{Name:" + pod + "," in l and "returns sandbox id" in l:
        sb = re.search(r"sandbox id \\\"([0-9a-f]{64})", l).group(1)
    if sb and f"within sandbox \\\"{sb}\\\"" in l and "returns container id" in l:
        cid = re.search(r"container id \\\"([0-9a-f]{64})", l).group(1)
for l in log:
    m = re.match(r"time=\"[0-9-]+T([0-9:.]{12})[^\"]*\" level=\w+ msg=\"(.*)\"$", l)
    if m and (f"Name:{pod}," in l or (sb and sb in l) or (cid and cid in l)) and re.search(r"RunPodSandbox|CreateContainer|StartContainer", l):
        print(m.group(1), short(m.group(2)))
    c = re.match(r"[0-9-]+ ([0-9:.]{12}) .*(Calico CNI using IPs: \[[^]]*\])", l)
    if c and sb and sb in l:
        print(c.group(1), c.group(2))
```

## 정리

- `kubectl apply`는 HTTP 요청이고, 서버가 `201 Created`로 답하는 순간 파드는 아직 없다. etcd를 읽고 쓰는 건 API Server뿐이다.
- 컨트롤러는 원하는 상태와 지금 상태의 차이를 메운다. Deployment는 ReplicaSet을, ReplicaSet은 파드를 만들고, 만든 쪽이 주인으로 적힌다.
- 스케줄러는 파드의 `nodeName` 한 칸을 채우고, kubelet은 그 칸이 자기 노드인 파드만 받아 containerd에 넘긴다.
- 실습 노드에서 Deployment가 생기고 파드가 Ready가 되기까지 2.77초 중 컨트롤 플레인 몫은 156ms였고, 가장 오래 걸린 건 샌드박스(1.32초)였다.
- controller-manager를 30초 꺼 둬도 다시 켜자 지금 상태만 보고 0.76초 만에 맞췄다. etcd가 멈추면 API는 실패하지만 떠 있는 컨테이너는 containerd-shim 밑에서 그대로 돈다.

apply 한 줄이 지나간 길을 단계로 다시 늘어놓으면 여덟 단계다. 쿠버네티스 시리즈들은 단계마다 쿠버네티스 쪽을, 기본기 시리즈들은 그 아래 리눅스와 네트워크, 스토리지 원리를 하나씩 열어 볼 계획이다.

| 단계 | 쿠버네티스 시리즈 | 기본기 시리즈 |
| --- | --- | --- |
| 1. kubectl → API Server | 보안 (인증 · 인가) | CS 기본기 (TCP · TLS) |
| 2. etcd에 저장 | 구조 · 운영 (etcd) | 스토리지 기본기 (fsync) |
| 3. 컨트롤러가 ReplicaSet · 파드를 만든다 | 워크로드 | |
| 4. 스케줄러가 노드를 정한다 | 워크로드 (스케줄러) | |
| 5. kubelet → containerd → runc | 구조 (파드 · 이미지) | 리눅스 컨테이너 기본기 |
| 6. CNI가 파드 IP를 붙인다 | 네트워킹 | 리눅스 네트워크 기본기 |
| 7. 볼륨을 붙인다 (이번엔 없음) | 스토리지 | 스토리지 기본기 |
| 8. Ready → Service로 트래픽 | 네트워킹 · 워크로드 | CS 기본기 (시그널) |

기본기 글이 하나씩 나오면 이 글 아래 "이 글이 기대는 기본기"에 이어 붙인다. 지금은 연결을 다룬 [TCP·TLS 편](/33)과 샌드박스의 격리를 다룬 [namespace·PID 1 편](/35)이 붙어 있다.

이번에 가장 오래 걸린 샌드박스 안은 [namespace·PID 1 편](/35)에서 쿠버네티스 없이 `unshare` 같은 리눅스 명령만으로 직접 열어 봤다.
