<Lead>
지난 글에서 파드를 띄우는 데 가장 오래 걸린 건 샌드박스였는데, 그 안에서 무엇이 만들어지는지는 격리 공간이라는 말로 넘어갔다. 그래서 이번에는 쿠버네티스를 빼고 리눅스 명령만으로 그 격리를 하나씩 만들어 봤다. 파드 안에서 `ps`를 치면 nginx가 PID 1인데, 노드에서 같은 프로세스를 찾으면 3756479번이다. 컨테이너는 노드 커널 위에서 도는 보통 프로세스이고, 커널이 namespace로 그 프로세스에게 보이는 것만 바꿔 놓았을 뿐이었다.
</Lead>

<Note title="누구를 위한 글인가">
컨테이너를 쓰고는 있지만 노드에서 그 프로세스를 직접 들여다본 적은 없는 사람을 기준으로 썼다. CPU와 메모리 한도를 거는 cgroup은 [cgroup 편](/36)에서 따로 다룬다.
</Note>

## 컨테이너 프로세스는 노드에서도 보인다

지난 글에서 쓴 nginx 파드를 다시 띄우고, 같은 질문을 안과 밖에서 해 봤다. 이 프로세스는 몇 번인가.

<Lab title="파드 안의 PID 1이 노드에서는 3756479번이었다">
<Shot src="/img/35/outside.webp" w={1720} h={776} phone={{ src: '/img/35/outside-phone.webp', w: 1170, h: 1272 }} name="lab-node:/tmp/jd-l1" alt="kubectl exec로 본 파드 안 ps에서 nginx master는 PID 1, PPID 0이다. 노드에서 crictl로 찾은 같은 컨테이너의 PID는 3756479, /proc/3756479/status의 NSpid 줄은 3756479 1, pstree는 systemd(1)---containerd-shim(3756421)---nginx(3756479)" />

`/proc/3756479/status`의 `NSpid` 줄이 두 번호를 함께 적고 있는데, 앞은 노드에서 본 번호, 뒤는 컨테이너 안에서 본 번호다.
</Lab>

컨테이너는 노드 커널이 직접 스케줄하는 프로세스라서, VM의 게스트와 달리 노드의 `ps`에 그대로 나온다.

안쪽 `ps`에서 nginx master와 `ps`의 부모가 0으로 찍힌 건, 실제 부모가 컨테이너 밖에 있어 안에서는 번호를 붙일 수 없어서다.

## namespace는 커널 자원마다 하나씩 있다

커널에는 프로세스 번호표, 네트워크 장치와 라우팅 표, 마운트 목록, 호스트 이름처럼 원래 시스템에 하나뿐인 자원이 있다. 리눅스 namespace는 이런 자원을 종류별로 감싸서, 그 안에 든 프로세스에게는 자기만의 사본처럼 보이게 하는 기능이다. 프로세스가 종류마다 어느 namespace에 들어 있는지는 `/proc/<pid>/ns/` 아래 링크로 남는다.

<Lab title="nginx는 다섯 종류에서 노드와 다른 namespace에 있었다">
<Shot src="/img/35/nslist.webp" w={1720} h={1038} phone={{ src: '/img/35/nslist-phone.webp', w: 1170, h: 1572 }} name="lab-node:/tmp/jd-l1" alt="노드 셸의 /proc/self/ns와 nginx의 /proc/3756479/ns 비교. ipc, mnt, net, pid, uts는 번호가 4026532655, 4026532657, 4026532506, 4026532658, 4026532587로 노드와 다르고, cgroup 4026531835, time 4026531834, user 4026531837은 노드와 같다" />

위는 노드의 셸, 아래는 nginx다. 대괄호 안 숫자가 namespace 번호인데, 다섯 줄은 노드와 다르고 세 줄은 같다.
</Lab>

번호가 같으면 같은 namespace다.[^dev]

종류는 여덟 가지다.[^time] user namespace가 노드와 같다는 건 컨테이너 안의 root가 노드의 root와 같은 사용자라는 뜻이고, 권한을 다루는 이 시리즈 4편에서 다시 본다.

`kubectl create ns`로 만드는 Namespace는 리눅스 namespace와 이름만 같은 API 객체다. 파드가 어느 Namespace에 있든 리눅스 namespace는 파드마다 따로 생긴다. 여덟 가지에 든 cgroup namespace도 한도와는 상관없이 자기 cgroup 경로가 보이는 모양만 가린다.

## PID namespace는 자식부터 들어간다

같은 방식으로 `unshare --pid`만 주면 될 줄 알았는데, 첫 시도에서 메모리가 모자란다는 에러가 났다.

<Lab title="--fork를 빼자 두 번째 ls에서 fork가 실패했다">
<Shot src="/img/35/pidtrap.webp" w={1720} h={477} phone={{ src: '/img/35/pidtrap-phone.webp', w: 1170, h: 972 }} name="lab-node:/tmp/jd-l1" alt="unshare --pid bash에서 $$는 3758937, 첫 ls 뒤 one이 찍히고 두 번째 ls에서 bash: fork: Cannot allocate memory가 난다. unshare --pid --fork --mount-proc bash에서는 $$가 1이고 ps -ef에는 bash(PID 1)와 ps(PID 2)만 보인다" />

첫 줄의 `$$`(셸 자신의 PID)가 3758937, 노드의 번호다. bash는 새 PID namespace로 옮겨지지 않았다. 두 번째 `ls`에서 `fork: Cannot allocate memory`가 났지만 노드의 메모리는 넉넉했다.
</Lab>

`unshare`는 호출한 프로세스를 새 namespace로 옮기는데, PID namespace는 예외다(time도 같다). 프로세스의 PID는 태어날 때 정해져 바꿀 수 없으니, 호출한 쪽은 그대로 두고 그 뒤에 만드는 자식부터 새 namespace에 넣는다.[^enomem]

### 핸들러가 없으면 SIGTERM도 버려진다

보통 프로세스는 SIGTERM을 받으면 핸들러가 없어도 기본 동작으로 끝난다. PID 1은 다르다. 커널은 PID 1에게 핸들러를 달아 둔 시그널만 전달하고, 예외는 조상 namespace에서 보낸 SIGKILL과 SIGSTOP뿐이다.

### 고아를 입양하고, 끝나면 함께 끝난다

부모가 먼저 끝난 프로세스(고아)는 노드에서라면 systemd가 입양한다. PID namespace 안에서는 그 안의 PID 1이 입양한다.

<Lab title="부모를 잃은 sleep 700은 PID 1의 자식이 됐다">
<Shot src="/img/35/orphan.webp" w={1720} h={796} phone={{ src: '/img/35/orphan-phone.webp', w: 1170, h: 1542 }} name="lab-node:/tmp/jd-l1" alt="새 PID namespace 안의 ps: PID 1은 bash -c (sleep 700 &); sleep 800, PID 3 sleep 700의 PPID는 1, PID 4 sleep 800. 노드에서는 3760733 bash, 3760736 sleep 700, 3760737 sleep 800. PID 1인 bash를 SIGKILL로 끝낸 뒤 pgrep 결과는 none" />

괄호 안의 서브셸(PID 2)이 `sleep 700`을 띄우고 바로 끝나서, `sleep 700`은 부모를 잃고 PPID가 1이 됐다. 그다음 노드에서 PID 1인 bash만 SIGKILL로 끝냈는데, `sleep 700`과 800도 함께 사라졌다.
</Lab>

PID 1이 끝나면 커널이 그 namespace의 나머지 프로세스에 SIGKILL을 보낸다. 컨테이너의 주 프로세스가 끝나면 그 안에서 띄운 것들이 정리 없이 한꺼번에 끝나는 것도 이 규칙 때문이다.

### 거두지 않으면 좀비가 남는다

끝난 자식은 부모가 `wait`로 종료 상태를 거둘 때까지 프로세스 표에 남는데, 이 상태를 좀비라고 부른다. 입양한 고아도 PID 1이 거둬야 사라진다.

## 쿠버네티스 파드는 namespace를 나눠 쓴다

지금까지 손으로 한 일을 쿠버네티스에서는 kubelet이 containerd에 시키고, containerd가 runc로 처리한다. 파드 하나에는 컨테이너가 하나 더 있는데, 지난 글에서 샌드박스로 부른 pause 컨테이너다. 노드에서 둘의 namespace를 나란히 놓아 봤다.

## 실습에서 쓴 명령

실습에서 쓴 명령을 무엇을 보는 명령인지와 함께 모았다. `<…>`는 그때그때 바꿔 넣는 값이다.

```bash title="namespace를 보는 명령"
# 프로세스가 종류마다 어느 namespace에 있는지. 대괄호 안이 namespace 번호
ls -l /proc/<pid>/ns

# 노드 PID와 안쪽 PID를 함께 적은 줄, 핸들러를 단 시그널의 비트맵
grep -E 'NSpid|SigCgt' /proc/<pid>/status

# 그 namespace에 프로세스가 몇 개고, 어디에 bind mount로 붙어 있나
lsns -t net -p <pid>
findmnt -t nsfs
```

```bash title="namespace를 만들고 들어가는 명령"
# 새 uts·net namespace에서 명령 하나를 돌린다
unshare --uts sh -c 'hostname jd-box; hostname'
unshare --net ip -br link

# 새 PID namespace. --fork는 자식을 PID 1로, --mount-proc는 /proc을 새로 붙인다
unshare --pid --fork --mount-proc bash

# 고른 namespace만 들어간다. -n은 net, -p는 pid, -m은 mnt
nsenter -t <pid> -n ss -ltn
nsenter -t <pid> -p -m ps -o pid,ppid,stat,cmd -e
```

```bash title="프로세스를 찾고 다루는 명령"
# 명령줄 전체로 찾는다. -a는 명령줄까지 찍고, -x는 전체가 같을 때만
pgrep -fa '[s]leep 1000'             # [s]는 pgrep이 자기 셸을 찾지 않게 하는 요령
pgrep -fx 'sleep 1000'

# 부모를 따라 올라간다. -s는 조상까지, -p는 PID까지
pstree -sp <pid>

# 런타임(CRI)에 컨테이너 PID를 묻는다
crictl inspect -o go-template --template '{{.info.pid}}' <컨테이너 id>

# 시그널을 보낸다. TERM은 정리할 기회를 주고, KILL은 바로 끝낸다
kill -TERM <pid>; kill -KILL <pid>
```

## 실습 환경과 한계

실습은 실습 서버(Rocky Linux 8.10, 커널 4.18, x86_64)에서 했다. 도구는 util-linux 2.32.1의 `unshare`·`nsenter`·`lsns`이고, 파드는 RKE2 v1.28.2 단일 노드에 `jd-l1` 네임스페이스를 만들고 `kubectl run web --image=docker.io/library/nginx:1.27-alpine`으로 띄웠다. 실측 화면은 명령과 출력을 그대로 기록한 뒤 터미널 모양으로 그려 찍었고, 출력은 고치지 않았다. 노드 이름만 `lab-node`로 바꿨다.

명령은 모두 root로 돌렸고, 아래 환경 파일을 먼저 읽게 했다. `crictl`과 `kubectl`이 RKE2 경로에 있어서다.

```bash title="/tmp/jd-l1/env.sh"
export PATH=$PATH:/var/lib/rancher/rke2/bin KUBECONFIG=/etc/rancher/rke2/rke2.yaml CONTAINER_RUNTIME_ENDPOINT=unix:///run/k3s/containerd/containerd.sock
cd /tmp/jd-l1
```

Go 런타임이 PID 1에서 SIGTERM을 어떻게 받는지는 아래 프로그램을 `GOOS=linux`로 빌드해(Go 1.24.0) `unshare --pid --fork --mount-proc`로 띄워 확인했다.

```go title="/tmp/jd-l1/main.go · 시그널 코드가 없는 Go 프로그램"
package main

import "time"

// 시그널 처리 코드 없이 잠만 잔다
func main() { time.Sleep(time.Hour) }
```

이번 실습으로 확인하지 못한 것도 있다.

| 확인한 것 | 알 수 없는 것 |
| --- | --- |
| namespace 종류와 번호 | user · time namespace를 새로 만들 때의 동작. util-linux 2.32의 `unshare`에는 `--time`이 없고, user namespace는 권한 편에서 다룬다 |
| PID 1의 세 규칙 | tini를 PID 1로 둔 결과. 실습 서버에 없어서 돌리지 않았다 |
| 파드의 namespace 공유 | `shareProcessNamespace`를 켠 파드. 이번에는 켜지 않았다 |

## 정리

- 컨테이너는 노드 커널이 직접 돌리는 프로세스다. 파드 안의 PID 1 nginx가 노드에서는 3756479번이었고, `NSpid` 줄에 두 번호가 함께 있었다.
- 리눅스 namespace는 여덟 가지(pid · net · mnt · uts · ipc · user · cgroup · time)이고, `/proc/<pid>/ns`의 번호가 같은 프로세스끼리 같은 namespace에 있다. 쿠버네티스 Namespace는 이름만 같은 API 객체다.
- `unshare`는 호출한 프로세스를 옮기지만 PID namespace는 자식부터 들어간다. `--fork` 없이 쓰면 첫 자식이 PID 1이 됐다가 끝나서 `fork: Cannot allocate memory`가 났다.
- PID 1은 핸들러를 단 시그널만 받고(SIGTERM이 버려졌다), 고아를 입양하며, 끝나면 안의 프로세스가 모두 SIGKILL로 끝난다. 시작 스크립트는 `exec`로 서버를 PID 1에 앉히거나 tini 같은 init을 둔다.
- 파드의 컨테이너는 net · ipc · uts를 함께 쓰고 pid · mnt는 따로 쓴다. net namespace는 `/run/netns/cni-…`에 bind mount로 붙어 있었다.

이 글은 리눅스 컨테이너 기본기 시리즈의 첫 편이다. 쿠버네티스 글이 노드까지 내려왔을 때 기대는 리눅스 원리를 시리즈 몇 개로 나눠 쓰고 있다.
