<Lead>
DB 총정리 둘째 편은 트랜잭션이다. ACID, 격리 수준, 복구(Redo/Undo)는 따로 외우면 셋이지만 사실 한 묶음이다. ACID는 트랜잭션이 지켜야 할 약속이고, 격리 수준은 그중 I(격리성)를 성능과 맞바꾸는 다이얼이며, Redo/Undo는 A(원자성)와 D(지속성)를 장애 속에서도 지키는 장치다. 이번에는 MySQL 8.4에 세션 두 개를 열어 격리 수준마다 무엇이 보이는지 비교하고, 트랜잭션을 열어 둔 채 mysqld를 강제로 죽여 재시작 때 무엇이 남는지 확인했다.
</Lead>

<Summary>
1. ACID 중 A와 D는 DBMS가 로그로 지켜 준다. C와 I는 개발자가 챙길 몫이 크다.
2. 격리 수준은 이상 현상 세 가지를 어디까지 허용할지 고르는 네 단계 다이얼이다. MySQL 기본값은 REPEATABLE READ, PostgreSQL은 READ COMMITTED.
3. MySQL의 REPEATABLE READ는 첫 SELECT 때 잡은 스냅샷을 끝까지 읽는다. 하지만 UPDATE와 `FOR UPDATE`는 최신 row를 읽어서, 스냅샷에 없던 row까지 바꾼다.
4. 재시작하면 Redo로 커밋한 것을 살리고 Undo로 커밋하지 못한 것을 되돌린다. MySQL 8.4 기본 설정은 커밋마다 redo 로그와 binlog를 한 번씩 fsync해서, 실습 서버에서 커밋 한 번에 약 16ms가 걸렸다.
</Summary>

<Note title="누구를 위한 글인가">
격리 수준 표는 외웠지만 내 DB에서 실제로 어떤 값이 보이는지 확인해 본 적은 없는 사람을 기준으로 썼다. 1절은 ACID, 2~3절은 격리 수준과 그 밑의 MVCC, 4~5절은 장애 복구와 커밋 한 번의 비용이다. 운영 DB의 내구성 설정을 바꾸려는 참이라면 5절부터 읽어도 된다.
</Note>

## ACID: 트랜잭션의 네 가지 약속

트랜잭션은 논리적으로 하나인 작업 단위다. 계좌 이체가 늘 예제로 나오는 데는 이유가 있다. A 잔고를 빼는 일과 B 잔고를 늘리는 일은 <mark>둘 다 되거나 둘 다 안 되어야</mark> 한다.

```sql title="계좌 이체"
START TRANSACTION;
UPDATE account SET balance = balance - 200000 WHERE id = 'A';
UPDATE account SET balance = balance + 200000 WHERE id = 'B';
COMMIT;  -- 여기까지 오기 전에는 언제든 ROLLBACK으로 전부 취소할 수 있다
```

<Compare>
<Side title="A · Atomicity 원자성">

전부 되거나 전부 안 된다. 중간에 죽으면 한 일을 모두 되돌린다. **DBMS가 Undo 로그로 지킨다.**

</Side>
<Side title="C · Consistency 일관성">

트랜잭션 앞뒤로 제약 조건과 비즈니스 규칙이 깨지지 않는다. **무엇이 규칙인지는 개발자가 정한다.**

</Side>
</Compare>

<Compare>
<Side title="I · Isolation 격리성">

동시에 돌아도 서로 없는 것처럼 동작한다. 완벽하게 하면 느려서 **격리 수준으로 타협한다.**

</Side>
<Side title="D · Durability 지속성">

커밋한 것은 정전이 나도 남는다. **DBMS가 Redo 로그(WAL)로 지킨다.**

</Side>
</Compare>

A와 D는 DBMS가 알아서 해 준다. 하지만 C는 무엇이 일관된 상태인지 개발자가 제약 조건과 검증 로직으로 정의해야 하고, I는 개발자가 격리 수준을 골라야 한다. 잔고가 음수가 되면 안 된다는 규칙도 `CHECK (balance >= 0)` 같은 제약으로 적어 둬야 DB가 막는다. MySQL 8.4에서 이 제약을 건 뒤 잔고를 음수로 만드는 UPDATE를 보내 보니 `ERROR 3819`로 거부됐다. "트랜잭션으로 감쌌으니 안전하겠지"가 통하지 않는 곳이 바로 C와 I다.

## 격리 수준: 이상 현상 세 가지와 다이얼 네 단계

격리성을 완벽하게, 즉 트랜잭션을 하나씩 차례로 실행한 것과 똑같이 보장하면 동시성이 사라진다. 그래서 SQL 표준은 어떤 이상 현상까지 참을지를 네 단계로 정해 두었다. 이상 현상부터 보자.

- **Dirty Read**: 다른 트랜잭션이 아직 커밋하지 않은 값을 읽는다. 그 트랜잭션이 롤백하면 나는 존재한 적 없는 값을 읽은 셈이다.
- **Non-repeatable Read**: 한 트랜잭션 안에서 같은 row를 두 번 읽었는데 값이 다르다. 그 사이에 다른 트랜잭션이 UPDATE하고 커밋했다.
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 처음엔 없던 row가 나타난다. 그 사이에 다른 트랜잭션이 INSERT하고 커밋했다.

기본값이 DBMS마다 다르다는 게 은근한 함정이다. <mark>MySQL(InnoDB)은 REPEATABLE READ, PostgreSQL과 Oracle은 READ COMMITTED</mark>가 기본이다. 같은 코드도 DB를 바꾸면 다르게 동작할 수 있다. 지금 격리 수준은 `SELECT @@transaction_isolation;`(PostgreSQL은 `SHOW transaction_isolation;`)으로 확인한다.

<Lab title="READ UNCOMMITTED는 롤백될 값을 읽는다">

MySQL 8.4 컨테이너에 연결 두 개(A, B)를 열고 문장을 차례로 보냈다. 계좌 A의 잔고는 1,000,000이다. B가 트랜잭션 안에서 200,000을 빼고, 커밋하기 전에 A가 읽었다. 왼쪽 숫자는 시작부터 지난 시간이다.

```text frame="terminal" title="실행 결과 · MySQL 8.4.13"
    0ms  A  SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED
            → ok
    0ms  A  BEGIN
            → ok
    0ms  B  BEGIN
            → ok
    1ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
    2ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=800000
    2ms  B  ROLLBACK
            → ok
    8ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=1000000
    9ms  A  COMMIT
            → ok
```

A는 B가 커밋하지 않은 800,000을 읽었고, B가 롤백한 뒤에는 다시 1,000,000을 읽었다. 같은 트랜잭션 안에서 한 번도 커밋된 적 없는 잔고를 본 셈이다.

</Lab>

<Lab title="READ COMMITTED는 두 번 읽는 사이에 값이 바뀐다">

이번에는 B가 autocommit으로 200,000을 빼고 바로 커밋했다. A는 그 앞뒤로 같은 row를 읽었다. A의 격리 수준만 바꿔 두 번 돌렸다.

```text frame="terminal" title="실행 결과 · READ COMMITTED (BEGIN·COMMIT 줄은 줄였다)"
    0ms  A  SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED
            → ok
    0ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=1000000
    1ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   15ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=800000
```

```text frame="terminal" title="실행 결과 · REPEATABLE READ (BEGIN·COMMIT 줄은 줄였다)"
    0ms  A  SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ
            → ok
    0ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=1000000
    8ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   22ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=1000000
```

READ COMMITTED의 A는 두 번째 읽기에서 B가 커밋한 800,000을 봤고, REPEATABLE READ의 A는 1,000,000을 그대로 봤다. READ COMMITTED는 문장마다 새 스냅샷을 잡고, REPEATABLE READ는 처음 잡은 스냅샷을 트랜잭션이 끝날 때까지 쓴다.

</Lab>

## 스냅샷은 언제 잡히고 무엇을 읽나

요즘 DBMS는 격리를 락만으로 풀지 않는다. 주력은 **MVCC**(다중 버전 동시성 제어)로, 트랜잭션마다 자기 시점의 스냅샷을 보여 준다. 읽기가 쓰기를 막지 않고 쓰기가 읽기를 막지 않는 이유가 이것이다. InnoDB에서 그 예전 버전은 Undo 로그에 있다. row는 최신 값만 들고 있고, 바뀌기 전 값은 Undo 로그에 남아 포인터로 이어진다.

평범한 SELECT(스냅샷 읽기)는 이 사슬을 따라 내려가 스냅샷 시점에 커밋돼 있던 버전을 찾는다. UPDATE, DELETE, `FOR UPDATE`(잠그는 읽기)는 맨 위 최신 row를 읽는다. 앞 표의 별표, "InnoDB는 phantom을 대부분 막는다"는 말이 이 두 읽기에서 나온다.

<Lab title="스냅샷은 BEGIN이 아니라 첫 SELECT에서 잡힌다">

A가 `BEGIN`만 보낸 상태에서 B가 잔고를 바꾸고 커밋했다. 그 뒤 A가 처음 읽고, B가 한 번 더 바꾼 뒤 다시 읽었다.

```text frame="terminal" title="실행 결과 · REPEATABLE READ"
    0ms  A  BEGIN
            → ok
    0ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   12ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=800000
   13ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   23ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=800000
   24ms  A  COMMIT
            → ok
   24ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=600000
```

`BEGIN` 직후 B가 바꾼 800,000이 A의 첫 SELECT에 보였다. 스냅샷이 그 SELECT에서 잡혔기 때문이다. 그 뒤 B가 600,000으로 바꿔도 A는 커밋할 때까지 800,000을 읽었다. 그림의 사슬이 바로 이 순간이다.

```text frame="terminal" title="실행 결과 · START TRANSACTION WITH CONSISTENT SNAPSHOT (앞부분)"
    0ms  A  START TRANSACTION WITH CONSISTENT SNAPSHOT
            → ok
    1ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   15ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=1000000
```

`START TRANSACTION WITH CONSISTENT SNAPSHOT`으로 시작하면 시작하는 순간 스냅샷을 잡아서, 첫 SELECT부터 B가 바꾸기 전 값이 보였다.

</Lab>

<Lab title="UPDATE는 스냅샷에 없던 row도 바꾼다">

계좌는 A(1,000,000), B(500,000), C(1,200,000), D(300,000) 넷이다. A가 잔고 100만 원 이상인 계좌를 센 뒤, B가 150만 원짜리 계좌 E를 넣고 커밋했다.

```text frame="terminal" title="실행 결과 · REPEATABLE READ"
    0ms  A  BEGIN
            → ok
    0ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000
            → COUNT(*)=2
    1ms  B  INSERT INTO account (id, balance) VALUES ('E', 1500000)
            → 1 row(s)
   15ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000
            → COUNT(*)=2
   16ms  A  UPDATE account SET flagged = 1 WHERE balance >= 1000000
            → 3 row(s)
   16ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000
            → COUNT(*)=3
   17ms  A  ROLLBACK
            → ok
```

A의 두 번째 SELECT는 스냅샷대로 2개였다. 그런데 같은 조건의 UPDATE는 3 row를 바꿨다. UPDATE는 잠그는 읽기라 B가 커밋한 E까지 읽는다. 내가 바꾼 row는 내 스냅샷에도 보이므로, 그 뒤의 SELECT는 3개를 셌다. 같은 트랜잭션 안에서 센 숫자와 바꾼 숫자가 다를 수 있다.

</Lab>

<Lab title="FOR UPDATE로 범위를 잠그면 REPEATABLE READ만 INSERT를 막는다">

이번에는 A가 처음부터 `FOR UPDATE`로 세고, 그사이 B가 E를 넣었다. A는 0.5초 뒤 한 번 더 센 다음 커밋했다. `balance`에는 인덱스가 있다.

```text frame="terminal" title="실행 결과 · REPEATABLE READ (SET·BEGIN 줄은 줄였다)"
    0ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=2
    1ms  B  INSERT INTO account (id, balance) VALUES ('E', 1500000)
            … 기다림
  553ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=2
  555ms  A  COMMIT
            → ok
  578ms  B  ↳ 1 row(s) (기다린 시간 577ms)
```

```text frame="terminal" title="실행 결과 · READ COMMITTED (SET·BEGIN 줄은 줄였다)"
    1ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=2
    1ms  B  INSERT INTO account (id, balance) VALUES ('E', 1500000)
            → 1 row(s)
  513ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=3
```

REPEATABLE READ에서는 B의 INSERT가 A가 커밋할 때까지 기다렸다. 잠그는 읽기가 찾은 row뿐 아니라 그 사이 빈 곳(gap)까지 잠그는 next-key lock 때문이다. READ COMMITTED는 gap을 잠그지 않아서 INSERT가 바로 들어갔고, A의 두 번째 `FOR UPDATE`는 3개를 셌다. 정리하면 InnoDB의 REPEATABLE READ는 스냅샷 읽기끼리, 잠그는 읽기끼리는 phantom을 막는다. 앞 실습처럼 둘을 섞으면 phantom이 보인다.

</Lab>

<Lab title="열어 둔 스냅샷은 Undo를 붙잡는다">

A가 스냅샷을 잡아 둔 채로, B가 같은 row를 autocommit으로 1,000번 바꿨다. 그동안 아직 지우지 못한 Undo 기록의 수(history list length)를 `information_schema.INNODB_METRICS`에서 읽었다.

```text frame="terminal" title="실행 결과 · MySQL 8.4.13 (5초마다 찍은 줄은 줄였다)"
history list length 시작: 7
A  SELECT balance FROM account WHERE id = 'A'  → balance=1000000
B  UPDATE ×1000 (autocommit) 16741ms
A  SELECT balance FROM account WHERE id = 'A'  → balance=1000000
history list length A가 열려 있을 때: 1001
history list length A 커밋 뒤 5s: 1002
…
history list length A 커밋 뒤 55s: 1002
history list length A 커밋 뒤 60s: 0
```

B가 1,000번 커밋하는 동안 A는 여전히 1,000,000을 읽었다. A가 그 예전 버전을 읽을 수 있으니 Undo 기록 1,000개를 지울 수 없었고, history list length가 1,001까지 올랐다. A가 커밋한 뒤에도 바로 줄지는 않았다. 55초까지 1,002였다가 60초에 0이 됐다. Undo를 지우는 purge는 백그라운드에서 따로 돈다. 트랜잭션을 열어 둔 채 오래 두면 그동안의 Undo가 그만큼 쌓인다.

</Lab>

</Note>

## 복구: 정전이 나도 커밋은 살아남는다

DB는 데이터를 바꿀 때 디스크에 바로 쓰지 않는다. 성능 때문에 메모리(버퍼 풀)에서 고치고, 디스크에는 나중에 몰아서 반영한다. 그 사이에 서버가 죽으면 어떻게 될까. 이 틈을 로그가 메운다.

원칙은 **WAL(Write-Ahead Logging)**, 데이터보다 로그를 먼저 디스크에 쓰는 것이다. 로그에는 두 가지 정보가 담긴다.

- **Redo 로그**: 바꾼 뒤의 값. 커밋했지만 아직 디스크에 반영되지 않은 변경을 다시 재생하는 데 쓴다.
- **Undo 로그**: 바꾸기 전의 값. 커밋하지 못하고 죽은 트랜잭션의 변경을 되돌리는 데 쓴다. 앞 절에서 본 것처럼 InnoDB와 Oracle에서는 MVCC가 보여 주는 예전 버전도 여기서 나온다. PostgreSQL은 예전 버전을 테이블 안에 그대로 남기는 방식이라 Undo 로그가 따로 없다.

체크포인트는 주기적으로 버퍼의 변경을 디스크에 반영하고 표시를 남기는 일이다. 덕분에 재시작할 때 로그를 처음부터가 아니라 마지막 체크포인트부터만 재생하면 된다. 재시작하면 먼저 Redo로 장애 직전 상태를 다시 만들고(커밋한 건 반드시 살린다, 지속성), 그다음 커밋하지 못한 트랜잭션을 Undo로 되돌린다(흔적을 남기지 않는다, 원자성).

## 커밋 한 번은 무엇을 기다리나

로그를 OS 버퍼에 쓰기만 해서는 전원이 나가면 같이 사라진다. 그래서 커밋할 때 fsync로 디스크까지 내리는데, 이게 커밋 한 번의 값이다. MySQL에서는 두 설정이 언제 내릴지를 정한다.

- `innodb_flush_log_at_trx_commit`(기본 1): 1이면 커밋마다 redo 로그를 쓰고 fsync한다. 2면 커밋마다 쓰기만 하고 fsync는 1초마다, 0이면 쓰기와 fsync를 모두 1초마다 한다.
- `sync_binlog`(기본 1): 1이면 커밋마다 binlog를 fsync하고, 0이면 fsync를 OS에 맡긴다.

MySQL 8.4는 바이너리 로그(binlog)가 기본으로 켜져 있다. 그래서 기본 설정의 커밋은 redo 로그와 binlog를 한 번씩 fsync한다. autocommit INSERT 100번 동안 카운터가 얼마나 늘었는지 봤다.

```text frame="terminal" title="INSERT 100번 동안 늘어난 수 · performance_schema"
Innodb_os_log_fsyncs                    +118
wait/io/file/sql/binlog (COUNT_MISC)    +100
```

연결 하나로 autocommit INSERT를 1,000번 보내고, 두 설정을 바꿔 가며 세 번씩 쟀다.

빨라진 만큼 무엇을 잃는지도 봤다. 문서는 `innodb_flush_log_at_trx_commit`이 0이면 mysqld가 죽기만 해도, 2면 OS가 죽거나 전원이 나갈 때 최근 약 1초치 커밋을 잃을 수 있다고 적는다.

<Lab title="mysqld만 죽였을 때 잃은 커밋">

autocommit INSERT를 쉬지 않고 보내다가 3초쯤 뒤 mysqld를 SIGKILL로 죽였다. 클라이언트가 성공 응답을 받은 마지막 id와 재시작 뒤 남은 row 수를 비교했다.

| 설정 | 응답받은 커밋 | 남은 row | 잃은 커밋 |
| --- | --- | --- | --- |
| 1 · 1 (기본) | 241 | 242 | 0 |
| 2 · 1 | 378 | 378 | 0 |
| 0 · 1 | 375 | 376 | 0 |
| 0 · 0 | 9,254 | 9,246 | 8 |
| 0 · 0 (다시) | 9,755 | 9,754 | 1 |

binlog를 커밋마다 fsync하는 동안에는 세 설정 모두 잃은 커밋이 없었다. 남은 row가 하나 더 많은 건, 커밋은 됐는데 응답이 가기 전에 연결이 끊긴 한 건이다. 둘 다 0으로 내리자 응답받은 커밋 8개와 1개가 사라졌다. 초당 3,000건쯤 넣던 중이었으니 몇 ms 분량이다. 0 · 1에서 잃지 않은 이유는 이 실습만으로 가르지 못했다. binlog fsync를 기다리느라 커밋이 초당 100건 남짓으로 느려져서, 그사이 redo가 OS로 넘어갈 시간이 충분했을 수 있다. 그러니 0 · 1이 안전하다는 근거로 쓰지 않는다. 이 실습은 mysqld 프로세스만 죽였다. OS가 함께 죽거나 전원이 나가는 경우는 재현하지 않았다. PostgreSQL의 `synchronous_commit = off`도 같은 거래로, 가장 최근 커밋 몇 개를 잃을 수 있는 대신 커밋 응답이 빨라진다.

</Lab>

## 실습 환경과 한계

실습은 [1편](/7)과 같은 Rocky Linux 8.10 서버(4코어)의 podman 컨테이너에서 MySQL 8.4.13을 기본 설정으로 돌렸다. 격리 수준은 REPEATABLE READ, binlog는 켜져 있고 `sync_binlog`와 `innodb_flush_log_at_trx_commit`은 1이다. 두 세션 실습은 같은 서버의 Go 프로그램(go-sql-driver/mysql)이 연결 두 개로 문장을 차례로 보낸 것이다. 터미널 두 개에서 `mysql`로 같은 순서로 쳐도 같은 결과가 나온다. 바꾼 설정(`innodb_flush_log_at_trx_commit`, `sync_binlog`, `log_error_verbosity`)은 실습이 끝난 뒤 기본값으로 되돌렸다.

2026-07에 처음 올린 글은 커밋 응답이 로그 fsync 한 번으로 끝난다고 적었다. binlog가 켜진 8.4 기본 설정에서는 redo 로그와 binlog를 한 번씩 fsync해서 그 문장을 고쳤다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| 두 세션 실습 | 격리 수준마다 보이는 값, 스냅샷 읽기와 잠그는 읽기의 차이 | PostgreSQL의 결과. 문서로만 확인했다 |
| history list length | 열린 스냅샷이 Undo를 붙잡는다 | purge가 55~60초 뒤에 돈 이유. 부하가 있으면 달라진다 |
| SIGKILL 복구 | Redo 재생 뒤 Undo 롤백, 커밋한 row만 남는다 | 수백만 row를 되돌리는 데 걸리는 시간 |
| 커밋 시간 | 설정마다 커밋 한 번에 드는 시간 | NVMe나 배터리 달린 캐시에서의 차이, 동시 커밋의 group commit |
| 강제 종료 손실 | mysqld만 죽을 때 설정마다 잃는 커밋 | OS 장애나 정전 때 잃는 양. 공용 서버라 재현하지 않았다 |

## 정리

| 상황 | 일어난 일 | 할 일 |
| --- | --- | --- |
| READ COMMITTED에서 두 번 읽기 | 사이에 커밋된 값이 보인다 | 다시 읽은 값으로 판단한다면 격리 수준부터 확인한다 |
| REPEATABLE READ에서 UPDATE | 스냅샷에 없던 row까지 바뀐다 | 센 숫자와 바꾼 숫자를 따로 확인한다 |
| 스냅샷을 오래 열어 둠 | Undo가 쌓이고 purge가 밀린다 | 트랜잭션을 짧게 끝낸다 |
| mysqld가 죽음 | Redo로 살리고 Undo로 되돌린다 | 커밋 응답을 받은 것만 믿는다 |
| 커밋이 느림 | redo와 binlog fsync 두 번 | 두 설정을 같이 보고, 잃을 수 있는 커밋을 받아들일지 정한다 |

돈이 걸린 구간은 격리 수준이 아니라 [1편](/7)의 명시적 락으로 지킨다.

다음 편은 설계 이야기다. 정규화를 왜 하고 어디서 멈출지, 비즈니스 로직을 ORM에 둘지 Stored Procedure에 둘지를 다룬다.
