<Lead>
Go는 예외를 뺐고, 그 자리를 `defer`와 값으로서의 error로 채웠다. 셋 다 문법은 30초면 배우는데 함정은 몇 년째 나온다. 각각이 정확히 언제 무엇을 붙잡는지를 기준으로 다시 정리했다.

defer는 등록하는 순간의 인자를, 클로저는 변수 자체를, `%w`는 감싼 하위 에러를 붙잡는다. 이 글은 defer의 평가 시점과 비용, defer가 돌지 않는 경우, panic과 recover, error와 `%w`, 클로저와 루프 변수 순서로 간다. 예제는 Go 1.26.10에서 다시 돌려 확인했다.
</Lead>

<Summary>
1. defer는 실행만 미룬다. 인자는 등록하는 순간 박제된다. 함정 대부분이 이 어긋남에서 나온다.
2. error는 리턴되는 값이다. 그리고 `%w`로 감싸는 순간 그 하위 에러는 사실상 공개 API 계약이 된다.
3. 클로저는 바깥 변수 자체를 붙잡는다. 루프 변수 버그는 Go 1.22에서 언어가 고쳤지만, `go.mod`를 올리지 않으면 여전히 옛 동작이다.
</Summary>

<Note title="누구를 위한 글인가">
Go로 `defer`와 `if err != nil`을 매일 쓰지만, defer가 인자를 언제 평가하는지, `%w`가 호출자에게 무엇을 약속하는지는 따로 따져 본 적 없는 사람을 기준으로 썼다. 1\~3절은 defer, 4절은 panic과 recover, 5절은 error와 `%w`, 6\~7절은 클로저와 루프 변수다. 인터페이스 값의 두 칸은 [1편](/11), 슬라이스와 맵은 [2편](/12)에서 다뤘다.
</Note>

## defer: 실행은 미뤄도 인자는 미루지 않는다

`defer`를 함수가 끝날 때 실행된다고만 외우면 절반이다. 정확히는 이 호출을 함수 끝에 실행해 달라고 지금 예약하는 것이고, <mark>예약하는 그 순간에 인자가 전부 평가되어 박제된다.</mark>

그림의 두 줄에 값 리시버 메서드 하나를 더해 돌려 봤다.

```go title="args/main.go"
type T struct{ n int }

func (t T) show() { fmt.Println("C:", t.n) }

func main() {
	i := 0
	t := T{n: 0}
	defer fmt.Println("A:", i)              // 인자 평가: 0이 박제된다
	defer func() { fmt.Println("B:", i) }() // 클로저: 변수 i를 붙잡는다
	defer t.show()                          // 값 리시버도 인자다: 복사본이 잡힌다
	i = 1
	t.n = 1
}
```

```text frame="terminal" title="실행 결과"
$ go run ./args
C: 0
B: 1
A: 0
```

나중에 등록한 것부터 도니 C, B, A 순서로 찍혔고, 바뀐 뒤의 값을 본 건 클로저인 B뿐이었다. C가 잘 안 짚이는 부분인데, 메서드 리시버도 인자라서 값 리시버인 `t.show()`는 등록할 때의 복사본을 잡고 `t.n = 1` 이전의 0을 찍었는데, [1편](/11)에서 본 값 리시버가 복사본을 받는다는 이야기가 defer에도 그대로 걸린 것이다.

같은 이유로 함수 맨 앞에 둔 `defer log.Println(time.Since(start))`는 거의 0을 찍는다. 200ms를 자는 함수에 두 방식을 같이 걸어 보니 인자로 넘긴 쪽은 24µs, 클로저로 감싼 쪽은 201ms였다. 그래서 실행 시점의 값이 필요하면 클로저로 감싸고, 등록 시점의 값을 고정하고 싶을 때만 인자로 넘긴다.

## defer의 진짜 비용: 루프 안에 넣으면 두 번 손해다

defer는 느리다는 말은 이제 반쯤 틀렸다. Go 1.14부터 open-coded defer가 들어가면서, 조건이 맞으면 컴파일러가 defer를 함수 끝에 그냥 펼쳐 넣는다. 릴리스 노트는 함수를 직접 부르는 것과 비교해 오버헤드가 거의 없다고 적었다.

문제는 그 조건이 깨질 때다. 대표적인 게 루프 안의 defer인데, 여기서 손해가 두 겹으로 온다.

<Compare>
<Side title="조건이 맞으면: open-coded" tone="good">

- 컴파일러가 함수 끝에 호출을 그대로 펼쳐 넣는다
- defer 레코드를 만들지 않아서 직접 부르는 것과 비용이 거의 같다
- 조건: 함수 안 defer가 8개 이하, 루프 안 defer가 없을 것, return 문 수 × defer 수가 15 이하

</Side>
<Side title="루프 안에 있으면: 힙 레코드" tone="bad">

- 반복마다 defer 레코드를 꺼내 리스트로 잇는다
- ① 호출마다 런타임을 거쳐서 느려지고
- ② 함수가 끝날 때까지 실행이 쌓인다. 파일 핸들이 그때까지 닫히지 않는다

</Side>
</Compare>

루프 안 defer를 피하라는 말은 이 컴파일러 동작에서 나왔고, 해결은 알려진 대로 루프 본문을 익명 함수로 감싸는 것이다. 그러면 반복마다 그 익명 함수가 끝나면서 바로 정리되고, defer도 루프 밖으로 나가 open-coding 대상이 된다. 두 번째 손해부터 확인하려고 파일 다섯 개를 루프에서 열면서 지금 열린 디스크립터 수를 찍었다.

```go title="deferfd/main.go · 일부"
func inLoop(names []string) {
	for _, name := range names {
		f, err := os.Open(name)
		if err != nil {
			panic(err)
		}
		defer f.Close() // 함수가 끝나야 실행된다
		fmt.Print(openFDs(), " ")
	}
	fmt.Println()
}

func perIter(names []string) {
	for _, name := range names {
		func() {
			f, err := os.Open(name)
			if err != nil {
				panic(err)
			}
			defer f.Close() // 이 익명 함수가 끝날 때 실행
			fmt.Print(openFDs(), " ")
		}()
	}
	fmt.Println()
}
```

```text frame="terminal" title="실행 결과"
$ go run ./deferfd
루프 안 defer:    6 7 8 9 10
본문을 함수로:    6 6 6 6 6
```

루프 안에 defer를 둔 쪽은 반복마다 하나씩 늘어 10까지 갔고, 다섯 개가 함수가 끝날 때까지 전부 열려 있었다. 본문을 익명 함수로 감싼 쪽은 반복마다 그 익명 함수가 끝나면서 닫혀서 매번 6이었다. 파일이 수천 개면 이 차이가 <C k="err">too many open files</C>로 나온다.

<Lab title="루프 안 defer는 할당 없이도 아홉 배 느렸다">

첫 번째 손해는 할당이라고 알고 있었다. 먼저 컴파일러가 defer마다 어떤 방식을 골랐는지 `-d=defer`로 찍어 봤는데, 비교하려고 `nine.go`에 defer 아홉 개만 있는 함수 `nine`을 따로 뒀다.

```go title="deferkind/main.go"
package main

import "fmt"

func once() {
	defer fmt.Println("once")
}

func inLoop(n int) {
	for i := range n {
		defer fmt.Println("loop", i)
	}
}

func perIter(n int) {
	for i := range n {
		func() {
			defer fmt.Println("iter", i)
		}()
	}
}

func main() { once(); inLoop(2); perIter(2); nine() }
```

루프 안의 defer만 heap-allocated였고, 익명 함수 안으로 옮긴 defer는 open-coded가 됐다. `nine`은 루프가 없는데도 아홉 개가 모두 stack-allocated로 빠졌다. 컴파일러가 어떤 defer를 등록했는지를 한 바이트의 비트로 적어 두기 때문에 8개까지만 펼쳐 넣는다(`maxOpenDefers = 8`).

이제 시간과 할당을 쟀다. 같은 함수를 100번 부르는 루프를 세 가지로 짰다.

```go title="deferbench/bench_test.go · 일부"
func inLoop(n int) { // 루프 안 defer
	for i := 0; i < n; i++ {
		defer inc()
	}
}

func perIter(n int) { // 본문을 익명 함수로
	for i := 0; i < n; i++ {
		func() { defer inc() }()
	}
}

func direct(n int) { // defer 없이 직접 호출
	for i := 0; i < n; i++ {
		inc()
	}
}
```

## defer를 믿으면 안 되는 순간들

`defer`를 무조건 실행되는 정리 코드로 믿고 쓰다가 데인 적이 있다. 실행되지 않는 경우가 분명히 있다.

| 상황 | defer 실행 여부 |
| --- | --- |
| 정상 return | 실행 |
| panic | 실행. 스택을 되감으며 역순으로 |
| `runtime.Goexit` | 실행. 이 고루틴의 defer를 전부 돌린 뒤 종료 |
| `os.Exit` | **실행 안 됨.** 즉시 프로세스 종료 |
| `log.Fatal` 계열 | **실행 안 됨.** 안에서 `os.Exit(1)`을 부른다 |
| fatal error | **실행 안 됨.** 맵 동시 쓰기 등 |

main에 defer를 하나 걸어 두고, 인자에 따라 다섯 가지 방법으로 끝내 봤다.

```go title="notrun/main.go"
func main() {
	defer fmt.Println("main의 defer 실행")
	switch os.Args[1] {
	case "return":
		return
	case "panic":
		panic("boom")
	case "goexit":
		var wg sync.WaitGroup
		wg.Add(1)
		go func() {
			defer wg.Done()
			defer fmt.Println("고루틴의 defer 실행")
			runtime.Goexit()
		}()
		wg.Wait()
	case "exit":
		os.Exit(3)
	case "fatal":
		log.Fatal("설정 파일을 못 읽었다")
	}
}
```

```text frame="terminal" title="실행 결과 (스택 줄 생략)"
$ go run ./notrun return
main의 defer 실행
$ go run ./notrun panic
main의 defer 실행
panic: boom
…
exit status 2
$ go run ./notrun goexit
고루틴의 defer 실행
main의 defer 실행
$ go run ./notrun exit
exit status 3
$ go run ./notrun fatal
2026/11/02 13:56:53 설정 파일을 못 읽었다
exit status 1
```

panic과 Goexit은 defer를 돌리고 끝났고, `os.Exit(3)`과 `log.Fatal`은 종료 코드만 남겼다. `log.Fatal`은 이름은 로깅처럼 생겼지만 실제로는 로그 한 줄을 쓰고 `os.Exit(1)`을 부른다. 편하다고 에러 처리 자리에 뿌려 두면 defer로 걸어 둔 정리 코드가 통째로 날아가니, `main` 함수 맨 바깥 말고는 쓰지 않는 게 안전하다. [2편](/12)에서 본 맵 동시 쓰기 fatal error도 같은 부류여서, 세 번 돌려 세 번 모두 defer도 recover도 돌지 않았다.

### defer f.Close()가 조용히 삼키는 것

이건 실행은 되는데 결과를 버리는 경우다. `Close()`는 에러를 반환하는데 `defer f.Close()`는 그걸 그냥 버리는데, 읽기 전용이면 대개 상관없지만 쓰기 파일이라면 얘기가 다르다. Linux의 close(2) 매뉴얼을 보면 NFS에서는 공간 부족(<C k="err">ENOSPC</C>, <C k="err">EDQUOT</C>)이 처음 넘친 write에서는 대개 보고되지 않고, 뒤의 write, fsync, close에서 보고된다. 그 에러를 버리면 함수는 `nil`을 리턴했는데 파일은 잘려 있는 상태가 된다.

```go title="Close 에러를 반환값에 합치기"
// named return + defer 로 Close 에러를 반환값에 합류시킨다
func save(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}

	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = cerr // 본문이 성공했을 때만 Close 에러를 올린다
		}
	}()

	_, err = f.Write(data)
	return err
}
```

여기서 named return이 핵심이다. 반환값에 이름이 있어야 defer 안에서 그 값을 고칠 수 있고, 이 패턴은 바로 다음 절에서 panic을 error로 바꾸는 코드에도 그대로 쓰인다. Go 1.20부터는 `err = errors.Join(err, f.Close())` 한 줄로 두 에러를 다 남길 수도 있다. 다만 같은 매뉴얼은 close가 성공해도 데이터가 디스크에 닿았다는 뜻은 아니라고 적고 있어서, 꼭 남아야 하는 파일은 닫기 전에 `f.Sync()`를 부른다.

## panic과 recover: 되감기와 세 가지 조건

recover가 동작하려면 세 조건이 전부 맞아야 한다.

1. defer된 함수 안에서
2. 그 함수가 `recover()`를 직접 호출하고
3. panic이 난 것과 같은 고루틴이어야 한다.

두 번째 조건이 특히 함정이다. 한 단계만 건너뛰어도 무효다. 공통 에러 처리를 헬퍼로 빼려다 조용히 망가지는 코드가 여기서 나온다.

세 번째 조건은 더 무섭다. 고루틴 하나가 panic으로 죽으면 프로그램 전체가 죽는다. 아무리 위에서 recover를 걸어 놔도 다른 고루틴의 panic은 잡히지 않으니, 서버라면 고루틴을 띄우는 자리마다 방어를 넣어야 한다.

```go title="panic을 error로, 고루틴 경계마다 방어"
// panic을 error로 바꿔 내보내는 표준 패턴: named return + recover
func safeParse(b []byte) (result Node, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("parse panic: %v", r) // named return을 덮어쓴다
		}
	}()
	return parse(b), nil // parse 안에서 panic이 나도 여기서 error가 된다
}

// 고루틴 경계마다 방어: 안 하면 하나가 죽을 때 프로세스가 같이 죽는다
go func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("worker panic: %v\n%s", r, debug.Stack())
		}
	}()
	doWork()
}()
```

그렇다면 panic은 언제 쓰는 게 맞을까. 기준은 호출자가 이걸 처리해서 계속 진행할 수 있느냐다.

세 번째 경우는 표준 라이브러리에도 있다. `text/template/parse`는 파싱하다 문법 오류를 만나면 `errorf`에서 panic을 던지고, 맨 위의 `recover` 메서드에서 그걸 error로 바꿔 돌려준다. 이때 `runtime.Error`는 잡지 않고 다시 던지는데, 인덱스 범위 초과 같은 진짜 버그까지 error로 덮지 않으려는 것이다. 패키지 안에서는 panic을 써도 밖으로는 error만 내보내는 구조이고, 공개 API가 panic을 던지면 안 된다는 것도 같은 기준이다.

<Lab title="recover가 조용히 실패하는 경우">

직접 호출 조건이 진짜인지 확인하려고, 헬퍼로 뺀 버전과 직접 호출한 버전을 나란히 돌려 봤다.

```go title="recover/main.go"
func cleanup() {
	if r := recover(); r != nil {
		fmt.Println("잡았다:", r)
	}
}

func direct()   { defer cleanup(); panic("boom") }              // 직접 호출
func indirect() { defer func() { cleanup() }(); panic("boom") } // 한 단계 건너뜀
```

```text frame="terminal" title="실행 결과 (스택 줄 생략)"
$ go run ./recover direct
잡았다: boom
main 계속
$ go run ./recover indirect
panic: boom

goroutine 1 [running]:
main.indirect()
…
exit status 2
```

같은 `cleanup` 함수인데 `defer cleanup()`이면 잡히고 `defer func() { cleanup() }()`이면 안 잡혔다. 한 겹 감싼 것만으로 방어가 사라지는데, 컴파일 에러도 경고도 없다.

세 번째 조건도 돌려 봤다. main에 recover를 걸어 두고 다른 고루틴에서 panic을 냈다.

```go title="gopanic/main.go"
func main() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("main이 잡았다:", r)
		}
	}()
	go func() {
		panic("worker boom")
	}()
	time.Sleep(100 * time.Millisecond)
	fmt.Println("main 끝")
}
```

```text frame="terminal" title="실행 결과 (스택 줄 생략)"
$ go run ./gopanic

…
```

main의 recover는 돌지 않았고 `main 끝`도 찍히지 않은 채 프로세스가 끝났다.

덤으로 알게 된 것 하나. Go 1.21부터 `panic(nil)`은 그대로 통과하지 않고 `*runtime.PanicNilError` 패닉으로 바뀐다. 예전에는 `recover()`가 `nil`을 돌려줘서 패닉 중인데도 패닉이 아니라고 오판하는 함정이 있었는데, 언어 차원에서 막아 둔 셈이다. 그런데 이 변경도 `go.mod`의 `go` 줄을 따른다고 해서, 같은 코드를 `go` 줄만 바꾼 두 모듈에서 돌렸다.

```go title="pnil120/main.go · pnil121/main.go"
func main() {
	defer func() {
		r := recover()
		fmt.Printf("recover() = %v (%T)\n", r, r)
	}()
	panic(nil)
}
```

```text frame="terminal" title="실행 결과"
$ cd pnil120 && go run .
recover() = <nil> (<nil>)
$ cd ../pnil121 && go run .
recover() = panic called with nil argument (*runtime.PanicNilError)
```

`go 1.20`인 모듈은 1.26.10으로 빌드했는데도 `GODEBUG=panicnil=1`이 저절로 켜져서 옛 동작 그대로였다. 7절의 루프 변수도 같은 방식으로 `go` 줄을 따른다.

## error는 값이다: 예외를 뺀 자리

Go에서 `error`는 메서드 하나짜리 인터페이스다.

```go title="error의 정의"
type error interface {
	Error() string
}
// 이게 전부다. 언어 차원의 특별 취급은 없고, 그냥 값이다
```

인터페이스라서 [1편](/11)에서 본 nil 함정도 그대로 걸려서, nil인 `*MyErr`를 `error`로 돌려주면 호출한 쪽의 `err != nil`이 참이 된다.

예외를 뺐다는 건 문법을 뺐다는 게 아니라 보이지 않는 제어 흐름을 뺐다는 뜻이다. 예외가 있는 언어에서는 어떤 함수 호출이든 그 줄에서 실행이 튀어 나갈 수 있고, 그게 코드에 보이지 않는다. Go에서는 실패할 수 있는 모든 지점이 `if err != nil`로 눈에 드러난다.

| | 예외 (try/catch) | 값 (Go) |
| --- | --- | --- |
| 에러 경로 | 코드에 보이지 않는다 | 모든 지점이 보인다 |
| 무시하면 | 위로 자동 전파된다 | 명시적으로 버려야 한다 |
| 조합 | 언어 문법에 묶인다 | 그냥 값이라 자유롭게 다룬다 |
| 대가 | 디버깅이 어렵다 | 장황하다 |

마지막 줄이 정직한 맞바꿈이다. `if err != nil`이 지겹다는 비판은 사실이고, Go 팀도 이걸 알지만 지겨운 대신 빠뜨릴 수 없는 쪽을 택했다.

사소해 보이지만 팀에서 자주 어긋나는 규칙이 하나 있는데, 에러 문자열은 소문자로 시작하고 마침표를 찍지 않는다. 에러는 `fmt.Errorf("saving user: %w", err)`처럼 앞에 문맥을 계속 붙여 나가는 구조라서, 중간에 대문자나 마침표가 끼면 문장이 어색하게 끊긴다. Go Code Review Comments도 같은 이유를 들고, 한 줄씩 끝나는 로그 메시지는 예외로 둔다.

그림의 두 체인을 그대로 만들고 `errors.As`와 `errors.Join`까지 같이 찍어 봤다.

```go title="errs/main.go · 일부"
repoW := fmt.Errorf("user 42 조회: %w", sql.ErrNoRows)
w := fmt.Errorf("주문 처리: %w", repoW)
repoV := fmt.Errorf("user 42 조회: %v", sql.ErrNoRows)
v := fmt.Errorf("주문 처리: %v", repoV)
fmt.Println("%w:", w)
fmt.Println("%v:", v)
fmt.Println("Is(%w):", errors.Is(w, sql.ErrNoRows))
fmt.Println("Is(%v):", errors.Is(v, sql.ErrNoRows))

_, err := os.Open("/없는/파일")
err = fmt.Errorf("설정 읽기: %w", err)
var pe *fs.PathError
if errors.As(err, &pe) {
	fmt.Println("As:", pe.Op, pe.Path)
}

joined := errors.Join(errValidate, errNotify)            // Go 1.20+
both := fmt.Errorf("두 곳 실패: %w, %w", errValidate, errNotify) // %w 여러 개
fmt.Printf("Join: %q\n", joined.Error())
fmt.Println("Is(Join, errNotify):", errors.Is(joined, errNotify))
fmt.Println("Is(%w%w, errNotify):", errors.Is(both, errNotify))
fmt.Println("Unwrap(Join):", errors.Unwrap(joined))
```

첫 두 줄의 메시지는 글자 하나 다르지 않은데 `errors.Is`는 true와 false로 갈렸다. `errors.As`는 한 겹 안의 `*fs.PathError`를 찾아 경로를 꺼냈고, `errors.Join`이나 `%w` 두 개로 묶은 에러에서는 둘 다 `errNotify`를 찾았다.

동작 원리는 단순하다. `errors.Is`와 `errors.As`는 `Unwrap()`을 계속 호출하며 체인을 타고 내려가면서 비교한다. 그래서 내가 만든 에러 타입에 `Unwrap()`을 붙이면 그 순간 체인에 참여하게 되고, `Is(target error) bool` 메서드를 직접 구현하면 비교 방식까지 바꿀 수 있다.

마지막 줄은 의외였는데, `errors.Unwrap`은 Join으로 묶은 에러를 풀지 못하고 `<nil>`을 돌려줬다. 여러 에러를 감싼 값은 `Unwrap() []error`를 갖는데 `errors.Unwrap`은 `Unwrap() error`만 부르기 때문이다. 체인을 `errors.Unwrap`으로 직접 따라 내려가는 코드는 이런 에러를 놓치니, 판별은 Is와 As에 맡긴다.

### 그런데 %w는 공짜가 아니다

`%w`로 감싸는 순간 <mark>그 하위 에러는 사실상 공개 API 계약이 된다.</mark> 호출자가 `errors.Is(err, sql.ErrNoRows)`로 판별하기 시작하면, 나중에 내가 `database/sql`을 떼고 다른 DB 라이브러리로 옮기는 순간 남의 코드가 조용히 깨진다. Go 블로그도 감싸는 건 호출자에게 드러내는 것이니, 구현 세부가 드러난다면 감싸지 말라고 적었다.

| 전략 | 언제 쓰나 |
| --- | --- |
| `%w`로 감싸기 | 같은 패키지·모듈 안에서. 호출자가 원인을 알아야 대응할 수 있을 때 |
| `%v`로 끊기 | 패키지·서비스 경계에서 내부 구현을 숨길 때. 어떤 DB 라이브러리를 쓰는지가 밖으로 새면 안 된다 |
| 도메인 에러로 번역 | 경계에서 가장 좋은 선택. `sql.ErrNoRows`를 내 `ErrUserNotFound`로 바꿔 올린다 |

## 클로저: 바깥 변수를 그대로 붙잡는다

클로저는 함수와 그 함수가 붙잡은 환경을 묶은 것인데, <mark>이때 값을 복사해 두지 않고 변수 자체를 붙잡는다.</mark> 그래서 바깥에서 그 변수가 바뀌면 클로저가 보는 값도 바뀐다.

함수가 끝났는데 캡처한 변수가 왜 살아 있는지는 escape analysis가 답하는데, 컴파일러는 그 값의 수명이 함수 프레임을 넘어가는지를 본다. 아래 `counter`처럼 클로저가 반환되면 `n`은 프레임과 함께 사라질 수 없으니 힙으로 올라가고, 클로저 값은 함수 코드 포인터와 캡처한 `n`의 주소를 들고 다닌다.

```go title="클로저의 쓰임"
// 상태를 가진 함수: n이 힙으로 올라가 살아남는다
func counter() func() int {
	n := 0
	return func() int { n++; return n } // n을 참조로 캡처
}

c := counter()
c(); c() // 1, 2: 호출마다 상태가 이어진다

// 미들웨어: 핸들러를 감싸는 클로저 (데코레이터 패턴)
func withLog(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Println(r.URL.Path, time.Since(start)) // next와 start를 캡처
	})
}

// 함수형 옵션 패턴: 클로저 + 가변 인자
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

srv := NewServer(WithTimeout(3*time.Second), WithRetries(2))
```

컴파일러가 실제로 무엇을 힙에 올리고 어떻게 붙잡는지 보려고, 반환되는 `counter`의 클로저와 함수 안에서만 쓰고 끝나는 `sum`의 클로저를 나란히 두고 `-gcflags=-m=2`로 찍어 봤다. 인라이닝이 끼면 줄이 늘어나서 `-l`로 껐다.

```go title="escape/main.go · 일부"
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}

//go:noinline
func each(xs []int, f func(int)) {
	for _, x := range xs {
		f(x)
	}
}

func sum(xs []int) int {
	base := 10
	total := 0
	each(xs, func(x int) { total += x + base })
	return total
}
```

```text frame="terminal" title="실행 결과 (캡처·힙 관련 줄만)"
$ go build -gcflags='-m=2 -l' ./escape

escape/main.go:7:2: moved to heap: n
escape/main.go:8:9: func literal escapes to heap
escape/main.go:21:2: sum capturing by ref: total (addr=false assign=true width=8)
escape/main.go:20:2: sum capturing by value: base (addr=false assign=false width=8)
escape/main.go:22:11: func literal does not escape
```

`counter`의 `n`은 클로저가 반환되면서 힙으로 옮겨졌고, `sum`의 클로저는 함수 밖으로 나가지 않아 힙에 올라가지 않았다. 캡처 방식도 갈렸다. `base`는 값으로, `total`은 참조로 잡혔다. 컴파일러 소스(`escape.go`)를 보면 값으로 잡는 조건이 128바이트 이하이고, 주소를 가져가지 않고, 캡처한 뒤 다시 대입하지 않는 변수다. `total`은 `+=`로 다시 대입돼서 빠졌다.

비용도 같은 곳에서 나온다. 클로저가 함수 밖으로 새면(반환되거나 고루틴으로 넘어가면) 클로저와 캡처한 변수가 힙에 올라가서, 핫 패스에서 그런 클로저를 남발하면 `allocs/op`가 올라간다.

더 조용한 문제는 큰 객체를 캡처할 때다. 클로저 안에서 필드 하나만 읽더라도, 그 객체를 가리키는 변수를 붙잡고 있는 한 클로저가 살아 있는 내내 객체 전체가 GC되지 않는다.

<Lab title="Name 하나만 읽는 클로저가 64MB를 붙잡았다">

정말 그런지 보려고 64MB짜리 보고서 구조체를 만들고, `Name`만 읽는 클로저 두 개를 비교했다. 하나는 포인터를 그대로 붙잡고 하나는 `Name`을 먼저 복사해 두며, 객체가 회수되는 순간은 `runtime.AddCleanup`으로 찍었다.

```go title="bigcap/main.go · 일부"
type Report struct {
	Name string
	Data [64 << 20]byte // 64MB
}

// 객체를 붙잡는 클로저: Name 하나만 읽는다
func titleOf(r *Report) func() string {
	return func() string { return r.Name }
}

// 필드만 떼어 붙잡는 클로저
func titleCopy(r *Report) func() string {
	name := r.Name
	return func() string { return name }
}
```

```text frame="terminal" title="실행 결과"
$ go run ./bigcap
객체 클로저가 살아 있는 동안 힙: 64.2 MB
객체 클로저를 놓은 뒤 힙: 0.2 MB
  회수: 객체

  회수: 필드

```

포인터를 붙잡은 쪽은 클로저가 살아 있는 동안 힙이 64.2MB였고, 클로저를 놓은 뒤에야 객체가 회수되어 0.2MB로 내려갔다. 필드만 복사한 쪽은 클로저가 살아 있는데도 0.2MB였다(회수 줄은 cleanup이 따로 도는 고루틴에서 찍혀서 앞뒤가 조금 밀린다). 클로저가 읽는 건 필드 하나여도 붙잡는 건 변수 `r`이고, `r`이 가리키는 객체 전체가 함께 살아남는데, [2편](/12)에서 본 3바이트 조각이 10MB 배열을 붙잡던 것과 같은 모양이다.

</Lab>

가장 중요한 건 이 변경이 저절로 적용되지 않는다는 점이다. 툴체인을 1.26으로 올려도 소용없고, <mark>`go.mod`의 `go` 지시어가 1.22 이상</mark>이어야 새 동작이 적용된다. 기존 코드의 의미를 바꾸지 않으려는 하위 호환 장치인데, 거꾸로 말하면 오래된 모듈은 최신 Go로 빌드해도 여전히 옛 동작이라는 뜻이다.

```go title="go.mod와 버전에 상관없이 안전한 관용구"
// go.mod
module example.com/app

go 1.22 // 이 줄이 1.22 미만이면 최신 Go로 빌드해도 옛 동작이다

// 버전에 상관없이 안전한 관용구: 의도도 분명해서 지금도 자주 쓴다
for _, v := range items {
	go func(v Item) { process(v) }(v) // 인자로 넘겨 값을 복사
}
```

<Lab title="툴체인은 그대로 두고 go 줄만 바꿨다">

툴체인을 올려도 소용없다는 말을 직접 확인하려고, 같은 `main.go`를 `go 1.21`과 `go 1.22` 두 모듈에 넣고 Go 1.26.10으로 세 번씩 돌렸다.

```go title="loop121/main.go · loop122/main.go"
func main() {
	var wg sync.WaitGroup
	for _, v := range []string{"a", "b", "c"} {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Print(v, " ")
		}()
	}
	wg.Wait()
	fmt.Println()
}
```

```text frame="terminal" title="실행 결과"
$ cd loop121 && for i in 1 2 3; do go run .; done
c c c
c c c
c c c
$ cd ../loop122 && for i in 1 2 3; do go run .; done
c b a
c a b
c b a
```

`go 1.21`로 적힌 모듈은 1.26.10으로 빌드했는데도 세 번 모두 c만 찍었고, `go 1.22` 모듈은 a, b, c가 매번 다른 순서로 나왔다.

</Lab>

이 버그가 얼마나 찾기 어려운지는 Go 블로그가 든 Let's Encrypt 사례가 보여 준다. 코드를 짠 사람은 문제를 알고 있어서 루프 변수 `k`는 복사해 뒀는데, 같은 루프에서 `modelToAuthzPB(&v)`로 넘긴 `v`의 필드 포인터가 결과에 담기고 있었고 거기서 터졌다. 캡처가 여러 함수에 흩어지면 눈으로 잡는 건 사실상 불가능하다.

### 테스트가 조용히 통과하는 함정

이 버그는 실패해야 할 테스트를 통과시키기도 한다. 아래 테스트는 1이 홀수니까 실패해야 한다.

```go title="even_test.go"
func TestAllEven(t *testing.T) {
	for _, v := range []int{1, 2, 4, 6} {
		t.Run("sub", func(t *testing.T) {
			t.Parallel() // 루프가 끝날 때까지 기다린다
			if v%2 != 0 {
				t.Fatal("odd v", v)
			}
		})
	}
}
```

```text frame="terminal" title="실행 결과"
$ cd loop121 && go test .
ok  	loopvar	0.274s
$ cd ../loop122 && go test .
--- FAIL: TestAllEven (0.00s)
    --- FAIL: TestAllEven/sub (0.00s)
        even_test.go:10: odd v 1
FAIL
FAIL	loopvar	0.247s
FAIL
```

`t.Parallel()`이 서브테스트를 루프가 끝날 때까지 붙잡아 두기 때문에, 1.21 모듈에서는 실행 시점에 `v`가 이미 마지막 값 6이다. 테스트는 초록불인데 아무것도 검증하지 않고 있었다. Go 팀도 1.22를 준비하면서 구글 안에서 이런 테스트를 많이 고쳐야 했다고 적었다.

`go vet`도 두 모듈에서 다르게 나왔다.

```text frame="terminal" title="실행 결과"
$ cd loop121 && go vet .
main.go:14:14: loop variable v captured by func literal
even_test.go:9:7: loop variable v captured by func literal
even_test.go:10:22: loop variable v captured by func literal
$ cd ../loop122 && go vet .
```

1.21 모듈에서는 세 군데를 짚었고, 1.22 모듈에서는 아무것도 나오지 않았다. 반복마다 변수가 새로 생기니 더는 버그가 아니기 때문이다. `go test`도 vet 검사 일부를 함께 돌리는데, 1.21 모듈의 테스트가 ok로 통과한 걸 보면 이 검사는 거기에 들어 있지 않다.

<Note title="그래서 지금 할 일 세 가지">

1. `go.mod`의 `go` 줄을 확인한다. 1.22 미만이면 툴체인이 몇 버전이든 아직 옛 동작이다.
2. 올리기 전에 `go vet`을 따로 돌린다. `go test`만으로는 이 경고가 나오지 않았다.
3. 올리고 나서 갑자기 실패하는 테스트가 생기면, 원래 실패했어야 할 테스트가 이제야 드러난 것이다. 테스트를 되돌리지 말고 코드를 고친다.

</Note>

## 실습 환경과 한계

예제는 모두 이 맥(Apple M5, 10코어, darwin/arm64)에서 Go 1.26.10으로 다시 돌렸다. 처음 올린 글의 recover 실습 출력은 실제 형식과 달라서 새로 찍은 출력으로 바꿨다. 루프 안 defer가 할당을 만든다는 문장과 `go vet`의 `loopclosure` 검사를 CI에 넣으라는 조언은 다시 잰 결과로 고쳤다. Close 에러는 NFS 환경이 없어 재현하지 못했고, close(2) 매뉴얼을 근거로 적었다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| defer 인자 · 리시버 · `time.Since` | 등록할 때 평가된 값과 실행 순서 | 없다. 명세가 정한 동작이라 버전마다 같다고 본다 |
| defer 종류 · 벤치마크 · 디스크립터 | 컴파일러가 고른 방식, 이 루프의 시간과 할당, 열린 파일 수 | GC가 defer 풀을 비운 직후의 할당, 다른 아키텍처의 배수 |
| defer가 안 도는 경우 · recover | 다섯 가지 종료 방식과 recover 세 조건 | SIGKILL처럼 시그널로 죽을 때 |
| `%w` · `%v` · Join | 이 체인에서 Is, As, Unwrap 결과 | 직접 만든 Is·Unwrap 메서드가 있는 에러 |
| 클로저 캡처 · 64MB 객체 | 이 예제의 캡처 방식과 힙 크기 | 다른 버전 컴파일러의 캡처 판단 |
| 루프 변수 · test · vet | go 줄 1.21과 1.22의 차이 | `//go:build`로 파일마다 버전을 바꾼 경우 |

## 정리

| 이 글에서 본 것 | 원인 |
| --- | --- |
| `defer t.show()`가 바꾸기 전 값 0을 찍었다 | 리시버도 인자라 등록할 때 복사된다 |
| 루프 안 defer로 연 파일 다섯 개가 함수 끝까지 열려 있었다 | defer는 함수가 끝날 때 실행된다 |
| `os.Exit`, `log.Fatal` 뒤 defer가 찍히지 않았다 | 프로세스가 그 자리에서 끝난다 |
| 한 겹 감싼 recover가 panic을 못 잡았다 | defer된 함수가 직접 불러야 한다 |
| 메시지는 같은데 `%v`로 감싼 쪽은 Is가 false였다 | `%v`는 원인을 문자열로 녹인다 |
| `Name`만 읽는 클로저가 64MB를 붙잡았다 | 클로저는 필드가 아니라 변수를 붙잡는다 |
| 1.26.10으로 빌드해도 c c c가 찍혔다 | `go.mod`의 `go` 줄이 1.21이었다 |

그래서 루프 안에서 여는 자원은 본문을 함수로 떼어 바로 닫고, 패키지 경계에서는 `%w`로 감쌀지 한 번 더 따져 보고, 오래된 모듈은 `go` 줄부터 확인한다.

이번 편을 쓰면서 셋을 꿰는 질문이 하나라는 걸 알았다. 이건 정확히 언제, 무엇을 붙잡는가. defer는 등록 시점의 인자를, 클로저는 변수 자체를, `%w`는 하위 에러를 붙잡는다. 이 글에 적은 함정은 전부 붙잡는 대상을 착각한 데서 나왔다.
