<Lead>
데이터베이스 핵심을 주제별로 나눠 정리하는 시리즈의 첫 편이다. 데드락과 라이브락, 비관적 락과 낙관적 락, 그리고 UPDATE 한 줄로 전체 유저를 로그아웃시킨 사고까지 다룬다. 동시성 문제는 로컬에선 재현되지 않다가 트래픽이 붙는 순간 터지기 때문에, 미리 머리에 넣어 두는 수밖에 없다.
</Lead>

<Summary>
1. 데드락은 서로가 서로의 락을 기다리는 순환 대기다. 락을 잡는 순서를 통일하면 대부분 막힌다.
2. 충돌이 잦으면 비관적 락(`SELECT ... FOR UPDATE`), 드물면 낙관적 락(version 비교 UPDATE)을 쓴다.
3. UPDATE와 DELETE는 같은 WHERE로 SELECT부터 해 보고, WHERE에 PK나 유니크 조건을 건다.
</Summary>

## 데드락: 서로가 서로를 기다리다 멈춘다

두 트랜잭션이 상대가 잡은 락을 서로 기다리면서 둘 다 진행하지 못하는 상태다. 교과서에서는 네 가지 조건(상호 배제, 점유 대기, 비선점, 순환 대기)이 모두 성립할 때 생긴다고 하지만, DB에서 실제로 만나는 모양은 거의 하나다. <mark>두 트랜잭션이 같은 자원을 서로 다른 순서로 잠글 때</mark>다.

DBMS는 이걸 그냥 두지 않는다. MySQL(InnoDB)은 대기 그래프에서 사이클을 찾으면 둘 중 하나를 희생자(victim)로 골라 강제로 롤백하고 에러를 던진다.

```text frame="terminal" title="희생자 쪽이 받는 에러"
ERROR 1213 (40001): Deadlock found when trying to get lock;
try restarting transaction
```

그래서 애플리케이션이 할 일은 두 가지다.

- **예방한다.** 여러 자원을 잠글 땐 항상 같은 순서로 잠근다(예: 항상 id 오름차순). 순서가 같으면 순환 대기가 생길 수 없다.
- **회복한다.** 그래도 생기면 희생자가 된 쪽이 트랜잭션을 다시 시도한다. 1213은 코드가 틀렸다는 뜻이 아니라 다시 해 보라는 뜻이다.

보조 수단으로 `innodb_lock_wait_timeout` 같은 락 대기 타임아웃도 있다.

### 라이브락: 멈춘 게 아니라 헛돈다

데드락이 복도에서 마주쳐 둘 다 멈춘 상태라면, 라이브락은 둘 다 계속 비켜 주는데 매번 같은 쪽으로 비켜서 영원히 지나가지 못하는 상태다. 상태는 계속 바뀌는데(live) 진행이 없다. 충돌하면 무조건 바로 재시도하는 로직 두 개가 맞물리면 이렇게 된다. 재시도에 랜덤 지연(jitter)과 백오프를 넣어 푼다.

혼자만 계속 밀리는 기아(starvation)는 또 다른 문제로, 대기 큐의 공정성(FIFO)으로 푼다.

## 비관적 락과 낙관적 락

같은 row를 여러 트랜잭션이 고칠 수 있을 때 접근은 두 가지다. 비관적(pessimistic) 쪽은 어차피 충돌할 테니 미리 잠근다. 낙관적(optimistic) 쪽은 충돌이 거의 없을 테니 일단 하고, 쓸 때 확인한다.

### 비관적 락: 읽을 때 잠근다

```sql title="재고 차감 (비관적 락)"
START TRANSACTION;

SELECT stock FROM item WHERE id = 7 FOR UPDATE;  -- 여기서 락을 잡는다
-- 다른 트랜잭션의 FOR UPDATE · UPDATE는 여기서 모두 기다린다

UPDATE item SET stock = stock - 1 WHERE id = 7;
COMMIT;                                          -- 락을 푼다
```

`FOR UPDATE`로 읽는 순간부터 커밋까지 그 row는 내 것이다. 확실한 대신, 락을 오래 잡을수록 다른 트랜잭션이 줄줄이 기다리고, 여러 row를 잠그기 시작하면 앞에서 본 데드락의 재료가 된다.

### 낙관적 락: 잠그지 않고 쓸 때 검증한다

락 대신 version 컬럼을 둔다. 읽을 때 version을 기억해 뒀다가, 쓸 때 그 version이 그대로일 때만 업데이트한다.

```sql title="재고 차감 (낙관적 락)"
-- 읽기 (락 없음)
SELECT stock, version FROM item WHERE id = 7;   -- version = 3

-- 쓰기: 내가 읽은 version일 때만 성공
UPDATE item
SET stock = stock - 1, version = version + 1
WHERE id = 7 AND version = 3;

-- RowsAffected가 0이면 누가 먼저 썼다 → 다시 읽고 재시도
```

[여러 Pod 환경의 CAS 패턴](/3)과 같은 원리다. DB 락을 잡지 않으니 대기도 데드락도 없다. 대신 충돌했을 때 재시도는 애플리케이션 몫이고, 충돌이 잦은 데이터에서는 재시도가 반복되면서 비관적 락보다 오히려 느려진다.

<Compare>
<Side title="비관적 락">

읽을 때 잠근다. 대기가 생기고 데드락이 날 수 있다. **충돌이 잦은 곳**(재고 차감, 포인트, 좌석)에 맞다.

</Side>
<Side title="낙관적 락">

잠그지 않고 쓸 때 version을 검증한다. 재시도가 필요하다. **충돌이 드문 곳**(프로필 수정, 문서 저장)에 맞다.

</Side>
</Compare>

고르는 기준은 충돌 확률 하나다. 충돌이 잦으면 어차피 기다려야 하니 비관적으로 확실히 잠그고, 드물면 낙관적으로 가서 락 비용 자체를 없앤다. 낙관적 락에는 재시도 상한을 꼭 둔다. 상한이 없으면 앞에서 본 라이브락의 재료가 된다.

## UPDATE 한 줄로 전체 유저를 로그아웃시키다

유저 한 명의 세션을 정리하려던 쿼리가 전체 유저의 세션을 날린 사고다. 원인은 허무하다. WHERE 조건이 의도와 다르게, 혹은 아예 없이 나갔다.

<Compare>
<Side title="의도한 쿼리" tone="good">

```sql
-- 유저 123만 로그아웃
UPDATE user SET token = NULL
WHERE id = 123;
```

</Side>
<Side title="실제로 나간 쿼리" tone="bad">

```sql
-- WHERE 누락: 전원 로그아웃
UPDATE user SET token = NULL;
```

</Side>
</Compare>

비슷한 변종도 많다. `AND`와 `OR`의 우선순위를 헷갈려 조건이 사실상 전부 참이 되는 경우, 조인 UPDATE에서 조인 조건이 빠져 카티전 곱으로 퍼지는 경우. 공통점은 실행하기 전엔 멀쩡해 보인다는 것이다.

### 운영 DB에 쓰기 쿼리를 보내기 전에

- **같은 WHERE로 SELECT부터 한다.** `SELECT COUNT(*)`가 기대한 건수(보통 1)인지 눈으로 확인하고, 그 WHERE를 그대로 복사해 UPDATE에 붙인다.
- **트랜잭션으로 감싼다.** `START TRANSACTION` → UPDATE → RowsAffected 확인 → 이상하면 `ROLLBACK`. autocommit을 켠 채 콘솔에서 손으로 치는 게 가장 위험하다.
- **safe update mode를 켠다.** MySQL에서 `sql_safe_updates=1`이면 키 조건이 없는 UPDATE와 DELETE를 아예 거부한다.
- **사람 손을 거치지 않게 한다.** 반복되는 운영 쿼리는 검증된 스크립트나 어드민 기능으로 만들어 두는 게 근본적인 해결이다.

이 사고를 동시성 편에 넣은 이유가 있다. 락과 격리 수준을 아무리 정교하게 설계해도, 쿼리 한 줄의 WHERE가 무너지면 소용이 없다. 동시성 제어는 내 쿼리가 정확히 어떤 row를 건드리는지 아는 데서 시작한다.
