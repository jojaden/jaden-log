<Lead>
"컴파일 언어"와 "정적 타입"이라는 말은 익숙한데, 그게 런타임에 어떤 이득으로 바뀌는지는 설명하기 어려웠다. 그래서 같은 일을 Go와 Python에 시켜 봤다. 구조체 100만 개를 정렬하는 시간은 두 배 차이였는데, 같은 객체 100만 개를 만드는 데는 약 80배, 한 번 훑는 데는 약 360배, 메모리는 7배 차이가 났다. 차이는 계산보다 값을 메모리에 어떻게 놓느냐에서 먼저 났다. 주 언어인 Go 1.26을 기준으로 이 연결 고리를 따라가며, 컴파일러와 런타임이 내린 결정을 도구로 하나씩 확인했다.
</Lead>

<Summary>
1. 정적 타입이면 값의 크기와 필드 위치가 컴파일 시점에 정해진다. 필드 순서만 바꿔도 구조체 100만 개가 24MB에서 16MB가 됐다.
2. 컴파일러는 인라이닝과 escape analysis로 값을 스택에 둘지 힙에 둘지 정한다. 포인터를 돌려주는 생성자 하나를 인라이닝하면 할당이 0번, 인라이닝을 끄면 호출마다 1번이었다.
3. Go는 컴파일 언어인데 GC와 스케줄러가 바이너리에 들어 있어서, 할당이 많을수록 GC가 자주 돈다. 문자열 10만 개를 `+=`로 이으면 GC가 약 1,650번, `strings.Builder`로 이으면 0번 돌았다.
</Summary>

<Note title="누구를 위한 글인가">
Go로 서비스를 짜지만 컴파일러와 GC가 무엇을 결정하는지는 따로 확인해 본 적 없는 사람을 기준으로 썼다. 1절은 Go의 자리와 정적 타입이 정하는 메모리 배치, 2~3절은 컴파일러가 하는 일, 4절은 GC, 5~6절은 고루틴과 바이너리, 그리고 확인 도구다. 고루틴 스케줄러(G·M·P)는 [GMP·GOMAXPROCS 글](/21)에서 따로 다룬다.
</Note>

## 정적 타입과 AOT 컴파일이 정하는 것

### Go는 컴파일 언어인데 런타임이 있다

언어의 실행 방식은 스펙트럼이다. 소스를 그때그때 해석하는 인터프리터부터, 바이트코드를 VM이 돌리며 자주 쓰는 경로를 실행 중에 기계어로 바꾸는 JIT, 빌드할 때 기계어를 전부 만들어 두는 AOT까지 있다.

AOT와 JIT의 차이는 최적화에 쓰는 정보에서 갈린다. JIT는 실제 실행 프로파일을 보고 최적화하는 대신 워밍업이 필요하고, AOT는 첫 실행부터 최고 속도지만 정적 분석만으로 최적화해야 한다.

| | AOT (Go) | JIT (JVM · V8) |
|---|---|---|
| 최적화 정보 | 정적 분석만 | 실행 프로파일 (분기 예측, 인라이닝 캐시) |
| 워밍업 | 없음, 첫 실행부터 최고 속도 | 있음, 수천 번 실행한 뒤 최적화 |
| 시작 시간 | 매우 빠름 | 느림 (VM 부팅 + 클래스 로딩) |
| 성능 예측 | 쉬움 | 어려움 (역최적화 · 재컴파일) |
| 배포 | 바이너리 하나 | 런타임 설치 필요 |

서버리스, 컨테이너, CLI에서 Go를 자주 고르는 이유가 이 표에 있다. 콜드 스타트가 잦은 환경일수록 워밍업 없는 AOT가 유리하다.

타입 시스템은 두 축으로 나누면 정리된다. 타입이 변수에 붙어 컴파일 시점에 검사되면 정적, 값에 붙어 실행 시점에 검사되면 동적이다. 암묵적 변환을 거부하면 강 타입이다.

| | 강 타입 | 약 타입 |
|---|---|---|
| **정적** | **Go**, Rust, Java, Haskell | C, C++ (암묵적 변환이 많다) |
| **동적** | Python, Ruby | JavaScript, PHP |

Go는 정적 · 강 타입 중에서도 엄격해서 `int`와 `int64` 사이도 명시적으로 변환해야 한다.

잘 언급되지 않는 세 번째 축도 있다. 런타임의 두께다. 같은 AOT · 정적 타입이어도 이 축에서 언어가 갈린다.

| 언어 | 컴파일 | 타입 | 런타임 |
|---|---|---|---|
| C/C++ | AOT | 정적 · 약 | 사실상 없음 (libc 수준) |
| Go | AOT | 정적 · 강 | 있음 (GC · 스케줄러 · 할당자 정적 링크) |
| Rust | AOT | 정적 · 강 | 최소한 (GC 없음) |
| Java | 바이트코드 + JIT | 정적 · 강 | 무거움 (JVM) |
| Python | 인터프리터 | 동적 · 강 | 무거움 |

여기서 Go의 특이한 자리가 보인다. <mark>컴파일 언어인데 런타임이 있다.</mark> C와 Rust는 런타임이 얇아서 GC나 스케줄러를 체감할 일이 없고, Java는 JVM이 블랙박스다. Go는 런타임이 코드 성능에 그대로 드러나고, 그 런타임 소스(`src/runtime/`)가 Go로 쓰여 있어 직접 읽을 수 있다.

<Lab title="정렬보다 만들기와 훑기에서 갈렸다">

이 구분이 정말 성능 차이로 이어지는지 같은 일을 두 언어에 시켰다. 정수 두 개(x, y)로 된 구조체 100만 개를 만들고, x 기준으로 정렬하고, x를 한 번씩 더했다. Python 쪽은 `__slots__`를 둔 클래스로 만들었다.

비교할 때마다 타입을 확인하니 정렬에서 가장 크게 벌어질 줄 알았는데, 정렬은 두 배 차이였다. CPython의 `list.sort`는 C로 짜여 있어서, 키를 한 번 뽑아 두면 비교가 C 코드 안에서 끝나기 때문이다. 크게 벌어진 건 Python 코드가 원소마다 도는 곳이었다. 객체를 하나 만들 때마다, 속성을 하나 읽을 때마다 동적 타입을 확인하는 일이 낀다. Go의 `[]Point`는 16바이트 구조체가 연속으로 놓여 있어서 100만 개를 훑는 데 0.4ms가 걸렸다.

최대 메모리(RSS)는 Go가 20MB, Python이 146MB였는데, Python의 list는 객체 포인터 배열이라 원소 100만 개가 저마다 힙의 다른 곳에 따로 놓이기 때문이다. 정수 하나도 참조 카운트를 얹은 28바이트짜리 객체이고, Point 하나는 48바이트다.

### 타입이 정해지면 메모리 배치가 정해진다

"정적 타입은 버그를 미리 잡아 준다"는 절반의 이야기다. 나머지 절반은 성능이다. 타입이 컴파일 시점에 정해지면 런타임에 이런 일이 가능해진다.

| 정적 타입이라서 | 런타임에 일어나는 일 |
|---|---|
| 타입 크기를 컴파일 시점에 안다 | 필드 접근이 **고정 오프셋 덧셈 한 번** (동적 언어는 이름으로 찾는다) |
| 값을 박싱할 필요가 없다 | `[]int`는 정수가 연속 배치, **캐시에 잘 맞는다** (Python list는 포인터 배열) |
| 호출 대상을 대부분 안다 | **정적 디스패치 + 인라이닝** (동적 언어는 호출마다 조회) |
| 어떤 필드가 포인터인지 안다 | GC가 **타입 정보로 정확히 스캔** |
| 컴파일러가 불변식을 안다 | 경계 검사 제거, 데드 코드 제거, **escape analysis** |

구조체 메모리 레이아웃이 가장 손에 잡히는 예다. 필드 순서만 바꿔도 크기가 달라진다. 정렬(alignment) 때문에 패딩이 들어가서다.

<Compare>
<Side title="Bad · 24바이트" tone="bad">

```go
type Bad struct {
	a bool  // 1 + 패딩 7
	b int64 // 8
	c bool  // 1 + 패딩 7
}
```

</Side>
<Side title="Good · 16바이트" tone="good">

```go
type Good struct {
	b int64 // 8
	a bool  // 1
	c bool  // 1 + 패딩 6
}
```

</Side>
</Compare>

필드 순서만 바꿨는데 33% 줄었다. `unsafe.Sizeof`, `Alignof`, `Offsetof`로 확인할 수 있다. 이런 구조체는 x/tools의 `fieldalignment` 분석기가 찾아 준다. `go vet`에는 이 검사가 없어서, `go vet -fieldalignment`로 돌리면 `flag provided but not defined: -fieldalignment`가 나온다. 이 레이아웃이 컴파일 시점에 확정되니까 필드 접근이 `기준 주소 + 상수 오프셋` 명령 하나가 된다.

<Lab title="필드 순서를 바꿔 실측하기">

정말 16바이트와 24바이트인지 `unsafe`로 찍고, 타입마다 100만 개짜리 슬라이스를 만들어 `runtime.ReadMemStats`로 힙 사용량을 쟀다.

```text frame="terminal" title="실행 결과"
Sizeof(Bad{})=24   Offsetof(Bad{}.b)=8   ← a 뒤 패딩 7
Sizeof(Good{})=16  Offsetof(Good{}.a)=8

make([]Bad, 1_000_000)  → HeapAlloc +24.0MB
make([]Good, 1_000_000) → HeapAlloc +16.0MB
```

`b` 필드를 100만 번 더하는 순회는 Good이 약 18% 짧았다(0.37ms 대 0.30ms, 여섯 번 잰 값). 원소가 작으면 같은 캐시 라인에 더 많이 들어간다. 64바이트 줄이라면 Bad는 2.6개, Good은 4개다.

</Lab>

## 컴파일러가 정하는 것: 인라이닝과 스택·힙

Go 컴파일러가 `.go` 파일을 실행 파일로 만드는 순서다.

1. **Lexer · Parser**: AST를 만든다.
2. **타입 검사**: 타입을 추론하고 검증한다.
3. **중간 최적화**: 인라이닝, escape analysis.
4. **SSA 최적화**: 40개가 넘는 패스.
5. **기계어 생성**: `.o` 파일.
6. **링킹**: 런타임까지 포함해 바이너리 하나로.

눈여겨볼 건 마지막 단계다. 링킹할 때 GC, 스케줄러, 할당자가 통째로 실행 파일에 들어간다. `fmt.Println` 한 줄짜리 hello world가 2.4MB인 이유이고, 반대로 런타임 설치 없이 파일 하나만 배포하면 되는 이유다.

이 중 성능에 바로 이어지는 최적화 다섯 가지다. 모두 도구로 확인할 수 있다.

| 최적화 | 내용 | 확인 |
|---|---|---|
| 인라이닝 | 작은 함수를 호출 지점에 펼친다 | `-gcflags='-m'` |
| Escape analysis | 함수 밖으로 새지 않는 값은 **스택에 할당** | `-gcflags='-m'` |
| Devirtualization | 인터페이스 호출을 구체 타입 호출로 | `-gcflags='-m'` |
| 경계 검사 제거 | 필요 없는 `a[i]` 범위 검사를 지운다 | `check_bce` 디버그 출력 |
| 데드 코드 제거 | 도달할 수 없는 코드와 안 쓰는 함수를 지운다 | 바이너리 크기 비교 |

경계 검사는 `-gcflags='-d=ssa/check_bce/debug=1'`로 빌드하면 지우지 못하고 남은 검사가 줄마다 `Found IsInBounds`로 찍힌다.

인라이닝이 첫 줄인 이유가 있다. 호출 비용이 사라지는 것보다, 인라이닝된 뒤에야 escape analysis, 상수 전파, 경계 검사 제거가 이어서 적용되는 효과가 더 크다. 인라이닝은 다른 최적화의 전제 조건이다.

<Lab title="인라이닝의 경계와 값 재기">

함수의 비용이 예산 80을 넘으면 인라이닝을 포기한다. 작은 함수에 분기를 하나씩 더하며 `-gcflags='-m -m'`으로 그 경계를 찾았다. 분기 하나에 비용이 7씩 올라 열한 번째에서 넘었다.

```text frame="terminal" title="인라이닝 판단"
$ go build -gcflags='-m -m' .
./add.go:3:6: can inline Add with cost 4 as: func(int, int) int { return a + b }
./branches.go:174:6: can inline Add10 with cost 74 as: …
./branches.go:208:6: cannot inline Add11: function too complex: cost 81 exceeds budget 80
```

값은 인라이닝을 끄고(`-gcflags=-l`) 같은 벤치마크를 돌려 쟀다. `Add` 하나는 켜나 끄나 1ns 안팎이라 차이가 잡음에 묻혔고, 차이가 분명하게 난 건 포인터를 돌려주는 생성자였다.

```go title="p.go"
func NewPoint(x, y int) *Point { return &Point{x, y} }
```

```text frame="terminal" title="인라이닝 켜고 끄기"
$ go build -gcflags='-m' .
./p.go:6:41: &Point{...} escapes to heap
./p.go:10:31: &Point{...} does not escape   ← 펼쳐진 자리에서는 스택

BenchmarkNewPoint          1.1 ns/op    0 B/op   0 allocs/op
BenchmarkNewPoint (-l)     7.1 ns/op   16 B/op   1 allocs/op
```

함수 안에서만 보면 `&Point{...}`는 밖으로 나가니 힙이다. 호출한 자리에 펼쳐지면 그 포인터가 호출한 쪽 안에서 끝난다는 걸 알 수 있어서 스택에 둔다. 인라이닝이 escape analysis의 결과를 바꾼 것이다.

컴파일러가 어디까지 미리 계산하는지도 보려고 10번 도는 덧셈 루프(`for i := 0; i < 10; i++ { sum += i }`)를 `go tool objdump`로 열어 봤다. 비교와 분기가 그대로 남아 있었다. Go 1.26 컴파일러는 이 루프를 상수 45로 접지 않았다.

</Lab>

### 스택이냐 힙이냐: escape analysis

C는 `malloc`을 쓰면 힙, 아니면 스택이다. Go에는 그런 문법이 없고 컴파일러가 정한다. 규칙을 외울 필요는 없고, 원리 하나만 보면 된다. <mark>값의 수명이 함수 프레임을 넘어가는가.</mark> 넘어가면(판단할 수 없으면 보수적으로) 힙, 아니면 스택이다.

```go title="힙으로 탈출하는 대표 패턴"
func f() *int { x := 1; return &x }    // 포인터 반환
func g(v any) { ... }                  // 인터페이스로 전달 (대상을 모른다)
func h(n int) { s := make([]int, n) }  // 크기를 컴파일 시점에 모른다
go func() { use(x) }()                 // 클로저 캡처 + 고루틴
fmt.Println(x)                         // ...any 가변 인자 (의외의 단골)
```

스택 할당은 프레임 포인터만 움직이면 끝이라 사실상 공짜고 함수가 끝나면 저절로 사라지는데, 힙 할당은 할당자를 거친 뒤 나중에 GC가 치워야 하는 빚으로 남는다. 그래서 Go 성능을 손볼 때는 할당을 빠르게 하기보다 덜 하는 쪽부터 본다.

escape analysis 결과는 컴파일러 버전마다 달라진다. Go 1.25는 슬라이스 백킹 스토어를 스택에 두는 경우를 넓혔다. 어떤 패턴이 힙이라고 외우기보다, 쓰는 버전에서 `-gcflags='-m'`으로 확인하는 편이 맞다.

<Lab title="fmt.Println 하나가 만드는 힙 탈출">

위 패턴 중 가장 의외였던 가변 인자 경우를 재현했다. 지역 변수 하나를 `fmt.Fprintln(io.Discard, x)`에 넘기기만 해도 이렇다.

```text frame="terminal" title="escape analysis와 벤치마크"
$ go build -gcflags='-m' .
./log.go:12:14: ... argument does not escape
./log.go:12:18: x escapes to heap        ← any 인자로 들어가는 순간

$ go test -bench=. -benchmem
BenchmarkDirect          1.5 ns/op   0 B/op   0 allocs/op
BenchmarkPrintln        22.0 ns/op   8 B/op   1 allocs/op   // x = 1000
BenchmarkPrintlnSmall   16.5 ns/op   0 B/op   0 allocs/op   // x = 7
```

가변 인자를 담는 슬라이스는 스택에 남았고, int 값을 any에 담는 박싱이 힙으로 갔다. 0~255 같은 작은 정수는 런타임이 미리 만들어 둔 값을 가리켜서 할당이 없었다. 핫 패스 안의 디버그 로그가 왜 프로파일에 잡히는지가 이걸로 설명된다. 같은 값을 구체 타입을 받는 함수에 넘기면 할당이 0이다. escape analysis가 결국 API 시그니처 설계 문제라는 걸 처음 체감했다.

</Lab>

## 인터페이스와 제네릭은 무엇을 내주나

정적 타입이 런타임에 어떻게 생겼는지 보면 유명한 함정이 전부 설명된다. 개념적으로는 이렇다.

```go title="런타임 표현 (개념)"
// slice: 3워드 (데이터 포인터 + 길이 + 용량)
type slice struct { array unsafe.Pointer; len, cap int }

// string: 2워드, 불변
type string struct { data *byte; len int }

// 인터페이스: 2워드 (타입 정보 + 데이터 포인터)
type iface struct { tab *itab; data unsafe.Pointer }
// itab: (인터페이스, 구체 타입) 쌍마다 하나. 메서드 함수 포인터 테이블
```

여기서 이런 것들이 나온다.

- **append와 재할당.** cap을 넘으면 새 배열을 할당하고 복사한다. 이 순간 원본과의 공유가 끊긴다. "append 했는데 원본이 바뀔 때도 있고 아닐 때도 있어요"의 정체다.
- **재슬라이싱 메모리 누수.** 큰 배열의 작은 조각(`huge[:3]`)을 들고 있으면, 슬라이스 헤더가 배열 전체를 가리키고 있어서 전체가 GC되지 않는다.
- **nil 인터페이스 함정.** 인터페이스는 (타입, 데이터) 두 워드라서, nil 포인터를 담으면 `{tab: T, data: nil}`이 된다. 타입 정보가 있으니 `!= nil`이다.
- **인터페이스 변환 비용.** 포인터가 아닌 값을 인터페이스에 담으면 보통 힙 할당이 생긴다(0~255 같은 작은 정수, 크기가 0인 값 등은 예외).

### 정적 디스패치와 동적 디스패치

```go title="같은 함수, 두 시그니처"
func Do(w *bytes.Buffer)  // 정적: 직접 호출 → 인라이닝 가능
func Do(w io.Writer)      // 동적: itab.fun 을 거치는 간접 호출
                          //       인라이닝 불가 + 할당 가능성
```

인터페이스는 유연성을 주는 대신 인라이닝 기회와 직접 호출을 포기하는 트레이드오프다. 인터페이스를 피하라는 게 아니라, 핫 패스에서는 비용을 알고 쓰라는 것이다. 조건이 맞으면 컴파일러가 devirtualize 해 주고, PGO(프로파일 기반 최적화)를 쓰면 그 범위가 넓어진다.

### 제네릭은 어느 쪽도 아니다

<Compare>
<Side title="C++ 템플릿">

타입마다 코드를 전부 복제한다. 코드가 커진다.

</Side>
<Side title="Java erasure">

타입을 전부 지운다. 박싱 비용이 든다.

</Side>
<Side title="Go stenciling">

GC 모양(포인터 배치)이 같은 타입끼리 코드를 공유하고, 타입별 딕셔너리를 붙인다.

</Side>
</Compare>

Go는 그 중간이다. 코드 팽창도 전면 박싱도 피하지만, 타입 매개변수의 메서드는 딕셔너리를 거쳐 부르기 때문에 인라이닝되지 않는다. 제네릭도 공짜는 아니다.

<Lab title="nil 인터페이스 함정과 디스패치 세 가지 벤치마크">

nil 함정은 코드 몇 줄이면 재현된다. `unsafe`로 인터페이스 내부의 두 워드를 들여다보면 이유가 그대로 보인다.

```go title="nil_iface.go"
func mayFail() error {
	var p *MyErr // nil 포인터
	return p     // nil 포인터를 error 인터페이스에 담아 반환
}

err := mayFail()
fmt.Println(err == nil) // false

// unsafe로 iface 내부를 찍으면:
// (tab=0x1023af998, data=0x0)  ← 타입 정보가 있으니 nil이 아니다
// 진짜 nil 인터페이스는 (tab=0x0, data=0x0)
```

에러가 없을 때는 `return nil`을 명시적으로 쓰고, 구체 에러 타입 변수를 그대로 error로 반환하지 않는다.

디스패치 비용은 같은 로직(사각형 1,000개의 넓이 합)을 구체 타입, 제네릭, 인터페이스 세 가지로 짜서 비교했다.

```text frame="terminal" title="디스패치 벤치마크 (1,000개를 한 번 훑기)"
BenchmarkConcrete     278 ns/op    0 B/op   0 allocs/op   // Area 인라이닝
BenchmarkGeneric      728 ns/op    0 B/op   0 allocs/op   // 딕셔너리로 호출
BenchmarkInterface   1770 ns/op    0 B/op   0 allocs/op   // itab 간접 호출
BenchmarkBoxing       7.2 ns/op   16 B/op   1 allocs/op   // Rect 하나를 []Shape에 담기
```

## GC: 할당한 만큼 GC가 돈다

Go GC의 성격을 표 하나에 모았다.

| 항목 | Go GC |
|---|---|
| 알고리즘 | 3색(tri-color) **Mark & Sweep** |
| 동시성 | **Concurrent**, 애플리케이션과 함께 돈다. 프로그램을 멈추는 건 짧은 두 지점뿐 |
| 이동 | **Non-moving**, 객체 주소가 바뀌지 않는다 |
| 세대 | Non-generational |
| 목표 | 처리량보다 **지연 시간** |

동작 원리는 3색 마킹이다. 흰색(미방문)에서 회색(방문, 자식은 아직)을 거쳐 검은색(끝)으로 칠해 나가고, 끝났을 때 남은 흰 객체를 치운다. 문제는 이걸 애플리케이션이 돌아가는 중에 한다는 것이다. 마킹하는 사이에 프로그램이 포인터를 바꿔 버리면 어떻게 될까.

write barrier는 포인터를 쓸 때마다 컴파일러가 심어 둔 코드가 끼어드는 장치다. 그리고 여기서 이 글의 주제가 한 바퀴 돈다. GC가 힙을 정확히 스캔할 수 있는 건 정적 타입 덕분이다. 컴파일러가 모든 타입의 어느 오프셋이 포인터인지 메타데이터로 남겨 두니까, GC는 정수를 포인터로 착각하는 보수적 스캔을 할 필요가 없다. 고루틴 스택을 자유롭게 옮길 수 있는 것도 같은 이유다. 스택 안의 포인터를 전부 정확히 아니까 복사한 뒤 다시 맞출 수 있다.

### GC 한 사이클과 힙 할당자

한 사이클은 네 단계다. STW(Stop The World)는 시작과 끝의 짧은 두 지점뿐이고, 무거운 마킹은 애플리케이션과 함께 돈다. 마킹에는 CPU의 25%를 쓰는 걸 목표로 한다.

1. **Sweep 종료**: 짧은 STW.
2. **Mark**: 동시에 진행, write barrier 켬.
3. **Mark 종료**: 짧은 STW.
4. **Sweep**: 동시에 진행, 할당할 때 조금씩.

GC가 치울 객체를 만드는 할당자도 계층 구조다. TCMalloc 계열로, 락 없는 P별 캐시에서 시작해 부족할 때만 아래로 내려간다.

```text title="할당자 계층"
mcache   (P마다 하나, 락 없음)        ← 대부분의 할당이 여기서 끝난다
  ↓ 부족하면
mcentral (size class별, P끼리 공유)   ← 작은 객체(≤32KB)는 67개
  ↓ 부족하면                            size class별 span에서 할당
mheap    (전역, 페이지 단위)          ← 큰 객체(>32KB)는 여기서 바로
  ↓ 부족하면
OS (mmap)
```

size class 덕분에 외부 단편화가 억제되고, 16바이트 미만이면서 포인터가 없는 값은 tiny allocator가 묶어서 처리한다. 할당 한 번은 이렇게 빠르게 설계돼 있다.

### 튜닝 노브는 사실상 두 개

- `GOGC`(기본 100): 직전 GC가 끝났을 때 살아 있던 힙(과 스택, 전역 변수)만큼 새로 할당하면 다음 GC를 시작한다. 키우면 GC는 덜 돌고 메모리는 더 쓴다.
- `GOMEMLIMIT`(1.19+): 소프트 메모리 상한. 컨테이너 OOM을 막는 데 사실상 필수다.
- 실전 조합: `GOGC=off GOMEMLIMIT=512MiB`. 상한까지 쓰고 GC는 최소로.

```text frame="terminal" title="gctrace"
$ GODEBUG=gctrace=1 ./app
gc 1666 @0.265s 9%: 0.033+0.073+0.007 ms clock, …, 3->4->1 MB, 4 MB goal, …
#                   ↑ STW + 동시 마킹 + STW, 멈춘 시간은 0.04ms
```

GC는 지금도 바뀌고 있다. Go 1.25에서 실험으로 나온 Green Tea GC가 1.26부터 기본이 됐다. 객체 하나씩이 아니라 메모리 블록 단위로 마킹해서 캐시 지역성을 살리는 방식이고, 릴리스 노트는 GC를 많이 쓰는 실제 프로그램에서 GC 오버헤드가 10~40% 줄 것으로 본다. `GOEXPERIMENT=nogreenteagc`로 끌 수 있고, 이 설정은 1.27에서 없어질 예정이다.

## 런타임의 나머지: 고루틴, 숨은 비용, 바이너리

### 고루틴과 데이터 레이스

고루틴이 OS 스레드보다 훨씬 가벼운 이유도 런타임에 있다. 시작 스택이 2KB(OS 스레드는 보통 1~8MB)이고, 모자라면 런타임이 두 배짜리 새 스택을 잡아 내용을 통째로 옮긴 뒤 포인터를 다시 맞춘다. 런타임 스케줄러는 고루틴(G)을 OS 스레드(M)에 태우는데, Go 코드를 실행하려면 실행 자원(P)을 쥐어야 한다. G·M·P와 `GOMAXPROCS`, 고루틴 10만 개의 메모리는 [GMP·GOMAXPROCS 글](/21)에서 따로 쟀다.

동시성 이야기에 하나만 덧붙이면, 데이터 레이스는 가끔 틀린 값이 나오는 정도로 끝나지 않을 수 있다. Go 메모리 모델은 레이스가 난 프로그램도 C처럼 아무 일이나 일어나게 두지는 않는다. 한 워드 이하의 값은 실제로 쓰인 값 가운데 하나를 읽는다. 다만 인터페이스, 슬라이스, 문자열처럼 여러 워드인 값은 반쯤 쓰인 값을 읽을 수 있고, 그러면 메모리가 깨질 수도 있다. 보장되는 건 채널 송수신, mutex, atomic이 만드는 happens-before 관계뿐이다. 그래서 `go test -race`를 기본으로 켠다.

<Lab title="-race가 짚은 레이스">

두 고루틴이 같은 변수를 1,000번씩 증가시키는 레이스를 일부러 만들고 `-race`로 돌렸다.

```text frame="terminal" title="race detector"
$ go run -race ./race
==================
WARNING: DATA RACE
Read at 0x00c00019e038 by goroutine 7:
  main.main.func1()
      race/race.go:16 +0x88

Previous write at 0x00c00019e038 by goroutine 8:
  main.main.func1()
      race/race.go:16 +0x98
==================
```

일반 빌드로는 가끔만 값이 틀려서 잡기 어려웠을 버그를, race detector는 한 번 실행으로 정확한 파일과 줄을 짚었다. 그 뒤로 CI 테스트는 항상 `-race`로 돌린다.

</Lab>

### 숨은 비용과 바이너리

문법은 공짜처럼 보여도 런타임 가격표가 붙어 있다. 자주 쓰는 것만 추렸다.

| 기능 | 런타임에서 일어나는 일 |
|---|---|
| defer | 1.14+ open-coded defer로 거의 공짜. 단 **루프 안에서는 힙에 쌓인다**. 루프 밖으로 뺀다 |
| panic · recover | 스택 되감기 + defer 체인 순회. **에러 처리용으로 쓰면 안 되는 이유** |
| 클로저 | 캡처한 변수가 힙으로 탈출할 수 있다 |
| string ↔ []byte | 기본적으로 **복사**. 핫 패스에서 반복하면 보이지 않는 할당이 쌓인다 |
| range over map | 매번 무작위 시작점. 순서에 기대는 코드를 못 짜게 한 의도된 설계 |
| cgo | 호출마다 시스템 스택으로 갈아타고 시스템 콜처럼 다뤄진다. GC · 스케줄러 경계를 넘는 비용 |

링킹까지 끝난 Go 바이너리도 볼거리다. `.text`(코드), `.rodata`(상수) 같은 표준 섹션에 더해 Go만의 `.gopclntab`(PC와 소스 줄을 잇는 테이블)이 들어 있다. 스택 트레이스와 GC의 정확한 스캔이 둘 다 여기에 기댄다. hello world가 몇 MB인 건 런타임, 리플렉션 메타데이터, DWARF 디버그 정보가 모두 정적으로 들어가기 때문이다.

호출 규약(ABI)도 컴파일 언어라서 보이는 부분이다. Go 1.17부터 인자를 스택 대신 레지스터로 넘기는 내부 ABI로 바뀌었고, 릴리스 노트는 대표 벤치마크에서 약 5% 빨라졌다고 적었다. `go tool objdump`로 역어셈블하면 인자가 AX, BX 레지스터에 실리는 게 그대로 보인다(amd64 기준, arm64에서는 R0, R1).

<Lab title="바이너리 다이어트와 CGO_ENABLED의 함정">

간단한 HTTP 서버를 linux/amd64로 옵션별로 빌드해 크기를 비교했다. 맥에서 크로스 빌드했다.

```text frame="terminal" title="빌드 옵션별 결과"
$ GOOS=linux GOARCH=amd64 go build -o app .
8.4M app        ELF 64-bit, statically linked
$ GOOS=linux GOARCH=amd64 go build -ldflags="-s -w" -o app-small .
5.8M app-small  # 심볼 · DWARF 제거, -31%
```

```text frame="terminal" title="CGO 켜고 끄기 (리눅스 amd64, Go 1.26.10)"
$ CGO_ENABLED=1 go build -o app-cgo . && ldd app-cgo
        linux-vdso.so.1 (0x00007fff535d0000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f687f3f8000)   ← 동적 링크
        /lib64/ld-linux-x86-64.so.2 (0x00007f687f5f1000)
$ CGO_ENABLED=0 go build -o app-static . && ldd app-static
        not a dynamic executable   ← 완전 정적

$ podman run --rm jl-go8-scratch   # FROM scratch에 app-cgo만 넣은 이미지
exec /app: no such file or directory
```

실무에서 가장 중요했던 건 이 두 빌드의 차이다. `CGO_ENABLED=1`로 빌드한 바이너리를 scratch나 `distroless/static`처럼 libc가 없는 이미지에 넣으면, 동적 링커를 찾지 못해 `no such file or directory`라는 에러로 죽는다. 파일은 분명히 있는데 이 메시지가 나오니, 에러만 봐서는 원인을 찾기 어렵다. `net` 패키지가 cgo 여부에 따라 DNS 구현을 바꾸는 것까지 생각하면, 컨테이너로 배포할 땐 `CGO_ENABLED=0`을 기본으로 둔다.

</Lab>

## 전부 도구로 확인할 수 있다

이 주제를 공부하며 가장 크게 배운 건 개념이 아니라 태도였다. 읽어서 아는 것과 확인해서 아는 것은 다르다. Go는 확인 도구가 전부 표준 툴체인에 들어 있다.

| 도구 | 답하는 질문 |
|---|---|
| `go build -gcflags='-m'` | 인라이닝됐나? 힙으로 탈출했나? |
| `GOSSAFUNC=f go build` | SSA 최적화 전 과정 (ssa.html) |
| `GODEBUG=gctrace=1` | GC가 얼마나 자주, STW는 얼마나 길게? |
| `GODEBUG=schedtrace=1000` | P가 놀고 있나? 런 큐가 쌓이나? |
| `go tool pprof` (CPU · heap · mutex …) | **무엇이** 느린가, 무엇이 할당하나 |
| `go tool trace` | **왜 CPU가 놀고 있나** (GC STW, 블로킹을 시간축으로) |
| `go test -race` · `-benchmem` + benchstat | 레이스 검출, 통계적으로 의미 있는 개선인가 |

<Lab title="pprof로 병목 하나 잡기">

응답마다 상품 200개 목록을 JSON으로 만드는 API 핸들러를 벤치마크로 돌리며 CPU 프로파일을 떴다.

```text frame="terminal" title="pprof -top -cum"
$ go test -bench=Handler -cpuprofile cpu.out
BenchmarkHandler   25090 ns/op   14443 B/op   3 allocs/op
$ go tool pprof -top -cum -focus=pprofjson cpu.out
      flat    cum
         0  0.85s  pprofjson.slow
         0  0.83s  encoding/json.(*Encoder).Encode
         0  0.79s  encoding/json.(*encodeState).marshal   ← 범인
     0.13s  0.79s  encoding/json.structEncoder.encode
```

핸들러 시간의 93%가 목록을 marshal하는 데 들었다. 목록은 바뀔 때만 한 번 marshal해 두고, 요청마다 다른 앞부분만 `sync.Pool`에서 꺼낸 버퍼에 붙이게 바꿨다. 두 버전의 응답이 같은지 테스트로 확인한 뒤 여섯 번씩 쟀다.

```text frame="terminal" title="전후 비교 (여섯 번의 중앙값)"
BenchmarkHandler       24.6µs/op   14,441 B/op   3 allocs/op
BenchmarkHandlerFast    0.18µs/op       0 B/op   0 allocs/op
```

프로파일이 먼저 범인을 짚었고 최적화는 그다음이었다.

</Lab>

도구가 있어도 순서가 틀리면 시간만 버린다. 최적화는 이 순서로 한다.

1. 측정한다. 추측하지 않는다.
2. 알고리즘과 자료 구조를 본다.
3. **할당을 줄인다.**
4. 동시성 구조를 본다.
5. 마이크로 최적화를 한다.
6. 다시 측정한다.

## 실습 환경과 한계

이번 판의 숫자는 모두 이 맥(Apple M5, 10코어, darwin/arm64)에서 Go 1.26.10과 Python 3.9.6으로 다시 쟀다. 2026-07에 처음 올린 수치는 측정 환경 기록이 남아 있지 않아서, 같은 실험을 새로 짜서 돌리고 숫자를 바꿨다. 정렬 비교는 16배에서 2배가 됐고, 디스패치 벤치마크는 제네릭이 구체 타입과 비슷하다던 결과가 2.6배 차이로 바뀌었다. 크기를 잰 리눅스 바이너리는 맥에서 크로스 빌드했고, CGO를 켠 빌드와 scratch 실행은 실습 서버(x86_64)의 `golang:1.26` 컨테이너(Go 1.26.10 linux/amd64)에서 돌렸다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| Go·Python 100만 개 | 단계마다 차이가 어디서 나는지 | 다른 Python(3.12 이상, PyPy)이나 다른 자료 모양에서의 차이 |
| 필드 순서 | 패딩과 힙 사용량. 어느 기계에서나 같다 | 순회 속도 차이(18%). 캐시 크기에 따라 달라진다 |
| 인라이닝 · escape | Go 1.26 컴파일러가 내린 결정 | 다른 버전의 결정. 버전마다 바뀐다 |
| 디스패치 벤치마크 | 이 모양(1,000개 합)에서 세 방식의 차이 | 실제 서비스 코드에서 호출이 차지하는 비중 |
| gctrace · GOGC | 할당량과 GC 횟수의 관계 | 살아 있는 힙이 큰 프로그램의 GC 비용. 이 실험은 살아 있는 힙이 1MB 안팎이다 |
| pprof 예제 | 예제 핸들러의 병목 | 네트워크와 직렬화가 섞인 실제 서버의 병목 |
| 바이너리 · CGO | linux/amd64 빌드 크기와 CGO 링크 | musl(Alpine) 같은 다른 libc에서의 결과 |

## 정리

| 단계 | 정해지는 것 | 이 글에서 본 값 |
| --- | --- | --- |
| 정적 타입 | 값의 크기와 필드 위치 | 필드 순서만으로 24MB → 16MB |
| 컴파일러 | 인라이닝, 스택과 힙 | 생성자를 인라이닝하면 할당 1번 → 0번 |
| 디스패치 | 직접 호출, 딕셔너리, itab | 원소당 0.28ns · 0.73ns · 1.77ns |
| GC | 할당한 만큼 도는 GC | `+=` 약 1,650번, Builder 0번 |

이 글에서 잰 차이는 대부분 값이 메모리에 어떻게 놓이느냐와, 컴파일러가 그걸 보고 무엇을 지우느냐에서 나왔다. 이 결정은 컴파일러 버전마다 바뀌니, 숫자는 글보다 내 코드에서 `-gcflags='-m'`과 `gctrace`로 다시 보는 편이 정확하다.

지금 바로 해 볼 수 있는 출발점을 남겨 둔다. 컴파일러의 결정을 읽고, GC와 스케줄러를 관찰하는 데 각각 명령 하나면 된다.

```go title="esc.go"
type Point struct{ X, Y int }

func stack() Point { return Point{1, 2} }
func heap() *Point { p := Point{1, 2}; return &p }
```

```text frame="terminal" title="관찰 명령"
$ go build -gcflags='-m -m' esc.go    # 컴파일러의 결정 읽기
$ GODEBUG=gctrace=1 ./app             # GC 관찰
$ GODEBUG=schedtrace=1000 ./app       # 스케줄러 관찰
```
