<Lead>
컨테이너 limit이 1GB인데 힙 800MB에서 OOMKilled가 났다. GC가 있는 언어인데 왜 메모리가 넘쳤을까. GC는 살아 있는 힙의 비율로 돌고, 컨테이너는 절대값으로 프로세스를 죽인다. 이 글은 두 기준 사이를 잇는 `GOMEMLIMIT`과, 값을 힙에 둘지 스택에 둘지 컴파일러가 정하는 escape analysis를 함께 본다.

순서는 escape analysis, GC가 도는 방식, `GOGC`, OOMKilled, `GOMEMLIMIT`이다. 예제는 Go 1.24.7과 Go 1.27.0으로 돌렸고 이번에 Go 1.26.10으로도 다시 돌렸으며, 컨테이너 OOMKilled는 리눅스 실습 서버의 1GiB 컨테이너에서 재현했다.
</Lead>

<Summary>
1. 값을 스택에 둘지 힙에 둘지는 컴파일러가 정한다. 같은 `&Pair{}`가 인라이닝에 따라 0 allocs/op와 1 allocs/op로 갈렸고, 크기를 모르는 `make`는 Go 1.24.7에서 힙으로, Go 1.27.0에서 탈출하지 않는다고 나왔다. 그래서 문법만 보고 짐작하지 않고 `-gcflags=-m`과 `-benchmem`으로 잰다.
2. `GOGC`는 살아 있는 힙에 비례해 다음 목표를 잡아서 절대 상한이 없다. live가 600MB면 목표가 1.2GB 근처라, limit이 1GB인 컨테이너에서는 GC가 돌기 전에 커널이 먼저 죽인다. 실습 서버의 1GiB 컨테이너에서도 목표가 1,218MiB로 잡히자 힙 989MiB를 넘긴 뒤 죽었다. 커널이 세는 RSS는 힙보다 크다.
3. `GOMEMLIMIT`은 그 옆에 절대값 상한을 하나 더 둔다. 같은 프로그램에 300MiB를 걸자 GC 목표가 400MB 언저리에서 287MB로 내려가고 GC 횟수는 두 배가 넘었다. 설정을 다섯 가지로 바꿔도 할당 누계는 256MiB로 같았다.
</Summary>

<Note title="누구를 위한 글인가">
컨테이너에 Go 서비스를 올리면서 `GOGC`와 `GOMEMLIMIT`을 기본값으로 두고 있거나, 힙 그래프는 여유로운데 OOMKilled를 겪어 본 사람을 기준으로 썼다. 1\~2절은 값이 힙으로 가는지 컴파일러에 묻는 법, 3절은 GC가 도는 방식, 4\~6절은 `GOGC`, OOMKilled, `GOMEMLIMIT` 순서이고, CPU 쪽의 `GOMAXPROCS`는 [앞 글](/21)에서 다뤘다.
</Note>

## 스택이냐 힙이냐는 컴파일러가 정한다

Go에는 C의 `malloc`처럼 힙에 놓으라고 지정하는 문법이 없다. `new`나 `&`를 써도 마찬가지다. 어디에 놓을지는 컴파일러가 escape analysis로 정하고, 기준은 이 값이 함수 밖에서도 필요한가 하나다.

함수를 회의실로 보면 쉽다. 회의 중에 화이트보드에 쓴 메모는 회의가 끝나면 지워진다. 이게 스택이고, 치우는 데 따로 드는 비용이 없다. 메모를 회의실 밖으로 들고 나가야 하면 종이에 옮겨 창고에 넣어야 하고, 창고는 GC가 관리한다. 이게 힙이다.

두 가지는 짚고 가자. 지역 변수의 주소를 반환하는 Go 코드가 잘못된 포인터를 만들지는 않는다. 필요한 수명만큼 컴파일러가 저장 공간을 마련해 주니, C에서 스택 지역 변수의 주소를 돌려줄 때 생기는 문제가 Go에는 없다.

또 탈출하지 않는다고 나온 값이 꼭 스택에 객체 하나로 놓이는 것도 아니고, 레지스터에만 남거나 계산이 단순해져 객체 자체가 사라질 수도 있다. 언어가 약속하는 건 동작뿐이고, 실제 배치는 컴파일러 버전과 최적화마다 다르다. 값이 힙에 갔는지 스택에 남았는지는 어떻게 알까? 배치는 문법으로 추측하지 않고 도구에 물어본다.

<Lab title="값으로 돌려준 onStack만 진단에 나오지 않는다">

탈출이 생기기 쉬운 모양을 다섯 함수에 담아 한 파일에 넣고, 컴파일러의 진단을 읽어 보자.

```go title="escape/main.go · 전체 실행 코드"
package main

func main() {}

type Point struct{ X, Y int }

func onStack() Point    { p := Point{1, 2}; return p }  // 값 반환 — 복사되어 나감
func byPointer() *Point { p := Point{1, 2}; return &p } // ① 포인터 반환
func toIface() any      { p := Point{1, 2}; return p }  // ② 인터페이스로 반환
func captured() func() int {
	n := 0
	return func() int { n++; return n } // ③ 클로저 캡처
}
func unknownSize(n int) int {
	buf := make([]byte, n) // ④ 크기를 컴파일 때 모름
	return copy(buf, "hello")
}
```

```text frame="terminal" title="실행 결과 · Go 1.24.7 · darwin/arm64 (← 표시는 덧붙였다)"
$ go build -gcflags='-m' . 2>&1 | grep -v inlin
# escape
./main.go:8:27: moved to heap: p                  ← ① byPointer의 p
./main.go:9:52: p escapes to heap                 ← ② toIface의 박싱
./main.go:11:2: moved to heap: n                  ← ③ captured의 n
./main.go:12:9: func literal escapes to heap      ← ③ 클로저 자체
./main.go:15:13: make([]byte, n) escapes to heap  ← ④
$ GOTOOLCHAIN=go1.27.0 go build -gcflags='-m' . 2>&1 | grep make
./main.go:15:13: make([]byte, n) does not escape
```

출력에 `onStack`의 줄은 없다. 값을 복사해서 돌려주니 원본 `p`는 함수가 끝날 때 같이 사라져도 된다. 나머지 넷은 Go 1.24.7에서 힙으로 갔고, 그중 ④만 Go 1.27.0에서 판정이 바뀌었다.

④가 바뀐 이유는 Go 1.25 릴리스 노트에 한 줄로 나오는데, 슬라이스의 저장 공간을 스택에 두는 경우가 늘었다는 내용이다. 크기를 32바이트와 33바이트로 나눠 할당 횟수를 재면 경계가 보인다.

```go title="vmake/make_test.go · 크기만 다른 두 벤치마크"
package vmake

import "testing"

//go:noinline
func use(n int) int {
	buf := make([]byte, n)
	return copy(buf, "hello")
}

func BenchmarkMake32(b *testing.B) {
	for i := 0; i < b.N; i++ {
		use(32)
	}
}

func BenchmarkMake33(b *testing.B) {
	for i := 0; i < b.N; i++ {
		use(33)
	}
}
```

```text frame="terminal" title="실행 결과 · darwin/arm64"
$ GOTOOLCHAIN=go1.24.7 go test -run '^$' -bench . -benchmem -benchtime=100ms
BenchmarkMake32-10    13048869     9.401 ns/op    32 B/op    1 allocs/op
BenchmarkMake33-10    12464780     9.748 ns/op    48 B/op    1 allocs/op
$ GOTOOLCHAIN=go1.27.0 go test -run '^$' -bench . -benchmem -benchtime=100ms
BenchmarkMake32-10    55769622     1.802 ns/op     0 B/op    0 allocs/op
BenchmarkMake33-10    15216597     7.681 ns/op    48 B/op    1 allocs/op
```

Go 1.27.0의 `Make32` 줄만 0 allocs/op다. 크기를 컴파일할 때 몰라도 실행할 때 32바이트 안이면 스택 버퍼를 쓰고, 33바이트부터는 Go 1.24.7처럼 힙에 할당한다. 소스는 그대로인데 툴체인만 바꿔서 결과가 달라졌다.

그래서 이 넷을 힙 할당 목록으로 외우지는 않는다. 인터페이스로 넘기든 클로저를 만들든, 컴파일러가 실제 사용 범위를 볼 수 있으면 같은 문법도 스택에 남는다. 이 넷은 확인할 후보다.

그래도 자주 도는 코드에서 흔히 눈에 띄는 쪽은 ②로, `any`로 받는 함수에 값을 계속 넘기면 그 값들이 힙으로 나가 `allocs/op`가 올라가곤 한다. 이것도 빌드에서 확인할 일이다.

Go의 할당 자체는 빠르다. 그래도 할당이 많으면 문제가 되는 건, 할당한 만큼이 나중에 GC가 훑고 치울 일로 돌아오기 때문이다.

</Lab>

<Lab title="같은 NewPair가 한 빌드 안에서 두 판정을 받는다">

앞 실험의 진단은 한 줄씩 떼어 읽으면 헷갈릴 때가 있다. 같은 생성식에 "힙으로 탈출한다"와 "탈출하지 않는다"가 함께 나올 수 있기 때문이다. 짧은 함수 하나로 확인해 보자.

```go title="alloc/allocation.go · 같은 NewPair를 두 방식으로 쓴다"
package allocation

type Pair struct {
	A, B int64
}

func NewPair(n int64) *Pair {
	return &Pair{A: n, B: n + 1}
}

func SumLocal(n int64) int64 {
	p := NewPair(n)
	return p.A + p.B
}

var Published *Pair

func Publish(n int64) {
	Published = NewPair(n)
}
```

`NewPair`는 두 정수를 가진 객체의 주소를 돌려준다. `SumLocal`은 필드의 합만 구하고 끝내고, `Publish`는 전역 변수에 그 주소를 남긴다. 전역 저장은 탈출을 분명히 만들려고 넣은 실험 장치다.

```go title="alloc/allocation_test.go · 두 함수의 벤치마크"
package allocation

import "testing"

var sink int64

func BenchmarkLocal(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink += SumLocal(int64(i))
	}
}

func BenchmarkPublished(b *testing.B) {
	for i := 0; i < b.N; i++ {
		Publish(int64(i))
	}
}
```

```text frame="terminal" title="실행 결과 · darwin/arm64 · Go 1.24.7 (판정 줄만 남겼다)"
$ go build -gcflags='-m=2' allocation.go 2>&1 | grep -E 'inline NewPair|inlining call|escapes to heap$|does not escape'
./allocation.go:7:6: can inline NewPair with cost 9 as: func(int64) *Pair { return &Pair{...} }
./allocation.go:12:14: inlining call to NewPair
./allocation.go:19:21: inlining call to NewPair
./allocation.go:8:9: &Pair{...} escapes to heap
./allocation.go:12:14: &Pair{...} does not escape
./allocation.go:19:21: &Pair{...} escapes to heap
```

마지막 세 줄이 모두 같은 `&Pair{}`인데 판정이 다르다. 8번째 줄은 `NewPair` 자체의 본문이고, 12번째와 19번째 줄은 `SumLocal`과 `Publish`에 펼쳐 넣은 사본이다. 인라이닝은 짧은 함수의 내용을 호출한 자리에 펼쳐 넣는 최적화인데, 펼치고 나면 컴파일러가 그 값이 어디까지 쓰이는지 정확히 볼 수 있다. `SumLocal`에서는 합을 구한 뒤 주소가 남지 않아 탈출하지 않고, `Publish`에서는 전역에 남아 탈출한다.

그래서 진단을 읽을 때는 메시지 문구보다 파일과 줄 번호, 그 주변의 `inlining call`부터 본다. 벤치마크로 옮기면 차이가 그대로 나온다.

```text frame="terminal" title="실행 결과 · Go 1.24.7 · linux/amd64 2코어"
$ go test -run '^$' -bench . -benchmem -benchtime=200ms -count=3 allocation.go allocation_test.go
```

옵션 하나로 `BenchmarkLocal`의 할당이 0에서 1로 바뀌었고, 코드는 한 글자도 건드리지 않았다. 포인터를 쓰면 힙으로 간다는 말로는 이 결과를 설명할 수 없다.

이 맥(darwin/arm64, Go 1.24.7)에서도 다시 돌렸는데, `Local`은 0.78ns에 0 allocs/op, `Published`는 6.8ns에 16 B/op, 1 allocs/op였고, `-l`을 주면 `Local`도 16 B/op, 1 allocs/op가 됐다. 시간은 환경마다 다르지만 할당 횟수는 원문과 같았다.

`-l`이나 `//go:noinline`은 원인을 떼어 보는 보조 실험에는 쓸 수 있지만 실제 배포 빌드와 다른 결과를 만드니, 최종 비용은 평소 빌드 조건에서 다시 잰다. `B/op`도 작업당 힙에 할당한 바이트의 누계라서 이미 회수된 것까지 들어 있고, 지금 살아 있는 메모리는 이 숫자로 알 수 없다.

## 탈출을 다 없애면 빨라지나

꼭 그렇지는 않다. 힙 할당 하나를 없애려다 복사 비용이나 공유 상태를 새로 얻을 수 있다. 진단을 읽을 줄 알게 되면 탈출을 전부 없애고 싶어지는데, 그 전에 아래 두 가지 대가를 본다.

<Compare>
<Side title="값으로 돌려준다">

```go title="config.go"
// 호출마다 Config 전체를 복사한다
func Load() Config
```

힙 할당 하나를 없애는 대신 호출마다 구조체를 통째로 복사한다. 호출자가 그 값을 오래 들고 있어야 한다면 값 반환으로는 요구를 맞추지 못한다.

</Side>
<Side title="전역 버퍼를 다시 쓴다">

```go title="buf.go"
// 요청끼리 나눠 쓴다

```

할당은 줄지만 공유 상태가 생긴다. 동시 접근을 누가 막는지, 이전 요청의 내용이 남지 않는지를 책임져야 한다.

</Side>

삼색은 탐색이 어디까지 왔는지를 가리키는 이름일 뿐, 객체에 실제로 색 정보가 들어 있지는 않다. 회수 대상은 루트에서 닿을 수 없는 객체이고, 루트에는 고루틴 스택과 전역 변수의 참조가 들어간다. 오래됐다거나 이제 안 쓸 것 같다는 이유로 지우지는 않으니, 살아 있는 데이터는 설정으로 줄일 수 없다.

마킹을 앱과 같이 돌리는 대가는 쓰기 장벽이다. 마킹 중에 포인터가 바뀌어도 살아 있는 객체를 놓치지 않도록 포인터 쓰기에 일이 조금 붙는다. 짧은 전체 정지(STW)도 두 번 남아 있으니, 동시 GC라고 멈춤이나 비용이 아예 없지는 않다.

Go가 정확하게 마킹할 수 있는 건 정적 타입 덕이다. 어떤 필드가 포인터인지 컴파일할 때 알기 때문에, 힙을 훑으면서 이 8바이트가 포인터인지 정수인지 추측할 필요가 없다. 마킹 방식은 버전마다 다듬어지는데, 최근에는 Go 1.25에 실험으로 들어온 Green Tea GC가 Go 1.26부터 기본이 됐다. 같은 메모리 블록에 있는 작은 객체를 한꺼번에 훑어 CPU 캐시를 더 잘 쓰게 한 설계이고, 릴리스 노트는 GC를 많이 쓰는 프로그램에서 GC 오버헤드가 10~40% 줄 것으로 본다.[^greentea]

GC 비용은 살아 있는 데이터의 양, 포인터 구조, 새로 할당하는 속도에 함께 달려 있다. 같은 바이트 수라도 큰 바이트 배열 하나와 포인터로 촘촘히 엮인 구조는 훑는 비용이 다를 수 있다. 알고리즘은 설정으로 바꿀 수 없고, 설정으로 바꿀 수 있는 건 GC가 언제 시작하느냐다. 그 값이 `GOGC`와 `GOMEMLIMIT`이다.

## GOGC는 살아 있는 힙의 비율로 목표를 잡는다

GC가 언제 돌지 정하는 값이 `GOGC`다. 기본값은 100이고, 다음 목표 힙 크기를 이렇게 잡는다.

```text title="GC 가이드의 목표 힙 계산"
목표 힙 = 라이브 힙 + (라이브 힙 + GC 루트) × GOGC / 100
```

루트가 작으면 `GOGC=100`은 대략 살아남은 힙의 2배다. live가 200MB면 목표는 400MB 근처, 600MB면 1.2GB 근처다. 값을 키우면 힙을 더 크게 허용하는 대신 GC 빈도를 낮출 여지가 생긴다.

> 목표 힙에 닿는 순간 GC가 시작된다.

런타임은 목표 근처에서 수집을 마칠 수 있게 그보다 먼저 마킹을 시작하고, 진행 속도도 조절한다. 최소 힙 목표나 메모리 제한 같은 조건도 함께 끼어든다. 실제 출력에서 확인해 보자.

<Lab title="gctrace로 보면 목표가 live를 따라 두 배씩 올라간다">

live 200MiB를 끝까지 붙잡고, 64KiB짜리 쓰레기를 계속 만드는 프로그램이다. `GODEBUG=gctrace=1`을 주면 GC가 돌 때마다 한 줄씩 찍힌다.

```go title="saw/main.go · 전체 실행 코드"
package main

import "fmt"

var live [][]byte // 끝까지 살아 있는 데이터
var sink []byte   // 바로 버려지는 데이터

func main() {
	for i := 0; i < 200; i++ { // live 약 200MiB
		live = append(live, make([]byte, 1<<20))
	}
	for i := 0; i < 100_000; i++ { // 64KiB 쓰레기를 계속 만든다
		sink = make([]byte, 64<<10)
	}
	fmt.Println("live MiB:", len(live))
}
```

## 힙 800MB에서 왜 OOMKilled가 나나

힙보다 RSS가 왜 클까? RSS에는 힙 말고도 고루틴 스택, 런타임 메타데이터, 아직 OS에 돌려주지 않은 페이지가 들어가서, 힙 수치만 보면 여유가 있는데도 죽는다. 그림 2번 막대의 비율은 예시이고, 실제 비율은 서비스마다 다르다.

GC가 끝나 힙이 줄어도 운영체제가 보는 메모리가 바로 같은 만큼 줄지는 않는다. 런타임이 공간을 다시 쓰려고 들고 있을 수 있고, OS로 돌려주는 일은 따로 일어난다. 설정을 바꾼 직후 RSS가 바로 떨어지기를 기대하면 그래프를 잘못 읽기 쉽다.

이 글을 처음 올릴 때는 컨테이너 OOMKilled를 재현하지 않았는데, 이번에 리눅스 실습 서버에서 그림 1번 막대를 실제로 만들어 봤다.

<Lab title="1GiB 컨테이너에서 목표가 1,218MiB로 잡히자 커널이 먼저 죽였다">

메모리 limit 1GiB에 스왑을 막은 컨테이너를 띄우고, live 600MiB를 끝까지 붙잡은 채 1MiB짜리 쓰레기를 계속 만드는 프로그램을 돌렸다. 커널이 세는 양도 같이 보려고 100번마다 `/proc/self/status`에서 RSS를 읽어 찍는다.

```go title="oom/main.go · 전체 실행 코드"
package main

import (
	"fmt"
	"math"
	"os"
	"runtime"
	"runtime/debug"
	"strconv"
	"strings"
)

var live [][]byte    // 끝까지 붙잡는 600MiB
var recent [8][]byte // 최근 쓰레기 8개만 남긴다

// 커널이 세는 RSS를 /proc에서 읽는다
func rssMiB() int {
	b, _ := os.ReadFile("/proc/self/status")
	for _, l := range strings.Split(string(b), "\n") {
		if f := strings.Fields(l); len(f) > 1 && f[0] == "VmRSS:" {
			kb, _ := strconv.Atoi(f[1])
			return kb >> 10
		}
	}
	return -1
}

// 페이지마다 한 바이트씩 써서 실제로 메모리를 잡게 한다
func touch(b []byte) {
	for i := 0; i < len(b); i += 4096 {
		b[i] = 1
	}
}

func main() {
	if lim := debug.SetMemoryLimit(-1); lim == math.MaxInt64 {
		fmt.Println("GOMEMLIMIT: 없음")
	} else {
		fmt.Println("GOMEMLIMIT:", lim>>20, "MiB")
	}
	for i := 0; i < 600; i++ {
		b := make([]byte, 1<<20)
		touch(b)
		live = append(live, b)
	}
	var m runtime.MemStats
	for i := 0; i <= 3000; i++ {
		b := make([]byte, 1<<20) // 1MiB 쓰레기
		touch(b)
		recent[i%len(recent)] = b
		if i%100 == 0 {
			runtime.ReadMemStats(&m)
			fmt.Printf("%4d  힙 %4d MiB  목표 %4d MiB  RSS %4d MiB  GC %d\n",
				i, m.HeapAlloc>>20, m.NextGC>>20, rssMiB(), m.NumGC)
		}
	}
	fmt.Println("끝까지 돌았다")
}
```

맥에서 `GOOS=linux GOARCH=amd64 CGO_ENABLED=0`으로 빌드해 서버에 올렸고, 컨테이너 이미지는 서버에 받아 둔 Go 1.26 공식 이미지를 썼다.

live를 다 쌓은 뒤 목표가 1,218MiB로 잡혔다. 그 뒤로 GC는 한 번도 돌지 않았고, 힙이 989MiB를 넘긴 뒤 다음 줄을 찍기 전에 커널이 프로세스를 죽였다. 종료 코드 137은 128에 SIGKILL의 번호 9를 더한 값이고, 커널 로그의 anon-rss 1,045,452kB는 1,021MiB로 limit과 거의 같다. 다른 실행에서는 마지막 GC가 돈 시점에 따라 목표가 1,096MiB로 잡혔고, 똑같이 죽었다.

이 프로그램은 힙 밖에 쓰는 메모리가 거의 없어 RSS가 힙보다 4MiB쯤 컸을 뿐이라, 그림 2번 막대처럼 RSS가 힙보다 한참 큰 서비스라면 힙이 더 낮을 때 죽는다. 그리고 `podman inspect`의 `OOMKilled` 필드는 이 서버(cgroup v1)에서 false로 나와서, 죽은 이유는 종료 코드와 커널 로그로 확인했다.

## GOMEMLIMIT으로 절대값 상한을 하나 더 둔다

`GOMEMLIMIT`은 Go 1.19에 들어온 소프트 메모리 상한이다. 이 값에 가까워지면 `GOGC` 목표가 아직 멀어도 GC를 앞당긴다. 비율 규칙 옆에 절대값 규칙을 하나 더 두어, 커널과 같은 단위로 맞춘다.

| 설정 | 기준 | 상한 |
| --- | --- | --- |
| `GOGC` | live에 대한 비율. 기본 100 | 없다 |
| `GOMEMLIMIT` | 런타임이 쓰는 메모리의 바이트 수 | 소프트. 넘을 수 있다 |

런타임이 쓰는 메모리는 `runtime.MemStats`의 `Sys`에서 `HeapReleased`를 뺀 값이다. 여기에는 힙뿐 아니라 런타임이 매핑해 관리하는 메모리가 들어간다. Go 바이너리 자체, cgo가 직접 할당한 메모리, 운영체제가 프로세스 대신 쥔 메모리는 빠진다. 그래서 컨테이너 limit을 그대로 넣으면 모자랄 수 있다. 제한에 가까워지면 런타임은 GC를 앞당기는 것과 함께 OS에 메모리를 더 적극적으로 돌려준다.

<Lab title="할당 누계는 그대로 두고 설정만 다섯 번 바꿨다">

기준 데이터 8MiB를 계속 들고 있으면서 64KiB 배열을 4,096번 만든다. 최근 16개만 전역 배열에 남기니 나머지는 참조가 끊겨 회수 대상이 되고, 모두 256MiB를 할당하지만 한꺼번에 붙잡고 있지는 않는다.

```go title="gc/main.go · 전체 실행 코드"
package main

import (
	"fmt"
	"os"
	"runtime"
	"time"
)

var recent [16][]byte

func main() {
	fmt.Println("Go:", runtime.Version(), "GOGC:", os.Getenv("GOGC"), "GOMEMLIMIT:", os.Getenv("GOMEMLIMIT"))
	base := make([]byte, 8<<20)
	for i := range base {
		base[i] = 1
	}
	runtime.GC() // 기준점 정렬. 아래 GC 증가량에는 포함하지 않는다.
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)

	start := time.Now()
	var checksum uint64
	var peak uint64
	for i := 0; i < 4096; i++ {
		data := make([]byte, 64<<10)
		data[0] = byte(i)
		data[len(data)-1] = byte(i >> 8)
		recent[i%len(recent)] = data
		checksum += uint64(data[0]) + uint64(data[len(data)-1])
		if i%64 == 0 {
			var m runtime.MemStats
			runtime.ReadMemStats(&m)
			if m.HeapAlloc > peak {
				peak = m.HeapAlloc
			}
		}
	}
	elapsed := time.Since(start)
	runtime.ReadMemStats(&after)
	runtime.KeepAlive(base)

	const mib = 1 << 20
	fmt.Printf("할당 누계 증가: %.1f MiB\n", float64(after.TotalAlloc-before.TotalAlloc)/mib)
	fmt.Printf("GC 횟수 증가: %d\n", after.NumGC-before.NumGC)
	fmt.Printf("표본 힙 최고점: %.1f MiB\n", float64(peak)/mib)
	fmt.Printf("종료 시 NextGC: %.1f MiB\n", float64(after.NextGC)/mib)
	fmt.Printf("종료 시 Sys-HeapReleased: %.1f MiB\n", float64(after.Sys-after.HeapReleased)/mib)
	fmt.Println("체크섬:", checksum, "경과:", elapsed)
}
```

시작 직후의 `runtime.GC()`는 기준점을 맞추려고 부른 것이고, 아래 GC 횟수에는 넣지 않았다. 이 호출을 반복문 안에 넣어 GC를 강제로 돌리는 요령으로 쓰지는 않는다. `runtime.KeepAlive(base)`는 마지막 측정까지 기준 데이터가 살아 있어야 한다는 표시이고, 서비스 코드의 변수마다 붙이라는 뜻은 아니다.

```bash title="같은 바이너리를 다섯 설정으로 실행"
go build -o gc-demo main.go
GOGC=50  GOMEMLIMIT=off    ./gc-demo
GOGC=200 GOMEMLIMIT=off    ./gc-demo
GOGC=200 GOMEMLIMIT=24MiB  ./gc-demo
GOGC=off GOMEMLIMIT=24MiB  ./gc-demo
GOGC=off GOMEMLIMIT=off    ./gc-demo
```

| 설정 | GC 횟수 | 힙 최고점 |
| --- | --- | --- |
| GOGC=50 · 제한 없음 | 58 | 14.6 MiB |
| GOGC=200 · 제한 없음 | 13 | 32.3 MiB |
| GOGC=200 · 24MiB | 25 | 19.5 MiB |
| GOGC=off · 24MiB | 30 | 20.4 MiB |
| GOGC=off · 제한 없음 | 0 | 260.1 MiB |

Go 1.24.7, linux/amd64 2코어에서 잰 값이다. 다섯 번 모두 할당 누계 증가는 256.0MiB, 체크섬은 552960으로 같았다. 힙 최고점은 64번에 한 번 읽은 표본이라 진짜 최고치보다 낮을 수 있고, GC 횟수는 같은 명령을 다시 돌려도 몇 번씩 흔들린다.

`GOGC`를 50에서 200으로 올리자 GC가 58번에서 13번으로 줄고 최고점은 14.6MiB에서 32.3MiB로 올랐다. 방향은 분명하지만, GOGC를 4배로 올린다고 GC가 4분의 1로 준다고 볼 수는 없다.

같은 `GOGC=200`에 24MiB 제한을 더하자 최고점이 32.3MiB에서 19.5MiB로 눌리고 GC는 13번에서 25번으로 늘었다. 메모리를 묶어 두는 대가로 CPU를 더 쓴 것이다.

네 번째 줄이 가장 중요하다. <mark>`GOGC=off`인데도 GC가 30번 돌았다.</mark> 비율 규칙을 꺼도 메모리 제한을 걸어 두면 그 제한을 지키려고 GC가 돈다. 마지막 줄처럼 둘 다 끄면 GC가 한 번도 돌지 않고 힙이 260MiB까지 자란다. 두 설정은 함께 목표를 정한다.

할당 누계는 다섯 번 모두 256.0MiB였으니, 설정을 어떻게 바꿔도 애플리케이션이 만드는 쓰레기의 양은 그대로다.

숫자를 읽을 때는 무엇을 센 값인지부터 본다.

| 관측값 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| `HeapAlloc` | 할당돼 있는 힙 객체의 바이트 수 | 커널이 보는 RSS |
| `NextGC` | 런타임이 잡은 다음 목표 | 프로세스 전체의 한도 |
| `Sys - HeapReleased` | 메모리 제한이 세는 양 | cgo 할당, 런타임 밖 매핑 |
| 프로세스 RSS | OS와 컨테이너가 보는 양 | 런타임 안에서 어디에 썼는지 |

`HeapAlloc`에는 아직 회수되지 않은 죽은 객체도 들어 있고, `NextGC`는 목표일 뿐 상한이 아니다. 그래서 실제 설정은 이렇게 잡는다.

```go title="main.go · 컨테이너 limit이 1GB일 때"
// env: GOMEMLIMIT=900MiB  ← limit의 90% 안팎. RSS에는 런타임이 모르는 메모리도 있다
// env: GOGC=100           ← 비율 규칙은 그대로 둔다. live가 작을 땐 이쪽이 먼저 걸린다

// 코드로 걸 수도 있다
debug.SetMemoryLimit(900 << 20)

// GOGC=off + GOMEMLIMIT은 "상한까지는 GC를 돌리지 않겠다"는 뜻이다.
// 메모리를 꽉 채워 써도 되는 배치 작업에 맞고, 지연에 민감한 서비스에는 맞지 않는다.
```

GC 가이드는 컨테이너처럼 메모리가 정해진 환경이라면 런타임이 모르는 메모리를 위해 5~10% 여유를 더 두라고 권한다. cgo를 많이 쓰거나 큰 파일 매핑이 있으면 여유를 더 둔다.

소프트 상한이라는 점도 기억해 둔다. 살아 있는 데이터만으로 상한을 넘으면 아무리 수집해도 내려가지 않는다. 런타임은 GC가 CPU를 다 가져가지 않도록 GC의 CPU 사용을 대략 50%로 묶어 두기 때문에, 그럴 때는 제한을 넘긴 채 계속 돌다가 결국 OOMKilled가 된다. `GOMEMLIMIT`이 막아 주는 건 쓰레기가 쌓여서 넘치는 경우이고, 살아 있는 데이터가 많아서 넘치는 경우는 막지 못한다. 가이드도 이미 환경 한도에 가까운 프로그램이라면 메모리 제한으로 버티기보다 limit을 올리거나 `GOGC`를 낮추라고 한다.

## 실습 환경과 한계

예제는 처음 올릴 때 이 맥(Apple M5, darwin/arm64)에서 Go 1.24.7과 Go 1.27.0으로 돌렸고, 이번에 같은 코드를 다시 돌려 탈출 판정, 할당 횟수, GC 목표가 그대로인 것을 확인했다. Go 1.26.10으로도 돌렸는데 ④의 `make`가 탈출하지 않는 것과 32바이트에서 0 allocs/op인 것은 Go 1.27.0과 같았다. 컨테이너 실습은 리눅스 실습 서버(Rocky Linux 8.10, podman 4.9, cgroup v1)에서 Go 1.26.10으로 빌드한 linux/amd64 바이너리로 했다. 처음 글에 있던 "재현하지 않았다"는 문장은 이 실습으로 바꿨다. 런타임이 쓰는 메모리를 설명하며 "limit을 그대로 넣으면 모자란다"고 쓴 문장도, 이 실습에서 1GiB를 그대로 걸어도 살아남아 "모자랄 수 있다"로 고쳤다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| `-gcflags=-m` 진단 · `make` 벤치마크 | 버전마다 바뀐 판정과 32바이트 경계 | 다른 아키텍처의 경계. 맥에서만 돌렸다 |
| `gctrace` · 다섯 가지 설정 | 목표가 live를 따라가는 모양과 GC 횟수의 방향 | 실제 서비스의 GC 비용. 횟수는 실행마다 몇 번씩 흔들린다 |
| 1GiB 컨테이너 | 제한 없이 죽고 900MiB로 사는 것, 종료 코드와 커널 로그 | cgroup v2나 쿠버네티스가 OOMKilled를 보여 주는 방식 |
| limit과 같은 1GiB 설정 | 힙 밖 메모리가 거의 없는 프로그램은 살아남는 것 | cgo나 파일 매핑이 큰 서비스에 필요한 여유 |
| 런타임 소스 | Go 1.27.0까지 cgroup 메모리 limit을 읽지 않는 것 | 다음 버전의 계획 |

## 정리

- 스택이냐 힙이냐는 컴파일러가 정한다. 같은 `&Pair{}`도 인라이닝에 따라, 같은 `make`도 툴체인에 따라 판정이 갈렸다. 문법만 보고 짐작하지 말고 `-gcflags=-m`과 `-benchmem`으로 잰다.
- GC는 앱과 동시에 도는 삼색 마크·스윕이고 객체를 옮기지 않는다. 짧은 멈춤을 얻는 대신 쓰기 장벽을 낸다.
- `GOGC`는 비율이라 live가 늘면 목표도 늘어난다. 마킹은 목표에 닿기 전에 시작한다.
- 컨테이너는 RSS의 절대값으로 죽인다. limit 1GB에서 힙 800MB로도 죽을 수 있는 이유다.
- `GOMEMLIMIT`을 limit보다 낮게 걸면 목표가 그 아래로 내려오고, GC 횟수가 그만큼 늘어난다. `GOGC=off`여도 제한이 있으면 GC는 돈다.

GC를 공부할 때는 삼색 마킹과 쓰기 장벽이 핵심이라고 생각했는데, 서비스가 죽은 자리에서 문제가 된 건 GC가 언제 시작하느냐였다. 그 기준과 커널의 기준은 단위부터 달랐다.

[앞 글](/21)의 `GOMAXPROCS`와 모양이 같다는 것도 정리하면서 보였다. 런타임은 코어 수와 힙의 비율로 정하고, 컨테이너는 CPU quota와 RSS로 제한한다. 둘을 맞추는 값이 CPU 쪽에 `GOMAXPROCS`, 메모리 쪽에 `GOMEMLIMIT` 하나씩 있는데, CPU 쪽은 Go 1.25부터 런타임이 quota를 읽어 맞추고 메모리 쪽은 아직 직접 걸어야 한다.

설정을 다섯 번 바꾸는 동안 할당 누계 256MiB는 그대로였다. 이 숫자를 줄이는 건 코드 쪽 일이고, 다음에는 버퍼를 다시 쓰는 `sync.Pool`을 본다.
