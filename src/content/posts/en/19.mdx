<Lead>
I thought putting a one-hour `context.WithTimeout` on a request meant it would wait up to an hour. It died at 30 seconds. The context made it all the way through; it just wasn't the only timer. And once I fixed the timer, the real problem turned out to be somewhere else.
</Lead>

<Summary>
1. An HTTP request in Go carries several timers that know nothing about each other: the ctx deadline, `Client.Timeout`, and the per-phase timers on `Transport`. Whichever expires first wins.
2. The culprit was a `ResponseHeaderTimeout` of 30 seconds, hard-coded into an `http.Transport` three repositories away, where callers could neither see nor change it.
3. A timeout doesn't mean failure; it means the outcome is unknown. If a non-idempotent operation succeeds but the response is lost, retries become a permanent failure loop, and no timeout value fixes that.
</Summary>

## When the logs said three words

This didn't start as a timeout investigation. Volume attaches were failing intermittently in production, and this was all the logs had to say.

```text title="Incident log · what we had at first"
Cause: ipc failed bad request
  {"cause":"rpc error: code = Unavailable desc = http call failed"}
```

`http call failed`. Nothing about which host, which request, or why. The problem wasn't on the side producing the error but on the side reading it. gRPC status details carry different metadata for different kinds of failure, and the upstream service read only three of those keys.

## First hypothesis: the ctx got dropped somewhere

To test that, you first need to know how `context` crosses a process boundary. A `context.Context` is a value inside a Go process; it doesn't travel over the network. <mark>What travels is a single number that the protocol serializes separately.</mark>

How it travels depends on the protocol. gRPC propagates it automatically in the `grpc-timeout` header; there's nothing for the developer to do.

```go title="grpc-go · deadlines travel as a header"
// Client: if ctx has a deadline, grpc-go adds the grpc-timeout header for you
resp, err := client.Invoke(ctx, req)

// Server: that header is read and the deadline is planted in the handler's ctx
func (s *Server) Invoke(ctx context.Context, in *Request) (*Response, error) {
	d, ok := ctx.Deadline() // ok == true, d ≈ the time the client set
	// ...
}
```

go-micro sends a `timeout` header (in nanoseconds), and the server plugin reads it and applies `WithTimeout`.

```go title="go-micro grpc plugin · handling the timeout header"
// go-micro grpc client plugin
header["timeout"] = fmt.Sprintf("%d", opts.RequestTimeout)

// go-micro grpc server plugin
if n, err := strconv.ParseUint(to, 10, 64); err == nil {
	ctx, cancel = context.WithTimeout(ctx, time.Duration(n))
	defer cancel()
}
```

The last hop, HTTP, attaches the ctx to the request with `http.NewRequestWithContext(ctx, ...)`. If the ctx dies, the in-flight request is canceled. I checked every hop.

| Hop | Result |
| --- | --- |
| orchestrator → cluster-api | go-micro sends the `timeout` header; the server sets the deadline on the handler ctx ✓ |
| cluster-api → openstack-client | grpc-go propagates `grpc-timeout` automatically ✓ |
| inside openstack-client | `Invoke(ctx)` → dispatcher → adapter → `NewRequestWithContext(ctx, ...)` ✓ |
| Conclusion | The one-hour deadline reached the Nova request intact. Hypothesis rejected |

Nothing switched to `context.Background()`. The idea that ctx propagation broke was wrong. But the check wasn't wasted: only after it could I move on to "then something other than ctx cut it off."

## The error string had pointed at the culprit all along

Only after rejecting the hypothesis did I reread the error string. If the ctx deadline had expired, the message would have been different.

```text title="Two error strings · they come from different places"
context deadline exceeded                      ← what an expired ctx produces
net/http: timeout awaiting response headers    ← what we actually got
```

The second is a fixed string in Go's standard library, produced when `http.Transport.ResponseHeaderTimeout` expires. <mark>They are two different events.</mark> The moment I told them apart, the investigation turned around and the culprit showed up immediately.

```go title="openstack-client/httpclient/http.go · the Transport in question"
var DefaultTransport = &http.Transport{
	DialContext: (&net.Dialer{
		Timeout:   3 * time.Second,
		KeepAlive: 30 * time.Second,
	}).DialContext,
	TLSHandshakeTimeout:   5 * time.Second,
	ResponseHeaderTimeout: 30 * time.Second, // ← this
	IdleConnTimeout:       90 * time.Second,
	MaxConnsPerHost:       128,
}
```

## Go's HTTP stack has more than one timer, and they don't know about each other

The heart of this incident is that Go's HTTP stack has several timers, each measuring a different phase, each independent. Split one request's lifetime into phases and you can see which timer covers what.

| Timer | Measures | Owner |
| --- | --- | --- |
| `ctx` deadline | The whole request; on expiry, the in-flight request is canceled | Caller |
| `http.Client.Timeout` | The whole request, including reading the body | Client owner |
| `Dialer.Timeout` | Establishing the TCP connection | Transport |
| `TLSHandshakeTimeout` | The TLS handshake | Transport |
| `ResponseHeaderTimeout` | From finishing the request to receiving response headers. Server processing time falls here | Transport |
| `IdleConnTimeout` | Reclaiming idle connections (unrelated to the request limit) | Transport |

Two things stand out. First, `ResponseHeaderTimeout` measures the time the server spends working. It isn't about connecting or sending; it caps how long the server takes to build a response. Set it short on a slow API and it cuts off healthy responses. Second, the owners differ. The caller owns the ctx; whoever wrote the client library owns the Transport timers, and that person has no idea what policy the caller will set.

<Note title="A ctx deadline is the limit? Only half true">

The ctx is just one candidate for the limit. If a lower layer has its own timers, the effective limit is the smallest of them, and those lower timers are usually hard-coded where callers can neither see nor change them.

</Note>

## 30 seconds wasn't a safety net; it was an everyday failure trigger

So why did it only blow up on attach? Nova's volume attach is `POST /servers/{id}/os-volume_attachments`. Before responding, this API makes a synchronous RPC to the compute node to reserve a device name and goes through work on the Cinder side; physically attaching the device to the hypervisor comes afterward. Depending on instance locks and the state of the compute node and Cinder backend, response headers taking more than 30 seconds wasn't an exception. It was within the normal range.

So these 30 seconds weren't a last line of defense against extreme failures. They were a trigger that fired a certain fraction of the time on an ordinary day. Nobody noticed because fast APIs like listing never hit it.

## A nastier problem: it succeeded but was recorded as a failure

That's the timeout bug. Fixing the constant seemed like the end of it. But digging further into production logs turned up something much worse. <mark>Nova had completed the attach successfully.</mark> It just hadn't sent response headers within 30 seconds.

It can't recover on its own. Three things combine to cause it.

- **Attach is non-idempotent.** You can't attach the same volume twice; the second call is rejected with `already in-use`.
- **A network error doesn't mean the operation didn't happen.** The request can arrive and be processed while only the response is lost. From the client's side, a timeout and "the server never got the request" are indistinguishable.
- **The retry decision looked only at its own database.** If the `(action, state)` columns said `failed`, it retried. Nothing anywhere re-observed the actual cluster state.

This is an old distributed-systems problem. When no response comes back, you can't tell whether the other side never got the request or processed it and the response died. There are three responses: make the operation idempotent (idempotency keys), re-observe the actual state after a failure and correct the verdict, or both. Interestingly, a sibling module already had the second one.

```go title="Look at the real state once more before declaring failure"
if err := attach(ctx, vol); err != nil {
	attached, lerr := listAttachedVolumes(ctx, instanceID)
	if lerr == nil && contains(attached, vol.ID) {
		logger.Warn("treat attach as success: volume is already attached")
		return nil // only the response was lost; the operation succeeded
	}
	return err
}
```

The module that broke simply didn't have this. The answer was already in the same codebase; only one side knew it.

<Note title="A timeout means the outcome is unknown">

Treat "failed" and "unknown" the same on a non-idempotent operation and the inconsistency becomes permanent. Raising the timeout doesn't make this go away; it only narrows the window where responses get lost. At 30 seconds or an hour, some request will always straddle the boundary.

</Note>

## Two defects: cause and consequence

Here the problem changed shape. It wasn't one bug but two defects in two different repositories.

| Axis | Defect | Fix only this and… |
| --- | --- | --- |
| A · cause | A hard-coded lower-layer constant overrides the upper layer's timeout policy (openstack-client) | requests caught in the narrower window still fail permanently |
| B · consequence | No re-observation of real state after a lost response (orchestrator) | the cause remains and keeps recurring on other APIs |

<mark>They complement each other; neither replaces the other.</mark> Axis B shipped immediately, since lost responses exist regardless of the timeout value and the fix is needed no matter what. The question was how far to take axis A.

## Weighing five options one by one

There was plenty I could do. The criteria were the smallest change that fixes this bug, and whether it removes the whole class of defect.

### ① Go async with a message queue: rejected

Move long operations like attach off synchronous RPC and onto a queue, and the timeout problem disappears entirely. Retries, backoff, and a DLQ move into infrastructure, and load leveling comes for free. Tempting. But it adds a broker to operate, changes the API contract from sync to async so every caller has to write new status polling, and forces the application to re-implement ordering guarantees like create volume → attach → start replication.

The decisive blow was elsewhere. Queues are usually at-least-once. If a worker finishes the attach and dies just before acking, the message is redelivered and the second attach fails with `already in-use`. The non-idempotency problem remains. Queue or no queue, axis B's re-observation is needed just the same, and that took the shine off this option for good.

### ② Re-observe up front only: necessary but not sufficient

One repository, one deploy unit. Porting a proven pattern gets it into production fastest, and in fact it shipped first. But the 30-second cap isn't specific to attach. Every slow OpenStack API keeps getting cut off: instance creation, snapshots, large listings. And every call site would need its own copy of the re-observation code. This incident alone needed two; a third was only a matter of time.

### ③ A separate Transport just for attach: rejected

Give only the slow APIs a separate `Transport` with a longer `ResponseHeaderTimeout`. The change surface is tiny and there's no regression risk. But it hard-codes "which APIs are slow," which varies by environment and changes over time. And since `ResponseHeaderTimeout` is a Transport field, two Transports mean two connection pools, two pools to the same host, and `MaxConnsPerHost` math split in two. It hides one symptom and leaves the cause.

### ⑤ Clean up every fixed timeout: split off

Applying the same principle across the whole repository would make "one owner" literally true. But there are nearly 20 polling-limit constants alone, each with its own reason. Some have real constraints that prevent using the caller's ctx directly, like token refresh: with a shared cache, one caller canceling must not kill another caller's token refresh. It would grow past reviewable size and put regression risk on the release schedule. I split it out of this change.

| Option | Cause | Surface | Ops | Speed |
| --- | --- | --- | --- | --- |
| ① Message queue | sidesteps | very large | large (broker) | low |
| ② Up front only | ✘ | small | none | high |
| ③ Own Transport | partly | very small | split pools | high |
| ④ ctx owns it | ✓ | small | longer-held conns | medium |
| ⑤ Full cleanup | ✓ | very large | none | low |

## The choice: one owner for the timeout, the caller

Remove `ResponseHeaderTimeout` so that <mark>the caller's ctx deadline alone owns the request limit</mark>. Every slow API gets better, not just attach; changing the policy means changing only the caller; and there's still one connection pool.

```go title="httpclient/http.go · after the fix"
var DefaultTransport = &http.Transport{
	DialContext: (&net.Dialer{
		Timeout:   3 * time.Second, // ✓ keep: ctx can't stand in for guarding connection setup
		KeepAlive: 30 * time.Second,
	}).DialContext,
	TLSHandshakeTimeout: 5 * time.Second, // ✓ keep: same reason

	// No ResponseHeaderTimeout.
	// A transport constant cuts requests regardless of the ctx deadline, overriding
	// the caller's timeout policy. The caller's ctx deadline alone owns the request limit.

	IdleConnTimeout: 90 * time.Second,
	MaxConnsPerHost: 128,
}
```

`Dialer.Timeout` and `TLSHandshakeTimeout` stayed. Connection setup isn't time the server spends working. If TCP doesn't open in 3 seconds, that's a network problem, not a policy question, and a short limit doesn't hurt normal operation. Not every constant is bad; <mark>the problem is a constant that overrides upper-layer policy</mark>. I also left a comment explaining why the field is gone. A missing field's reason can't be read from code, and without the comment someone will helpfully add it back.

### When the limit moves to ctx, error classification has to follow

With the constant gone, every timeout now happens through ctx. Lump those in with transport failures as `Unavailable` like before, and "the server died" looks the same as "we gave up waiting." Diagnosis would get worse.

```go title="httpclient/http.go · mapping errors to gRPC codes"
func mapRequestError(err error, method, rawURL string) error {
	switch {
	case errors.Is(err, context.DeadlineExceeded):
		return status.Error(codes.DeadlineExceeded, "http call timeout")
	case errors.Is(err, context.Canceled):
		return status.Error(codes.Canceled, "http call canceled")
	default:
		return status.Error(codes.Unavailable, "http call failed")
	}
}
```

It has to be `errors.Is`. `net/http` wraps ctx errors in a `*url.Error`, which implements `Unwrap()`, so `errors.Is` reaches through the wrapper.

```go title="Comparing · == versus errors.Is"
// ✘ compares against *url.Error{Err: context.DeadlineExceeded}, so always false
if err == context.DeadlineExceeded { /* ... */ }

// ✓ follows the Unwrap chain down to the cause
if errors.Is(err, context.DeadlineExceeded) { /* ... */ }
```

I applied the same check not just around the `Do` call but around reading the body, too. Obvious in hindsight: with the header limit gone, the deadline on a large listing response most likely expires while reading the body, not the headers. Lump `io.ReadAll` errors into `Internal` there, and the classification you just built falls apart in exactly that spot.

### The safety net only steps in when there's no deadline

With the constant gone, calls that arrive without a deadline hold connections indefinitely. So I added an interceptor on the server side, with one rule: <mark>never override a deadline the caller provided.</mark>

```go title="server/interceptor.go · filling in a default deadline"
func deadlineInterceptor(timeout time.Duration) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req any, _ *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
		if timeout <= 0 {
			return handler(ctx, req)
		}
		if _, ok := ctx.Deadline(); ok {
			return handler(ctx, req) // ✓ the caller's policy always wins
		}
		ctx, cancel := context.WithTimeout(ctx, timeout) // default only when there's no deadline
		defer cancel()
		return handler(ctx, req)
	}
}
```

This is where the second return value of `ctx.Deadline()`, `ok`, earns its keep. `ok == false` means there's no deadline at all, and that's the only thing this interceptor asks. It sits outermost in the chain, because everything after it needs to run under a deadline.

```go title="main.go · interceptor order"
// In ChainUnaryInterceptor, the first argument is the outermost
// Get it backwards and logging runs outside the deadline
grpc.ChainUnaryInterceptor(
	deadlineInterceptor(cfg.RequestTimeout),
	loggingInterceptor,
	authInterceptor,
)
```

<Note title="Lower layers must not override upper-layer policy">

Keep defenses that only make sense at your own layer (connection setup) as constants, and hand the areas where the caller owns the policy (the whole-request limit) to the caller. The safety net fills in only when there's no policy.

</Note>

## Nothing is free: holding connections longer

With `ResponseHeaderTimeout`, a connection stuck on an unresponsive endpoint freed itself every 30 seconds. Now it's held until the ctx deadline. With `MaxConnsPerHost` at 128, a burst of simultaneous failures could exhaust the pool.

At first I thought the interceptor guaranteed a limit, so the risk was low. That was wrong. The interceptor only steps in for calls with no deadline. By design it leaves calls with a deadline alone, so when the caller sets one, that value is the limit as-is, and the default doesn't shorten it. And the protagonist of this story, attach, sets one hour. <mark>The scenario I had dismissed as an unusually long deadline was the default scenario.</mark>

So I accepted the trade-off knowingly. If connection exhaustion shows up in production, the remedy is to shorten the caller's deadline, not to lower the server default. That's the consistent consequence of "the caller owns the policy."

## A green test that protects nothing

Verifying the removal of `ResponseHeaderTimeout` behaviorally needs a server that stalls for more than 30 seconds, and a 40-second test in CI isn't realistic. So the main regression guard is a structural assertion.

```go title="httpclient/http_test.go · keeping the constant from coming back"
// The caller's deadline must be the only limit, so this must be 0 (no limit).
// This one line catches anyone putting the constant back.
func TestDefaultTransportHasNoResponseHeaderTimeout(t *testing.T) {
	if got := httpclient.DefaultTransport.ResponseHeaderTimeout; got != 0 {
		t.Fatalf("ResponseHeaderTimeout = %v, want 0", got)
	}
}
```

The interceptor side taught me something more interesting. All four interceptor unit tests passed, and they still passed after I removed the interceptor from the server chain, because the tests called `deadlineInterceptor(...)` directly. <mark>The feature's entire value hung on one `ChainUnaryInterceptor` line, and that was exactly the line left unprotected.</mark>

```go title="server/interceptor_test.go · testing the wiring too"
// ✘ Calls the interceptor directly: green even if the main.go wiring is missing
_, err := deadlineInterceptor(3*time.Minute)(ctx, req, info, handler)

// ✓ Start a server with the same chain as main (only a shorter default deadline) and call with no deadline
// The handler waits until ctx ends. Without the wiring it waits forever and the test times out red
client := newTestClient(t, 50*time.Millisecond)
_, err = client.Call(context.Background(), req)
require.Equal(t, codes.DeadlineExceeded, status.Code(err)) // check gRPC errors by status code
```

<Note title="When you add a test, make it fail">

If breaking the code on purpose doesn't turn it red, the test might as well not exist. I removed the interceptor, ran it, saw red, and only then committed it.

</Note>

## Summary

- **A ctx deadline is one candidate for the limit.** A ctx propagating all the way is different from a ctx being the real limit. If lower layers have fixed timers, the effective limit is the smallest of them.
- **Go's HTTP timers are separate per phase and unaware of each other.** `ResponseHeaderTimeout` caps the time the server spends working, so set short on a slow API it cuts off healthy responses.
- **Read the error string exactly.** `context deadline exceeded` and `net/http: timeout awaiting response headers` are different events, and telling them apart set the direction of the whole investigation.
- **A timeout means the outcome is unknown, not that it failed.** Treat the two the same on a non-idempotent operation and the inconsistency becomes permanent; no timeout value fixes that. Re-observe the actual state.
- **Lower layers must not override upper-layer policy.** Keep defenses meaningful only at your own layer as constants, and hand the caller the areas the caller owns.
- **Observability comes first.** Back when the logs said only `http call failed`, this investigation couldn't even start.

### Looking back

What took longest in this incident wasn't finding the bug but doubting the premise that setting a ctx meant setting the limit. Checking that premise hop by hop wasn't wasted effort; only once it was done could I move on to "then something other than ctx cut it off."

And only after fixing the timeout did the real problem show itself. Changing 30 seconds to an hour narrows the window; it doesn't close it. In front of a non-idempotent operation, "no response came back" doesn't mean "it didn't happen." It means "I don't know," and when you don't know, you go and look again.

<mark>Fixing a timeout wasn't about changing a number. It was about deciding who owns that number.</mark>
