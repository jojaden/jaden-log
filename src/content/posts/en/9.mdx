<Lead>
Part two of the DB series is about transactions. ACID, isolation levels, and recovery (Redo/Undo) look like three topics to memorize, but they're really one. ACID is the set of promises a transaction makes. Isolation levels are the dial that trades one of them, I (isolation), for performance. Redo/Undo is the machinery that keeps A (atomicity) and D (durability) intact through a crash. This time I opened two sessions on MySQL 8.4 to compare what each isolation level shows, then killed mysqld with a transaction still open to see what survives a restart.
</Lead>

<Summary>
1. Of ACID, the DBMS guarantees A and D with its logs. C and I are largely on you.
2. Isolation levels are a four-step dial for how many of three anomalies you'll tolerate. MySQL defaults to REPEATABLE READ, PostgreSQL to READ COMMITTED.
3. MySQL's REPEATABLE READ reads the snapshot taken at the first SELECT until the end. UPDATE and `FOR UPDATE`, though, read the latest rows, so they change rows the snapshot never had.
4. On restart, Redo brings back what was committed and Undo rolls back what wasn't. MySQL 8.4's defaults fsync both the redo log and the binlog on every commit, so one commit took about 16 ms on the lab server.
</Summary>

## ACID: four promises a transaction makes

A transaction is a unit of work that is logically one thing. There's a reason bank transfers are the eternal example: taking money out of A and adding it to B must <mark>both happen or neither happen</mark>.

```sql title="Bank transfer"
START TRANSACTION;
UPDATE account SET balance = balance - 200000 WHERE id = 'A';
UPDATE account SET balance = balance + 200000 WHERE id = 'B';
COMMIT;  -- until this point, ROLLBACK can undo all of it
```

<Compare>
<Side title="A · Atomicity">

All or nothing. If it dies halfway, everything it did is rolled back. **The DBMS guarantees this with the undo log.**

</Side>
<Side title="C · Consistency">

Constraints and business rules hold before and after the transaction. **You decide what the rules are.**

</Side>
</Compare>

<Compare>
<Side title="I · Isolation">

Concurrent transactions behave as if the others weren't there. Doing it perfectly is slow, so **we compromise with isolation levels.**

</Side>
<Side title="D · Durability">

What's committed survives a power cut. **The DBMS guarantees this with the redo log (WAL).**

</Side>
</Compare>

The DBMS handles A and D for you. C, though, requires you to define what a consistent state is through constraints and validation logic, and I requires you to pick an isolation level. A rule like a balance never going negative has to be written down as a constraint such as `CHECK (balance >= 0)` before the database will stop it. On MySQL 8.4, with that constraint added, an UPDATE that would make a balance negative was rejected with `ERROR 3819`. "It's wrapped in a transaction, so it must be safe" falls apart exactly at C and I.

## Isolation levels: three anomalies, four settings

Perfect isolation, meaning a guarantee identical to running transactions one at a time, would eliminate concurrency. So the SQL standard defines four levels based on which anomalies you're willing to tolerate. Let's start with the anomalies.

- **Dirty read**: you read a value another transaction hasn't committed yet. If that transaction rolls back, you've read a value that never existed.
- **Non-repeatable read**: you read the same row twice within one transaction and get different values. Another transaction updated it and committed in between.
- **Phantom read**: you run the same query twice and a row that wasn't there the first time shows up. Another transaction inserted it and committed in between.

The quiet trap is that defaults differ between databases. <mark>MySQL (InnoDB) defaults to REPEATABLE READ, while PostgreSQL and Oracle default to READ COMMITTED.</mark> The same code can behave differently after you switch databases. Check your current level with `SELECT @@transaction_isolation;` (in PostgreSQL, `SHOW transaction_isolation;`).

I opened two connections (A and B) to a MySQL 8.4 container and sent statements in turn. Account A holds 1,000,000. B takes 200,000 out inside a transaction, and A reads before B commits. The number on the left is time since the start.

A read the 800,000 that B never committed, then read 1,000,000 again after B rolled back. Within one transaction, it saw a balance that was never committed.

```text frame="terminal" title="Output · READ COMMITTED (BEGIN and COMMIT lines omitted)"
    0ms  A  SELECT balance FROM account WHERE id = 'A'
```

```text frame="terminal" title="Output · REPEATABLE READ (BEGIN and COMMIT lines omitted)"
    0ms  A  SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ

    0ms  A  SELECT balance FROM account WHERE id = 'A'
```

</Lab>

## When is the snapshot taken, and what does it read?

Modern databases don't handle isolation with locks alone. The main tool is **MVCC** (multi-version concurrency control), which shows each transaction a snapshot as of its own point in time. That's why reads don't block writes and writes don't block reads. In InnoDB, those old versions live in the undo log. The row holds only its latest value; the values from before each change stay in the undo log, linked by pointers.

A plain SELECT (a snapshot read) walks down this chain to find the version that was committed as of its snapshot. UPDATE, DELETE, and `FOR UPDATE` (locking reads) read the latest row at the top. The asterisk in the table above, "InnoDB prevents most phantoms," comes from these two kinds of reads.

<Lab title="The snapshot is taken at the first SELECT, not at BEGIN">

With A having sent only `BEGIN`, B changed the balance and committed. Then A read for the first time, B changed it once more, and A read again.

```text frame="terminal" title="Output · REPEATABLE READ"
    0ms  A  BEGIN
            → ok
    0ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   12ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=800000
   13ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   23ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=800000
   24ms  A  COMMIT
            → ok
   24ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=600000
```

The 800,000 that B wrote right after `BEGIN` showed up in A's first SELECT, because that SELECT is where the snapshot was taken. Even after B changed it to 600,000, A kept reading 800,000 until it committed. The chain in the figure is exactly this moment.

```text frame="terminal" title="Output · START TRANSACTION WITH CONSISTENT SNAPSHOT (first part)"
    0ms  A  START TRANSACTION WITH CONSISTENT SNAPSHOT
            → ok
    1ms  B  UPDATE account SET balance = balance - 200000 WHERE id = 'A'
            → 1 row(s)
   15ms  A  SELECT balance FROM account WHERE id = 'A'
            → balance=1000000
```

Starting with `START TRANSACTION WITH CONSISTENT SNAPSHOT` takes the snapshot the moment the transaction starts, so even the first SELECT showed the value from before B's change.

</Lab>

<Lab title="UPDATE changes rows the snapshot never had">

There are four accounts: A (1,000,000), B (500,000), C (1,200,000), and D (300,000). After A counted the accounts holding at least 1,000,000, B inserted a 1,500,000 account E and committed.

```text frame="terminal" title="Output · REPEATABLE READ"
    0ms  A  BEGIN
            → ok
    0ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000
            → COUNT(*)=2
    1ms  B  INSERT INTO account (id, balance) VALUES ('E', 1500000)
            → 1 row(s)
   15ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000
            → COUNT(*)=2
   16ms  A  UPDATE account SET flagged = 1 WHERE balance >= 1000000
            → 3 row(s)
   16ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000
            → COUNT(*)=3
   17ms  A  ROLLBACK
            → ok
```

A's second SELECT counted 2, as its snapshot said. But the UPDATE with the same condition changed 3 rows. UPDATE is a locking read, so it reads E, which B committed. Rows I've changed are visible in my own snapshot, so the SELECT after it counted 3. Within one transaction, the number you counted and the number you changed can differ.

</Lab>

<Lab title="Locking a range with FOR UPDATE blocks the INSERT only under REPEATABLE READ">

This time A counted with `FOR UPDATE` from the start, and B inserted E in the meantime. Half a second later A counted again, then committed. `balance` has an index.

```text frame="terminal" title="Output · REPEATABLE READ (SET and BEGIN lines omitted)"
    0ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=2
    1ms  B  INSERT INTO account (id, balance) VALUES ('E', 1500000)
            … waiting
  553ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=2
  555ms  A  COMMIT
            → ok
  578ms  B  ↳ 1 row(s) (waited 577ms)
```

```text frame="terminal" title="Output · READ COMMITTED (SET and BEGIN lines omitted)"
    1ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=2
    1ms  B  INSERT INTO account (id, balance) VALUES ('E', 1500000)
            → 1 row(s)
  513ms  A  SELECT COUNT(*) FROM account WHERE balance >= 1000000 FOR UPDATE
            → COUNT(*)=3
```

Under REPEATABLE READ, the INSERT from B waited until A committed. That's the next-key lock: a locking read locks not only the rows it finds but also the gaps between them. READ COMMITTED doesn't lock gaps, so the INSERT went straight in and A's second `FOR UPDATE` counted 3. Put together, InnoDB's REPEATABLE READ prevents phantoms among snapshot reads and among locking reads. Mix the two, as in the previous lab, and a phantom shows up.

</Lab>

<Lab title="An open snapshot holds on to Undo">


While B committed 1,000 times, A still read 1,000,000. Since A could still read those old versions, the 1,000 undo records couldn't be removed, and the history list length climbed to 1,001. It didn't drop right after A committed, either: it stayed at 1,002 through 55 seconds and hit 0 at 60. Purge, which removes undo, runs separately in the background. Leave a transaction open for a long time and the undo from that whole stretch piles up.

</Lab>

<Note title="In practice">

For most services, READ COMMITTED or REPEATABLE READ is enough. What matters is knowing which level your database is running at, and whether each query reads a snapshot or the latest rows. For anything that must never drift, like money, don't lean on the isolation level. Protect it explicitly with the pessimistic or optimistic locks from [part one](/en/7).

</Note>

## Recovery: commits survive a power cut

A database doesn't write changes straight to disk. For speed, it modifies pages in memory (the buffer pool) and flushes them to disk later in batches. So what happens if the server dies in between? The log fills that gap.

The rule is **WAL (write-ahead logging)**: write the log to disk before the data. The log carries two kinds of information.

- **Redo log**: the value after the change. Used to replay changes that were committed but hadn't reached the data files yet.
- **Undo log**: the value before the change. Used to roll back changes from transactions that died before committing. As the previous section showed, in InnoDB and Oracle the old versions MVCC shows to readers come from here too. PostgreSQL keeps old row versions in the table itself, so it has no separate undo log.

A checkpoint periodically flushes buffered changes to disk and leaves a marker. Thanks to that, a restart only replays the log from the last checkpoint instead of from the beginning. On restart, the database first uses Redo to rebuild the state just before the crash (anything committed must survive: durability). Then it uses Undo to roll back the transactions that never committed (they must leave no trace: atomicity).

First it read the redo log from around the checkpoint and replayed it up to the crash (`Apply batch completed!`), then it rolled back the 50,000 rows of the one transaction that never committed. So a successful `COMMIT` doesn't mean the data is all on disk. It means <mark>the redo log is safely on disk</mark>. That's enough, because whenever the server dies, the log can rebuild the data.

## What does a single commit wait for?

A log that's only written to the OS buffer vanishes with a power cut. So a commit fsyncs it down to disk, and that's the price of one commit. In MySQL, two settings decide when that happens.

- `innodb_flush_log_at_trx_commit` (default 1): at 1, every commit writes and fsyncs the redo log. At 2, every commit writes it and the fsync happens once a second; at 0, both the write and the fsync happen once a second.
- `sync_binlog` (default 1): at 1, every commit fsyncs the binlog; at 0, the fsync is left to the OS.

MySQL 8.4 has the binary log (binlog) on by default. So on default settings, a commit fsyncs the redo log and the binlog once each. I checked how much the counters grew over 100 autocommit INSERTs.

```text frame="terminal" title="Growth over 100 INSERTs · performance_schema"
Innodb_os_log_fsyncs                    +118
wait/io/file/sql/binlog (COUNT_MISC)    +100
```

I also looked at what the speed costs. The documentation says that with `innodb_flush_log_at_trx_commit` at 0, a mysqld crash alone can lose roughly the last second of commits, and at 2 it takes an OS crash or power loss.

As long as the binlog was fsynced on every commit, none of the three settings lost an acknowledged commit. This lab killed only the mysqld process; I didn't reproduce the OS going down with it or a power cut. PostgreSQL's `synchronous_commit = off` makes the same trade: faster commit responses in exchange for possibly losing the last few commits.

</Lab>

## Lab setup and limits

The labs ran MySQL 8.4.13 with default settings in a podman container on the same Rocky Linux 8.10 server (4 cores) as [part one](/en/7). The isolation level is REPEATABLE READ, the binlog is on, and both `sync_binlog` and `innodb_flush_log_at_trx_commit` are 1. The two-session labs come from a Go program (go-sql-driver/mysql) on the same server sending statements in turn over two connections; typing the same steps into two `mysql` terminals gives the same results. The settings I changed (`innodb_flush_log_at_trx_commit`, `sync_binlog`, `log_error_verbosity`) were put back to their defaults after the labs.

The version first published in July 2026 said a commit only waits for one log fsync. On 8.4 defaults with the binlog on, it fsyncs the redo log and the binlog once each, so I corrected that sentence.

| What I checked | What it tells you | What it doesn't |
| --- | --- | --- |
| Two-session labs | What each level shows; snapshot reads vs. locking reads | PostgreSQL's results, which I only checked in the docs |
| History list length | An open snapshot holds on to undo | Why purge ran 55–60 seconds later; it changes under load |
| SIGKILL recovery | Redo replay, then undo rollback; only committed rows remain | How long rolling back millions of rows takes |
| Commit time | Time per commit for each setting | NVMe or battery-backed caches; group commit under concurrent commits |
| Loss on a kill | Commits lost per setting when only mysqld dies | Losses on an OS crash or power cut, not reproduced on a shared server |

## Wrapping up

| Situation | What happened | What to do |
| --- | --- | --- |
| Two reads under READ COMMITTED | Values committed in between show up | If a decision rests on re-reading, check the isolation level first |
| UPDATE under REPEATABLE READ | Rows the snapshot never had change too | Check the counted and changed numbers separately |
| A snapshot left open | Undo piles up and purge falls behind | Keep transactions short |
| mysqld dies | Redo brings back, Undo rolls back | Trust only commits that were acknowledged |
| Slow commits | Two fsyncs, redo and binlog | Look at both settings and decide whether you can accept losing commits |

For anything involving money, don't rely on the isolation level; use the explicit locks from [part one](/en/7).
