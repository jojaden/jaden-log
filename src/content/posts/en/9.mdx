<Lead>
Part two of the DB series is about transactions. ACID, isolation levels, and recovery (Redo/Undo) look like three topics to memorize, but they're really one. ACID is the set of promises a transaction makes. Isolation levels are the dial that trades one of them, I (isolation), for performance. Redo/Undo is the machinery that keeps A (atomicity) and D (durability) intact through a crash.
</Lead>

<Summary>
1. Of ACID, the DBMS guarantees A and D with its logs. C and I are largely on you.
2. Isolation levels are a four-step dial for how many of three anomalies you'll tolerate. MySQL defaults to REPEATABLE READ, PostgreSQL to READ COMMITTED.
3. Recovery rests on WAL. After a crash, committed work is redone and uncommitted work is undone.
</Summary>

## ACID: four promises a transaction makes

A transaction is a unit of work that is logically one thing. There's a reason bank transfers are the eternal example: taking money out of A and adding it to B must <mark>both happen or neither happen</mark>.

```sql title="Bank transfer"
START TRANSACTION;
UPDATE account SET balance = balance - 200000 WHERE id = 'A';
UPDATE account SET balance = balance + 200000 WHERE id = 'B';
COMMIT;  -- until this point, ROLLBACK can undo all of it
```

<Compare>
<Side title="A · Atomicity">

All or nothing. If it dies halfway, everything it did is rolled back. **The DBMS guarantees this with the undo log.**

</Side>
<Side title="C · Consistency">

Constraints and business rules hold before and after the transaction. **You decide what the rules are.**

</Side>
</Compare>

<Compare>
<Side title="I · Isolation">

Concurrent transactions behave as if the others weren't there. Doing it perfectly is slow, so **isolation levels make a trade-off.**

</Side>
<Side title="D · Durability">

Once committed, it survives a power cut. **The DBMS guarantees this with the redo log (WAL).**

</Side>
</Compare>

A and D come for free from the DBMS. C is different: you have to define what a consistent state is, through constraints and validation. And for I, you have to pick the isolation level. "It's in a transaction, so it's safe" stops being true exactly at C and I.

## Isolation levels: three anomalies, four settings

Perfect isolation, meaning results identical to running transactions one at a time, kills concurrency. So the SQL standard defines four levels by which anomalies you're willing to put up with. Here are the anomalies first.

- **Dirty read**: you read a value another transaction hasn't committed yet. If it rolls back, you read a value that never existed.
- **Non-repeatable read**: you read the same row twice in one transaction and get different values. Someone else updated and committed in between.
- **Phantom read**: you run the same query twice and a row appears that wasn't there before. Someone else inserted and committed in between.

The quiet trap is that defaults differ between databases. <mark>MySQL (InnoDB) defaults to REPEATABLE READ, while PostgreSQL and Oracle default to READ COMMITTED.</mark> The same code can behave differently after you switch databases.

The asterisk in the table depends on the database too. InnoDB's REPEATABLE READ serves plain SELECTs from a snapshot and takes gap (next-key) locks for locking reads like `FOR UPDATE`, which prevents most phantoms. PostgreSQL's REPEATABLE READ is snapshot isolation, so phantoms don't show up there either.

Modern databases don't solve this with locks alone. The main tool is **MVCC** (multi-version concurrency control), which shows each transaction a snapshot as of its own point in time. That's why reads don't block writes and writes don't block reads.

<Note title="In practice">

For most services, READ COMMITTED or REPEATABLE READ is enough. What matters is knowing which level your database is running at right now. For anything that must never drift, like money, don't lean on the isolation level. Protect it explicitly with the pessimistic or optimistic locks from [part one](/en/7).

</Note>

<Lab title="See a non-repeatable read with two sessions">

Open two MySQL consoles and run the steps in numbered order. Check the current level with `SELECT @@transaction_isolation;` (in PostgreSQL, `SHOW transaction_isolation;`).

```sql title="Session A"
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT balance FROM account WHERE id = 'A';  -- ① 1000000

SELECT balance FROM account WHERE id = 'A';  -- ③ 800000, same transaction, different value
COMMIT;
```

```sql title="Session B"
UPDATE account SET balance = balance - 200000 WHERE id = 'A';  -- ② commits immediately (autocommit)
```

Switch session A to `REPEATABLE READ` and try again: step ③ now returns the same value as ①, because the transaction keeps reading the snapshot it took on its first read.

</Lab>

## Recovery: commits survive a power cut

A database doesn't write changes straight to disk. For speed, it modifies pages in memory (the buffer pool) and flushes them to disk later in batches. So what happens if the server dies in between? The log fills that gap.

The rule is **WAL (write-ahead logging)**: write the log to disk before the data. The log carries two kinds of information.

- **Redo log**: the value after the change. Used to replay changes that were committed but hadn't reached the data files yet.
- **Undo log**: the value before the change. Used to roll back changes from transactions that died before committing. In InnoDB and Oracle, the old versions MVCC shows to readers come from here too. PostgreSQL keeps old row versions in the table itself, so it has no separate undo log.

A checkpoint periodically flushes buffered changes to disk and leaves a marker. Thanks to that, a restart only replays the log from the last checkpoint instead of from the beginning. On restart, the database first uses Redo to rebuild the state just before the crash (anything committed must survive: durability). Then it uses Undo to roll back the transactions that never committed (they must leave no trace: atomicity).

So a successful `COMMIT` doesn't mean the data is all on disk. It means <mark>the redo log is safely on disk</mark>. That's enough, because whenever the server dies, the log can rebuild the data. And since a commit only waits for one log fsync, it's fast too. This is why WAL is the heart of every serious database, and of systems like Kafka as well.

That guarantee depends on configuration, though. In MySQL, `innodb_flush_log_at_trx_commit` defaults to 1, which fsyncs the log on every commit. Set it to 0 for speed and even a MySQL crash can lose roughly the last second of commits; set it to 2 and it takes an OS crash or power loss. PostgreSQL's `synchronous_commit = off` makes the same trade.

## Wrap-up

- In ACID, the DBMS covers A and D with its logs, and **C and I are on you**.
- Isolation levels are a dial for which anomalies you allow. **Start by checking your database's default** (REPEATABLE READ in MySQL, READ COMMITTED in PostgreSQL).
- Where money is involved, protect it with **explicit locks**, not the isolation level.
- WAL writes the log first and the data later. After a crash, **committed work is redone, uncommitted work is undone**.
