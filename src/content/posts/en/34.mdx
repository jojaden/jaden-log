<Lead>
Every Kubernetes post I wrote started with a Pod that was already running, but what happens between `kubectl apply` and that Pod was something I only knew from diagrams. So I timed it on a lab node, down to the millisecond. I also stopped the controllers for 30 seconds, deleted Pods and changed the replica count while they were off, and then turned them back on. The count was back where it should be in under a second.
</Lead>

<Summary>
1. `kubectl apply` sends HTTP requests to the API Server, and the API Server is the only component that reads and writes etcd. Controllers, the scheduler, and the kubelet watch the API Server, act when there is work for them, and write the result back to it.
2. Controllers don't react to "a Pod was deleted." They look at "how many are there now" and fix the difference, so they catch up on whatever happened while they were down.
3. When etcd stops, API requests fail, but containers that are already running keep running. A container process's parent is containerd-shim, not the kubelet.
</Summary>

<Note title="Who this is for">
This is for people who have deployed with `kubectl` but have only seen what happens next in diagrams. Sections 1 and 2 follow a request to the API Server and etcd, sections 3 and 4 cover controllers and the scheduler, section 5 follows a container being created on the node, and section 6 is about the control plane going down. The summary at the end includes a map of where later posts dig into each step. The lab screenshots show commands and output exactly as they ran on the lab server.
</Note>

## kubectl apply is an HTTP request

Kubernetes splits its work across a handful of programs. The API Server takes requests, etcd (a distributed key-value store) keeps what was requested, controllers and the scheduler act on what is stored, and on every node the kubelet actually starts the containers. The first four together are called the control plane.

What to look at here is the shape of the lines. Controllers, the scheduler, and the kubelet never talk to each other directly. Each one watches the API Server, does its part when there is work, and writes the result back to the API Server. Only the API Server opens etcd.

kubectl is just one more box on the outside of this picture. With `-v=6`, it prints each HTTP request it sends.

<Lab title="One apply sent six requests, and only the last POST created anything">
<Shot src="/img/34/apply.webp" w={1720} h={586} phone={{ src: '/img/34/apply-phone.webp', w: 1170, h: 1602 }} name="lab-node:/tmp/jd-k1" alt="kubectl apply -v=6 output: three GETs for the OpenAPI schema, a GET for Deployment web returning 404, a GET for the namespace returning 200, and a final POST returning 201 Created in 30 ms, followed by deployment.apps/web created" />

The first three lines fetch the schema (OpenAPI) so kubectl can check that the YAML has the right shape. Next, a `GET` asks whether a Deployment with the same name exists and gets a 404, so the final `POST` creates it. Once the server answers `201 Created`, kubectl is done. At that moment, there isn't a single Pod yet.
</Lab>

The address `https://127.0.0.1:6443` is worth a look too. kubectl talks to the API Server over TLS and identifies itself with the client certificate in its kubeconfig. I covered how TLS checks the other side in the [TCP and TLS post](/en/33).

Authentication asks who sent the request, and authorization asks whether they may do this. Admission either changes the incoming object (filling in defaults) or blocks it if it breaks a policy. I plan to open each of these gates in a later Kubernetes security series.

An object that passes is written to etcd as a single key. I read the keys directly with the `etcdctl` inside the etcd Pod.

</Lab>

## Controllers act on differences, not commands

Writing a Deployment to etcd doesn't start anything by itself. A Deployment is a document that records the desired state (spec), and the controller is what compares it with the current state (status) and closes the gap.

The Kubernetes docs explain this with a thermostat[^thermo]. You don't tell it "run the heater for 10 minutes." You set "keep it at 22 degrees," and it keeps checking the temperature and turns the heater on and off. This is called a reconcile loop, and a single process, the controller-manager, runs many such controllers, one for each kind of object like Deployments, ReplicaSets, and namespaces.

## The kubelet only takes its own Pods

## What stops when the control plane stops?

So far, controllers look like they react to events. I deleted a Pod, and they made a new one. Kubernetes' design principles say the opposite, though.

> Functionality must be *level-based* … regardless of how many intermediate state updates may have been missed. Edge-triggered behavior must be just an optimization.

[Kubernetes design principles · Control logic](https://github.com/kubernetes/design-proposals-archive/blob/main/architecture/principles.md#control-logic)

The way to test that is to turn a controller off so it can't hear any events. This RKE2 cluster also runs other services, though, and I decided not to touch anything I hadn't created myself. So I started a separate lab control plane on the same server, on different ports, with only etcd, an API Server, and a controller-manager, and no nodes. Without nodes the Pods stay Pending, but creating and deleting Pod objects is the controllers' job, so it doesn't matter for this experiment.

```python title="/tmp/jd-k1/node-steps.py · pull one Pod's steps from the containerd log"
"""Pull one Pod's sandbox, network, and container steps from the containerd log, in time order"""
import re, sys
pod = sys.argv[1]
log = open("/var/lib/rancher/rke2/agent/containerd/containerd.log", errors="replace").read().splitlines()
def short(s):
    s = re.sub(r"&(PodSandbox|Container)Metadata\{Name:([^,]*),[^}]*\}", r"{Name:\2,…}", s.replace("\\\"", "\""))
    return re.sub(r"[0-9a-f]{64}", lambda m: m.group(0)[:12] + "…", s)
sb = cid = None
for l in log:
    if "PodSandboxMetadata{Name:" + pod + "," in l and "returns sandbox id" in l:
        sb = re.search(r"sandbox id \\\"([0-9a-f]{64})", l).group(1)
    if sb and f"within sandbox \\\"{sb}\\\"" in l and "returns container id" in l:
        cid = re.search(r"container id \\\"([0-9a-f]{64})", l).group(1)
for l in log:
    m = re.match(r"time=\"[0-9-]+T([0-9:.]{12})[^\"]*\" level=\w+ msg=\"(.*)\"$", l)
    if m and (f"Name:{pod}," in l or (sb and sb in l) or (cid and cid in l)) and re.search(r"RunPodSandbox|CreateContainer|StartContainer", l):
        print(m.group(1), short(m.group(2)))
    c = re.match(r"[0-9-]+ ([0-9:.]{12}) .*(Calico CNI using IPs: \[[^]]*\])", l)
    if c and sb and sb in l:
        print(c.group(1), c.group(2))
```

## Summary

- `kubectl apply` is an HTTP request, and when the server answers `201 Created` there is no Pod yet. Only the API Server reads and writes etcd.
- Controllers close the gap between desired and current state. The Deployment creates a ReplicaSet, the ReplicaSet creates Pods, and the creator is recorded as the owner.
- The scheduler fills in a Pod's `nodeName`, and the kubelet takes only the Pods with its own node in that field and hands them to containerd.
- On the lab node, of the 2.77 seconds from the Deployment appearing to the Pod being Ready, the control plane took 156 ms, and the slowest step was the sandbox at 1.32 seconds.
- Even after 30 seconds off, the controller-manager caught up in 0.76 seconds by reading the current state. When etcd stops the API fails, but running containers keep going under containerd-shim.

Laid out as steps, the path of one apply has eight of them. The Kubernetes series will open the Kubernetes side of each step, and the basics series will open the Linux, networking, and storage principles underneath.

[^magic]: The Kubernetes API docs describe these four bytes (`0x6b 0x38 0x73 0x00`) as a prefix that marks content on disk or in etcd as protobuf rather than JSON.

[^thermo]: The first example in the [Controllers](https://kubernetes.io/docs/concepts/architecture/controller/) page is a room thermostat. The temperature you set is the desired state, and the actual room temperature is the current state.

[^bind]: The default binder plugin (`defaultbinder`) creates a `v1.Binding` and sends it to the Pod's `binding` subresource, and the API Server uses it to fill in `spec.nodeName`.
