## kubectl apply is an HTTP request

Kubernetes splits its work across a few programs: the API Server takes requests, etcd (a distributed key-value store) keeps them, controllers and the scheduler act on what is stored, and the kubelet on each node starts the containers. The first four make up the control plane.

Controllers, the scheduler, and the kubelet never talk to each other directly. Each one watches the API Server, does its part when there is work, and writes the result back to the API Server. Only the API Server opens etcd.

kubectl is just one more box on the outside of this picture. With `-v=6`, it prints each HTTP request it sends.

<Lab title="One apply sent six requests, and only the last POST created anything">
<Shot src="/img/34/apply.webp" w={1720} h={586} phone={{ src: '/img/34/apply-phone.webp', w: 1170, h: 1602 }} name="lab-node:/tmp/jd-k1" alt="kubectl apply -v=6 output: three GETs for the OpenAPI schema, a GET for Deployment web returning 404, a GET for the namespace returning 200, and a final POST returning 201 Created in 30 ms, followed by deployment.apps/web created" />

The first three lines fetch the schema (OpenAPI) to check the YAML, and after a `GET` gets a 404, the final `POST` creates the Deployment. Once the server answers `201 Created`, kubectl is done. At that moment, there isn't a single Pod yet.
</Lab>

kubectl talks to the API Server (`https://127.0.0.1:6443`) over TLS and identifies itself with the client certificate in its kubeconfig. I covered how TLS checks the other side in the [TCP and TLS post](/en/33).

Authentication asks who sent the request, and authorization asks whether they may do this. Admission either changes the incoming object (filling in defaults) or blocks it if it breaks a policy.

An object that passes is written to etcd as one key, which I read with `etcdctl` inside the etcd Pod.

<Shot src="/img/34/etcd.webp" w={1720} h={693} phone={{ src: '/img/34/etcd-phone.webp', w: 1170, h: 1272 }} name="lab-node:/tmp/jd-k1" alt="etcdctl get /registry --prefix --keys-only filtered to jd-k1 shows eight keys, and the first 48 bytes of the Deployment web value viewed with od -c start with k 8 s \0" />

Each key is built from the resource type, the namespace, and the name, in that order. The value isn't YAML. It's protobuf that starts with the three letters `k8s` and a zero byte[^magic], followed by readable bits like `apps/v1`, `Deployment`, `web`, and `jd-k1`.
</Lab>

## Controllers act on differences, not commands

A Deployment in etcd starts nothing by itself. It records the desired state (spec), and a controller compares it with the current state (status) and closes the gap.

The Kubernetes docs compare this to a thermostat[^thermo]: you set "keep it at 22 degrees," not "run the heater for 10 minutes," and it keeps checking and switching. This is a reconcile loop, and one process, the controller-manager, runs a controller for each kind of object, such as Deployments, ReplicaSets, and namespaces.

Notice that a Deployment doesn't create Pods directly. Controllers create the next object one step at a time, and the creator is recorded as the owner.

## What stops when the control plane stops?

Controllers look like they react to events, since deleting a Pod made them create one. Kubernetes' design principles say the opposite.

> Functionality must be *level-based* … regardless of how many intermediate state updates may have been missed. Edge-triggered behavior must be just an optimization.

[Kubernetes design principles · Control logic](https://github.com/kubernetes/design-proposals-archive/blob/main/architecture/principles.md#control-logic)

```python title="/tmp/jd-k1/node-steps.py · pull one Pod's steps from the containerd log"
"""Pull one Pod's sandbox, network, and container steps from the containerd log, in time order"""
import re, sys
pod = sys.argv[1]
log = open("/var/lib/rancher/rke2/agent/containerd/containerd.log", errors="replace").read().splitlines()
def short(s):
    s = re.sub(r"&(PodSandbox|Container)Metadata\{Name:([^,]*),[^}]*\}", r"{Name:\2,…}", s.replace("\\\"", "\""))
    return re.sub(r"[0-9a-f]{64}", lambda m: m.group(0)[:12] + "…", s)
sb = cid = None
for l in log:
    if "PodSandboxMetadata{Name:" + pod + "," in l and "returns sandbox id" in l:
        sb = re.search(r"sandbox id \\\"([0-9a-f]{64})", l).group(1)
    if sb and f"within sandbox \\\"{sb}\\\"" in l and "returns container id" in l:
        cid = re.search(r"container id \\\"([0-9a-f]{64})", l).group(1)
for l in log:
    m = re.match(r"time=\"[0-9-]+T([0-9:.]{12})[^\"]*\" level=\w+ msg=\"(.*)\"$", l)
    if m and (f"Name:{pod}," in l or (sb and sb in l) or (cid and cid in l)) and re.search(r"RunPodSandbox|CreateContainer|StartContainer", l):
        print(m.group(1), short(m.group(2)))
    c = re.match(r"[0-9-]+ ([0-9:.]{12}) .*(Calico CNI using IPs: \[[^]]*\])", l)
    if c and sb and sb in l:
        print(c.group(1), c.group(2))
```

## Summary

- `kubectl apply` is an HTTP request, and when the server answers `201 Created` there is no Pod yet. Only the API Server reads and writes etcd.
- Controllers close the gap between desired and current state. The Deployment creates a ReplicaSet, the ReplicaSet creates Pods, and the creator is recorded as the owner.
- The scheduler fills in a Pod's `nodeName`, and the kubelet takes only the Pods with its own node in that field and hands them to containerd.
- On the lab node, of the 2.77 seconds from the Deployment appearing to the Pod being Ready, the control plane took 156 ms, and the slowest step was the sandbox at 1.32 seconds.
- Even after 30 seconds off, the controller-manager caught up in 0.76 seconds by reading the current state. When etcd stops the API fails, but running containers keep going under containerd-shim.

Laid out as steps, the path of one apply has eight of them. The Kubernetes series will open the Kubernetes side of each step, and the basics series will open the Linux, networking, and storage principles underneath.

| Step | Kubernetes series | Basics series |
| --- | --- | --- |
| 1. kubectl → API Server | Security (authn, authz) | CS basics (TCP, TLS) |
| 2. Stored in etcd | Architecture, operations (etcd) | Storage basics (fsync) |
| 3. Controllers create RS and Pods | Workloads | |
| 4. The scheduler picks a node | Workloads (scheduler) | |
| 5. kubelet → containerd → runc | Architecture (Pods, images) | Linux container basics |
| 6. CNI attaches the Pod IP | Networking | Linux networking basics |
| 7. Volumes attach (none here) | Storage | Storage basics |
| 8. Ready → traffic via Service | Networking, workloads | CS basics (signals) |
