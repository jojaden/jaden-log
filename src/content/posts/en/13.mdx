<Lead>
Go dropped exceptions and filled the gap with `defer` and errors as values. The syntax for all three takes thirty seconds to learn, yet the traps keep showing up years later. I reorganized them around one question: exactly when, and what, does each one hold on to?

The short answer is that defer holds the arguments as they are at registration, a closure holds the variable itself, and `%w` holds the error it wraps. This post covers when defer evaluates and what it costs, when defer doesn't run, panic and recover, errors and `%w`, then closures and loop variables. I reran every example on Go 1.26.10.
</Lead>

<Summary>
1. defer only postpones execution. The arguments are frozen the moment it's registered, and most of its traps come from that mismatch.
2. An error is a returned value. And the moment you wrap with `%w`, the wrapped error effectively becomes part of your public API.
3. A closure holds on to the outer variable itself. Go 1.22 fixed the loop variable bug in the language itself, but unless you bump `go.mod`, you still get the old behavior.
</Summary>

<Note title="Who this is for">
I wrote this for people who use `defer` and `if err != nil` every day but have never pinned down when defer evaluates its arguments, or what `%w` promises to callers. Sections 1\~3 cover defer, 4 covers panic and recover, 5 covers errors and `%w`, and 6\~7 cover closures and loop variables. The two words of an interface value were in [part one](/en/11), and slices and maps in [part two](/en/12).
</Note>

## defer: execution is postponed, arguments aren't

If you only remember `defer` as "runs when the function ends," you have half of it. More precisely, it schedules this call to run at the end of the function, right now, and <mark>at that moment every argument is evaluated and frozen.</mark>

I added a method with a value receiver to the two lines in the figure and ran it.

```go title="args/main.go"
type T struct{ n int }

func (t T) show() { fmt.Println("C:", t.n) }

func main() {
	i := 0
	t := T{n: 0}
	defer fmt.Println("A:", i)              // argument evaluated now: 0 is frozen
	defer func() { fmt.Println("B:", i) }() // closure: captures the variable i
	defer t.show()                          // a value receiver is an argument too: a copy
	i = 1
	t.n = 1
}
```

```text frame="terminal" title="Output"
$ go run ./args
C: 0
B: 1
A: 0
```

The last one registered runs first, so the order is C, B, A, and only the closure B saw the value after the change. C is the one people tend to miss. A method receiver is an argument too, so `t.show()` with a value receiver captured a copy at registration and printed the 0 from before `t.n = 1`. The point from [part one](/en/11) that a value receiver gets a copy applies to defer as well.

For the same reason, `defer log.Println(time.Since(start))` at the top of a function prints almost nothing. I put both forms in a function that sleeps for 200ms: passed as an argument it printed 30µs, wrapped in a closure it printed 201ms. So if you need the value at execution time, wrap it in a closure, and pass it as an argument only when you want the value at registration.

## The real cost of defer: in a loop, you lose twice

"defer is slow" is only half true now. Since Go 1.14, open-coded defers let the compiler, when conditions allow, simply expand the deferred call at the end of the function. The release notes say it costs almost nothing compared to calling the function directly.

The problem is when those conditions break. The classic case is a defer inside a loop, and there the cost comes in two layers.

<Compare>
<Side title="When conditions hold: open-coded" tone="good">

- The compiler expands the call inline at the end of the function
- No defer record is made, so it costs about the same as a direct call
- Conditions: at most 8 defers in the function, no defer in a loop, and returns × defers no more than 15

</Side>
<Side title="Inside a loop: heap records" tone="bad">

- Each iteration takes a defer record and links it into a list
- ① Every call goes through the runtime, which is slower, and
- ② the calls pile up until the function ends. File handles stay open until then

</Side>
</Compare>

That compiler behavior is where "don't defer in a loop" comes from. The well-known fix is to wrap the loop body in an anonymous function. Each iteration then cleans up as soon as that function returns, and the defer is out of the loop again, eligible for open coding. To check the second cost first, I opened five files in a loop and printed how many file descriptors were open at each step.

```go title="deferfd/main.go (excerpt)"
func inLoop(names []string) {
	for _, name := range names {
		f, err := os.Open(name)
		if err != nil {
			panic(err)
		}
		defer f.Close() // runs only when the function ends
		fmt.Print(openFDs(), " ")
	}
	fmt.Println()
}

func perIter(names []string) {
	for _, name := range names {
		func() {
			f, err := os.Open(name)
			if err != nil {
				panic(err)
			}
			defer f.Close() // runs when this anonymous function ends
			fmt.Print(openFDs(), " ")
		}()
	}
	fmt.Println()
}
```

```text frame="terminal" title="Output"
$ go run ./deferfd
defer in loop:    6 7 8 9 10
body as a func:   6 6 6 6 6
```

With the defer in the loop, the count went up by one each time until it hit 10, and all five files stayed open until the function returned. With the body wrapped in an anonymous function, it was 6 every time. With thousands of files, that difference shows up as <C k="err">too many open files</C>.

## When you can't count on defer

I've been burned by trusting `defer` as cleanup that always runs. There are definitely cases where it doesn't.

| Situation | Does defer run? |
| --- | --- |
| Normal return | Yes |
| panic | Yes, in reverse while the stack unwinds |
| `runtime.Goexit` | Yes, all of this goroutine's defers run before it exits |
| `os.Exit` | **No.** The process ends immediately |
| `log.Fatal` and friends | **No.** They call `os.Exit(1)` internally |
| fatal error | **No.** Concurrent map writes and the like |

I put one defer in `main` and ended the program five different ways, picked by an argument.

```go title="notrun/main.go"
func main() {
	defer fmt.Println("main defer ran")
	switch os.Args[1] {
	case "return":
		return
	case "panic":
		panic("boom")
	case "goexit":
		var wg sync.WaitGroup
		wg.Add(1)
		go func() {
			defer wg.Done()
			defer fmt.Println("goroutine defer ran")
			runtime.Goexit()
		}()
		wg.Wait()
	case "exit":
		os.Exit(3)
	case "fatal":
		log.Fatal("cannot read config file")
	}
}
```

```text frame="terminal" title="Output (stack lines omitted)"
$ go run ./notrun return
main defer ran
$ go run ./notrun panic
main defer ran
panic: boom
…
exit status 2
$ go run ./notrun goexit
goroutine defer ran
main defer ran
$ go run ./notrun exit
exit status 3
$ go run ./notrun fatal
2026/11/02 14:00:32 cannot read config file
exit status 1
```

panic and Goexit ran the defers before ending, while `os.Exit(3)` and `log.Fatal` left nothing but an exit code. `log.Fatal` looks like logging, but it writes one log line and calls `os.Exit(1)`. Sprinkle it into error handling for convenience and every bit of cleanup you set up with defer is gone. So it's safest to use it nowhere but the outermost level of `main`. The concurrent map write fatal error from [part two](/en/12) is the same kind: in three runs out of three, neither defer nor recover ran.

### What defer f.Close() quietly swallows

Here defer does run, but it throws the result away. `Close()` returns an error, and `defer f.Close()` just discards it. For read-only files that's usually fine, but files you write are another matter. The Linux close(2) man page says that on NFS, running out of space (<C k="err">ENOSPC</C>, <C k="err">EDQUOT</C>) is usually not reported on the write that first exceeded it, but on a later write, fsync, or close. Drop that error and the function returns `nil` while the file is cut short.

```go title="Folding the Close error into the return value"
// named return + defer folds the Close error into the result
func save(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}

	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = cerr // surface the Close error only if the body succeeded
		}
	}()

	_, err = f.Write(data)
	return err
}
```

The named return is the key. The return value needs a name for the defer to modify it, and the same pattern shows up again in the next section, in code that turns a panic into an error. Since Go 1.20 you can also keep both errors with a single `err = errors.Join(err, f.Close())`. The same man page also notes that a successful close doesn't mean the data reached the disk, so for a file that must survive, call `f.Sync()` before closing it.

## panic and recover: unwinding and three conditions

When a `panic` happens, Go first unwinds the stack, running each frame's deferred calls in reverse. If `recover` is called inside one of those deferred calls along the way, unwinding stops there and that function is treated as if it returned normally.

For recover to work, all three conditions must hold.

1. It's inside a deferred function,
2. that function calls `recover()` directly, and
3. it's in the same goroutine that panicked.

The second condition is the sneaky one. Skipping even one level makes it useless. This is where code breaks silently when someone pulls common error handling into a helper.

The third is scarier. If one goroutine dies from a panic, the whole program dies. No matter where you put recover up top, a panic in another goroutine isn't caught. So in a server, every place you launch a goroutine needs its own guard.

```go title="Panic to error, and a guard at every goroutine boundary"
// the standard pattern for turning a panic into an error: named return + recover
func safeParse(b []byte) (result Node, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("parse panic: %v", r) // overwrite the named return
		}
	}()
	return parse(b), nil // a panic inside parse becomes an error here
}

// a guard at every goroutine boundary: without it, one crash takes the process down
go func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("worker panic: %v\n%s", r, debug.Stack())
		}
	}()
	doWork()
}()
```

So when is panic the right tool? The test is whether the caller can handle the failure and carry on.

<Compare>
<Side title="Where panic fits" tone="good">

- Unrecoverable initialization failures (the `MustCompile` family)
- Programmer mistakes that break an invariant
- Escaping all the way out of a deeply recursive parser in one go

</Side>
<Side title="Where panic is wrong" tone="bad">

- Failed input validation, network or file errors, no results found
- Every failure you can anticipate is an error
- Use panic as control flow and the caller has no way to respond

</Side>

## Errors are values: what fills the gap left by exceptions

In Go, `error` is a one-method interface.

```go title="The definition of error"
type error interface {
	Error() string
}
// That's all. No special treatment in the language; it's just a value
```

Because it's an interface, the nil trap from [part one](/en/11) applies here too. Return a nil `*MyErr` as an `error` and the caller's `err != nil` is true.

Dropping exceptions didn't drop syntax; it dropped invisible control flow. In a language with exceptions, any function call can jump out at that line, and you can't see it in the code. In Go, every point that can fail is visible as `if err != nil`.

| | Exceptions (try/catch) | Values (Go) |
| --- | --- | --- |
| Error path | Invisible in the code | Visible at every point |
| If ignored | Propagates up automatically | Must be discarded explicitly |
| Composition | Tied to language syntax | Just values, handled freely |
| Cost | Harder to debug | Verbose |

The last row is the honest trade-off. The complaint that `if err != nil` is tedious is true, and the Go team knows it. They chose "tedious, but impossible to miss."

One small rule teams often get out of sync on: error strings start lowercase and don't end with a period. Errors keep picking up context in front, as in `fmt.Errorf("saving user: %w", err)`, so a capital letter or a period in the middle breaks the sentence awkwardly. Go Code Review Comments gives the same reason and leaves log messages out, since each one ends its own line.

### Error chains: the contract %w creates

When you pass an error up, you want to add context without losing the cause. That's what `%w` is for. `%v` melts the cause into a string, while `%w` wraps it with the original value intact.

The first two messages match character for character, yet `errors.Is` split into true and false. `errors.As` found the `*fs.PathError` one layer down and pulled out the path, and both the `errors.Join` error and the one with two `%w` verbs found `errNotify`.

The mechanism is simple. `errors.Is` and `errors.As` keep calling `Unwrap()` and compare as they walk down the chain. So the moment you add `Unwrap()` to your own error type, it joins the chain, and implementing an `Is(target error) bool` method lets you customize the comparison too.

The last line surprised me. `errors.Unwrap` could not unwrap the joined error and returned `<nil>`. A value that wraps several errors has `Unwrap() []error`, while `errors.Unwrap` only calls `Unwrap() error`. Code that walks the chain with `errors.Unwrap` by hand misses these errors, so leave the checking to Is and As.

### But %w isn't free

The moment you wrap with `%w`, <mark>the wrapped error effectively becomes part of your public API.</mark> Once callers start checking `errors.Is(err, sql.ErrNoRows)`, moving off `database/sql` to another DB library later quietly breaks someone else's code. The Go blog puts it the same way: wrapping exposes the error to callers, so don't wrap when that would expose implementation details.

| Strategy | When to use it |
| --- | --- |
| Wrap with `%w` | Within the same package or module, when the caller needs the cause to respond |
| Cut with `%v` | At package or service boundaries, to hide internals. Which DB library you use shouldn't leak out |
| Translate to a domain error | The best choice at boundaries. Turn `sql.ErrNoRows` into your own `ErrUserNotFound` |

## Closures: holding on to the outer variable

A closure is a function bundled with the environment it holds on to, and <mark>it holds on to the variables themselves instead of copying their values.</mark> So if the variable changes outside, the value the closure sees changes too.

Why a captured variable survives after the function returns is answered by escape analysis. The compiler asks whether the value's lifetime extends beyond the function's frame. When a closure is returned, as in `counter` below, `n` can't disappear with the frame, so it moves to the heap, and the closure value carries the function code pointer and the address of the captured `n`.

```go title="Where closures show up"
// a function with state: n moves to the heap and survives
func counter() func() int {
	n := 0
	return func() int { n++; return n } // captures n by reference
}

c := counter()
c(); c() // 1, 2: state carries across calls

// middleware: a closure wrapping a handler (the decorator pattern)
func withLog(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Println(r.URL.Path, time.Since(start)) // captures next and start
	})
}

// functional options: closures + variadic arguments
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

srv := NewServer(WithTimeout(3*time.Second), WithRetries(2))
```

I had the compiler show what it moves to the heap and how it captures, with `-gcflags=-m=2`. I put the returned closure from `counter` next to the closure in `sum`, which is used and done inside the function. Inlining adds noise to the output, so I turned it off with `-l`.

```go title="escape/main.go (excerpt)"
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}

//go:noinline
func each(xs []int, f func(int)) {
	for _, x := range xs {
		f(x)
	}
}

func sum(xs []int) int {
	base := 10
	total := 0
	each(xs, func(x int) { total += x + base })
	return total
}
```

escape/main.go:8:9: func literal escapes to heap

escape/main.go:22:11: func literal does not escape

The `n` in `counter` moved to the heap because its closure is returned, while the closure in `sum` never left the function and stayed off the heap. The capture mode differed too: `base` was captured by value and `total` by reference. In the compiler source (`escape.go`), a variable is captured by value when it is 128 bytes or less, its address is never taken, and it is never reassigned after capture. `total` is reassigned by `+=`, so it didn't qualify.

The cost comes from the same place. When a closure escapes the function (returned or handed to a goroutine), the closure and its captured variables go to the heap, and overusing such closures on a hot path drives up `allocs/op`.

The quieter problem is capturing a large object. Even if the closure reads a single field, as long as it holds the variable pointing to that object, the whole object can't be garbage-collected while the closure lives.

The closure reads one field, but what it holds is the variable `r`, and the whole object `r` points to stays alive with it. The most important part is that this change doesn't apply automatically. Upgrading the toolchain to 1.26 doesn't help; <mark>the `go` directive in `go.mod` must be 1.22 or later</mark> for the new behavior. It's a backward-compatibility safeguard so existing code keeps its meaning, which also means old modules still get the old behavior even when built with the latest Go.

```go title="go.mod and an idiom that is safe on any version"
// go.mod
module example.com/app

go 1.22 // below 1.22, even the latest Go builds with the old behavior

// safe on any version, and the intent is clear, so it's still common
for _, v := range items {
	go func(v Item) { process(v) }(v) // pass it as an argument to copy the value
}
```

<Lab title="Same toolchain, only the go line changed">

I wanted to see for myself that upgrading the toolchain doesn't help. I put the same `main.go` in two modules, one with `go 1.21` and one with `go 1.22`, and ran each three times with Go 1.26.10.

```go title="loop121/main.go and loop122/main.go"
func main() {
	var wg sync.WaitGroup
	for _, v := range []string{"a", "b", "c"} {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Print(v, " ")
		}()
	}
	wg.Wait()
	fmt.Println()
}
```

```text frame="terminal" title="Output"
$ cd loop121 && for i in 1 2 3; do go run .; done
c c c
c c c
c c c
$ cd ../loop122 && for i in 1 2 3; do go run .; done
c b a
c a b
c b a
```

The module with `go 1.21` printed only c in all three runs even though it was built with 1.26.10, and the `go 1.22` module printed a, b, and c in a different order each time.

</Lab>

The Let's Encrypt case in the Go blog shows how hard this bug is to spot. The author knew about the problem and had already copied the loop variable `k`. But in the same loop, `modelToAuthzPB(&v)` was handed `v`, and pointers to its fields ended up in the result; that's where it broke. Once captures are spread across several functions, catching them by eye is practically impossible.

### Tests that quietly pass

This bug can also make a failing test pass. The test below should fail, since 1 is odd.

```go title="even_test.go"
func TestAllEven(t *testing.T) {
	for _, v := range []int{1, 2, 4, 6} {
		t.Run("sub", func(t *testing.T) {
			t.Parallel() // waits until the loop finishes
			if v%2 != 0 {
				t.Fatal("odd v", v)
			}
		})
	}
}
```

```text frame="terminal" title="Output"
$ cd loop121 && go test .
ok  	loopvar	0.274s
$ cd ../loop122 && go test .
--- FAIL: TestAllEven (0.00s)
    --- FAIL: TestAllEven/sub (0.00s)
        even_test.go:10: odd v 1
FAIL
FAIL	loopvar	0.247s
FAIL
```

`t.Parallel()` holds subtests until the loop finishes, so in the 1.21 module, `v` already has its last value, 6, by the time they run. The tests were green and verified nothing. The Go team wrote that while preparing 1.22, they had to fix many tests like this inside Google.

`go vet` also behaved differently in the two modules.

```text frame="terminal" title="Output"
$ cd loop121 && go vet .
main.go:14:14: loop variable v captured by func literal
even_test.go:9:7: loop variable v captured by func literal
even_test.go:10:22: loop variable v captured by func literal
$ cd ../loop122 && go vet .
```

It flagged three places in the 1.21 module and printed nothing for the 1.22 module. A new variable each iteration means it's no longer a bug. `go test` runs some vet checks too, but the 1.21 module's test passed as ok, so this check isn't among them.

<Note title="Three things to do now">

1. Check the `go` line in `go.mod`. Below 1.22, you still have the old behavior, whatever your toolchain version.
2. Run `go vet` on its own before bumping it. `go test` alone didn't show this warning.
3. If tests start failing after you bump the version, those are tests that should have been failing all along and are only now showing it. Fix the code, not the test.

</Note>

## Lab setup and limits

I reran every example on this Mac (Apple M5, 10 cores, darwin/arm64) with Go 1.26.10. The recover lab output in the original post didn't match the real format, so I replaced it with freshly captured output. I corrected the claim that a defer in a loop allocates and the advice to add `go vet`'s `loopclosure` check to CI after measuring again. I couldn't reproduce the Close error because I have no NFS setup, so that part rests on the close(2) man page.

| --- | --- | --- |

## Wrap-up

| What we saw | Why |
| --- | --- |
| `defer t.show()` printed 0, the value before the change | The receiver is an argument, copied at registration |
| Five files opened with a defer in the loop stayed open until the function ended | defer runs when the function ends |
| No defer output after `os.Exit` or `log.Fatal` | The process ends on the spot |
| A recover one wrapper away missed the panic | The deferred function must call it directly |
| Same message, but Is was false for the `%v` chain | `%v` melts the cause into a string |
| A closure reading only `Name` held 64MB | A closure holds variables, not fields |
| Built with 1.26.10, it still printed c c c | The `go` line in `go.mod` said 1.21 |

So I now close resources opened in a loop by moving the body into its own function, think twice about `%w` at package boundaries, and check the `go` line first in older modules.

Writing this part, I realized one question runs through all three: exactly when, and what, does this hold on to? defer holds the arguments at registration, a closure holds the variable itself, and `%w` holds the wrapped error. Every pitfall in this post came from misjudging what was being held.
