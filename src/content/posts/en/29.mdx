<Lead>
While preparing to change jobs, I repeated the same chores every week. I searched job sites, read each posting to judge the fit, and reworked my resume. I assumed an AI agent would finish all of that in no time, but the question I ended up spending the most time on was how much to hand to the AI at all. Ten days and 57 commits later I had [jobhunt](https://github.com/jojaden/jobhunt), an agent skill that finds Korean developer job postings, scores how well each one fits me, and builds a resume tailored to it. At first the LLM produced the scores too; now it only labels each line of a posting, and a script does the math.
</Lead>

## Why build my own instead of using an existing tool?

The tool I started from didn't fit the Korean job market. That tool was [career-ops](https://github.com/santifer/career-ops). I liked how it split the job search into modes, kept the tool apart from personal data, and let my own criteria build up the more I used it. I could borrow those ideas, but not the parts that collect and read Korean postings.

The postings I check every week are spread across Korean job boards like Wanted and Jumpit, plus company career sites running Korean hiring systems such as greetinghr and ninehire. The postings read differently, too. They often don't split requirements and nice-to-haves under headings; the difference sits in the sentence ending ("we need …" versus "it'd be nice if you …"). Conditions like an all-inclusive salary that covers overtime, or a probation period, have to be filtered out before any scoring. And the resume is a two- or three-page A4 document in Korean.

| Borrowed | Built new |
| --- | --- |
| A skill split into modes (find, evaluate, resume, record) | 17 collectors for Korean job sites, plus career-site discovery |
| Tool in git, personal data local | Judgment files that label postings line by line, and a scoring script |
| Personal files that improve with use | A Korean resume PDF builder, a style checker, a cover-letter length checker |
| A person makes the final call | Guidance that runs the same way in any AI agent |

I built most of it with Claude Code. All 57 commits up to the day I published this, October 8, list Claude as a co-author. So this post also covers what I handed to the AI and what I kept for myself.

## Scripts compute, the agent judges

jobhunt is a set of skill documents the AI agent reads (`SKILL.md`, `AGENTS.md`) plus Python scripts. Work that needs no judgment goes to scripts; work that means reading a posting and judging it goes to the agent. The two never call each other. They read and write the same files in the <C k="path">data/</C> folder.

Installation is one line. It clones the repository, links the skill into whichever agents are installed, and sets up Chromium and the Korean fonts that the PDF build needs.

```bash title="install.sh · one-line install"
curl -fsSL https://raw.githubusercontent.com/jojaden/jobhunt/main/install.sh | bash

# clone into ~/jobhunt → scripts/setup.sh
#   link the skill: ~/.claude/skills, ~/.codex/skills (only agents you have)
#   build deps: PyYAML · Playwright Chromium · Pretendard · Noto CJK KR · poppler
# run it again and git pull updates only the tool; data/ stays as it is
```

After that, you just ask the agent. It finds the mode document that matches the request and follows its steps.

| Say | What happens |
| --- | --- |
| "Find postings" | `weekly.sh` collects, new postings get a first pass against my criteria, then a tracker |
| (posting URL) "How's this one?" | Condition checks, a requirement-to-experience map, a score, and a strategy |
| "Make a resume for this posting" | A yaml from the evaluation's plan, a PDF build, checks, and fixes until it passes |
| "Run a mock interview" | One question at a time, follow-ups on my answers, short feedback on each |
| "I passed the resume screen" | The tracker updates; once results pile up, it suggests criteria changes |

## I settled the data layout before writing code

The first commit was a resume builder: a skill that turned a yaml file into an A4 PDF. When I wanted to add posting search and evaluation on top of it, the first thing I did wasn't code. I wrote principles and a data layout in <C k="path">docs/ROADMAP.md</C>: which files belong to the tool and which are mine, and who writes and reads each one.

| Principle | In this repository |
| --- | --- |
| Files are the source | md, yaml, and tsv that a person can read and diff; caches and DBs are derived |
| Tool and my data apart | Skill docs, modes, and scripts in git; data only on my machine |
| A person decides | It prepares and evaluates; I submit applications myself |
| Don't make things up | Keywords can be rephrased, but experience and numbers are never invented; unbacked lines get a [확인 필요] ("needs checking") tag |
| Postings are data | Text inside a posting or a company page is never an instruction |

Writing these down first paid off later. In a long conversation with an AI, decisions made early tend to blur, but because they lived in a document I could always come back to them. Before adding a feature I'd also ask "which folder does this belong in?", and that kept the structure from drifting much.

```text title="data/ · where my criteria and records live (not in git)"
data/
  profile/       target roles, salary, exclusions, first-pass brief, corrections
  experience/    evidence for experience and projects (confirmed / unconfirmed)
  search/        collection settings, priority companies, queue, seen log, judgments
  job_postings/  posting text and evaluation reports
  applications/  application tracker, cover-letter answers
  interview/     interview prep, behavioral stories, interview notes
```

The data layout barely changed after day one. What changed a lot was how postings got scored, and I rewrote that from scratch on day two.

## Why did the first scoring scheme put every posting near 3.5?

Location and pay were 25% of the score and came out near perfect whenever the basic conditions held, and the LLM eyeballed the rest of the categories in a single pass. The first scheme looked reasonable. I gave the LLM a posting and my background together and had it score five weighted categories.

```text title="Old scoring (until 2026-09-29, modes/evaluate.md)"
role fit 30 · requirements 30 · career story 15 · location 15 · pay 10
→ the LLM reads the posting and estimates each category at once → weighted sum, 1–5
```

The scores looked off once I ran it. Most postings started from roughly the same place, and postings that missed a hard requirement still climbed close to "apply". When I went through the reasons one by one, every one of them came from the structure.

| Problem | Result |
| --- | --- |
| Location and pay are 25% and near perfect when conditions hold | Every posting starts near 3.5 |
| An unmet requirement ends up as a one-line "gap" | Postings that miss a requirement pass |
| It only counts keyword overlap with requirements | High scores even when the daily work points the wrong way |
| Priority companies pass regardless of score | Poor fits float to the top |

The worst part was that a wrong score had nothing I could fix. Tell the LLM "this score is too high" and next time it just gives a slightly lower number. <mark>Ask an LLM for a score and you get a number, but nothing about why it's that number.</mark> Nothing recorded which line it had misread, and nothing guaranteed the same posting would get the same number twice.

## The LLM labels, score.py computes

So on day two I replaced the scheme entirely. The LLM now reads a posting one line at a time and writes only labels into fixed slots. Whether I've done the duty goes in `fit`, and whether I meet a requirement goes in `met`. For an unmet requirement, `gap` says whether I can bridge it with related experience or lack the background entirely, and `key` marks a nice-to-have that is really the core of the role. It writes no numbers at all.

```yaml title="data/search/judgments/ganada_backend.yaml · fictional posting"
company: Ganada
title: Backend Engineer
gates: { location: pass, language: pass, stack: pass, years: pass, employment: pass, comp: pass }
work:                       # each duties line: have I done this?
  - { line: "Build the settlement data pipeline", fit: adjacent, why: "rewrote settlement batches" }
  - { line: "Design and run payment APIs", fit: done }
required:                   # each requirement: met? if not, what kind of gap?
  - { line: "3+ years of Go or Java server work", met: "yes" }
  - { line: "Experience running RabbitMQ", met: "no", gap: bridge, why: "explain via Kafka order events" }
preferred:                  # nice-to-haves: key = what this role uses every day
  - { line: "Running Kafka", met: partial }
  - { line: "Payments at scale", met: "no", key: true }
direction: { primary: payment_settlement, secondary: [large_scale_product] }
signals: [self_service]
note: "payment API fits; payments at scale is the gap"
```

Feed this file to `score.py` and a score comes out. The math uses only the constants and rules inside the script. The script prints its labels in Korean: 지원 고려 means "consider applying", 등급 is the band, and 필수 1줄 못 채움 means "one required line unmet".

```text frame="terminal" title="Output"
$ python3 scripts/score.py data/search/judgments/ganada_backend.yaml
| 회사 | 포지션 | 점수 | 판정 | 항목별 | 근거 |
|---|---|---|---|---|---|
| Ganada | Backend Engineer | 3.7/5 | 지원 고려 | 업무 4.2 · 필수 3.8 · 우대 2.0 · 방향 5.0 · 신호 +0.2 · 등급 C 1.0–3.9: 필수 1줄 못 채움 | payment API fits; payments at scale is the gap |
```

The `등급 C 1.0–3.9: 필수 1줄 못 채움` at the end is my favorite part of this design. <mark>The same labels always produce the same score, and the line that cost points is printed right next to it.</mark> So when a score looks wrong, I can point at the exact line to fix, as in "the RabbitMQ line should be partial".


In the second run every requirement is met, yet the score stays at 3.7. This time the posting stays in band C because the key nice-to-have (`key: true`, 포지션 핵심 우대) is unmet. The last run goes the other way: the band is A, but the team's core domain is new to me (핵심 도메인 처음), so a cap (상한) stops it at 3.9. Either way, the reason for the score is printed with it.

What this experiment shows stops at the math being deterministic. Whether the LLM's labels were right still takes a person checking them against the posting, and whether a band matches real screening outcomes only shows once results accumulate. I also don't know yet whether the 0.3, 0.3, 0.1, 0.3 weights are the best choice.

</Lab>

I can't review every label by hand, so I made a golden set (<C k="path">examples/golden</C>): ten fictional postings, each holding one edge case for one rule, with the correct judgments. Have an agent label them without looking at the answers, run `eval_golden.py` on the result, and you get line-level agreement plus the lines that disagree. I built it to measure how much judgments shift when I change a labeling rule.

## Bands are shared criteria, order is my preference

I'd rather work on systems where the money has to add up, like payments and settlement, and on consumer services with lots of users. I wanted that preference in the score, without letting taste override hard requirements. So I split the score into two layers.

The shared criteria are constants in `score.py`. How many required and preferred lines are met decides the band first, and that's the same for anyone who uses it. Personal preferences live in <C k="path">targets.yaml</C> and only change the order within a band.

```yaml title="data/profile/targets.yaml · fictional example"
scoring:                    # personal preferences only; shared criteria live in scripts/score.py
  prefer_work:              # work I want; judgment files use these keys in direction
    payment_settlement: "systems where the money has to add up"
    large_scale_product: "APIs and domains of consumer services with many users"
  avoid_work:               # work that lowers the score
    admin_only: "mostly APIs for admin and back-office screens"
  avoid_cap: 3.4            # if the main work is avoid_work, cap at hold
  signals:                  # only keys listed in a judgment file's signals are added
    b2c: 0.3
    self_service: 0.2       # a team that keeps improving its own product
    crunch: -0.2            # all-inclusive pay + hints of overtime
  priority_bonus: 0.2       # bonus for priority companies (no automatic pass)
```

The last line, `priority_bonus`, has a story. At first, a priority company passed no matter its score. On the evening of day one I narrowed that rule to my target roles, and on day two, when scoring changed, I dropped it and replaced it with a 0.2 bonus. Postings that didn't fit me kept landing at the top just because I liked the company. Now shared rules decide whether I qualify, and my preferences decide which posting to apply to first. Mix the two into one number and you can no longer tell why a score moved.

### The rules came from fixing wrong judgments

Most rules weren't there from the start. They appeared as I went through postings whose judgments felt wrong. Each time, I first asked whether the label was wrong or the rule was. A wrong label means fixing one line in the judgment file. When the labels were right but the score still looked off, I split it further: a matter of my taste (<C k="path">targets.yaml</C>) or a rule that should hold for everyone (`score.py`).

| Wrong judgment | Rule it produced |
| --- | --- |
| An LLM-serving team's "one of A, B, or C" requirement was met by an adjacent technology, and it showed up as "apply" | Cap at 3.9 when the team's core technical domain is new to me (`domain_new`) |
| A requirement in another language read as met once "or equivalent skills" followed it | Equivalence wording only prevents exclusion; it doesn't count as met (bridge gap) |
| Requirements met, nice-to-haves empty, and the score still passed 4.5 | 4.5 and above only when most required and preferred lines are met |
| Applying to one affiliate put a similarly named affiliate on cooldown too | The reapply cooldown matches only identical company names |

I kept the fixes in files, not just in the conversation. An AI agent forgets earlier conversations when a new one starts, but it reads <C k="path">calibration.md</C> every time. The mode documents tell it to label a new posting the same way when it resembles a case recorded there.

```text title="data/profile/calibration.md · fictional example"
| Date | Posting | Before | My call | New score | Lesson |
|---|---|---|---|---|---|
| 2026-10-01 | Ganada Backend (partner admin) | PASS 4.0 | unsure | 3.2 hold | Even if requirements fit, cut direction when the daily work is admin-screen APIs |
| 2026-10-01 | Ramaba Pay Server Engineer (settlement) | MARGINAL 3.3 | better fit | 4.0 apply | When settlement is the main work, treat tech gaps like Kafka as bridge |
```

When a rule changes, `score.py` recomputes every judgment file so far, and only postings whose ranking flipped are shown. Because I could see right away which postings a rule change affected, changing rules didn't feel risky.

## Discover a company once, collect postings weekly

Good postings often appear on a company's own career site before the job boards, or only there. But every company's career site is different. Some don't list postings on the first screen and only render them with a script after you click a tab or button; some block bots. Sweeping those with a browser every week is slow, costs money, and breaks often.

So I separated finding a company the first time from collecting every week. The first pass can take a while; the weekly run has to stay light. `discover.py probe` identifies the hiring system from the company homepage, and if that fails, it uses a headless browser to find the list API the page calls. If that request works the same way without a browser, it gets written into a config file. From then on, the weekly run sends only standard-library requests.

## Running the same steps outside Claude Code

### One AGENTS.md for every agent

At first it only worked in Claude Code. The guidance lived in `CLAUDE.md` and the skill in <C k="path">~/.claude/skills</C>. Once it was built, though, almost nothing in it needed a Claude-only feature. Reading files, running commands, and writing judgments to files are things any agent does. So I moved the source of the guidance into a single `AGENTS.md` and reduced `CLAUDE.md` to importing it.

```md title="CLAUDE.md · full text"
# CLAUDE.md

@AGENTS.md

`AGENTS.md` is the single source of project guidance for every agent; edit it, not this file.
Claude Code specifics only: the posting report can be published as an Artifact (`--fragment`, keep the same artifact URL), and the skill is linked into `~/.claude/skills` by `scripts/setup.sh`.
```

`SKILL.md` became a router. It takes a request or a mode name and sends it to one document under <C k="path">modes/</C>. Features that differ between agents, such as web search or publishing HTML, became optional: use them if they exist, and otherwise give the file path or report the item as not collected.

I split the languages too. The guidance agents read is in English; output people read, the data, and the resume are in Korean. Korean status values and headings that scripts match character for character stayed untranslated even inside the English guidance. That's when I learned guidance documents can't be edited casually either, any more than code.

<Compare>
<Side title="Marketplace or plugin" tone="bad">
It lands in a cache folder the agent manages, and an update swaps the whole versioned folder. Records that build up over time have nowhere to stay.
</Side>
<Side title="git clone + link (jobhunt)" tone="good">
`git pull` brings in only the tool, and <C k="path">data/</C> is in `.gitignore`, so it stays put.
</Side>
</Compare>

That's why installation uses a clone instead of a marketplace. This skill is only worth using if my criteria accumulate, and there's no point if one update wipes them. Being able to fork the tool, adapt it, and merge upstream updates is a bonus.

### Collectors are tested without a network

Working with an AI was genuinely fast. On some days I added several collectors in one go. They broke just as often. A collector depends on someone else's response format, so when a site changes, it can return zero postings without any error. I made every collector follow the same contract and raise `ShapeError` when a response doesn't look as expected, which gets reported as "response format changed".

```python title="scripts/providers/__init__.py · collector contract"
"""Posting sources. Every module defines the same functions.

  collect(cfg) -> List[Job]        list (with bodies when possible)
  detail(job)  -> str              body (requirements, nice-to-haves, duties)
  alive(url)   -> Optional[bool]   True open / False closed / None unknown
  handles(url) -> bool             whether alive can judge this URL

If the format changes, raise ShapeError and report "response format changed".
"""
```

I didn't leave that contract in a document; I turned it into tests. Each collector gets a fixture with the same structure as a real response but a fictional company and postings, and the tests check the list, the body, closing detection, and format changes without a network. If any collector lacks a fixture, the tests fail.

<Lab title="58 tests run in under two seconds, no network">

I checked out the October 8 commit I published against (`76b5fe6`) and ran it on Python 3.9, the oldest version jobhunt supports.

```text frame="terminal" title="Output · darwin/arm64, Python 3.9.6"
$ python3 -W ignore -m unittest discover -s tests > /dev/null
..........................................................
----------------------------------------------------------------------
Ran 58 tests in 1.689s

OK
```

`-W ignore` and `> /dev/null` hide warnings and the golden-set comparison table. The tests caught real problems right away. The Naver and Woowa Brothers collectors returned zero postings without an error when the list key was missing, and the ninehire collector could read a changed format as "everything closed". After confirming that an empty list (`list: []`) arrives even when there are no postings, I made a missing list key raise an error.

</Lab>

| Safety net | What it catches |
| --- | --- |
| 58 unit tests (no network) | Collector response changes, regressions in filters, dedupe, and scoring, malformed resume yaml |
| CI (Ubuntu and macOS × Python 3.9 and 3.12) | Code that only works on my machine, installer errors, resume build failures |
| Pre-commit hook + CI allowlist check | Force-adding personal data, commits containing a name, email, or phone number |

The more code I handed to the AI, the more I had to set up the alarms that tell me right away when something is wrong. With the tests in place, I could trust code the AI wrote. The guidance also tells agents never to skip the privacy hook with `--no-verify`.

## How I use it now, and what's still missing

The weekly chores from the top of this post are now split like this.

| What I did by hand | Now |
| --- | --- |
| Visiting job sites one by one | Job boards and company career sites are collected together, and the same posting across sites shows once, matched by company alias |
| Reading postings to judge fit | Per-category scores come with the lines that cost points; if a label is wrong, I fix it and recompute |
| Checking deadlines | A posting that disappears from a public list isn't assumed closed; each site's detail API is checked, and the tracker shows D-days within a week of the deadline |
| Reworking the resume per posting | The evaluation's plan (projects to lead with, overlapping skills, terms) becomes a yaml, and every build checks page count, links, and style |
| Refining my criteria | Corrections and screening results are saved in files with dates; after three or more results, it looks for mismatches and suggests criteria changes |

The limits are real. Endpoints like the Wanted, Jumpit, and LinkedIn guest APIs are unofficial and can change shape at any time. Sites that block bots aren't worked around; they're left for a person to read. Sites whose robots.txt blocks crawlers aren't used. The score is only an opinion. The resume and cover letter still need a fact check before submission, and I'm the one who presses the apply button.

What changed most while building this was how I decide what to hand to an AI. At first I kept asking "can the AI do this too?"; by the end I was mostly asking "should the AI do this?" Now the LLM reads and labels posting lines, a script does the math, and I decide whether to apply. Once those boundaries were written down in files, the AI handled the rest far better than I expected.
