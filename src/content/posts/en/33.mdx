<Lead>
With the name turned into an IP address, the next step is opening a connection to it. I knew `http.Client` reuses connections on its own, but I had never measured how much that saves. With a delay proxy in the middle, the first HTTPS request took <C k="num">155 ms</C> on TLS 1.2 and a reused connection took <C k="num">50 ms</C>, and a new connection for every request left almost one TIME_WAIT socket per request on the server. I also counted what happens when a response body is closed without being read, and on Go 1.27 the answer had changed for small responses.
</Lead>

<Summary>
1. TCP opens a connection with three messages and closes it with four. The side that closes first stays in TIME_WAIT for 60 seconds.
2. TLS checks the server's certificate and agrees on a session key, then encrypts the traffic with that key. The first response on a new connection takes three round trips with TLS 1.3 and four with TLS 1.2.
3. Reusing the connection removes that cost. In Go, share one Transport and raise `MaxIdleConnsPerHost` when many requests run at once. Closing an unread body threw the connection away through Go 1.26, and since 1.27 the client reads up to 256 KB of it for you.
</Summary>

## Three messages to open a TCP connection

The last post turned a name into an IP address, so this stop is about actually connecting to that IP. Opening a connection sets up two things: a channel that carries data completely and in order (TCP), and a layer that locks what goes through it so others can't read it while checking that the other side is who it claims to be (TLS).

Let's start with TCP. The internet sends data in small pieces (packets), and on the way a piece can go missing or arrive out of order. TCP is <mark>a protocol that resends the pieces that go missing and puts the received pieces back in the order they were sent</mark>. UDP just sends and takes no responsibility for what happens next.

On the phone, it's like “Hello?”, “Yes, hello,” and “Yes” before the conversation starts. What TCP actually checks, though, is the start number rather than a voice.

Why three? TCP numbers every byte it sends (the sequence number), and that number is how it knows what went missing. The 1–4 on the pieces in Figure 1 are those numbers. So each side picks a starting number, tells the other, and has to confirm that the other side got it. That takes two messages to send and confirm the client's number and two for the server's, and folding the middle two into one packet (SYN-ACK) makes three.

## Four to close, and the closer stays

Closing takes four messages. FIN means “I have nothing more to send.” A TCP connection has a separate path in each direction, so FIN has to be sent in each direction separately. When one side sends FIN, the other side may still have data to send, so it sends an ACK first and its own FIN once it's done.

The side that closed first stays around after sending the last ACK, in the TIME_WAIT state, for 2MSL.[^msl] On Linux that time is fixed at 60 seconds, and the standard kernel has no sysctl to change it. The similarly named `net.ipv4.tcp_fin_timeout` is the time spent in FIN_WAIT_2, waiting for the other side's FIN, and has nothing to do with TIME_WAIT.

Holding on to a finished connection for 60 seconds looks like a bug, but the design protects two things.

## Where does TIME_WAIT pile up?

Since TIME_WAIT stays with whoever closed first, where it piles up tells us who is closing first. In HTTP, keep-alive decides that. Keep-alive means leaving the connection open after a response so the next request can use it.

Let's count it and see whether it matches the figure.

<Lab title="A new connection every time piles TIME_WAIT on the server">

I started a Go HTTP server and sent it 100 requests from the same program, once with keep-alive off and once with it on. To count TIME_WAIT sockets, I read <C k="path">/proc/net/tcp</C>, where Linux lists TCP connections, counted lines whose state is `06`, and split them into server side and client side by whether the local port is the server port. At the end, I counted the server-side TIME_WAIT sockets again at 30, 59, and 65 seconds to see when they go away. It runs inside a Linux container, so sockets from other programs don't get mixed in.

```go title="tcplab/tw/main.go"
package main

import (
	"fmt"
	"io"
	"net"
	"net/http"
	"os"
	"strconv"
	"strings"
	"time"
)

// timeWait counts TIME_WAIT sockets (state 06) in /proc/net/tcp, split into server and client side.
func timeWait(serverPort int) (server, client int) {
	b, _ := os.ReadFile("/proc/net/tcp")
	for _, l := range strings.Split(string(b), "\n")[1:] {
		f := strings.Fields(l)
		if len(f) < 4 || f[3] != "06" {
			continue
		}
		local, _ := strconv.ParseInt(f[1][strings.Index(f[1], ":")+1:], 16, 32)
		if int(local) == serverPort {
			server++
		} else {
			client++
		}
	}
	return
}

func main() {
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	port := ln.Addr().(*net.TCPAddr).Port
	go http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		io.WriteString(w, "ok")
	}))

	var start time.Time
	for _, keepAlive := range []bool{false, true} {
		tr := &http.Transport{DisableKeepAlives: !keepAlive}
		c := &http.Client{Transport: tr}
		s0, c0 := timeWait(port)
		for i := 0; i < 100; i++ {
			resp, err := c.Get("http://" + ln.Addr().String())
			if err != nil {
				panic(err)
			}
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
		}
		if !keepAlive {
			start = time.Now() // when the 100 requests without keep-alive finished
		}
		tr.CloseIdleConnections() // the client closes the reused connection here
		time.Sleep(200 * time.Millisecond)
		s1, c1 := timeWait(port)
		fmt.Printf("keep-alive %-5v 100 requests → TIME_WAIT server side +%d, client side +%d\n",
			keepAlive, s1-s0, c1-c0)
	}

	// watch when the server-side TIME_WAIT sockets go away
	for _, sec := range []int{30, 59, 65} {
		time.Sleep(time.Until(start.Add(time.Duration(sec) * time.Second)))
		s, _ := timeWait(port)
		fmt.Printf("after %2ds: %d server-side TIME_WAIT\n", sec, s)
	}
}
```

With keep-alive off, the Go client sends `Connection: close` (a note asking to close the connection after this response) with each request, and the server usually closes the connection first after sending the response. That's why most of the TIME_WAIT sockets, 95 of them, ended up on the server side. The six on the client side are connections where the client finished reading the response and closed before the server did, or at about the same moment. When both sides send FIN at the same time, both end up in TIME_WAIT, which is why the total is a little over 100.

With keep-alive on, one connection was reused 100 times, and at the end the client closed it, leaving a single TIME_WAIT on the client side. In the last three lines we can see the 95 server-side sockets stay put through 59 seconds and disappear by 65 seconds. Counting once per second in a separate run, they went away between 60 and 62 seconds.

## TLS checks identity and agrees on a key

An open TCP connection still carries every byte in plain sight, so anyone looking at the packets in the middle can read everything. TLS does two jobs on top of it: it checks that the server you reached is the real one, and it locks the traffic with a key only the two sides know.

There are two kinds of keys here. Asymmetric keys use one key to lock and a different one to unlock, which lets two strangers start safely, but they're slow. Symmetric keys lock and unlock with the same key, which is fast, but both sides need that key first. So TLS uses asymmetric keys only in the handshake, to check the server and agree on a key for this connection alone (the session key), and from then on everything uses fast symmetric encryption with that session key.

The server proves who it is with a certificate. A certificate holds the server's name and public key, and a CA (certificate authority) that the client trusts signs it to say the contents are right. The client checks the two things below and drops the connection if either one fails.

```go title="tcplab/trust/main.go"
func main() {

			}
```

## Round trips before the first response

Let's go back to the question at the top. A round trip (RTT) is the time for a packet to reach the other side and for the answer to come back. A new HTTPS request on a new connection takes one round trip for the TCP handshake, one for the TLS handshake on TLS 1.3 (two on TLS 1.2), and one for the request and response. If an open connection is reused, only the request and response remain.

If one round trip takes 50 ms, a new TLS 1.2 connection waits 200 ms for its first response and a reused connection waits 50 ms. Every new connection pays for the boxes before the green one, so the gap grows with the number of requests.

TLS 1.3 saves a round trip with its first message. The key exchange needs the public values A and B from Figure 8, which TLS calls key shares. A TLS 1.2 client sends its key share only after hearing which key exchange the server picked. A TLS 1.3 client guesses which method the server will pick and puts its key share in the very first message.[^hrr] The server can then put its own key share, its certificate, and Finished (a message confirming that the handshake so far was not tampered with) in one reply, and the client computes the session key and sends the request as soon as that reply arrives.

<Lab title="Counting round trips with a delay proxy">

Inside one machine, round trips are too short to count. So I put a proxy between the client and server that delays every byte by <C k="num">25 ms</C> in each direction, which makes one round trip <C k="num">50 ms</C>. I timed each stage with `httptrace` (a standard package that reports when a request passes stages like connecting and the handshake), and the proxy code is in the lab setup section at the end.

```go title="tcplab/rtt/main.go"
package main

import (
	"context"
	"crypto/tls"
	"fmt"
	"io"
	"net/http"
	"net/http/httptrace"
	"time"

	"tcplab/certs"
)

// Send two requests each on TLS 1.2 and 1.3 and time the connect, the handshake, and the total. The delay proxy is in proxy.go.
func main() {
	cert, pool := certs.New("api.example.internal")
	ln, _ := tls.Listen("tcp", "127.0.0.1:0", &tls.Config{Certificates: []tls.Certificate{cert}})
	go http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { io.WriteString(w, "ok") }))
	addr := proxy(ln.Addr().String())

	for _, v := range []uint16{tls.VersionTLS12, tls.VersionTLS13} {
		tr := &http.Transport{TLSClientConfig: &tls.Config{
			ServerName: "api.example.internal", RootCAs: pool, MinVersion: v, MaxVersion: v,
		}}
		client := &http.Client{Transport: tr}
		for i := 1; i <= 2; i++ {
			var start, connDone, tlsDone time.Time
			trace := &httptrace.ClientTrace{
				ConnectDone:      func(string, string, error) { connDone = time.Now() },
				TLSHandshakeDone: func(tls.ConnectionState, error) { tlsDone = time.Now() },
			}
			req, _ := http.NewRequestWithContext(httptrace.WithClientTrace(context.Background(), trace),
				"GET", "https://"+addr, nil)
			start = time.Now()
			resp, err := client.Do(req)
			if err != nil {
				panic(err)
			}
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			total := time.Since(start)
			if connDone.IsZero() { // reused connection: no connect, no handshake
				fmt.Printf("%s request %d: reused connection                        total %3dms\n",
					tls.VersionName(v), i, total.Milliseconds())
				continue
			}
			fmt.Printf("%s request %d: TCP connect %2dms · TLS handshake %3dms · total %3dms\n",
				tls.VersionName(v), i, connDone.Sub(start).Milliseconds(),
				tlsDone.Sub(connDone).Milliseconds(), total.Milliseconds())
		}
		tr.CloseIdleConnections()
	}
}
```

Flow control protects the receiver. The receiver keeps announcing how much room is left in its buffer (the receive window), and the sender never sends more than that. When the receiving program reads slowly, the window shrinks and the sender slows down too.

Congestion control protects the network. The sender guesses how busy the path is and decides how much to send at once (the congestion window). It starts small and roughly doubles every round trip (slow start), then treats lost packets as a sign of congestion, cuts back hard, and grows again. The Linux default algorithm is CUBIC.

This gives new connections one more disadvantage. The congestion window starts small on every connection (10 packets on Linux), so a new connection can't send at full speed for a while even after the handshake. A reused connection keeps the window it has already grown. But if the connection sits idle longer than the RTO (how long TCP waits for an ACK before resending, at least 200 ms), Linux shrinks the window, and the longer the idle time, the closer it goes back to the starting size. That's what the default value 1 of `net.ipv4.tcp_slow_start_after_idle` does. So a connection used once every few seconds saves only the handshake, and the window benefit stays only when the connection is used without pause.

There's also a trap with small packets. When Nagle's algorithm, which batches small writes, meets delayed ACK, which holds an ACK back for a moment, a small request can be delayed by tens of milliseconds. That's why interactive protocols turn Nagle off with `TCP_NODELAY`, and Go already turns `TCP_NODELAY` on when it creates a TCP connection (`SetNoDelay` defaults to `true`).

<Lab title="Unread bodies and many parallel requests open new connections">

I sent 100 requests to a server that returns a 64 KB response and counted the new TCP connections with `ConnectDone` from `httptrace`. The `/big` path returns 1 MB. I ran the same code with Go 1.26.10 and Go 1.27.0.

```go title="tcplab/reuse/main.go"
package main

import (
	"context"
	"fmt"
	"io"
	"net"
	"net/http"
	"net/http/httptrace"
	"runtime"
	"strings"
	"sync"
	"sync/atomic"
)

// run sends 100 requests (parallel at a time) and counts the new TCP connections.
func run(c *http.Client, url string, parallel int, drain bool) int64 {
	var opened atomic.Int64
	trace := &httptrace.ClientTrace{ConnectDone: func(string, string, error) { opened.Add(1) }}
	ctx := httptrace.WithClientTrace(context.Background(), trace)
	for round := 0; round < 100/parallel; round++ {
		var wg sync.WaitGroup
		for i := 0; i < parallel; i++ {
			wg.Add(1)
			go func() {
				defer wg.Done()
				req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
				resp, err := c.Do(req)
				if err != nil {
					panic(err)
				}
				if drain {
					io.Copy(io.Discard, resp.Body) // read to the end
				}
				resp.Body.Close() // then close
			}()
		}
		wg.Wait()
	}
	return opened.Load()
}

func main() {
	small := strings.Repeat("x", 64*1024) // 64KB response
	big := strings.Repeat("x", 1<<20)     // 1MB response
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	go http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path == "/big" {
			io.WriteString(w, big)
			return
		}
		io.WriteString(w, small)
	}))
	url := "http://" + ln.Addr().String()

	fresh := func(maxIdle int) *http.Client {
		return &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: maxIdle}}
	}
	fmt.Println(runtime.Version())
	fmt.Printf("sequential, read Body to EOF, close     → new connections %3d\n", run(fresh(0), url, 1, true))
	fmt.Printf("sequential, close 64KB Body unread      → new connections %3d\n", run(fresh(0), url, 1, false))
	fmt.Printf("sequential, close 1MB Body unread       → new connections %3d\n", run(fresh(0), url+"/big", 1, false))
	fmt.Printf("10 at a time, MaxIdleConnsPerHost 2     → new connections %3d\n", run(fresh(0), url, 10, true))
	fmt.Printf("10 at a time, MaxIdleConnsPerHost 10    → new connections %3d\n", run(fresh(10), url, 10, true))
}
```

```go title="client.go"
func newClient() *http.Client {
	// copy the default Transport to keep its timeouts and proxy settings
	t := http.DefaultTransport.(*http.Transport).Clone()
	t.MaxIdleConnsPerHost = 10 // match the parallel requests
	return &http.Client{Transport: t, Timeout: 10 * time.Second}

func call(url string) error {
	resp, err := client.Get(url)
```

The good version calls `Clone()` on `http.DefaultTransport` and changes only what it needs. A new `&http.Transport{}` drops the default Transport's connect timeout (30 seconds), `IdleConnTimeout` (how long an idle connection stays open, 90 seconds), and proxy settings.

From Go 1.27, the line that reads the body to the end isn't needed for small responses. Keep it if you're on 1.26 or older or if responses can go over 256 KB. That said, for a really large response you don't need, dropping the connection can be cheaper than downloading the rest of it.

What you gain is no handshake round trips and no TIME_WAIT. What you give up is that idle connections hold on to resources. If the server closes an idle connection first, the client may be holding a dead connection and see an error, so it's safer to set `IdleConnTimeout` shorter than the server's keep-alive timeout. For a batch job with sparse requests, there's no reason to make the pool big.

```go title="tcplab/certs/certs.go"
// Package certs creates a private lab CA and a server certificate in memory.
package certs

import (
	"crypto/ecdsa"
	"crypto/elliptic"
	"crypto/rand"
	"crypto/tls"
	"crypto/x509"
	"crypto/x509/pkix"
	"math/big"
	"time"
)

// New returns a server certificate signed for name, and a CA pool that trusts it.
func New(name string) (tls.Certificate, *x509.CertPool) {
	caKey, _ := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	caTpl := &x509.Certificate{
		SerialNumber:          big.NewInt(1),
		Subject:               pkix.Name{CommonName: "lab CA"},
		NotBefore:             time.Now().Add(-time.Hour),
		NotAfter:              time.Now().Add(time.Hour),
		IsCA:                  true,
		KeyUsage:              x509.KeyUsageCertSign,
		BasicConstraintsValid: true,
	}
	caDER, _ := x509.CreateCertificate(rand.Reader, caTpl, caTpl, &caKey.PublicKey, caKey)
	ca, _ := x509.ParseCertificate(caDER)

	key, _ := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	tpl := &x509.Certificate{
		SerialNumber: big.NewInt(2),
		Subject:      pkix.Name{CommonName: name},
		DNSNames:     []string{name},
		NotBefore:    time.Now().Add(-time.Hour),
		NotAfter:     time.Now().Add(time.Hour),
		KeyUsage:     x509.KeyUsageDigitalSignature,
		ExtKeyUsage:  []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth},
	}
	der, _ := x509.CreateCertificate(rand.Reader, tpl, ca, &key.PublicKey, caKey) // signed by the CA
	pool := x509.NewCertPool()
	pool.AddCert(ca)
	return tls.Certificate{Certificate: [][]byte{der}, PrivateKey: key}, pool
}
```

```go title="tcplab/rtt/proxy.go"
package main

import (
	"net"
	"time"
)

const oneWay = 25 * time.Millisecond // 25ms each way → 50ms round trip (RTT)

// delayPipe writes each chunk read from src to dst oneWay later, keeping the order.
func delayPipe(dst, src net.Conn) {
	type chunk struct {
		at time.Time
		b  []byte
	}
	q := make(chan chunk, 1024)
	go func() {
		for c := range q {
			time.Sleep(time.Until(c.at))
			dst.Write(c.b)
		}
		dst.Close()
	}()
	buf := make([]byte, 32*1024)
	for {
		n, err := src.Read(buf)
		if n > 0 {
			q <- chunk{time.Now().Add(oneWay), append([]byte(nil), buf[:n]...)}
		}
		if err != nil {
			close(q)
			return
		}
	}
}

// proxy delays every byte between the client and the server.
func proxy(upstream string) string {
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	go func() {
		for {
			c, err := ln.Accept()
			if err != nil {
				return
			}
			u, _ := net.Dial("tcp", upstream)
			go delayPipe(u, c)
			go delayPipe(c, u)
		}
	}()
	return ln.Addr().String()
}
```

## Summary

- TCP opens a connection with three messages and closes it with four. The side that closes first stays in TIME_WAIT for 60 seconds.
- TIME_WAIT piling up on the server means the server is closing first. A client with keep-alive off is a common cause.
- TLS checks the server with its certificate and encrypts the traffic with a session key that each side computes on its own.
- The first response on a new connection takes three round trips with TLS 1.3 and four with TLS 1.2, and a reused connection takes one. TLS 1.3 saves a round trip by putting a key share in its first message.
- In Go, share one Transport and raise `MaxIdleConnsPerHost` to match parallel requests. Since Go 1.27, `Close()` discards small bodies for you, but a 1 MB response still threw the connection away.

With the connection open, the next stop is sending a request over it. Every reuse lab in this post was HTTP/1.1. HTTP/2 carries several requests on one connection at once, so numbers like `MaxIdleConnsPerHost` should behave differently there. In the next post I'll measure that, along with how HTTP/1.1 lines requests up on a single connection.
