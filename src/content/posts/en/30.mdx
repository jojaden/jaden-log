<Lead>
Writing the [GOMEMLIMIT post](/en/22), I mentioned container memory limits often, but on the Kubernetes side I only knew requests as a floor and limits as a ceiling. My study notes then asked: "a pod keeps dying; what do you check first when it's OOMKilled, and when it's Evicted?" I assumed both meant it ran out of memory. So I traced where requests and limits are actually used, reproducing the cgroup side with Docker since I had no cluster.
</Lead>

<Note title="Who this is for">
This is for people who have set requests and limits by feel, or who have looked at a pod killed by OOMKilled or Evicted without knowing where to start. The Go runtime side is covered in the [`GOMAXPROCS`](/en/21) and [`GOMEMLIMIT`](/en/22) posts.
</Note>

## Who killed the pod: OOMKilled or Evicted?

Different killers. <mark>OOMKilled means the Linux kernel killed one container; Evicted means kubelet removed the pod from the node.</mark> OOMKilled happens because that container went over its own memory limit; Evicted happens because the whole node's memory or disk dropped below a threshold.

Where you actually tell them apart is `kubectl describe pod`. Both are "it died", but the record lands in different places. The two outputs below are examples copied to show the format.

```text frame="terminal" title="Expected output · OOMKilled (format example)"
$ kubectl describe pod api-7d9c6b5f4-x2k8p
Status:         Running
Containers:
  api:
    State:          Running
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
    Restart Count:  3
```

```text frame="terminal" title="Expected output · Evicted (format example)"
$ kubectl describe pod api-7d9c6b5f4-q8w2n
Status:         Failed
Reason:         Evicted
Message:        The node was low on resource: memory. Threshold quantity: 100Mi,
                available: 87232Ki. Container api was using 412Mi, request is 256Mi,
                has larger consumption of memory.
```

In the OOMKilled output, the pod is still `Running`, with the record only in the container's `Last State`. I had memorized exit code 137 as the OOM marker, but 137 is just 128+9: the process got SIGKILL, which also happens after a termination grace period, so read `Reason` with it. With Evicted, the pod itself becomes `Failed`, and the message says which resource ran short and how far the container was over its requests.

## requests and limits are used at different times

I had memorized requests as a "guaranteed minimum", but nothing looks at them again after placement: requests are mostly for choosing where a pod goes, and limits for while it runs.

The scheduler treats a node's free space as its allocatable minus the requests of pods already on it, and ignores actual usage. The more generously you set requests, the more quiet-but-full nodes you get.

```yaml title="deployment.yaml · container resources"
resources:
  requests:
    cpu: 500m        # used by the scheduler for placement (unrelated to real usage)
    memory: 256Mi
  limits:
    cpu: "1"         # written as the cgroup CPU quota → over it, you wait
    memory: 512Mi    # written as the cgroup memory limit → over it, OOM kill
```

`cpu.shares` 512 sets no ceiling; it's only the ratio for sharing CPU when things are busy. On today's v2 nodes the files are named memory.max, cpu.max, and cpu.weight.[^weight][^v1]

The last row surprised me most. <mark>requests.memory isn't written as a fence in any cgroup file.</mark> A pod with requests and no limits can use as much node memory as it likes, and it pays for that in the eviction order when the node fills up.

On a Kubernetes v1.28.2 node (RKE2, cgroup v1), a container with requests of 25m and 16Mi and limits of 100m and 64Mi had `memory.limit_in_bytes` 67108864, `cpu.cfs_quota_us` 10000, and `cpu.shares` 25, so kubelet used the same arithmetic, and the 16Mi appeared in no file.

<Lab title="Over the memory limit, the kernel killed it at once">

A program grabs 10MiB at a time and writes one value every 4KiB, since untouched pages don't count, under a 64MiB limit. Every Go program here was built with Go 1.24.7.

The full program (`memhog/main.go`) is in "Commands used in the lab, with code" at the end.

```text frame="terminal" title="Output · Docker 29.8.2, 2 vCPU"

allocated: 10 MiB
allocated: 20 MiB
allocated: 30 MiB
allocated: 40 MiB
allocated: 50 MiB
allocated: 60 MiB
$ docker inspect hog --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}'
OOMKilled=true ExitCode=137
```

## Over the CPU limit, you wait instead of dying

Memory you've used can't be handed back, but CPU time you miss now can be used a moment later. So a CPU limit doesn't kill; it only sets how much you can use in each window, here 100ms of quota per 100ms period.

The whole container splits this one share, however many threads it runs, so two threads under a limit of 1 use it up in 50ms and both stop for the next 50ms, adding up to almost 50ms to a request. In Go, that thread count is `GOMAXPROCS` (see the [GOMAXPROCS post](/en/21)).

<Lab title="Two threads under a CPU limit of 1">

It runs GOMAXPROCS goroutines for 2 seconds and compares `nr_throttled` in `cpu.stat` (periods stopped after using up the share) before and after. Below is the core part.

```go title="cpuspin/main.go · core part"
n := runtime.GOMAXPROCS(0)
before := cpuStat() // reads /sys/fs/cgroup/cpu/cpu.stat
end := time.Now().Add(2 * time.Second)
for i := 0; i < n; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		for time.Now().Before(end) {
			// a CPU-only loop
		}
	}()
}
wg.Wait()
after := cpuStat() // prints the nr_periods and nr_throttled deltas
```

## OOMKilled with a heap smaller than the limit

My notes asked what happens when a Go service gets OOMKilled with a heap below its limit. The reason is in the [GOMEMLIMIT and GOGC post](/en/22); this time I recreated it with a cgroup limit.

With the default `GOGC=100`, the Go GC runs the next cycle when the heap reaches twice what survived the previous one. With 35MiB of live data, the next GC target is 70MiB. If the container limit is 64MiB, we cross it before the GC even runs. Setting `GOMEMLIMIT` makes the runtime pull that target under the limit.

In the kubelet docs, eviction order looks at usage before the class name: first whether a pod uses more than its requests, then PriorityClass, then how far it's over. BestEffort leaves first because its requests are 0, so it's always over; Guaranteed leaves last because its limit equals its requests.

So a Burstable pod within its requests lands in the last group, while a pod with small requests that routinely uses more stands near the front, whatever its class. <mark>Matching requests to real usage also sets your place in the eviction order</mark>, which I only learned this time.

| QoS | kubelet eviction | oom_score_adj |
| --- | --- | --- |
| Guaranteed | Always the last group | -997 |
| Burstable | Over requests or not | 2–999, lower with bigger requests |
| BestEffort | Always the first group | 1000 |

The last column is the score the kernel OOM killer uses if node memory runs out before kubelet acts; higher dies first, in the same direction as kubelet's order.

### An evicted pod isn't moved

My notes described Evicted as "rescheduled to another node", but the pod isn't moved. It stays `Failed`, and the ReplicaSet creates a new pod for the scheduler to place. A node short on memory gets a MemoryPressure condition plus a taint that keeps new pods away, so the new pod usually lands on another node.

## The three probes do different things on failure

The three probe names sound alike, but each failure does something different. A failed readiness probe only removes the pod from the Service endpoints; the pod stays alive. A failed liveness probe restarts the container. The startup probe holds off the other two until it succeeds, protecting apps that boot slowly.

```yaml title="deployment.yaml · probe settings"
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 24     # 5s × 24 = up to 120s to boot
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3      # out of traffic within 15s
  timeoutSeconds: 3
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3      # restart only after 30s of failures
  timeoutSeconds: 5        # the 1s default can kill healthy pods under load
```

It helps to ask "so what happens after how many seconds?" Detection takes about `periodSeconds` × `failureThreshold`. Leaving traffic is cheap, so do it fast; restarting is expensive, so do it slowly. `timeoutSeconds` defaults to 1 second, so any response slower than that under load counts as a failure. With a startup probe you don't need to guess boot time with `initialDelaySeconds`.

```go title="memhog/main.go"
// memhog: grabs 10MiB at a time and writes to it (touch) so RSS grows.
package main

import (
	"fmt"
	"os"
	"time"
)

func main() {
	var hold [][]byte
	for i := 1; ; i++ {
		b := make([]byte, 10<<20)
		for j := 0; j < len(b); j += 4096 {
			b[j] = 1 // a page only counts toward RSS once touched
		}
		hold = append(hold, b)
		fmt.Fprintf(os.Stdout, "allocated: %d MiB\n", i*10)
		time.Sleep(100 * time.Millisecond)
	}
}
```

```go title="gcpress/main.go"
// gcpress: 35MiB of data kept alive + temporary allocations thrown away constantly.
// Prints whether the heap stays under the limit and how many GCs ran.
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

var sink []byte

func main() {
	live := make([][]byte, 35)
	for i := range live {
		live[i] = make([]byte, 1<<20)
		for j := 0; j < len(live[i]); j += 4096 {
			live[i][j] = 1
		}
	}
	limit := "none"
	if l := debug.SetMemoryLimit(-1); l < 1<<40 {
		limit = fmt.Sprintf("%d MiB", l>>20)
	}
	fmt.Printf("GOMEMLIMIT=%s\n", limit)

	deadline := time.Now().Add(3 * time.Second)
	var peak uint64
	var ms runtime.MemStats
	next := time.Now()
	for time.Now().Before(deadline) {
		b := make([]byte, 512<<10) // temporary allocation, discarded
		for j := 0; j < len(b); j += 4096 {
			b[j] = 1
		}
		sink = b
		runtime.ReadMemStats(&ms)
		if ms.HeapAlloc > peak {
			peak = ms.HeapAlloc
		}
		if time.Now().After(next) {
			fmt.Printf("  heap %d MiB · runtime got %d MiB from the OS\n", ms.HeapAlloc>>20, ms.Sys>>20)
			next = time.Now().Add(500 * time.Millisecond)
		}
	}
	runtime.KeepAlive(live)
	fmt.Printf("peak heap %d MiB · %d GCs · survived to the end\n", peak>>20, ms.NumGC)
}
```

```go title="health/main.go"
// health: an HTTP server where liveness and readiness check different things.
package main

import (
	"fmt"
	"log"
	"net/http"
	"sync/atomic"
	"time"
)

var (
	lastBeat atomic.Int64 // last time the work loop ran (UnixNano)
	depOK    atomic.Bool  // state of an external dependency like a DB (a switch here)
)

func worker() {
	for {
		lastBeat.Store(time.Now().UnixNano())
		time.Sleep(time.Second) // a real service would process its queue here
	}
}

// healthz is for liveness. It only checks that this process itself is running.
func healthz(w http.ResponseWriter, _ *http.Request) {
	// Ignore external dependencies; fail only if my loop stalled for over 5s.
	if time.Since(time.Unix(0, lastBeat.Load())) > 5*time.Second {
		http.Error(w, "worker stuck", http.StatusInternalServerError)
		return
	}
	fmt.Fprintln(w, "ok")
}

// ready is for readiness. It checks whether we can take requests now, dependencies included.
func ready(w http.ResponseWriter, _ *http.Request) {
	if !depOK.Load() {
		http.Error(w, "dependency down", http.StatusServiceUnavailable)
		return
	}
	fmt.Fprintln(w, "ready")
}

func main() {
	depOK.Store(true)
	go worker()
	http.HandleFunc("/healthz", healthz)
	http.HandleFunc("/ready", ready)
	// a switch that simulates a dependency outage (example only)
	http.HandleFunc("/debug/dep", func(w http.ResponseWriter, r *http.Request) {
		depOK.Store(r.URL.Query().Get("up") == "1")
		fmt.Fprintf(w, "dependency up=%v\n", depOK.Load())
	})
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

## Lab setup and limits

When I first published this post I ran the cgroup experiments on Docker 29.8.2 (cgroup v1, 2 vCPU), and while moving it I rechecked them on a Kubernetes v1.28.2 node (RKE2, Rocky Linux 8.10, podman 4.9.4, runc 1.2.9, cgroup v1, 4 vCPU). The Go programs were built with Go 1.24.7 then. This time I built them with Go 1.24.7, Go 1.26.10, and Go 1.27.0 and ran each three times on the same node. All three versions agreed on the four cgroup values, on dying with exit 137 past the memory limit (podman recorded `OOMKilled=false`, the kernel log showed the OOM kill), on GOMAXPROCS=1 barely pausing under a limit of 1 while anything above it paused in nearly every period, and on dying without GOMEMLIMIT and surviving with 48MiB. Three things differed. Go 1.26.10 and 1.27.0 set GOMAXPROCS to 2 under a limit of 1 (Go 1.24.7 set 4). On Go 1.26.10, memhog died right after the 50MiB line in two of three runs. With 48MiB, the heap peaked at 46–56MiB on Go 1.24.7 and 42–46MiB on the other two. The RKE2 pod’s cgroup values and Go 1.25.8’s GOMAXPROCS of 4 also matched the post. The health server gave the same responses on all three versions on this Mac (Apple M5).

## Summary

- OOMKilled is the kernel killing a container over its limit; Evicted is kubelet removing a pod because of node pressure. Read Reason before exit code 137.
- requests are used when choosing a node, limits while running. requests.memory isn't written as a fence in any cgroup file.
- Going over a CPU limit means waiting for the next 100ms, not dying. More threads used up the share faster and stopped more often (19–20 of 20 periods versus 0–1 in 2 seconds).
- A Go app can die with a heap below the limit if its GC target goes over the limit. GOMEMLIMIT prevents that at the cost of more GC cycles.
- Eviction order goes by whether a pod is over its requests, then priority, then how far over. Evicted pods aren't moved; new ones are created.
- Probes do different things on failure. Put external dependencies in readiness only.

This time I only reproduced the cgroup side without a cluster, so I never triggered a real kubelet eviction. Next, on a test cluster, I want to put the node under memory pressure and watch the moment Evicted appears, and see how the eviction order shifts when I change requests.
