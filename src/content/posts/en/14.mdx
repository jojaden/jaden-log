<Lead>
Go has no classes and no inheritance, yet it's hard to call it non-object-oriented. The official FAQ answers "Is Go an object-oriented language?" with "Yes and no." This post explains why by following what Go put where inheritance used to be.

Go took the implementation reuse and polymorphism that inheritance handed over in one piece and gave them to embedding and interfaces separately. The post goes through a map of the four OOP pillars, embedding and promotion, why overriding doesn't work, embedding pitfalls, where generics fit, and design patterns, in that order. I reran every example on Go 1.26.10.
</Lead>

<Summary>
1. Inheritance bundles code reuse and polymorphism into one feature; Go hands reuse to embedding and polymorphism to interfaces.
2. Embedding is an anonymous field plus promotion. You can't override because there is no mechanism that sends a call back out to the outer type.
3. That makes interfaces the only route to dynamic dispatch. A method call on a concrete type is always resolved at compile time.
</Summary>

## Where Go keeps the four pillars of OOP

I'd memorized the four pillars for interviews, and the mapping fell apart when I moved to Go. Encapsulation, abstraction, inheritance, polymorphism: none of the mechanisms class-based languages use for them exists in Go as-is. Go still meets all four goals, by other means.

| Pillar | Class-based languages | Go |
| --- | --- | --- |
| Encapsulation | class + `private` / `protected` | package boundaries + identifier case. The unit is the package |
| Abstraction | abstract classes, interfaces | interfaces. There are no abstract classes |
| Inheritance | `extends`, type hierarchies | none. Embedding is not inheritance |
| Polymorphism | overriding + vtables | interfaces only. There is no other path |

The first row deserves a closer look. <mark>In Go, the unit of encapsulation is the package.</mark> Inside a package, every type can see every other type's lowercase fields. If you arrive thinking one type equals one class, that looks leaky. In practice the package boundary is the real wall, and everything inside it counts as one unit of implementation.

There's one more mechanism that doesn't get much attention: the `internal/` directory. A package under it can only be imported from within the tree rooted at `internal`'s parent. Even exported names stay unusable outside the project, which makes it a layer of encapsulation one step wider than the package.

```text title="The internal directory"
myapp/
├── internal/
│   └── auth/          ← importable only from under myapp/
│       └── token.go      exported names still can't be used by other modules
├── pkg/
│   └── client/        ← importable by anyone
└── main.go
```

To see whether it really holds outside the module, I imported `auth` from another module, `other`, that pulls in `myapp` through a `replace` directive.

```go title="other/main.go"
import (
	"fmt"
	"myapp/internal/auth"
	"myapp/pkg/client"
)
```

```text frame="terminal" title="Output"
$ cd other && go build .
package other
	main.go:5:2: use of internal package myapp/internal/auth not allowed
```

When `main.go` and `pkg/client` inside `myapp` imported the same `auth`, the build went through. The check isn't part of the language. The `go` command does it by looking at import paths[^internal], so the build stops while loading packages, before anything is compiled.

Methods aren't tied to classes either. We can attach methods to types that aren't structs, including a type built on a basic type, like `type Celsius float64`. Go never starts from the idea that an object is an instance of a class.

The official FAQ answers "Is Go an object-oriented language?" with "Yes and no." It has types and methods and lets you write in an object-oriented style, but there is no type hierarchy. When someone asks me, I say that only class-based inheritance is missing and the other goals are met by different tools, then walk through the tools in the table above.

## Not removed, but split in two

For a long time I took "why no inheritance?" to mean Go had left one feature out, and that makes for a weak answer. More precisely, Go separated two features that inheritance used to ship as one.

Class inheritance does two different jobs at once. It hands down the parent's implementation (code reuse), and it lets a child stand in wherever the parent is expected (polymorphism). Because the two are tied together, wanting only the implementation drags the type relationship along with it.

Some problems went away along with inheritance.

| Problem | What goes wrong |
| --- | --- |
| Tight coupling | Inheriting implementation binds parent and child tightly together |
| Fragile base class | Changing the parent can break every child, without knowing where the children are |
| Deep hierarchies | To find where a method came from, you have to climb the whole hierarchy |
| The diamond problem | With multiple inheritance, inheriting the same ancestor along two paths makes it unclear which one wins |

The FAQ gives one more reason, and it's the one that stuck with me. In object-oriented languages, too much time goes into declaring and debating the relationships between types up front. Go chose to let those relationships hold automatically, without declarations. The implicit interface satisfaction from [part one](/en/11) is exactly that mechanism. With no declared relationships, there's no type hierarchy to maintain.

There is a cost: more delegation code. Each call to a parent method, which inheritance gives you for free, has to be written out by hand. Embedding's promotion cuts down that repetition.

## What embedding really is: anonymous fields and promotion

If we write a type without a field name, the type's name becomes the field name. We can then reach the inner fields and methods while skipping a level. That skipping is called promotion.

<Compare>
<Side title="Embedded (anonymous field)">

```go
type Dog struct {
	Animal
	Breed string
}
```

- Reach it directly as `d.Name`
- Promoted methods join `Dog`'s method set

</Side>
<Side title="Named field">

```go
type Dog struct {
	Animal Animal
	Breed  string
}
```

- Reach it only as `d.Animal.Name`
- `Dog`'s method set is unchanged

</Side>
</Compare>

<Lab title="Same size as a named field, different method set">

I printed both with `unsafe` and `reflect` to check that they really have the same shape. `Dog` embeds `Animal` and defines its own `Sound()`, and `methods` is a small helper that collects method names through `reflect`.

```go title="layout/main.go"
type NamedDog struct {
	Animal Animal // named field
	Breed  string
}

func main() {
	var d Dog
	var n NamedDog
	fmt.Println("size:", unsafe.Sizeof(d), unsafe.Sizeof(n))
	fmt.Println("Breed offset:", unsafe.Offsetof(d.Breed), unsafe.Offsetof(n.Breed))
	fmt.Println("Dog methods:", methods(d))
	fmt.Println("NamedDog methods:", methods(n))
}
```

```text frame="terminal" title="Output"
$ go run ./layout
size: 32 32
Breed offset: 16 16
Dog methods: [Sound Speak]
NamedDog methods: []
```

The size and the offset of Breed matched. Only the methods differed: `NamedDog` has none, while `Dog` has the promoted `Speak` and its own `Sound`.

</Lab>

The only difference is promotion, and promotion does two things. It shortens the name, and it puts the inner methods into the outer type's method set. Thanks to the second, `Dog` satisfies every interface `Animal` satisfied. The abstract-class substitute later in this post depends on exactly that.

```go title="promote/main.go"
type Animal struct{ Name string }

func (a Animal) Sound() string { return "..." }
func (a Animal) Speak() string { return a.Name + ": " + a.Sound() }

type Dog struct {
	Animal // anonymous field
	Breed  string
}

func (d Dog) Sound() string { return "Woof" } // looks like an override…

func main() {
	d := Dog{Animal: Animal{Name: "Bori"}, Breed: "Jindo"}
	fmt.Println(d.Name)           // short for d.Animal.Name
	fmt.Println(d.Sound())        // the shallower one (Dog) wins
	fmt.Println(d.Animal.Sound()) // the inner method, reached directly
}
```

```text frame="terminal" title="Output"
$ go run ./promote
Bori
Woof
...
```

We can also reach the inner value by its type name, as in `d.Animal.Sound()`. It's the explicit way to call an inner method the outer type has shadowed, roughly where a `super` call would sit in other languages.

### When names collide

What happens when the outer type has a method with the same name as the inner one? The shallower depth wins: a name on the outer type shadows the same name inside. And two or more at the same depth are ambiguous. A common misconception is that declaring an ambiguous type is an error. It isn't. The compile error comes only when you actually use the name.

```go title="ambig/main.go"
package main

type A struct{ Name string }
type B struct{ Name string }

type C struct {
	A
	B
	Name string // shallower C.Name wins
}

type D struct{ A; B } // the declaration compiles

func main() {
	var c C
	_ = c.Name   // fine
	var d D
	_ = d.Name   // compile error
	_ = d.A.Name // explicit is fine
}
```

```text frame="terminal" title="Output"
$ go build ./ambig
# lab/ambig
ambig/main.go:18:8: ambiguous selector d.Name
```

Deleting just line 18 made the build pass. The declaration was never the problem. `D` holds two `Name` fields at the same depth, and the compiler stays quiet until a line actually uses the name; only that line stops and asks which `Name` you mean.

## No overriding: there's no way back out

The line that matters most in the code above is the one it didn't print. What does `d.Speak()` return?

<Lab title="Redefining Sound still left Speak calling Animal’s Sound">

`Dog` redefined `Sound()`, so anyone used to inheritance expects `Bori: Woof`. I also called it through an interface that has only `Sound()`.

```go title="speak/main.go"
type Sounder interface{ Sound() string }

func main() {
	d := Dog{Animal: Animal{Name: "Bori"}, Breed: "Jindo"}
	fmt.Println(d.Speak())

	var s Sounder = d
	fmt.Println(s.Sound())
}
```

```text frame="terminal" title="Output"
$ go run ./speak
Bori: ...
Woof
```

`Speak()` is a method on `Animal`, and inside it the a in a.Sound() is just an Animal. It has no way of knowing a `Dog` is wrapped around it. Put the same value in an interface, though, and `s.Sound()` reached `Dog`'s method, so the only call that checked the type at run time was the one through the interface.

</Lab>

The FAQ puts it in one sentence. The only way to get dynamic dispatch, picking the method by the value's type at run time, is through an interface, and methods on a struct or any other concrete type are always resolved at compile time. `a.Sound()` inside `Animal.Speak()` is fixed to Animal.Sound at compile time for the sole reason that `a` has type `Animal`. There's never a moment at run time to ask whether it's really a `Dog`. Effective Go names the same thing as the way embedding differs from subclassing: when a promoted method is called, its receiver is the inner type, not the outer one. <mark>Promotion only shortens names. It doesn't route calls back out.</mark>

### Flip the direction

Wanting the parent to call a method the child redefined is the template method pattern. Go can't build that structure, so we flip it into the strategy pattern: pull the varying part out into an interface and pass it in from outside.

### Filling the gap left by abstract classes

An abstract class puts two things in one type. The parent implements some behavior, and it forces subclasses to provide the rest. Go has nothing like it, so we split the two. Shared implementation comes in through embedding, and the methods a type must implement are declared as an interface.

```go title="abstract/main.go"
// ① Shared implementation: embed it and get it promoted
type BaseJob struct{ ID string }
func (b BaseJob) Key() string { return "job:" + b.ID }

// ② The required contract: declare it as an interface
type Runner interface {
	Key() string
	Run(context.Context) error
}

type SyncJob struct{ BaseJob }                               // shared part is promoted
func (SyncJob) Run(ctx context.Context) error { return nil } // contract implemented here

var _ Runner = SyncJob{} // forget Run and this line fails to compile (see part one)
```

I deleted the `Run` line and built it, and the build stopped at the assignment line.

```text frame="terminal" title="Output"
$ go build ./abstract
# lab/abstract
abstract/main.go:16:16: cannot use SyncJob{} (value of struct type SyncJob) as Runner value in variable declaration: SyncJob does not implement Runner (missing method Run)
```

`SyncJob` satisfies `Runner` because `Key()` was promoted into `SyncJob`'s method set. This is promotion's second job from earlier, put to work.

## Embedding pitfalls in practice

The convenience comes with a clear price. If you're writing a library in particular, know these before you embed.

| Pitfall | What happens |
| --- | --- |
| Internals leak into your public API | Every exported method of the embedded type becomes an exported method of yours. Removing one later breaks compatibility |
| Embedding `sync.Mutex` | `Lock`, `Unlock`, and `TryLock` become public API, so anyone can lock your value. A named field, `mu sync.Mutex`, is safer |
| Pointer-receiver methods | If you embed a type by value and its methods have pointer receivers, only `*Outer` satisfies the interface ([method sets in part one](/en/11)) |
| Name collisions | The shallower one wins; at equal depth you get an ambiguous error the moment you use it |

The first row is the one that bites most often. One convenience adds a whole set of exported methods to your public API. So in practice, picking the methods you need and delegating them yourself is more often the better choice. It costs a few more lines, but you decide what's public.

<Lab title="One embedded line added 54 exported methods">

To count how many, I set a `LeakyStore` that embeds the etcd client (v3.5.18) next to a `Store` that delegates only `Get`.

## Generics vs. interfaces

Generics arrived in 1.18 and added another option. At first I took them as a replacement for interfaces. Using them showed me the two belong in different places. One question settles the choice: <mark>what changes from type to type?</mark>

<Compare>
<Side title="Behavior differs → interface">

- Each type has to act differently
- Polymorphism, mocking, swapping implementations
- Example: a `Notifier` that sends via Slack, email, or SMS

</Side>
<Side title="Only the type differs → generics">

- The logic doesn't change by a single character
- Containers, `Map`, `Filter`
- Runtime type assertions disappear and types are checked at compile time

</Side>
</Compare>

```go title="map.go"
// Generics: only the type differs, the logic is identical
func Map[T, U any](in []T, f func(T) U) []U {
	out := make([]U, 0, len(in))
	for _, v := range in {
		out = append(out, f(v))
	}
	return out
}

doubled := Map([]int{1, 2}, func(i int) int { return i * 2 }) // [2 4]
names := Map(users, func(u User) string { return u.Name })

// Interface: each type does something different
type Notifier interface{ Notify(msg string) error } // Slack/email/SMS…
```

`Map` runs the same loop whether `T` is `int` or `User`, while each `Notifier` implementation does something different. Overused, though, generics make signatures hard to read fast. Introducing them once you've actually copy-pasted the same code two or three times worked well for me.

How are generics implemented in Go? They don't copy the code for every type like C++ templates, and they don't erase types and box values like Java. They sit in between. Types with the same GC shape, meaning the same underlying type or both pointers, share one copy of the machine code, and the information that differs per type is passed in a table called a dictionary.

## What design patterns look like in Go

Carry a pattern over by name and it usually comes out awkward. The shapes change in Go, and the reasons are the two things covered so far: no inheritance means inheritance-based patterns disappear, and first-class functions mean more closure-based forms.

| Pattern | What it looks like in Go |
| --- | --- |
| Strategy | Interface injection. By far the most common, since template method isn't possible and designs converge here |
| Decorator | `http.Handler` middleware: a closure that takes a handler and returns a wrapped one |
| Factory | A `NewXxx()` constructor function. A separate factory type is rarely needed |
| Builder | The functional options pattern, built from closures and variadic arguments |
| Singleton | `sync.Once`. Since 1.21, `sync.OnceValue` is shorter |
| Observer | Channels. Less need to build your own subscribe/unsubscribe machinery |

```go title="options.go"
// Functional options: closures take the builder's place
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithRetries(n int) Option           { return func(s *Server) { s.retries = n } }

func NewServer(opts ...Option) *Server {
	s := &Server{timeout: 5 * time.Second} // defaults
	for _, o := range opts {
		o(s) // each option applies itself
	}
	return s
}

srv := NewServer(WithTimeout(3*time.Second), WithRetries(2))

// Singleton: since 1.21, this one line does it
var conn = sync.OnceValue(func() *DB { return mustConnect() })
db := conn() // call it as often as you like; it initializes once
```

When I explain a pattern, I try to start with why it ended up in that shape rather than with its name. For the strategy pattern, "template method doesn't work, so I flipped the direction" tells you more than the name does.

<Note title="Aside: libraries vs frameworks">

This comes up in the same breath, and the test is who calls whom. You call a library; a framework calls your code. That reversal is called inversion of control (IoC).

It ties straight back to this post. For a framework to call your code, it has to invoke an implementation you handed it somewhere, and in Go that slot is filled by interface injection. Where inheritance-based frameworks made the slot by having you extend an abstract class, Go makes it by accepting an interface.

</Note>

| --- | --- | --- |
| `internal` · ambiguous selectors · a missing method | At which step, and with which message, the build stops | Messages from other compilers such as gccgo |
| Size · method sets · the `Speak` call | Layout, method lists, and call results in this example | Nothing left; the spec defines it, so I expect every version to match |
| etcd client method count | 54, as of the v3.5.18 source | Counts for other versions; I didn't count them from a binary |
| Embedded Mutex · test double | The promoted lock methods and the nil interface call | The panic message format in other versions |
| Overlapping interfaces | The difference between go lines 1.13 and 1.14 | A build with an actual 1.13 toolchain |
| GC shapes · sum benchmark | How these five types were grouped, and this loop's time | Numbers on other architectures. The method-call ratio comes from another post |

## Wrap-up

| What we saw | Why |
| --- | --- |
| `d.Speak()` printed `Bori: ...` | Methods on concrete types are fixed at compile time |
| `s.Sound()` through an interface printed `Woof` | Dynamic dispatch happens only through interfaces |
| `Dog` and `NamedDog` had the same size | An embedded field is an ordinary field; only promotion differs |
| The compile error came only on the line using `d.Name` | Ambiguous names are checked where they're used |
| Embedding the etcd client added 54 exported methods | Promotion puts the inner exported methods into the outer method set |
| The test double's `Delete` panicked | The embedded interface value is nil |
| A `go 1.13` module stopped on the duplicate `Close` | Overlapping methods start at 1.14 and follow the `go` line |
| `*User` and `*Order` shared one copy of the code | Pointer types share one GC shape |

So for library types I now delegate only the methods I need instead of embedding, keep `sync.Mutex` in a named field, and when a template method looks necessary, flip it around and pass an interface in.

Four parts in, Go's design has started to read as one idea. Types don't declare their relationships to each other in advance. That single principle shows up as implicit interface satisfaction and again as the absence of type hierarchies. With no declared relationships there's no hierarchy to manage, and when you need a relationship, you make one with an interface. Most of what first felt inconvenient follows from that.
