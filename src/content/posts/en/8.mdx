<Lead>
"Compiled language" and "static typing" are familiar terms, but I found it hard to explain what they actually buy you at run time. So I gave Go and Python the same job. Sorting a million structs took twice as long in Python. Building those million objects took about 80 times as long, walking them once about 360 times, and the memory was 7 times larger. The gap came less from computation than from how values sit in memory. Using Go 1.26, my main language, I traced that connection and checked each decision the compiler and runtime made with a tool.
</Lead>

<Summary>
1. With static types, a value's size and field positions are fixed at compile time. Just reordering fields took a million structs from 24 MB to 16 MB.
2. The compiler uses inlining and escape analysis to decide whether a value lives on the stack or the heap. When a constructor returning a pointer was inlined, it allocated zero times; with inlining off, it allocated once per call.
3. Go is a compiled language whose binary carries a GC and a scheduler, so the more you allocate, the more often the GC runs. Joining 100,000 strings with `+=` ran the GC about 1,650 times; `strings.Builder` ran it zero times.
</Summary>

## What static types and AOT compilation decide

### Go is a compiled language with a runtime

How languages execute sits on a spectrum. At one end, an interpreter reads the source as it goes; in the middle, a VM runs bytecode and a JIT turns hot paths into machine code while the program runs; at the other end, AOT compilation produces all the machine code at build time.

AOT and JIT differ in what information they optimize with. A JIT optimizes from real execution profiles but needs to warm up; AOT runs at full speed from the first execution but has to optimize from static analysis alone.

| | AOT (Go) | JIT (JVM · V8) |
|---|---|---|
| Optimization input | Static analysis only | Execution profile (branch prediction, inline caches) |
| Warm-up | None, full speed from the first run | Yes, optimizes after thousands of runs |
| Startup | Very fast | Slow (VM boot + class loading) |
| Predictability | Easy | Hard (deoptimization · recompilation) |
| Deployment | One binary | Runtime must be installed |

This table is why Go is a common pick for serverless, containers, and CLIs. The more often you cold-start, the more AOT's lack of warm-up pays off.

Type systems sort out along two axes. If types attach to variables and are checked at compile time, the language is static; if they attach to values and are checked at run time, it's dynamic. If it refuses implicit conversions, it's strongly typed.

| | Strong | Weak |
|---|---|---|
| **Static** | **Go**, Rust, Java, Haskell | C, C++ (many implicit conversions) |
| **Dynamic** | Python, Ruby | JavaScript, PHP |

Go is strict even among static, strongly typed languages: converting between `int` and `int64` has to be explicit.

There's a third axis people rarely mention: how thick the runtime is. Languages that share AOT and static typing still split here.

| Language | Compilation | Typing | Runtime |
|---|---|---|---|
| C/C++ | AOT | static · weak | Essentially none (libc level) |
| Go | AOT | static · strong | Yes (GC · scheduler · allocator statically linked) |
| Rust | AOT | static · strong | Minimal (no GC) |
| Java | Bytecode + JIT | static · strong | Heavy (JVM) |
| Python | Interpreter | dynamic · strong | Heavy |

That's where Go's odd position shows. <mark>It's a compiled language with a runtime.</mark> C and Rust have thin runtimes, so you rarely feel a GC or scheduler, and the JVM is a black box. Go's runtime shows up directly in your code's performance, and its source (`src/runtime/`) is written in Go, so you can read it.

Since every comparison checks types, I expected sorting to show the widest gap, but the sort differed by only 2x. ### Fixed types mean a fixed memory layout

"Static types catch bugs early" is half the story. The other half is performance. When types are fixed at compile time, the runtime can do this:

| Because of static types | What happens at run time |
|---|---|
| Type sizes are known at compile time | A field access is **one fixed-offset add** (dynamic languages look it up by name) |
| No need to box values | `[]int` stores integers contiguously, so **it fits the cache well** (a Python list is an array of pointers) |
| Most call targets are known | **Static dispatch + inlining** (dynamic languages look up every call) |
| Which fields are pointers is known | The GC **scans precisely using type info** |
| The compiler knows the invariants | Bounds-check elimination, dead-code elimination, **escape analysis** |

Struct memory layout is the most tangible example. Changing only the field order changes the size, because alignment adds padding.

<Compare>
<Side title="Bad · 24 bytes" tone="bad">

```go
type Bad struct {
	a bool  // 1 + 7 padding
	b int64 // 8
	c bool  // 1 + 7 padding
}
```

</Side>
<Side title="Good · 16 bytes" tone="good">

```go
type Good struct {
	b int64 // 8
	a bool  // 1
	c bool  // 1 + 6 padding
}
```

</Side>
</Compare>

Just reordering the fields cut it by 33%. You can check this with `unsafe.Sizeof`, `Alignof`, and `Offsetof`. The `fieldalignment` analyzer in x/tools finds such structs. `go vet` does not include this check, so `go vet -fieldalignment` fails with `flag provided but not defined: -fieldalignment`. Because this layout is fixed at compile time, a field access becomes a single `base address + constant offset` instruction.

<Lab title="Measure the effect of field order">

I printed the sizes with `unsafe` to confirm 16 and 24 bytes, then made a slice of a million of each type and measured heap usage with `runtime.ReadMemStats`.

```text frame="terminal" title="Output"
Sizeof(Bad{})=24   Offsetof(Bad{}.b)=8   ← 7 bytes of padding after a
Sizeof(Good{})=16  Offsetof(Good{}.a)=8

make([]Bad, 1_000_000)  → HeapAlloc +24.0MB
make([]Good, 1_000_000) → HeapAlloc +16.0MB
```

A loop adding up the `b` field a million times was about 18% faster for Good (0.37 ms vs 0.30 ms over six runs). Smaller elements mean more of them fit in each cache line. With 64-byte lines, that's 2.6 Bads against 4 Goods.

</Lab>

## What the compiler decides: inlining, stack, and heap

Here's the order in which the Go compiler turns `.go` files into an executable:

1. **Lexer · Parser**: builds the AST.
2. **Type checking**: infers and verifies types.
3. **Middle-end optimization**: inlining, escape analysis.
4. **SSA optimization**: more than 40 passes.
5. **Code generation**: `.o` files.
6. **Linking**: everything, runtime included, into one binary.

The last step is the one to watch. At link time, the GC, scheduler, and allocator go into the executable whole. That's why a one-line `fmt.Println` hello world is 2.4 MB, and also why you can ship a single file with no runtime to install.

Five of these optimizations feed straight into performance, and you can check each one with a tool.

| Optimization | What it does | How to check |
|---|---|---|
| Inlining | Expands small functions at the call site | `-gcflags='-m'` |
| Escape analysis | Puts values that don't leave the function **on the stack** | `-gcflags='-m'` |
| Devirtualization | Turns interface calls into concrete calls | `-gcflags='-m'` |
| Bounds-check elimination | Removes unneeded `a[i]` range checks | `check_bce` debug output |
| Dead-code elimination | Removes unreachable code and unused functions | Compare binary sizes |

For bounds checks, build with `-gcflags='-d=ssa/check_bce/debug=1'` and every check the compiler couldn't remove is printed as `Found IsInBounds`.

Inlining is first for a reason. More than the saved call itself, what matters is that escape analysis, constant propagation, and bounds-check elimination can only kick in after inlining. Inlining is a precondition for the other optimizations.

<Lab title="Find the inlining limit and measure its value">

When a function's "cost" goes over a budget of 80, the compiler gives up on inlining it. I added one branch at a time to a small function and used `-gcflags='-m -m'` to find the limit. Each branch added 7 to the cost, and the eleventh one went over.

```text frame="terminal" title="Inlining decisions"
$ go build -gcflags='-m -m' .
./add.go:3:6: can inline Add with cost 4 as: func(int, int) int { return a + b }
./branches.go:174:6: can inline Add10 with cost 74 as: …
./branches.go:208:6: cannot inline Add11: function too complex: cost 81 exceeds budget 80
```

To measure the value, I turned inlining off (`-gcflags=-l`) and ran the same benchmarks. For `Add` alone, on or off stayed around 1 ns and the difference got lost in the noise; the clear difference was in a constructor that returns a pointer.

```go title="p.go"
func NewPoint(x, y int) *Point { return &Point{x, y} }
```

```text frame="terminal" title="Inlining on and off"
$ go build -gcflags='-m' .
./p.go:6:41: &Point{...} escapes to heap
./p.go:10:31: &Point{...} does not escape   ← on the stack where it's expanded

BenchmarkNewPoint          1.1 ns/op    0 B/op   0 allocs/op
BenchmarkNewPoint (-l)     7.1 ns/op   16 B/op   1 allocs/op
```

Looking only inside the function, `&Point{...}` leaves it, so it goes to the heap. Once it's expanded at the call site, the compiler can see the pointer never leaves the caller and keeps it on the stack. Inlining changed what escape analysis concluded.

To see how much the compiler precomputes, I opened a loop that adds ten numbers (`for i := 0; i < 10; i++ { sum += i }`) with `go tool objdump`. The compare and branch were still there. The Go 1.26 compiler did not fold this loop into the constant 45.

</Lab>

### Stack or heap: escape analysis

In C, `malloc` means heap and anything else means stack. Go has no such syntax; the compiler decides. The rule isn't a list to memorize but a single principle. <mark>Does the value outlive the function frame?</mark> If yes (or if the compiler can't tell, to be safe), it goes on the heap; otherwise, the stack.

```go title="Common patterns that escape to the heap"
func f() *int { x := 1; return &x }    // returning a pointer
func g(v any) { ... }                  // passing as an interface (callee unknown)
func h(n int) { s := make([]int, n) }  // size unknown at compile time
go func() { use(x) }()                 // closure capture + goroutine
fmt.Println(x)                         // ...any variadic args (a surprise regular)
```

Stack allocation is just moving the frame pointer, so it's practically free, and it disappears when the function returns. Heap allocation goes through the allocator and becomes a debt the GC has to collect later. That's why the first principle of Go performance work is to allocate less, not to allocate faster.

Escape analysis results change between compiler versions. Go 1.25 widened the cases where a slice's backing store can live on the stack. Rather than memorizing which patterns go to the heap, it's better to check with `-gcflags='-m'` on the version you use.

<Lab title="The heap escape behind one fmt.Println">

I reproduced the most surprising pattern above, the variadic case. Just passing one local variable to `fmt.Fprintln(io.Discard, x)` does this:

```text frame="terminal" title="Escape analysis and benchmark"
$ go build -gcflags='-m' .
./log.go:12:14: ... argument does not escape
./log.go:12:18: x escapes to heap        ← the moment it becomes an any argument

$ go test -bench=. -benchmem
BenchmarkDirect          1.5 ns/op   0 B/op   0 allocs/op
BenchmarkPrintln        22.0 ns/op   8 B/op   1 allocs/op   // x = 1000
BenchmarkPrintlnSmall   16.5 ns/op   0 B/op   0 allocs/op   // x = 7
```

The slice holding the variadic arguments stayed on the stack; boxing the int into an any went to the heap. Small integers like 0 to 255 point at values the runtime prepared in advance, so they didn't allocate. This explains why debug logging inside a hot path shows up in profiles. Pass the same value to a function that takes a concrete type and the allocation goes to zero. It was the first time I felt that escape analysis is ultimately an API signature design problem.

</Lab>

## What interfaces and generics cost

Looking at what static types look like at run time explains all the famous traps. Conceptually:

```go title="Runtime representation (conceptual)"
// slice: 3 words (data pointer + length + capacity)
type slice struct { array unsafe.Pointer; len, cap int }

// string: 2 words, immutable
type string struct { data *byte; len int }

// interface: 2 words (type info + data pointer)
type iface struct { tab *itab; data unsafe.Pointer }
// itab: one per (interface, concrete type) pair; a table of method pointers
```

Here's what follows from that:

- **append and reallocation.** Once you exceed cap, a new array is allocated and copied, and at that moment sharing with the original breaks. That's the story behind "sometimes append changes the original and sometimes it doesn't."
- **Reslicing memory leaks.** Holding a small piece of a big array (`huge[:3]`) keeps the whole array from being collected, because the slice header points into it.
- **The nil interface trap.** An interface is two words, (type, data), so storing a nil pointer gives `{tab: T, data: nil}`. It carries type information, so it's `!= nil`.
- **Interface conversion cost.** Storing a non-pointer value in an interface usually allocates on the heap (small integers like 0 to 255 and zero-size values are exceptions).

### Static and dynamic dispatch

```go title="Same function, two signatures"
func Do(w *bytes.Buffer)  // static: direct call → can inline
func Do(w io.Writer)      // dynamic: indirect call through itab.fun
                          //          can't inline + may allocate
```

Interfaces trade inlining opportunities and direct calls for flexibility. The point isn't to avoid them but to know the cost on hot paths. When conditions are right, the compiler devirtualizes for you, and PGO (profile-guided optimization) widens that range.

### Generics are neither

<Compare>
<Side title="C++ templates">

Copies the code for every type. Code size grows.

</Side>
<Side title="Java erasure">

Erases every type. You pay for boxing.

</Side>
<Side title="Go stenciling">

Types with the same GC shape (pointer layout) share code, plus a per-type dictionary.

</Side>
</Compare>

Go sits in between. It avoids both code bloat and boxing everything, but methods on a type parameter are called through the dictionary, so they don't get inlined. Generics aren't free either.

<Lab title="Reproduce the nil interface trap and benchmark three kinds of dispatch">

The nil trap takes only a few lines to reproduce. Peek at the interface's two words with `unsafe` and the reason is right there.

```go title="nil_iface.go"
func mayFail() error {
	var p *MyErr // nil pointer
	return p     // returns a nil pointer inside an error interface
}

err := mayFail()
fmt.Println(err == nil) // false

// printing the iface internals with unsafe:
// (tab=0x1023af998, data=0x0)  ← it has type info, so it isn't nil
// a real nil interface is (tab=0x0, data=0x0)
```

When there is no error, write `return nil` explicitly, and don't return a variable of a concrete error type as an error.

For dispatch cost, I wrote the same logic (summing the areas of 1,000 rectangles) three ways: concrete type, generic, and interface.

## The GC runs as often as you allocate

Here's Go's GC in one table.

| Item | Go GC |
|---|---|
| Algorithm | Tri-color **mark & sweep** |
| Concurrency | **Concurrent**, runs alongside the application. It stops the program only at two short points |
| Moving | **Non-moving**, object addresses never change |
| Generations | Non-generational |
| Goal | **Latency** over throughput |

It works by tri-color marking: paint objects from white (unvisited) through gray (visited, children pending) to black (done), then free whatever is still white. The catch is that this happens while the application runs. What if the program changes a pointer in the middle of marking?

The write barrier is code the compiler plants so it runs on every pointer write. And this is where the post comes full circle: the GC can scan the heap precisely because of static types. The compiler records, as metadata, which offsets in every type are pointers, so the GC never has to do a conservative scan that mistakes integers for pointers. The same reason lets goroutine stacks move freely: since the runtime knows exactly where every pointer on a stack is, it can copy the stack and fix them up.

### One GC cycle and the heap allocator

A cycle has four phases. Stop the world (STW) happens only at two short points, the start and the end, and the heavy marking runs alongside the application. Marking aims to use 25% of the CPU.

1. **Sweep termination**: short STW.
2. **Mark**: concurrent, write barrier on.
3. **Mark termination**: short STW.
4. **Sweep**: concurrent, a little at each allocation.

The allocator that creates the objects the GC collects is layered too. It's in the TCMalloc family: it starts from a lock-free per-P cache and goes down a level only when that runs out.

```text title="Allocator layers"
mcache   (one per P, no lock)          ← most allocations end here
  ↓ when empty
mcentral (per size class, shared by Ps) ← small objects (≤32KB) come
  ↓ when empty                           from spans of 67 size classes
mheap    (global, page-granular)       ← large objects (>32KB) come straight from here
  ↓ when empty
OS (mmap)
```

Size classes keep external fragmentation down, and values under 16 bytes that hold no pointers get packed together by the tiny allocator. A single allocation is designed to be this fast.

### There are really only two tuning knobs

- `GOGC` (default 100): the next GC starts once you've allocated as much new memory as the heap (plus stacks and globals) that was live when the last GC finished. Raise it and the GC runs less but uses more memory.
- `GOMEMLIMIT` (1.19+): a soft memory limit. In containers it is practically required to avoid OOM kills.
- A practical combination: `GOGC=off GOMEMLIMIT=512MiB`. Use memory up to the limit and keep GC to a minimum.

```text frame="terminal" title="gctrace"
$ GODEBUG=gctrace=1 ./app
gc 1666 @0.265s 9%: 0.033+0.073+0.007 ms clock, …, 3->4->1 MB, 4 MB goal, …
#                   ↑ STW + concurrent mark + STW; the pauses total 0.04 ms
```

The GC keeps changing. Green Tea GC, an experiment in Go 1.25, became the default in 1.26. It marks memory in blocks rather than one object at a time to make better use of the cache, and the release notes expect a 10–40% cut in GC overhead for real programs that lean heavily on the GC. You can turn it off with `GOEXPERIMENT=nogreenteagc`, and that setting is slated for removal in 1.27.

## The rest of the runtime: goroutines, hidden costs, binaries

### Goroutines and data races

Goroutines are much lighter than OS threads because of the runtime too. They start with a 2 KB stack (OS threads usually get 1 to 8 MB), and when that runs out, the runtime allocates a stack twice the size, copies everything over, and fixes up the pointers. The runtime scheduler puts goroutines (G) on OS threads (M), and running Go code requires holding a processor (P). G, M, P, `GOMAXPROCS`, and the memory of 100,000 goroutines are measured in [a separate post](/en/21).

One more thing about concurrency: a data race may do more than occasionally give a wrong value. The Go memory model doesn't let a racy program do just anything, the way C does. A value of one word or less reads some value that was actually written. But multiword values such as interfaces, slices, and strings can be read half-written, and that can corrupt memory. The only guarantees come from the happens-before relationships that channel operations, mutexes, and atomics create. So I keep `go test -race` on by default.

<Lab title="A race that -race pinpointed">

I deliberately wrote a race where two goroutines each increment the same variable 1,000 times, and ran it with `-race`.

```text frame="terminal" title="race detector"
$ go run -race ./race
==================
WARNING: DATA RACE
Read at 0x00c00019e038 by goroutine 7:
  main.main.func1()
      race/race.go:16 +0x88

Previous write at 0x00c00019e038 by goroutine 8:
  main.main.func1()
      race/race.go:16 +0x98
==================
```

A regular build gets the value wrong only now and then, which makes this kind of bug hard to catch. The race detector pointed to the exact file and line in a single run. Since then, I always run CI tests with `-race`.

</Lab>

### Hidden costs and binaries

Syntax looks free, but it carries a runtime price tag. Here are just the common ones.

| Feature | What happens at run time |
|---|---|
| defer | Nearly free since 1.14 with open-coded defers. But **inside a loop it piles up on the heap**; move it out |
| panic · recover | Stack unwinding + walking the defer chain. **Why not to use it for error handling** |
| Closures | Captured variables can escape to the heap |
| string ↔ []byte | **Copies** by default. Repeated on a hot path, invisible allocations pile up |
| range over map | Random start point each time. Deliberately designed so you can't rely on order |
| cgo | Every call switches to the system stack and is treated like a system call. The cost of crossing the GC and scheduler boundary |

A fully linked Go binary is worth a look too. On top of standard sections like `.text` (code) and `.rodata` (constants), there's Go's own `.gopclntab` (the table mapping PCs to source lines). Stack traces and the GC's precise scanning both rely on it. Hello world is several MB because the runtime, reflection metadata, and DWARF debug info are all statically included.

The calling convention (ABI) is visible because Go is compiled too. Since Go 1.17, the internal ABI passes arguments in registers instead of on the stack, and the release notes report about a 5% speedup on representative benchmarks. Disassemble with `go tool objdump` and you can see arguments loaded into the AX and BX registers (on amd64; R0 and R1 on arm64).

## You can check all of it with tools

The biggest thing I learned studying this wasn't a concept but an attitude. Knowing something from reading is different from knowing it from checking. Go ships every one of these tools in the standard toolchain.

| Tool | Question it answers |
|---|---|
| `go build -gcflags='-m'` | Was it inlined? Did it escape to the heap? |
| `GOSSAFUNC=f go build` | Every SSA optimization step (ssa.html) |
| `GODEBUG=gctrace=1` | How often does GC run, and how long is STW? |
| `GODEBUG=schedtrace=1000` | Are Ps idle? Are run queues piling up? |
| `go tool pprof` (CPU · heap · mutex …) | **What** is slow, what allocates |
| `go tool trace` | **Why the CPU is idle** (GC STW and blocking on a timeline) |
| `go test -race` · `-benchmem` + benchstat | Race detection; is the improvement statistically significant? |

<Lab title="Catching one bottleneck with pprof">

I ran an API handler that builds a JSON list of 200 products on every response as a benchmark and took a CPU profile.

```text frame="terminal" title="pprof -top -cum"
$ go test -bench=Handler -cpuprofile cpu.out
BenchmarkHandler   25090 ns/op   14443 B/op   3 allocs/op
$ go tool pprof -top -cum -focus=pprofjson cpu.out
      flat    cum
         0  0.85s  pprofjson.slow
         0  0.83s  encoding/json.(*Encoder).Encode
         0  0.79s  encoding/json.(*encodeState).marshal   ← the culprit
     0.13s  0.79s  encoding/json.structEncoder.encode
```

93% of the handler's time went into marshaling the list. I changed it to marshal the list once, only when it changes, and to append just the per-request part to a buffer taken from a `sync.Pool`. After a test confirmed both versions return the same response, I ran each six times.

```text frame="terminal" title="Before and after (median of six runs)"
BenchmarkHandler       24.6µs/op   14,441 B/op   3 allocs/op
BenchmarkHandlerFast    0.18µs/op       0 B/op   0 allocs/op
```

The profile named the culprit first, and the optimization came second.

</Lab>

Even with the tools, the wrong order just wastes time. Optimize in this order:

1. Measure. Don't guess.
2. Look at algorithms and data structures.
3. **Reduce allocations.**
4. Look at the concurrency structure.
5. Micro-optimize.
6. Measure again.

## Test environment and limits

Every number in this version was remeasured on this Mac (Apple M5, 10 cores, darwin/arm64) with Go 1.26.10 and Python 3.9.6. No record survived of the environment behind the numbers first published in July 2026, so I rewrote the same experiments, ran them again, and replaced the numbers. The sort comparison went from 16 times to 2 times, and the dispatch benchmark, which had shown generics on par with concrete types, now shows a 2.6 times gap. The Linux binaries whose sizes I measured were cross-compiled from the Mac; the CGO builds and the scratch run were done in a `golang:1.26` container (Go 1.26.10 linux/amd64) on the lab server (x86_64).

| What I checked | What it tells you | What it doesn't |
| --- | --- | --- |
| Go vs Python, a million items | Where the gap comes from at each step | The gap on other Pythons (3.12+, PyPy) or other data shapes |
| Field order | Padding and heap usage, the same on any machine | The walking speed gap (18%), which depends on cache size |
| Inlining · escape | What the Go 1.26 compiler decided | Other versions' decisions, which change |
| Dispatch benchmark | The gap between the three styles for this shape (a sum over 1,000) | How much of real service code those calls account for |
| gctrace · GOGC | How allocation volume relates to GC count | GC cost for programs with a large live heap; this one's live heap is around 1 MB |
| pprof example | The bottleneck in the example handler | Bottlenecks in a real server mixing network and serialization |
| Binary · CGO | linux/amd64 build size and what CGO links to | Results with another libc, such as musl on Alpine |

## Wrapping up

| Stage | What gets decided | What we saw |
| --- | --- | --- |
| Static types | Value sizes and field positions | Field order alone: 24 MB → 16 MB |
| Compiler | Inlining, stack vs heap | Inlining the constructor: 1 allocation → 0 |
| Dispatch | Direct call, dictionary, itab | 0.28 ns · 0.73 ns · 1.77 ns per element |
| GC | A GC that runs as much as you allocate | `+=` about 1,650 runs, Builder 0 |

Most of the differences measured in this post came from how values are laid out in memory and from what the compiler can remove once it sees that layout. Those decisions change with each compiler version, so rechecking your own code with `-gcflags='-m'` and `gctrace` is more accurate than numbers written in a post.

Here's a starting point you can try right now. One command each for reading the compiler's decisions and for watching the GC and the scheduler.

```go title="esc.go"
type Point struct{ X, Y int }

func stack() Point { return Point{1, 2} }
func heap() *Point { p := Point{1, 2}; return &p }
```

```text frame="terminal" title="Commands to watch"
$ go build -gcflags='-m -m' esc.go    # read the compiler's decisions
$ GODEBUG=gctrace=1 ./app             # watch the GC
$ GODEBUG=schedtrace=1000 ./app       # watch the scheduler
```
