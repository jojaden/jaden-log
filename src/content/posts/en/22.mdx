<Lead>
The container limit was 1GB, yet the process was OOMKilled with an 800MB heap. Go has a garbage collector, so how did memory run out? The short answer is that the GC paces itself as a ratio of the live heap, while the container kills at an absolute number. This post covers `GOMEMLIMIT`, which bridges the two, and escape analysis, which keeps values off the heap in the first place.
</Lead>

<Summary>
1. The compiler decides whether a value lives on the stack or the heap. The same `&Pair{}` gave 0 allocs/op or 1 allocs/op depending on inlining, and a `make` of unknown size escaped on Go 1.24.7 but not on Go 1.27.0. So we measure with `-gcflags=-m` and `-benchmem` instead of counting syntax.
2. `GOGC` sets the next heap goal in proportion to the live heap, so it has no absolute ceiling. With 600MB live the goal is near 1.2GB, and in a container with a 1GB limit the kernel kills the process before the GC gets there. The RSS the kernel counts is also larger than the heap.
3. `GOMEMLIMIT` adds an absolute ceiling next to that ratio. Setting it to 300MiB on the same program pulled the GC goal from about 400MB down to 287MB and more than doubled the number of GC cycles. Across five settings, total allocation stayed at 256MiB.
</Summary>

## The compiler decides between stack and heap

Go has no syntax that says "put this on the heap," the way `malloc` does in C. Using `new` or `&` doesn't change that. The compiler decides with escape analysis, and the question it asks is whether the value is still needed after the function returns.

Think of a function as a meeting room. Notes on the whiteboard get wiped when the meeting ends; that's the stack, and cleaning up costs nothing extra. If a note has to leave the room, it goes on paper into a storeroom, and the GC looks after the storeroom. That's the heap.

Two things are worth stating up front. Returning the address of a local variable in Go doesn't produce a dangling pointer. The compiler arranges storage that lives as long as it needs to, so the bug you'd get in C by returning the address of a stack local doesn't exist in Go.

And "does not escape" doesn't necessarily mean "one object sits on the stack." The value may live only in registers, or the computation may simplify until the object disappears. The language guarantees behavior; the exact placement depends on the compiler version and its optimizations. So rather than guessing placement from syntax, we ask the tools.

<Lab title="Only onStack, which returns a value, is missing from the diagnostics">

Here are five functions in shapes that tend to escape. Put them in one file and read what the compiler says.

```go title="escape/main.go · full program"
package main

func main() {}

type Point struct{ X, Y int }

func onStack() Point    { p := Point{1, 2}; return p }  // returns a copy
func byPointer() *Point { p := Point{1, 2}; return &p } // ① returns a pointer
func toIface() any      { p := Point{1, 2}; return p }  // ② returns an interface
func captured() func() int {
	n := 0
	return func() int { n++; return n } // ③ closure capture
}
func unknownSize(n int) int {
	buf := make([]byte, n) // ④ size unknown at compile time
	return copy(buf, "hello")
}
```

```text frame="terminal" title="Output · Go 1.24.7 · darwin/arm64 (← notes added)"
$ go build -gcflags='-m' . 2>&1 | grep -v inlin
# escape

./main.go:9:52: p escapes to heap                 ← ② boxing in toIface
./main.go:11:2: moved to heap: n                  ← ③ n in captured
./main.go:12:9: func literal escapes to heap      ← ③ the closure itself

$ GOTOOLCHAIN=go1.27.0 go build -gcflags='-m' . 2>&1 | grep make

```

There's no line for `onStack`. It returns a copy, so the original `p` can disappear with the function. The other four went to the heap on Go 1.24.7, and only ④ changed on Go 1.27.0.

The Go 1.25 release notes explain ④ in one line: the compiler can now put the backing store for slices on the stack in more situations. Splitting the size into 32 and 33 bytes and counting allocations shows where the line is.

```go title="vmake/make_test.go · two benchmarks that differ only in size"
package vmake

import "testing"

//go:noinline
func use(n int) int {
	buf := make([]byte, n)
	return copy(buf, "hello")
}

func BenchmarkMake32(b *testing.B) {
	for i := 0; i < b.N; i++ {
		use(32)
	}
}

func BenchmarkMake33(b *testing.B) {
	for i := 0; i < b.N; i++ {
		use(33)
	}
}
```

```text frame="terminal" title="Output · darwin/arm64"
$ GOTOOLCHAIN=go1.24.7 go test -run '^$' -bench . -benchmem -benchtime=100ms
BenchmarkMake32-10    13048869     9.401 ns/op    32 B/op    1 allocs/op
BenchmarkMake33-10    12464780     9.748 ns/op    48 B/op    1 allocs/op
$ GOTOOLCHAIN=go1.27.0 go test -run '^$' -bench . -benchmem -benchtime=100ms
BenchmarkMake32-10    55769622     1.802 ns/op     0 B/op    0 allocs/op
BenchmarkMake33-10    15216597     7.681 ns/op    48 B/op    1 allocs/op
```

Only the `Make32` line on Go 1.27.0 shows 0 allocs/op. Even when the size isn't known at compile time, a request that fits in 32 bytes at run time uses a stack buffer; from 33 bytes on it goes to the heap, as on Go 1.24.7. The source didn't change. Only the toolchain did.

So I don't memorize these four as a list of things that allocate. Passing a value as an interface or creating a closure doesn't always mean a new allocation. If the compiler can see how far the value travels, the same syntax can stay on the stack. The four are candidates to check.

Still, ② is the one that shows up most on hot paths. Keep passing values to a function that takes `any`, and those values may escape and push `allocs/op` up. That, too, is something to confirm on the build.

Allocation in Go is fast. It still matters when there's a lot of it, because every allocation comes back later as work for the GC to scan and clean up.

</Lab>

<Lab title="The same NewPair gets two verdicts in one build">

Reading the previous diagnostics line by line can get confusing, because the same expression can be reported as both "escapes to heap" and "does not escape." Let's check with one short function.

```go title="alloc/allocation.go · one NewPair, used two ways"
package allocation

type Pair struct {
	A, B int64
}

func NewPair(n int64) *Pair {
	return &Pair{A: n, B: n + 1}
}

func SumLocal(n int64) int64 {
	p := NewPair(n)
	return p.A + p.B
}

var Published *Pair

func Publish(n int64) {
	Published = NewPair(n)
}
```

`NewPair` returns the address of an object holding two integers. `SumLocal` only adds the fields and returns, while `Publish` stores the address in a global. The global is there on purpose, to force an escape.

```go title="alloc/allocation_test.go · benchmarks for both"
package allocation

import "testing"

var sink int64

func BenchmarkLocal(b *testing.B) {
	for i := 0; i < b.N; i++ {
		sink += SumLocal(int64(i))
	}
}

func BenchmarkPublished(b *testing.B) {
	for i := 0; i < b.N; i++ {
		Publish(int64(i))
	}
}
```

```text frame="terminal" title="Output · darwin/arm64 · Go 1.24.7 (verdict lines only)"
$ go build -gcflags='-m=2' allocation.go 2>&1 | grep -E 'inline NewPair|inlining call|escapes to heap$|does not escape'
./allocation.go:7:6: can inline NewPair with cost 9 as: func(int64) *Pair { return &Pair{...} }
./allocation.go:12:14: inlining call to NewPair
./allocation.go:19:21: inlining call to NewPair
./allocation.go:8:9: &Pair{...} escapes to heap
./allocation.go:12:14: &Pair{...} does not escape
./allocation.go:19:21: &Pair{...} escapes to heap
```

The last three lines all refer to the same `&Pair{}`, with different verdicts. Line 8 is the body of `NewPair` itself; lines 12 and 19 are the copies inlined into `SumLocal` and `Publish`. Inlining pastes a short function's body into the call site, and once it's pasted, the compiler can see exactly how far the value goes. In `SumLocal` the address is gone once the sum is computed, so it doesn't escape. In `Publish` it ends up in a global, so it does.

That's why I read the file and line number, and any `inlining call` around it, before the message itself. The difference carries straight into the benchmark.

```text frame="terminal" title="Output · Go 1.24.7 · linux/amd64, 2 cores"
$ go test -run '^$' -bench . -benchmem -benchtime=200ms -count=3 allocation.go allocation_test.go
BenchmarkLocal-2         396647101    0.6096 ns/op     0 B/op    0 allocs/op
BenchmarkLocal-2         396067387    0.6077 ns/op     0 B/op    0 allocs/op
BenchmarkLocal-2         401408246    0.6848 ns/op     0 B/op    0 allocs/op
BenchmarkPublished-2      11122455   18.36   ns/op    16 B/op    1 allocs/op

BenchmarkPublished-2      13671566   16.87   ns/op    16 B/op    1 allocs/op
```

Both call the same `NewPair`, yet <mark>one makes 0 allocs/op and the other makes 1 alloc of 16 bytes</mark>. Now let's turn off inlining and nothing else.

```text frame="terminal" title="Output · side experiment with inlining off · Go 1.24.7 · linux/amd64, 2 cores"
$ go test -run '^$' -bench . -benchmem -benchtime=200ms -gcflags='-l' allocation.go allocation_test.go
BenchmarkLocal-2          13994080   16.01 ns/op    16 B/op    1 allocs/op
BenchmarkPublished-2      13299541   15.88 ns/op    16 B/op    1 allocs/op
```

One flag moved `BenchmarkLocal` from 0 allocations to 1, without touching a single character of code. "Pointers go to the heap" can't explain that result.

I ran it again on this Mac (darwin/arm64, Go 1.24.7). `Local` took 0.78ns with 0 allocs/op, `Published` 6.8ns with 16 B/op and 1 allocs/op, and with `-l` `Local` also became 16 B/op and 1 allocs/op. The timings differ by machine; the allocation counts matched the original.

`-l` and `//go:noinline` are fine for isolating a cause, but they produce a different binary than the one you ship. Measure the final cost again with your normal build. Also, `B/op` is the total bytes allocated per operation, including memory already reclaimed, so it tells you nothing about what is live right now.

## Is removing every escape faster?

Not necessarily. Removing one heap allocation can buy you extra copying or shared state instead. Once you can read the diagnostics, it's tempting to eliminate every escape; first, look at these two costs.

<Compare>
<Side title="Return by value">

```go title="config.go"
// copies the whole Config on every call
func Load() Config
```

One heap allocation goes away, and every call copies the whole struct instead. If the caller has to keep the value around for a long time, returning by value doesn't meet that need at all.

</Side>
<Side title="Reuse a global buffer">

```go title="buf.go"
// shared across requests
var buf [64 << 10]byte
```

Allocations drop, but now there's shared state. Someone has to guard concurrent access and make sure one request's data doesn't leak into the next.

</Side>
</Compare>

A fixed order keeps this straight. Correct lifetimes and API meaning come first, finding the slow path with a profiler comes next, and only then do you ask whether that path's allocations can shrink. After a change, compare correctness, latency, and allocations together. The win has to survive real input distributions, not just a short benchmark.

## The GC runs alongside the program and never moves objects

Go's GC is a tricolor mark-and-sweep collector. It runs concurrently with the program and doesn't move objects. Unlike the JVM's collectors, it isn't generational and doesn't compact. The design trades fragmentation for simplicity and short pauses.

The three colors name how far the traversal has gotten. Objects don't actually carry a color field. The GC reclaims objects that can't be reached from the roots, which include goroutine stacks and global variables. Nothing is freed for being old or looking unused, so no setting can shrink the data that's still live.

The price of marking alongside the program is the write barrier. To avoid losing a live object when a pointer changes mid-mark, each pointer write does a little extra work. There are also two short stop-the-world (STW) pauses, so a concurrent GC still has pauses and costs.

Go can mark precisely because it's statically typed. The compiler knows which fields are pointers, so the GC never has to guess whether some 8 bytes are a pointer or an integer. The marking itself keeps evolving: the Green Tea GC arrived as an experiment in Go 1.25 and became the default in Go 1.26. It scans small objects in batches per memory block for better cache locality, and the release notes expect a 10–40% cut in GC overhead for programs that lean on the GC heavily.[^greentea]

Cost depends on how much data is live, how pointers connect it, and how fast new memory is allocated. A big byte array and a dense web of pointers of the same size can cost very different amounts to scan. No setting changes the algorithm. What you can change is when the GC starts, and that's what `GOGC` and `GOMEMLIMIT` control.

## GOGC sets the goal as a ratio of the live heap

`GOGC` decides when the GC runs. The default is 100, and the next heap goal comes from this formula.

```text title="Heap goal from the GC guide"
Target heap = Live heap + (Live heap + GC roots) × GOGC / 100
```

When the roots are small, `GOGC=100` means roughly twice the surviving heap. With 200MB live the goal is around 400MB; with 600MB live it's around 1.2GB. A larger value allows a bigger heap in exchange for fewer collections.

A common misreading of the formula goes like this.

> The GC starts the moment the heap reaches the goal.

The runtime starts marking earlier, so that the cycle finishes near the goal, and it adjusts the pace as it goes. Other inputs, such as the minimum heap goal and the memory limit, come into play too. Let's see it in real output.

<Lab title="gctrace shows the goal doubling as live grows">

This program holds on to 200MiB of live data and keeps creating 64KiB of garbage. With `GODEBUG=gctrace=1`, every GC cycle prints one line.

func main() {
	for i := 0; i < 200; i++ { // about 200MiB live

	}
	for i := 0; i < 100_000; i++ { // keep making 64KiB of garbage

	}

## Why does an 800MB heap get OOMKilled?

Because the GC goal can be set above the container limit. With 600MB live and `GOGC=100`, the goal is near 1.2GB; with a 1GB limit, memory crosses the limit before the GC runs on its schedule. On top of that, what the kernel counts is RSS, which is larger than the heap. A container memory limit is an absolute rule (kill this process past 1GB), and <mark>the kernel has no idea when the GC plans to run.</mark>

When a GC cycle shrinks the heap, the memory the OS sees doesn't drop by the same amount right away. The runtime may keep the space for reuse, and returning it to the OS happens separately. If you change a setting and expect RSS to fall immediately, you'll misread what you see.

I didn't reproduce a container OOMKill for this post. Every experiment below ran outside a container and reads numbers the runtime reports.

## GOMEMLIMIT adds an absolute ceiling

`GOMEMLIMIT` is a soft memory limit added in Go 1.19. As memory approaches it, the GC runs early even if the `GOGC` goal is still far away. It puts an absolute rule next to the ratio, in the same units the kernel uses.

| Setting | Based on | Ceiling |
| --- | --- | --- |
| `GOGC` | a ratio of live heap, default 100 | none |
| `GOMEMLIMIT` | bytes of runtime-managed memory | soft, can be exceeded |

"Runtime-managed memory" means `Sys` minus `HeapReleased` in `runtime.MemStats` terms. It covers more than the heap, including other memory the runtime maps and manages. It leaves out the Go binary itself, memory allocated directly by cgo, and memory the OS holds on the process's behalf. That's why using the container limit as-is isn't enough. Near the limit, the runtime also returns memory to the OS more aggressively, not just runs the GC sooner.

This program keeps 8MiB of baseline data alive and creates a 64KiB array 4,096 times. Only the 16 most recent arrays stay in a global, so the rest lose their references and become garbage. It allocates 256MiB in total but never holds all of it at once.

```go title="gc/main.go · full program"
package main

import (
	"fmt"
	"os"
	"runtime"
	"time"
)

var recent [16][]byte

func main() {
	fmt.Println("Go:", runtime.Version(), "GOGC:", os.Getenv("GOGC"), "GOMEMLIMIT:", os.Getenv("GOMEMLIMIT"))
	base := make([]byte, 8<<20)
	for i := range base {
		base[i] = 1
	}
	runtime.GC() // align the baseline; not counted in the GC delta below
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)

	start := time.Now()
	var checksum uint64
	var peak uint64
	for i := 0; i < 4096; i++ {
		data := make([]byte, 64<<10)
		data[0] = byte(i)
		data[len(data)-1] = byte(i >> 8)
		recent[i%len(recent)] = data
		checksum += uint64(data[0]) + uint64(data[len(data)-1])
		if i%64 == 0 {
			var m runtime.MemStats
			runtime.ReadMemStats(&m)
			if m.HeapAlloc > peak {
				peak = m.HeapAlloc
			}
		}
	}
	elapsed := time.Since(start)
	runtime.ReadMemStats(&after)
	runtime.KeepAlive(base)

	const mib = 1 << 20
	fmt.Printf("TotalAlloc delta: %.1f MiB\n", float64(after.TotalAlloc-before.TotalAlloc)/mib)
	fmt.Printf("NumGC delta: %d\n", after.NumGC-before.NumGC)
	fmt.Printf("sampled peak heap: %.1f MiB\n", float64(peak)/mib)
	fmt.Printf("NextGC at exit: %.1f MiB\n", float64(after.NextGC)/mib)
	fmt.Printf("Sys-HeapReleased at exit: %.1f MiB\n", float64(after.Sys-after.HeapReleased)/mib)
	fmt.Println("checksum:", checksum, "elapsed:", elapsed)
}
```

The `runtime.GC()` right at the start aligns the baseline and isn't counted in the GC numbers below. It's not a technique to copy into a loop. `runtime.KeepAlive(base)` states that the baseline data must stay alive until the last measurement; it's not something to attach to every variable in a service.

When reading these numbers, start with what each one counts.

| Metric | Tells you | Doesn't tell you |
| --- | --- | --- |
| `HeapAlloc` | bytes in allocated heap objects | the RSS the kernel sees |
| `NextGC` | the runtime's next goal | a limit for the process |
| `Sys - HeapReleased` | what the memory limit counts | cgo, mappings outside Go |
| process RSS | what the OS and container see | where the runtime spent it |

`HeapAlloc` still includes dead objects that haven't been collected, and `NextGC` is a goal, not a ceiling. With that in mind, here's how I'd set things up.

```go title="main.go · for a 1GB container limit"
// env: GOMEMLIMIT=900MiB  ← around 90% of the limit; RSS includes memory the runtime can't see
// env: GOGC=100           ← keep the ratio rule; with little live data it triggers first

// or set it in code
debug.SetMemoryLimit(900 << 20)

// GOGC=off + GOMEMLIMIT means "don't collect until the limit."
// Fine for batch jobs that can fill memory, wrong for latency-sensitive services.
```

The GC guide recommends leaving an extra 5–10% of headroom for memory the runtime doesn't know about, in fixed-memory environments like containers. With heavy cgo use or large file mappings, leave more.

Remember that the limit is soft. If live data alone exceeds it, no amount of collecting brings memory back under. The runtime caps GC CPU use at roughly 50% so the GC can't take over the whole CPU, which means the process keeps running above the limit until it gets OOMKilled anyway. `GOMEMLIMIT` protects you when garbage piles up, and it can't help when the live data itself is too large. The guide says the same: for a program already close to its environment's limit, raise the limit or lower `GOGC` instead of leaning on the memory limit.

## Wrap-up

- The compiler picks stack or heap. The same `&Pair{}` changed with inlining, and the same `make` changed with the toolchain, so measure with `-gcflags=-m` and `-benchmem` instead of counting syntax.
- Go's GC is a concurrent tricolor mark-and-sweep that never moves objects. Short pauses come at the price of write barriers.
- `GOGC` is a ratio, so the goal grows as live data grows. Marking starts before the heap reaches the goal.
- The container kills on absolute RSS. That's how an 800MB heap can die under a 1GB limit.
- Setting `GOMEMLIMIT` below the limit pulls the goal under it, and GC cycles go up accordingly. Even with `GOGC=off`, a limit keeps the GC running.

When I studied the GC, I thought tricolor marking and write barriers were the heart of it. But where the service actually died, the problem was when the GC started, not the algorithm, and that rule and the kernel's rule didn't even use the same units.

While writing this up I also noticed it has the same shape as `GOMAXPROCS` in the [previous post](/en/21). The runtime decides from the host's cores and the heap ratio; the container limits by CPU quota and RSS. One setting reconciles each side: `GOMAXPROCS` for CPU and `GOMEMLIMIT` for memory.

Through all five settings, the 256MiB of total allocation didn't move. Shrinking that number is the code's job, and next I'll look at reusing buffers with `sync.Pool`.
