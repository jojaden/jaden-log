<Lead>
In the [previous post](/en/22), total allocations stayed at 256MiB however I set `GOGC` and `GOMEMLIMIT`. Reusing short-lived buffers with `sync.Pool` is one way to shrink it. The benchmark dropped to zero allocations, but when I kept reading `Bytes()` from a buffer I had already put back, `user=alice` turned into `user=bobce`. `Put` is the moment your right to that buffer ends, and any slice you took from it ends there too.
</Lead>

## `sync.Pool` doesn't promise to keep anything

Let's start with what a pool doesn't promise. The first paragraph of the docs says it plainly.

> Any item stored in the Pool may be removed automatically at any time without notification.

[sync.Pool documentation](https://pkg.go.dev/sync#Pool)

`Get` doesn't promise to hand back what you put in, either. If the pool is empty, `New` makes a fresh value. So the program has to work correctly even when the pool holds nothing at all.

Since Go 1.13, a GC doesn't empty the pool in one go. It moves what was in the pool to a victim cache for one more cycle and drops it at the next GC[^victim]. The pool still gets emptied eventually.

<Lab title="Two GCs and the same buffer is gone">

I wanted to see it disappear at the second GC. We put the same buffer back, run zero, one, and two GCs, and take it out again.

```go title="victim/main.go · full program"
package main

import (
	"bytes"
	"fmt"
	"runtime"
	"sync"
)

func main() {
	runtime.GOMAXPROCS(1) // with a single P, every run gives the same result
	made := 0
	pool := sync.Pool{New: func() any { made++; return new(bytes.Buffer) }}

	b := pool.Get().(*bytes.Buffer)
	for gcs := 0; gcs <= 2; gcs++ {
		pool.Put(b)
		for i := 0; i < gcs; i++ {
			runtime.GC()
		}
		got := pool.Get().(*bytes.Buffer)
		fmt.Printf("GCs=%d  same buffer=%t  New=%d\n", gcs, got == b, made)
		b = got
	}
}
```

```text frame="terminal" title="Output (darwin/arm64, Go 1.24.7)"
$ go run .
GCs=0  same buffer=true  New=1
GCs=1  same buffer=true  New=1
GCs=2  same buffer=false  New=2
```

On the third line, `New` runs a second time. The buffer survived one GC and was dropped at the second. Five runs gave the same output, and so did Go 1.27.0.

`runtime.GOMAXPROCS(1)` is there to make the result repeatable. A pool keeps a private slot per P, and it can't take from another P's private slot. With several Ps, the goroutine can move to a different P, miss the buffer it just put back, and call `New`.

</Lab>

So where does a pool fit? Several structures have similar names; which one fits depends on what you need.

| You need | Use | Why not a pool |
| --- | --- | --- |
| reusable temp buffers | `sync.Pool` | (it fits) |
| a cache with expiry | a real cache | items vanish unannounced |
| a cap on connections | a connection pool | no chance to `Close` |
| a cap on running jobs | a worker pool, semaphore | it doesn't count loans |

This post puts `bytes.Buffer` in the pool: the GC cleans it up if it's dropped, and it's cheap to make again.

## Writing the same record three ways

The output is `data=`, the input bytes, and a newline. All three functions produce the same output and errors; only the way they get a buffer differs.

<Lab title="Writing 1KiB through the pool allocated nothing">

```go title="reuse.go · full code"
package reuse

import (
	"bytes"
	"io"
	"sync"
)

const maxRetainedCapacity = 64 << 10

var buffers = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func encode(b *bytes.Buffer, payload []byte) {
	b.WriteString("data=")
	b.Write(payload)
	b.WriteByte('\n')
}

// Baseline: a fresh buffer on every call.
func WriteFresh(w io.Writer, payload []byte) error {
	var b bytes.Buffer
	encode(&b, payload)
	_, err := b.WriteTo(w)
	return err
}

// Reserve the needed capacity up front. No pool.
func WriteGrown(w io.Writer, payload []byte) error {
	var b bytes.Buffer
	b.Grow(len(payload) + 6)
	encode(&b, payload)
	_, err := b.WriteTo(w)
	return err
}

// Borrow a buffer from the pool and put it back.
func WritePooled(w io.Writer, payload []byte) error {
	b := buffers.Get().(*bytes.Buffer)
	b.Reset()
	defer func() {
		if b.Cap() <= maxRetainedCapacity {
			b.Reset()
			buffers.Put(b)
		}
	}()

	encode(b, payload)
	_, err := b.WriteTo(w)
	return err
}
```

A buffer taken from the pool belongs to one call. After `WriteTo` sends the result, the deferred function clears it and puts it back. The deferred function runs even when the write fails, so no old contents leak into the next use.

The fresh buffer allocates twice. When the first write is small, `bytes.Buffer` grabs only 64 bytes. Writing `data=` takes those 64 bytes, and appending the 1KiB body takes another 1152, which is where 64 + 1152 = 1216 B/op comes from. The pooled version reuses a buffer that has already grown, so it shows 0. That doesn't mean the first `New` allocates nothing.

I don't take these numbers as "`sync.Pool` makes it N times faster." `io.Discard` throws the bytes away, so all that's left to measure is encoding and the temporary buffer. Once a real file or network sits behind the writer, this saving becomes a much smaller share of the request.

<Note title="If the Writer holds on to the bytes">
This code assumes the `io.Writer` contract: once `Write` returns, the implementation doesn't keep the slice it was given. An asynchronous Writer that sends data later needs its own way to honor that, such as copying. Putting the buffer back early while the other side keeps reading the same array is not allowed.
</Note>

## What do you see if you read `Bytes()` after Put?

You see whatever the next request wrote into the same array. `b.Bytes()` returns a slice that points at the buffer's internal array, not a copy. Once the buffer is back in the pool, another request takes it, calls `Reset`, and writes again, and reading through the old slice shows that new content mixed in.

The `bytes.Buffer` docs already say the slice from `Bytes()` is valid only until the next modification of the buffer. With a pool, that next modification comes from another request instead of your own code.

<mark>Once you call `Put`, you stop calling the buffer's methods and you stop reading through any slice you took from it.</mark> It sounds obvious, but it's easy to miss in code.

<Lab title="Reading after Put printed user=bobce">

`encodeBad` returns the slice and then puts the buffer back. `encodeGood` makes a copy before putting it back.

```go title="own/main.go · reading after Put"
package main

import (
	"bytes"
	"fmt"
	"sync"
)

var pool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

// Bad: returns a slice into the buffer, then puts the buffer back.
func encodeBad(name string) []byte {
	b := pool.Get().(*bytes.Buffer)
	b.Reset()
	b.WriteString("user=")
	b.WriteString(name)
	out := b.Bytes() // a view of the internal array, not a copy
	pool.Put(b)      // our right to use it ends here
	return out
}

// Good: makes an independent copy before putting it back.
func encodeGood(name string) []byte {
	b := pool.Get().(*bytes.Buffer)
	b.Reset()
	b.WriteString("user=")
	b.WriteString(name)
	out := append([]byte(nil), b.Bytes()...)
	pool.Put(b)
	return out
}

func main() {
	bad := encodeBad("alice")
	fmt.Printf("right after Put  : %s\n", bad)
	_ = encodeBad("bob")
	fmt.Printf("after next call  : %s\n", bad)

	good := encodeGood("alice")
	_ = encodeGood("bob")
	fmt.Printf("copy             : %s\n", good)

	// Reset keeps the capacity, which is why we check Cap, not Len
	var buf bytes.Buffer
	buf.Write(make([]byte, 128<<10))
	fmt.Printf("\nafter big write  : Len=%d Cap=%d\n", buf.Len(), buf.Cap())
	buf.Reset()
	fmt.Printf("after Reset      : Len=%d Cap=%d\n", buf.Len(), buf.Cap())
}
```

```text frame="terminal" title="Output"
copy             : user=alice

after big write  : Len=131072 Cap=131072

```

That doesn't mean the next `Get` is guaranteed to return the buffer you just put back. The `Get` docs say not to assume any relation between what you pass to `Put` and what `Get` returns. If the bytes need to outlive the function, there are two options. Make a copy before putting the buffer back, or change the ownership rule so the caller puts it back when done. If you choose the copy, measure again to see whether the pool still pays off once the copy is included.

One more point. Being able to call `Get` and `Put` from many goroutines at once is a property of the pool itself. It doesn't make it safe for several goroutines to modify the buffer you took out. The pool won't stop you from putting the same buffer back twice or from using it after `Put`, either. And a `Pool` must not be copied after first use.

That's where the zero allocations came from. The same property means a buffer that once grew large stays large in the pool, bigger than ordinary requests need. So the decision to put a buffer back is based on `Cap`, not `Len`. That's why `WritePooled` checks `b.Cap() <= maxRetainedCapacity`.

The 64KiB here is the per-buffer limit I picked for this experiment. It isn't a universal best value or a memory cap for the whole pool. A buffer over the limit isn't put back; the function just lets go of it, and that memory doesn't go back to the OS right away. A per-buffer limit also doesn't fix how many buffers are on loan or how much the whole pool holds. If you need an exact memory budget, manage it with a separate structure.

<Note title="Reset doesn't erase anything">
`Reset` empties the buffer logically; it doesn't overwrite the old bytes with zeros. That's why `ce` was still there in `user=bobce`. Data that must be wiped, such as tokens or passwords, needs its own lifetime and deletion policy. When you reuse ordinary objects rather than buffers, clear the previous request's pointer fields as well as any lengths. A field left pointing at a large object keeps that object alive too.
</Note>

## With a pool, correctness breaks before performance does

So I wrote the tests first. They compare the three functions' output for an empty input, a normal input, and an input larger than the retention limit, and they check reuse after a write error and concurrent calls with separate Writers.

<Lab title="The error-path and concurrency tests passed under -race">

```go title="reuse_test.go · tests and benchmarks"
package reuse

import (
	"bytes"
	"errors"
	"io"
	"testing"
)

var errWrite = errors.New("write failed")

type failingWriter struct{}

func (failingWriter) Write(p []byte) (int, error) { return 0, errWrite }

func TestOutput(t *testing.T) {
	for _, size := range []int{0, 32, 128 << 10} {
		payload := bytes.Repeat([]byte("x"), size)
		var fresh, grown, pooled bytes.Buffer
		if err := WriteFresh(&fresh, payload); err != nil {
			t.Fatal(err)
		}
		if err := WriteGrown(&grown, payload); err != nil {
			t.Fatal(err)
		}
		if err := WritePooled(&pooled, payload); err != nil {
			t.Fatal(err)
		}
		want := "data=" + string(payload) + "\n"
		if fresh.String() != want || grown.String() != want || pooled.String() != want {
			t.Fatalf("output differs at size %d", size)
		}
	}
}

func TestErrorThenReuse(t *testing.T) {
	if err := WritePooled(failingWriter{}, []byte("previous")); !errors.Is(err, errWrite) {
		t.Fatalf("write error was not preserved: %v", err)
	}
	var out bytes.Buffer
	if err := WritePooled(&out, []byte("next")); err != nil {
		t.Fatal(err)
	}
	if out.String() != "data=next\n" {
		t.Fatalf("unexpected output: %q", out.String())
	}
}

func TestConcurrentWrites(t *testing.T) {
	for i := 0; i < 16; i++ {
		t.Run("independent output", func(t *testing.T) {
			t.Parallel()
			for j := 0; j < 100; j++ {
				var out bytes.Buffer
				if err := WritePooled(&out, []byte("hello")); err != nil {
					t.Fatal(err)
				}
				if out.String() != "data=hello\n" {
					t.Fatalf("outputs got mixed: %q", out.String())
				}
			}
		})
	}
}

func benchLoop(b *testing.B, fn func(io.Writer, []byte) error) {
	payload := bytes.Repeat([]byte("x"), 1024)
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		if err := fn(io.Discard, payload); err != nil {
			b.Fatal(err)
		}
	}
}

func BenchmarkFresh(b *testing.B)  { benchLoop(b, WriteFresh) }
func BenchmarkGrown(b *testing.B)  { benchLoop(b, WriteGrown) }
func BenchmarkPooled(b *testing.B) { benchLoop(b, WritePooled) }
```

`TestErrorThenReuse` checks that the call after a failed write produces clean output. Because the deferred function clears the buffer before putting it back, the old value didn't leak. The test doesn't assume the next `Get` returns the same buffer; the output has to be right whichever buffer comes out.

The concurrency test gives each call its own output buffer. `WritePooled` doesn't provide the synchronization you'd need if several goroutines shared one Writer.

</Lab>

Passing the race check means the detector found no conflict on the paths that actually ran. Reading after `Put` breaks a rule inside a single goroutine; it isn't a data race, and the detector can't catch it. ## `Grow` alone cuts an allocation without a pool

This is why the benchmark included `WriteGrown`. If you know the output length in advance, you can reserve the capacity in one step. The only change is one line, `b.Grow(len(payload) + 6)`, before `encode`.

| Version | B/op · allocs/op | Cost |
| --- | --- | --- |
| fresh buffer | 1216 · 2 | none (baseline) |
| `Grow` first | 1152 · 1 | needs the length |
| pooled | 0 · 0 | return rules, `Cap` check, copying |

In the original run, allocations went from 2 to 1 while ns/op ranges overlapped: 378.3–436.9 versus 386.5–387.8. On this Mac it went from 128.5ns to 119.1ns, about 7% less. <mark>Halving the allocations didn't halve the time.</mark> Here the pool won by a wide margin, but that result is tied to a fixed 1KiB input written to `io.Discard`.

If input sizes vary or there are many concurrent requests, this result isn't enough. Mix large requests in among small ones, and look at allocations and retained memory together over a long run with many GCs. Since the pool can be emptied at any time, also check that the code is correct and affordable when every call goes through `New`.

Decide the pool's scope, too. A new pool per request leaves nothing to reuse between calls. Mixing every type and size in one pool blurs what's inside and what state it comes out in. Start where the example does: one kind of temporary object with a clear rule for putting it back.

## Wrap-up

- `sync.Pool` is a box for reusing temporary objects you could rebuild. It promises neither storage nor a count, and a buffer left in it was gone after two GCs.
- Calling `Put` ends your right to the buffer. Slices you took from `Bytes()` end with it, so copy anything that has to leave before you put the buffer back.
- `Reset` zeroes `Len` and leaves `Cap` alone. Both the zero allocations and the oversized leftovers come from that, so decide on `Cap` whether to put a buffer back.
- Reading after `Put` isn't a data race, so `-race` doesn't catch it. In a race build it was hidden in roughly one run out of four.
- When the output length is known, `Grow` alone took allocations from 2 to 1. The time didn't drop by the same proportion.

What I kept coming back to while writing this wasn't a benchmark number but the single line `user=bobce`. The pool took allocations to zero, but buffers now live longer, and the code has a new job: putting each one back at the right moment.
