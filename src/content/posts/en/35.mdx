<Lead>
In the last post the slowest step in starting a pod was the sandbox, and I waved off what happens inside it as an isolated space. So this time I left Kubernetes out and built that isolation piece by piece with plain Linux commands. Run `ps` inside the pod and nginx is PID 1, but find the same process on the node and it's PID 3756479. A container is an ordinary process running on the node's kernel, and the kernel uses namespaces to change only what that process can see.
</Lead>

<Summary>
1. A container is a process the node's kernel runs directly. Linux namespaces make kernel resources such as PIDs, the network, mounts, and the hostname look like a private copy to that process.
2. `unshare` creates new namespaces and `nsenter` joins existing ones. The PID namespace is the exception: it applies to the children created afterward, not the caller, so leaving out `--fork` gets you `fork: Cannot allocate memory`.
3. The first process in a new PID namespace becomes PID 1 and plays by different rules. Without a handler it ignores SIGTERM, it has to reap orphans, and when it exits every process inside is killed with SIGKILL.
</Summary>

<Note title="Who this is for">
I wrote this for people who use containers but have never looked at a container's process from the node. Sections 1 and 2 look at a container from the node and at the namespace kinds, sections 3 and 4 build namespaces by hand with `unshare`, section 5 covers PID 1, and sections 6 and 7 cover `nsenter` and Kubernetes pods. cgroups, which set CPU and memory limits, get their own post next. The measured screens show commands and output exactly as I ran them on the lab server.
</Note>

## Each kernel resource gets its own namespace

The kernel has resources that normally exist once per system: the process ID table, network devices and routing tables, the mount list, and the hostname. A Linux namespace wraps one kind of resource so that the processes inside see it as their own copy. Which namespace a process belongs to, for each kind, is recorded as links under `/proc/<pid>/ns/`.

If the numbers match, the processes share that namespace. Strictly the device number has to match too, but within one node comparing this number is enough.[^dev] Lines ending in `_for_children`, such as `pid_for_children`, are where the process's future children will go.

There are eight kinds. The lab node runs kernel 4.18, yet `time` was there. Upstream added that kind in 5.6, so it looks like the distribution kernel (Rocky 8) backported it. A shared user namespace means root inside the container is the same user as root on the node, which we'll come back to in part 4 of this series, on privileges.

Two names cause confusion. The Namespace you create with `kubectl create ns` is an API object that only shares its name with Linux namespaces. Whatever Kubernetes Namespace a pod is in, it gets its own Linux namespaces. cgroups, which set resource limits, deal with how much CPU and memory a process uses rather than what it sees, so they wait for the next post. The cgroup namespace in the list of eight only hides how a process's own cgroup path looks.

## Splitting them off one by one with unshare

There are three ways to work with namespaces. From a shell we use `unshare` and `nsenter`, and each calls the system call that does the same job (`unshare` and `setns`). A container runtime combines these system calls when it creates a process, so the container starts in new namespaces from the beginning.

## The PID namespace starts with the children

I expected `unshare --pid` alone to work the same way, but the first try failed with an out-of-memory error.

<Lab title="Without --fork, the second ls failed to fork">
<Shot src="/img/35/pidtrap.webp" w={1720} h={477} phone={{ src: '/img/35/pidtrap-phone.webp', w: 1170, h: 972 }} name="lab-node:/tmp/jd-l1" alt="With unshare --pid bash, $$ is 3758937, one prints after the first ls, and the second ls fails with bash: fork: Cannot allocate memory. The `$$` (the shell's own PID) on the first line is 3758937, a node number, so bash did not move into the new PID namespace. `ls` ran once and printed `one`, and the second `ls` failed with `fork: Cannot allocate memory`. The node had plenty of memory.
</Lab>

`unshare` moves the calling process into the new namespace, except for the PID namespace (time works the same way). A process's PID is fixed at birth and can't change, so the caller stays where it is and only the children it creates afterward go into the new namespace. That made bash's first child, `ls`, PID 1 of the new namespace. When that `ls` exited, the namespace was left without a PID 1, and since no process can be created in a PID namespace whose init has exited, fork returned ENOMEM.[^enomem]

### Without a handler, even SIGTERM is dropped

An ordinary process that gets SIGTERM exits by default even without a handler. For PID 1, the kernel delivers only the signals it has handlers for, and the only exceptions are SIGKILL and SIGSTOP sent from an ancestor namespace.

`SigCgt` is the bitmap of signals the process has handlers for, and for sleep it is all zeros. A second after SIGTERM, sleep was still running, and it disappeared after SIGKILL. The last line is an ordinary sleep started from a normal shell for comparison, and the same SIGTERM ended it at once with exit code 143 (128 + 15).
</Lab>

Here's how this rule bites in Kubernetes. When you delete a pod, the kubelet goes through the runtime to send SIGTERM (or the image's `STOPSIGNAL`, if set) to the container's PID 1, and if it is still there after the grace period (`terminationGracePeriodSeconds`, 30 seconds by default), it ends it with SIGKILL. If a startup script is PID 1 and starts the server as a child, the script has no handler, so SIGTERM is dropped and never reaches the server. The pod waits the full 30 seconds and then ends with exit code 137 (128 + 9).

### It adopts orphans, and when it exits everything goes

A process whose parent exits first (an orphan) is adopted by systemd on the node. Inside a PID namespace, that namespace's PID 1 adopts it.

<Lab title="sleep 700 lost its parent and became a child of PID 1">
<Shot src="/img/35/orphan.webp" w={1720} h={796} phone={{ src: '/img/35/orphan-phone.webp', w: 1170, h: 1542 }} name="lab-node:/tmp/jd-l1" alt="ps inside the new PID namespace: PID 1 is bash -c (sleep 700 &); sleep 800, PID 3 sleep 700 has PPID 1, PID 4 is sleep 800. The subshell in parentheses (PID 2) started `sleep 700` and exited right away, leaving `sleep 700` without a parent. Inside, `ps` has no PID 2, and the PPID of `sleep 700` is 1. Then I killed only bash, the PID 1, with SIGKILL from the node, and sleep 700 and 800 disappeared with it.
</Lab>

When PID 1 exits, the kernel sends SIGKILL to every other process in the namespace. That's why everything started inside a container ends at once, without any cleanup, when the container's main process exits.

### Without reaping, zombies remain

A finished child stays in the process table until its parent collects its exit status with `wait`, and that state is called a zombie. Adopted orphans also disappear only when PID 1 reaps them.

### So, in the PID 1 seat

<Compare>
<Side title="Startup script as PID 1" tone="bad">

- `sh start.sh` starts the server as a child
- SIGTERM is dropped at the script and never reaches the server
- It only ends with SIGKILL after the grace period (137)

</Side>
<Side title="Server as PID 1 via exec" tone="good">

- The script's last line is `exec ./server`
- The server needs a SIGTERM handler to clean up
- If the server starts children, reaping them is its job too

</Side>
<Side title="A tiny init as PID 1" tone="good">

- Put tini or dumb-init in front (Docker has `--init`)
- It forwards signals to the child and reaps zombies
- The app doesn't need to know PID 1 rules

</Side>
</Compare>

For a Go server the second option is common. The Go runtime installs signal handlers on its own, so when I ran a Go program with no signal code as PID 1 and sent SIGTERM, its `SigCgt` was not zero and it exited at once with exit code 2. It does die, but it doesn't finish in-flight requests, so it still needs code that catches SIGTERM with `signal.NotifyContext` and cleans up.

`/run/netns/cni-…` is a file where the net namespace is bind-mounted. A namespace disappears when its last process exits, but it stays as long as it's mounted somewhere like this. containerd creates the net namespace first when it sets up the sandbox and mounts it at this path, and the CNI plugin takes this path to plug in a device and assign an IP. pause is a tiny process that holds the sandbox and sleeps.

## Commands used in the lab

Here are the commands from the lab, with what each one shows. `<…>` marks a value you fill in.

```bash title="Commands for looking at namespaces"
# Which namespace a process is in for each kind; the number in brackets is the namespace ID
ls -l /proc/<pid>/ns

# The node PID and inner PID on one line, and the bitmap of handled signals
grep -E 'NSpid|SigCgt' /proc/<pid>/status

# How many processes a namespace has, and where it is bind-mounted
lsns -t net -p <pid>
findmnt -t nsfs
```

```bash title="Commands for creating and entering namespaces"
# Run one command in a new uts or net namespace
unshare --uts sh -c 'hostname jd-box; hostname'
unshare --net ip -br link

# A new PID namespace. --fork makes the child PID 1, --mount-proc mounts a fresh /proc
unshare --pid --fork --mount-proc bash

# Enter only the namespaces you pick: -n for net, -p for pid, -m for mnt
nsenter -t <pid> -n ss -ltn
nsenter -t <pid> -p -m ps -o pid,ppid,stat,cmd -e
```

```bash title="Commands for finding and handling processes"
# Match the full command line. -a prints it, -x requires an exact match
pgrep -fa '[s]leep 1000'             # [s] keeps pgrep from matching its own shell
pgrep -fx 'sleep 1000'

# Walk up the parents. -s shows ancestors, -p shows PIDs
pstree -sp <pid>

# Ask the runtime (CRI) for a container's PID
crictl inspect -o go-template --template '{{.info.pid}}' <container id>

# Send signals. TERM gives a chance to clean up, KILL ends it at once
kill -TERM <pid>; kill -KILL <pid>
```

## Wrap-up

- A container is a process the node's kernel runs directly. The nginx that was PID 1 inside the pod was PID 3756479 on the node, and the `NSpid` line held both numbers.
- There are eight Linux namespace kinds (pid, net, mnt, uts, ipc, user, cgroup, time), and processes with the same number under `/proc/<pid>/ns` are in the same namespace. A Kubernetes Namespace is an API object that only shares the name.
- `unshare` moves the caller, but the PID namespace starts with the children. Without `--fork`, the first child became PID 1, exited, and the next fork failed with `fork: Cannot allocate memory`.
- PID 1 only receives signals it handles (SIGTERM was dropped), adopts orphans, and when it exits everything inside is killed with SIGKILL. A startup script should either `exec` the server into PID 1 or put an init such as tini in front.
- Containers in a pod share net, ipc, and uts and keep their own pid and mnt. The net namespace was bind-mounted at `/run/netns/cni-…`.
