<Lead>
I was already taking `ctx` as the first argument and passing it along. What I had never checked was whether canceling actually stops the goroutine. After stalling on that question in an interview, I went back to context from the start. Cancellation only sends a signal to stop; the side that receives it is the one that actually stops.

This post goes through what a context looks like and the tree it forms, how cancellation travels, time budgets, four pitfalls, and the APIs added since Go 1.20. I reran every example on Go 1.26.10.
</Lead>

<Summary>
1. Cancellation is a request for cooperation. Go has no way to kill a goroutine from outside; it stops only when the receiving side checks `Done()` itself.
2. Contexts form a tree. Cancel a parent and every child goes with it, and deadlines only ever get shorter. That's what turns into a time budget for a chain of services.
3. All four pitfalls are about lifetimes: not calling `cancel`, cleanup dying along with the work, overusing `WithValue`, and storing a context in a struct.
</Summary>

## Why it exists: ghost work

One incoming request fans out inside the server. It hits the database, calls an external API, reads files, and each of those may start more goroutines. Now suppose the client hangs up after three seconds.

With no way to tell anyone, the server keeps producing results nobody is waiting for. That's ghost work. It goes unnoticed most of the time, but once an incident slows responses and clients start timing out, <mark>abandoned work piles up, eats every resource, and turns into a cascading failure.</mark> Context is the standard way to carry "you can stop now" through the whole call chain.

What it actually is turns out to be simple: an interface with four methods.

```go title="context.Context"
type Context interface {
	Deadline() (deadline time.Time, ok bool) // until when
	Done() <-chan struct{}                   // a channel that signals the end (by closing)
	Err() error                              // why it ended (Canceled / DeadlineExceeded)
	Value(key any) any                       // request-scoped values
}
```

Using it comes down to four constructors and two ways of reading.

| Create | When |
| --- | --- |
| `Background()` | The root of the tree. main, initialization, tests, and the top of each incoming request |
| `WithCancel` | When you want to cut it off yourself |
| `WithTimeout` / `WithDeadline` | When you want a time limit. The one you'll use most in practice |
| `WithValue` | Only request-scoped metadata such as request IDs and traces (more below) |

| Read | What it tells you |
| --- | --- |
| `select` + `ctx.Done()` | Whether it has ended |
| `ctx.Err()` | Why it ended: `Canceled` or `DeadlineExceeded` |

The important part is that these build a tree. Each `WithXxx` takes a parent and returns a derived context, and <mark>cancellation flows only from top to bottom.</mark>

Being a tree brings two rules. First, canceling a child leaves the parent untouched. If the DB query hits its 1-second timeout, the request as a whole keeps going. Second, deadlines only get shorter. If the parent has three seconds and a child asks for ten, the real limit is still three. That you can't extend it is the safety feature.

## Cancellation is a request: the receiver stops

In an interview I was once asked whether canceling a context kills the goroutine, and I stalled. The answer is no.

<mark>Go has no way at all to forcibly stop a goroutine from outside.</mark> There's no API to kill a thread and no interrupts. So `cancel()` only closes a channel to say "you can stop now," and actually stopping is up to the receiver. The documentation is explicit that a `CancelFunc` does not wait for the work to stop.

<Compare>
<Side title="A loop that checks Done()" tone="good">

```go
for _, vm := range vms {
	select {
	case <-ctx.Done():
		return ctx.Err()
	default:
	}
	copyDisk(ctx, vm)
}
```

It exits on the next iteration.

</Side>
<Side title="A loop that ignores Done()" tone="bad">

```go
for _, vm := range vms {
	copyDisk(vm)
}
```

The signal arrives but nobody checks, so it runs to the end. That's ghost work.

</Side>
</Compare>

<Lab title="cancel() didn't wait, and the ignoring loop ran to the end">

I ran both loops. There are 10 items and each takes 100ms. `checks` looks at `Done()` before every item, and `ignores` only takes `ctx`. After 250ms I called `cancel()` and printed how long `cancel()` took to return and how many items were processed.

```go title="coop/main.go"
func run(name string, loop func(context.Context) int) {
	ctx, cancel := context.WithCancel(context.Background())
	start := time.Now()
	done := make(chan int)
	go func() { done <- loop(ctx) }()

	time.Sleep(250 * time.Millisecond)
	t := time.Now()
	cancel()
	took := time.Since(t)
	n := <-done
	fmt.Printf("%s: cancel() returned in %v, %d items, %v\n", name,
		took.Round(time.Microsecond), n, time.Since(start).Round(10*time.Millisecond))
}

func main() {
	run("checking loop", checks)
	run("ignoring loop", ignores)
}
```

```text frame="terminal" title="Output"
$ go run ./coop
checking loop: cancel() returned in 32µs, 3 items, 300ms
ignoring loop: cancel() returned in 3µs, 10 items, 1.01s
```

The checking loop finished the third item and stopped before the fourth. The ignoring loop processed all 10 even after the cancel. Both times `cancel()` came back within tens of microseconds; across four runs it ranged from 3µs to 62µs. That is exactly what the documentation says: it does not wait for the loop to stop.

</Lab>

When someone asks why canceling didn't stop anything, the answer is usually the loop that ignores `Done()`. That makes where you put the check the real design decision. The rule of thumb: right before anything that takes a while.

```go title="Check right before the slow part"
func migrate(ctx context.Context, vms []VM) error {
	for _, vm := range vms {
		select {
		case <-ctx.Done():
			return ctx.Err() // Canceled or DeadlineExceeded
		default: // with default, this never blocks
		}
		if err := copyDisk(ctx, vm); err != nil { // pass it down as well
			return err
		}
	}
	return nil
}
```

Fortunately, the standard library handles its side. APIs that take a ctx, such as `net/http` and `database/sql`, watch `Done()` internally, stop when it fires, and return an error. The checks you have to add yourself are in your own long loops and CPU-heavy work.

If a server passes `ctx` everywhere and the load still doesn't drop after cancellation, there's probably a stretch of the chain that never looks at `Done()`. When that happens, I start by looking for the long-running loops.

## Why Done() works as a broadcast

This raised a question for me. With a hundred goroutines, how does one cancellation reach all hundred at once? Send a value on a channel and only one receiver gets it.

The answer is that nothing is sent. Context closes the channel. <mark>Receiving from a closed channel immediately returns the zero value to every waiter, and they all wake up.</mark> A single channel can notify any number of goroutines.

This also explains why `Done()` returns `<-chan struct{}`. Because it's receive-only, the receiving side can't close it by accident (that's a compile error), and `struct{}` takes zero bytes, so the signal itself costs nothing.

I had 100 goroutines wait on one channel and counted how many had woken after sending one value and after closing the channel.

```go title="broadcast/main.go"
var woke atomic.Int32
for range 100 {

	}()
}

fmt.Println("size of struct{}:", unsafe.Sizeof(struct{}{}))
```

That property gives `select` two natural patterns. Pick whichever fits.

```go title="Non-blocking check and blocking wait"
// ① Non-blocking check: in the middle of a compute loop, just ask "canceled yet?"
select {
case <-ctx.Done():
	return ctx.Err()
default: // with default, this doesn't block
}

// ② Blocking wait: take whichever comes first, the result or the cancellation
select {
case res := <-resultCh:
	return res, nil
case <-ctx.Done():
	return nil, ctx.Err() // keeps you from blocking forever on a result
}
```

A single `default` line separates the two. With `default`, the select moves on instead of waiting on a `Done()` that has not closed yet; without it, the select sits there until cancellation.

## Time budgets: deadlines only get shorter

This was the last piece of context to click for me. I had thought of `WithTimeout` as "cut it off after a few seconds," but it actually assigns a time budget to the whole request and makes the chain share it.

<mark>A derived context's deadline can never be later than its parent's.</mark> If the parent ends in three seconds and the child asks for ten, the limit is still three. The further down you go, the less time is left.

What upstream spends, downstream loses, so you don't need to work out a timeout for every service. The budget even crosses process boundaries. gRPC sends the deadline in the request metadata, and the receiving server's ctx gets the same deadline. Pass that ctx on to the next call and the entire chain of services shares one budget. Set three seconds at the front and the limit follows all the way to the database at the back.

<Lab title="A child that asked for 10 seconds got its parent's deadline">

I made a 10-second child under a 3-second parent and printed the difference between the two deadlines. Then I canceled only the child.

```go title="deadline/main.go"
parent, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()
child, cancel2 := context.WithTimeout(parent, 10*time.Second)

pd, _ := parent.Deadline()
cd, _ := child.Deadline()
fmt.Println("child deadline - parent deadline:", cd.Sub(pd))
fmt.Println("time left for the child:", time.Until(cd).Round(100*time.Millisecond))

cancel2() // cancel only the child
fmt.Println("child Err:", child.Err())
fmt.Println("parent Err:", parent.Err())
```

```text frame="terminal" title="Output"
$ go run ./deadline

child Err: context canceled

```

The child asked for ten seconds, yet its deadline was identical to the parent's. When the parent's deadline is earlier, `WithDeadline` doesn't create a new timer at all; it hands back a `WithCancel` instead. And after the child was canceled, the parent's `Err()` was still `nil`.

</Lab>

Before heavy work, you can check the remaining time yourself with `Deadline()`.

```go title="Deciding by the time left"
if dl, ok := ctx.Deadline(); ok && time.Until(dl) < 500*time.Millisecond {
	return ErrNotEnoughTime // if it can't finish anyway, don't start
}
```

In an HTTP server, every request comes with its own ctx.

```go title="The request ctx in an HTTP server"
func handler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context() // canceled when the client's connection closes
	if err := doWork(ctx); err != nil {
		http.Error(w, err.Error(), http.StatusInternalServerError)
	}
}
```

<Lab title="The client hung up, and the handler's ctx ended 200ms in">

I had an `httptest` server's handler do five seconds of work and bail out when `r.Context()` ended. The client sent its request with a 200ms timeout.

```go title="httpctx/main.go"
srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	start := time.Now()
	select {
	case <-time.After(5 * time.Second): // five seconds of work
		got <- "finished the work"
	case <-r.Context().Done():

```

</Lab>

## Four pitfalls, all about lifetimes

The first two end a context's lifetime too late or too early; the last two keep a ctx that lives for one call somewhere that lives much longer.

### ① Skip cancel and it leaks

I wrote `defer cancel()` by rote for a long time without knowing exactly what leaks if you don't. The documentation answers briefly. Calling `cancel` does three things:

1. It cancels the child and its children.
2. It removes the parent's reference to the child.
3. It stops any associated timers.

Skip it and none of that happens. The documentation says the child leaks until the parent is canceled. If you derived it with `WithCancel` from a long-lived parent, that moment is when the server shuts down. <mark>You won't notice it on one request; you will at thousands per second.</mark>

<Lab title="100,000 children with discarded cancels held on to 11.5MB">

I kept one parent that lives as long as a server and derived 100,000 children from it with `WithCancel`. Once I called `cancel` right away; once I threw it away. `heapMB` is a small helper that runs the GC twice and measures the live heap.

```go title="leak/main.go"
parent, stop := context.WithCancel(context.Background()) // a parent that lives as long as the server
base := heapMB()

for range 100_000 {
	_, cancel := context.WithCancel(parent)
	cancel()
}
fmt.Printf("cancel called:       +%.1f MB\n", heapMB()-base)

for range 100_000 {
	context.WithCancel(parent) // throw cancel away
}
fmt.Printf("cancel not called:   +%.1f MB\n", heapMB()-base)

stop() // cancel the parent
fmt.Printf("after parent cancel: +%.1f MB\n", heapMB()-base)
```

```text frame="terminal" title="Output"
$ go run ./leak
cancel called:       +0.0 MB
cancel not called:   +11.5 MB
after parent cancel: +0.0 MB
```

Nothing in the code uses the children, yet the GC couldn't collect them, because the parent holds references to them in its list of children. That came to about 115 bytes per child, and canceling the parent brought it back to zero.

</Lab>

What if the timeout has already passed? When the timer fires, the context cancels itself and drops the parent's reference too, so `cancel` has almost nothing left to do. The real problem is work that finishes early. If it's done in two seconds and you never call `cancel`, the timer and the reference stay around for the remaining second. Either way, `defer cancel()` right after creating the context means you never have to think about it.

<Lab title="go vet catches a missing cancel">

I deliberately wrote code that calls `cancel` on only one branch and ran `go vet`.

```go title="leak.go"
func leak(ctx context.Context) {
	ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
	if ctx == nil {
		cancel()
		return
	}
}
```

```text frame="terminal" title="Output"
$ go vet ./...
leak.go:9:2: the cancel function is not used on all paths (possible context leak)
leak.go:14:1: this return statement may be reached without using the cancel var defined on line 9
```

It checks that `cancel` is called on every path and even points at the return that skips it. Put `go vet` in CI and nobody has to remember this one.

</Lab>

### ② Cancellation takes your cleanup down too

I only learned this one by living through it. A job failed and kicked off a rollback, and the rollback was being passed the same `ctx`. That ctx was already canceled. The rollback was canceled the moment it started, the snapshot it was supposed to delete stayed in storage, and the bill kept running. The error log only said `context canceled`, which made it hard to see that the real failure was the cleanup.

In hindsight it's obvious. A cancellation means "stop all work related to this request," and cleanup is part of that work. So <mark>cleanup has to be explicitly detached from the cancellation signal.</mark>

<Compare>
<Side title="Clean up with the same ctx" tone="bad">

```go
func rollback(ctx context.Context, id string) {
	deleteSnapshot(ctx, id) // context canceled
}
```

The cleanup dies as soon as it starts, and resources you meant to delete keep costing money.

</Side>
<Side title="Detach it and set a fresh limit" tone="good">

```go
func rollback(ctx context.Context, id string) {
	cctx := context.WithoutCancel(ctx)
	cctx, cancel := context.WithTimeout(cctx, 30*time.Second)
	defer cancel()
	deleteSnapshot(cctx, id)
}
```

The cleanup always runs, and it can't hang forever either (Go 1.21+).

</Side>
</Compare>

`WithoutCancel` keeps the values and cuts only the cancellation. The nice part is that the request ID and trace data survive, so the cleanup still logs with them. But the deadline goes away too, so you must set a new timeout. Otherwise you get the opposite problem: a cleanup that never ends.

### ③④ Overusing WithValue and storing ctx in structs

The other two are about using context where it doesn't belong. The documentation spells out the rules clearly, so when in doubt, follow them.

| Rule | Why |
| --- | --- |
| Don't store it in a struct | A ctx is tied to the lifetime of one call, not of an object. Stored in a field, nobody can tell when it will be canceled |
| First parameter, named `ctx` | It's the documented convention, so both readers and linters expect it there |
| Never pass nil | If you don't know what to pass, pass `context.TODO()`. It marks a spot to fix later |
| Value is for request-scoped data only | It is not a way to pass optional function parameters |
| Use an unexported type for keys | Basic types like `string` collide with keys from other packages |

The fourth row goes wrong most often in practice. `WithValue` looks convenient, but once required parameters start hiding in it, the signature no longer tells you what a function needs, and type safety is gone. A missing value still compiles, and the type assertion that reads it panics at run time.

```go title="Required values as arguments, keys as unexported types"
// Bad: a required parameter hidden in ctx. The signature tells you nothing
func createOrder(ctx context.Context) error {
	userID := ctx.Value("userID").(string) // panics at run time if missing
	// ...
}

// Good: required values as arguments, only request metadata in ctx
func createOrder(ctx context.Context, userID string) error { /* ... */ }

// Keys must be an unexported type
type traceIDKey struct{} // no other package can construct this type

func WithTraceID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, traceIDKey{}, id)
}
func TraceIDFrom(ctx context.Context) (string, bool) { // ship a type-safe accessor with it
	id, ok := ctx.Value(traceIDKey{}).(string)
	return id, ok
}

// A method argument, not a struct field
type Server struct{ ctx context.Context }          // bad
func (s *Server) Handle(ctx context.Context) error // good
```

## Newer APIs worth knowing

The context package has quietly kept growing. In particular, not knowing why something was canceled got fixed in 1.20, and I'd been staring at meaningless `context canceled` logs without knowing it.

- `WithCancelCause`, `Cause` (1.20): attach a reason to a cancellation. Debugging gets much easier.
- `WithoutCancel` (1.21): detach work that must finish even after cancellation, like cleanup and audit logs.
- `AfterFunc` (1.21): run a function when the ctx ends, without starting your own goroutine to watch `Done()`.
- `WithTimeoutCause`, `WithDeadlineCause` (1.21): attach a reason to timeouts too, so you can tell which stage blew the budget.

```go title="cause/main.go"
ctx, cancel := context.WithCancelCause(parent)
cancel(fmt.Errorf("upstream returned repeated 5xx: %w", err)) // err is the last 502
fmt.Println(ctx.Err(), "|", context.Cause(ctx))

tctx, cancel2 := context.WithTimeoutCause(parent, 10*time.Millisecond,
	errors.New("inventory lookup blew its 10ms budget"))
defer cancel2()
<-tctx.Done()
fmt.Println(tctx.Err(), "|", context.Cause(tctx))
```

```text frame="terminal" title="Output"
$ go run ./cause
context canceled | upstream returned repeated 5xx: 502
context deadline exceeded | inventory lookup blew its 10ms budget
```

`Err()` is always either `context canceled` or `context deadline exceeded`, which was never much help. The information I actually needed lives in `Cause()`.

When any one of several tasks failing should cancel all of them, `errgroup` wraps the pattern for you.

```go title="errgroup: the first error cancels the rest"
g, gctx := errgroup.WithContext(ctx)
g.Go(func() error { return fetchUser(gctx) })
g.Go(func() error { return fetchOrders(gctx) })
if err := g.Wait(); err != nil { // the first error cancels gctx automatically
	return err
}
```

I ran it with `fetchUser` failing after 50ms and `fetchOrders` taking two seconds while watching `gctx.Done()`.

```text frame="terminal" title="Output"
$ go run ./group
fetchOrders: stopped after 50ms (context canceled)
Wait: fetchUser: 503, took 50ms
```

The two-second fetchOrders stopped at 50ms, and `Wait` returned the first error. Here too, what stopped was the receiver watching `gctx.Done()`.

To tell errors apart, use the approach from [part 3](/en/13). The cause may be wrapped, so use `errors.Is` instead of `==`.

```go title="Handling each cause differently"
if errors.Is(err, context.DeadlineExceeded) {
	return status(504) // timed out
}
if errors.Is(err, context.Canceled) {
	return // the client already left; no need to respond
}
```

Wrap `ctx.Err()` once with `%w` and `==` already returns `false`; only `errors.Is` still finds the cause.

```text frame="terminal" title="Output"
$ go run ./iswrap
inventory lookup: context deadline exceeded
err == context.DeadlineExceeded: false
errors.Is(err, context.DeadlineExceeded): true
```

## Lab setup and limits

I reran every example on this Mac (Apple M5, 10 cores, darwin/arm64) with Go 1.26.10. errgroup is `golang.org/x/sync` v0.23.0. Two things differ from the original post. When I actually ran `go vet`, the file paths in its output had no leading `./`, so I copied the real output. And the documentation sentence about how long a missed `cancel` leaks changed in Go 1.24: through 1.23 it said until the parent is canceled or the timer fires, and now it says until the parent is canceled. I updated the text to the current wording.

| What I checked | What it tells you | What it can't tell you |
| --- | --- | --- |
| The two loops and `cancel()` | That a loop that never checks runs to the end, and that `cancel()` doesn't wait | The microsecond figures on other machines |
| Sending a value vs. closing | 1 and 100 goroutines woken | Nothing more; the spec defines this behavior |
| Child deadline · chain budget | The time left within one process | Crossing processes with gRPC; I checked that only in the docs |
| HTTP request ctx | When the handler ctx is canceled after an HTTP/1.1 connection closes | The timing over HTTP/2 or through a proxy |
| 100,000 children with discarded cancels | The 11.5MB of heap held on this Mac | The byte counts on other versions or architectures |
| `WithoutCancel` · `Cause` · errgroup | What survives, the printed strings, when things stopped | Message formats in other versions |
| `string` keys · type assertion | That values get overwritten, and the panic message | Warnings from other linters such as staticcheck, which I didn't run |

## Summary

| What we saw | Why |
| --- | --- |
| The loop that ignores `Done()` processed all 10 items after cancellation | Cancellation is just a signal that closes a channel; it doesn't stop goroutines |
| `cancel()` returned within tens of microseconds | A `CancelFunc` doesn't wait for the work to stop |
| One value woke 1 goroutine; closing the channel woke 100 | A receive on a closed channel returns to every waiter at once |
| A child that asked for 10 seconds got the parent's deadline | A deadline can't be later than the parent's |
| When the client hung up, the handler ctx was canceled 200ms in | `net/http` cancels the request ctx when the connection closes |
| 100,000 children with discarded cancels held 11.5MB | The parent keeps references in its list of children |
| Cleanup with a canceled ctx failed at once | Cleanup is work for the same request, so it's canceled too |
| A value stored under `"id"` came back as another package's value | Basic-type keys collide across packages |

So: put `Done()` checks in long loops, write `defer cancel()` as soon as you create a context, detach cleanup with `WithoutCancel` plus a fresh timeout, and use unexported types for keys.
