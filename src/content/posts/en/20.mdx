<Lead>
Interfaces, slices, defer, embedding, context. Looking back after five posts, most of the pitfalls came from two places. One is that everything is copied. The other is object orientation without classes. This post groups the five posts under those two ideas and works through, with hands-on examples, how to decide whether to copy or share.

The route: the copy rule, how to measure size and cost, object orientation without classes, the four things that act while one function runs (defer, errors, closures, and context), and how to decide between copying and sharing. I reran every example on Go 1.26.10 and measured the benchmarks on both this Mac and a Linux lab server.
</Lead>

<Summary>
1. Go has one rule for passing values: everything is copied. What differs is whether the copied value is an array, a header, or a two-slot box, and copying a header doesn't separate the data it points to.
2. The other half is the type system. Attach methods to a type, satisfy an interface when the method set matches, and compose by putting one inside another (embedding). There's no inheritance, overriding, or abstract classes.
3. Decide whether to copy or share by ownership and lifetime, not size. Check a value's size with `Sizeof` and its runtime cost with benchmarks. The two numbers answer different questions.
</Summary>

## One rule: everything is copied

Let's pin this down first. Are maps passed by value or by reference? Go has no separate pass-by-reference mechanism. Whether you pass something to a function, assign it to a variable, or receive it as a method receiver, <mark>the value is copied.</mark> Pass a pointer and the pointer, a value, is what gets copied.

But what that copied value is differs by type. That splits values into three kinds, and half the pitfalls in this series come from here.

Byte counts assume a 64-bit platform and may vary by architecture and implementation. Treat the numbers as a reference. The three kinds are what to remember. The middle kind shares its contents even when copied, and the last kind has two slots, which is why nil checks defy intuition.

<Lab title="Copying a struct still changes its tags and map">

A struct is a value holding its fields, so assigning it copies each field's value. An integer field copies the integer; a slice field copies the slice header. Until I ran the code below, I also assumed that assigning a struct detached everything inside it, map included.

```go title="shallow/main.go"
package main

import "fmt"

type User struct {
	Name string
	Tags []string
	Meta map[string]string
}

func main() {
	original := User{
		Name: "Jaden",
		Tags: []string{"reader"},
		Meta: map[string]string{"team": "backend"},
	}

	shallow := original               // struct assignment: each field's value is copied
	shallow.Name = "Copy"             // replace the string field
	shallow.Tags[0] = "editor"        // write into the array the slice points to
	shallow.Meta["team"] = "platform" // write into the hash table the map points to

	fmt.Println("original:", original.Name, original.Tags, original.Meta)
	fmt.Println("copy    :", shallow.Name, shallow.Tags, shallow.Meta)

	isolated := original
	isolated.Tags = append([]string(nil), original.Tags...) // separate the array too
	isolated.Tags[0] = "admin"
	fmt.Println("original tags:", original.Tags)
	fmt.Println("isolated copy:", isolated.Tags)
	fmt.Println("map unchanged:", original.Meta, isolated.Meta)
}
```

```text frame="terminal" title="Output"
$ go run shallow/main.go
original: Jaden [editor] map[team:platform]
copy    : Copy [editor] map[team:platform]
original tags: [editor]
isolated copy: [admin]
map unchanged: map[team:platform] map[team:platform]
```

All three fields were copied and then modified, yet the results differ. `shallow.Name = "Copy"` just swaps a different string into the copy's field and leaves the original string's contents alone. `Tags[0]` and `Meta["team"]`, on the other hand, write into the data the headers point to, which both structs share, so the original sees it too.

The last two lines matter. `Tags` was copied into a new array, so it can now change independently, but <mark>`Meta` is still shared.</mark> Separating `Meta` as well takes a new map from `maps.Clone`.

```go title="clone/main.go · inside main, User as above"
original := User{Meta: map[string]string{"team": "backend"}}

isolated := original
isolated.Meta = maps.Clone(original.Meta) // a new hash table
isolated.Meta["team"] = "infra"
fmt.Println("original:", original.Meta)
fmt.Println("copy    :", isolated.Meta)
```

```text frame="terminal" title="Output"
$ go run clone/main.go
original: map[team:backend]
copy    : map[team:infra]
```

`maps.Clone` is itself a shallow copy that sets keys and values by ordinary assignment, so slice or map values share their contents again. There's no need to copy every field recursively; detach just the fields you'll change independently, like this.

</Lab>

## Measure size and cost separately

<Lab title="What Sizeof measures, and what it doesn't">

Having seen how far a copy reaches, let's look at the size of the value itself. `unsafe.Sizeof` returns only the storage size of the value itself. It doesn't add the array the value points to or the concrete value stored in an interface.

```go title="size/main.go"
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

func main() {
	var arr [1000]int
	sl := make([]int, 1000)
	var m map[string]int
	var s string
	var boxed any = arr

	fmt.Println(runtime.GOOS, runtime.GOARCH)
	fmt.Println("array        :", unsafe.Sizeof(arr))
	fmt.Println("slice        :", unsafe.Sizeof(sl))
	fmt.Println("map          :", unsafe.Sizeof(m))
	fmt.Println("string       :", unsafe.Sizeof(s))
	fmt.Println("interface    :", unsafe.Sizeof(boxed))

	sl = make([]int, 100_000) // 100x the elements
	fmt.Println("bigger slice :", unsafe.Sizeof(sl))
}
```

```text frame="terminal" title="Output · 64-bit platform"
$ go run size/main.go
darwin arm64
array        : 8000
slice        : 24
map          : 8
string       : 16
interface    : 16
bigger slice : 24
```

Growing the slice from 1,000 to 100,000 elements still gives 24. `Sizeof` measures only the slice header, so the 800,000-byte array behind it never shows up in this number. The interface holding an 8,000-byte array measuring 16 is the same story.

The bigger limitation is that this number isn't the bytes actually moved during a call, nor an execution time. The compiler can inline functions or eliminate unneeded copies, so cost has to be measured separately, in the next experiment.

</Lab>

| Metric | What it tells you | What it doesn't |
| --- | --- | --- |
| `unsafe.Sizeof` | storage size of the value itself | total memory including referenced data, actual runtime |
| `ns/op` | time per operation on the measured code path | whether it holds on another CPU, Go version, or optimization setting |
| `B/op` · `allocs/op` | heap bytes and allocations per operation | whether anything was copied, whether CPU cost was zero |

<Note title="Three numbers, three different questions">

A small `Sizeof` doesn't mean low memory use, and `0 allocs/op` doesn't mean nothing was copied.

</Note>

<Lab title="Passing cost depends on how you measure">

Let's measure passing the same 1,000 integers as an array versus as a slice or a pointer. All three functions read only the first element; only the passing style differs. `//go:noinline` is a compiler directive that keeps the compared functions from being merged into their call sites. You'll rarely put it in production code; here it keeps the comparison fair.

```go title="copy_test.go"
package main

import "testing"

var sink int

//go:noinline
func byArray(a [1000]int) int { return a[0] }

//go:noinline
func bySlice(a []int) int { return a[0] }

//go:noinline
func byPointer(a *[1000]int) int { return a[0] }

func BenchmarkArray(b *testing.B) {
	var a [1000]int
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		a[0] = i
		sink = byArray(a) // keep the result so the work isn't optimized away
	}
}

func BenchmarkSlice(b *testing.B) {
	var a [1000]int
	s := a[:]
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		a[0] = i
		sink = bySlice(s)
	}
}

func BenchmarkPointer(b *testing.B) {
	var a [1000]int
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		a[0] = i
		sink = byPointer(&a)
	}
}
```

```text frame="terminal" title="Output · Go 1.24 · linux/amd64, 2 cores"
$ go test main.go copy_test.go -run '^$' -bench . -benchmem -count=3
BenchmarkArray-2      7447418     159.6 ns/op    0 B/op    0 allocs/op
BenchmarkSlice-2    755760110     1.576 ns/op    0 B/op    0 allocs/op
BenchmarkPointer-2  566290033     2.171 ns/op    0 B/op    0 allocs/op
```

All three show `0 allocs/op`, yet the times differ a lot. From this table we can see right away that <mark>copying a value and allocating on the heap are separate costs</mark>. On this machine the pointer was slightly slower than the slice, but we can't conclude from this that pointers are always faster or always slower.

Now delete the three `//go:noinline` lines and run it again. One changed condition, and every number moves.

```text frame="terminal" title="Rerun without //go:noinline"
BenchmarkArray-2     19423303     62.87 ns/op    0 B/op    0 allocs/op
BenchmarkSlice-2   1000000000    0.6354 ns/op    0 B/op    0 allocs/op
BenchmarkPointer-2 1000000000    0.3176 ns/op    0 B/op    0 allocs/op
```

With inlining allowed, all three got faster and the pointer and slice swapped places. Passing the array is still noticeably slower, because merging the call still leaves 8,000 bytes to move. Dumping the assembly with `-gcflags=-S` on this Mac confirmed it: even inlined, `BenchmarkArray` keeps a loop on the `sink = byArray(a)` line (line 18 once the three lines are gone) that moves 8,000 bytes in 125 passes of 64 bytes.

```text frame="terminal" title="Inlined BenchmarkArray · darwin/arm64 (addresses and paths trimmed)"
$ go test -c -o /dev/null -gcflags=-S main.go copy_test.go
copy_test.go:18  MOVD     $125, R24
copy_test.go:18  FLDPQ.P  32(R3), (F16, F17)
copy_test.go:18  FSTPQ.P  (F16, F17), 32(R2)
copy_test.go:18  FLDPQ.P  32(R3), (F16, F17)
copy_test.go:18  FSTPQ.P  (F16, F17), 32(R2)
copy_test.go:18  SUB      $1, R24
copy_test.go:18  CBNZ     R24, 120
```

`FLDPQ.P` and `FSTPQ.P` load and store 32 bytes, twice per pass, until `R24` counts down from 125 to 0.

I reran the same code on Go 1.26.10, on this Mac (Apple M5, darwin/arm64) and on a Linux lab server (4-core Xeon VM, linux/amd64), under three conditions. The first two are the ones above, inlining blocked and inlining allowed, and the third rewrites the loop with `b.Loop`, added in Go 1.24. `b.Loop` keeps the arguments and results of calls in the loop alive, so `sink` isn't needed, and the testing package docs recommend it for new benchmarks.

```go title="copy_test.go · the array side rewritten with b.Loop (the other two match; inlining allowed)"
func BenchmarkArray(b *testing.B) {
	var a [1000]int
	for b.Loop() {
		byArray(a) // b.Loop keeps the result alive
	}
}
```

Times are ns/op, the median of three runs. Every run was `0 B/op` and `0 allocs/op`.

| Condition | Machine | Array | Slice | Pointer |
| --- | --- | --- | --- | --- |
| `//go:noinline` | Mac | 119 | 1.15 | 0.53 |
| `//go:noinline` | Linux | 242 | 2.70 | 2.21 |
| Inlined | Mac | 111 | 0.23 | 0.23 |
| Inlined | Linux | 93.5 | 0.49 | 0.44 |
| `b.Loop` | Mac | 74.8 | 1.55 | 1.54 |
| `b.Loop` | Linux | 93.9 | 1.99 | 2.00 |

Order and ratios depend on the environment. On Linux with Go 1.26.10, blocking inlining made the pointer faster than the slice, the reverse of the original Go 1.24 run. With inlining allowed the two came out nearly equal on both machines, and under `b.Loop` both sat at 1.5–2 ns. What held across all six combinations is that passing the array was more than an order of magnitude slower and nothing was allocated on the heap.

</Lab>

The two runs measure different things. Blocking inlining makes the copy cost show up in the numbers, while default optimization is closer to a real call path.

Note too that this benchmark can't measure memory copying on its own. It also measures updating the first element in the loop and the call and return. So I don't fix any particular ratio as the takeaway. What held across every run above is that passing an array by value costs in proportion to its size, and that cost never shows up in `allocs/op`.

Here's the question each step raises, with a one-line answer.

- Why put interfaces on the consuming side? When the package that uses the interface declares only the methods it needs, the interface is small and swapping implementations or testing gets easier. Consumer-side interfaces are possible in other languages too, though. What Go's implicit satisfaction removes is the need for the implementation to declare or `import` that interface. ([part 1](/en/11))
- Why isn't embedding inheritance? An embedded type doesn't know about the type wrapping it. So there's no overriding, and the template method pattern, where a parent calls a child's implementation, doesn't work. When you need polymorphism, inject an interface and flip the direction. ([part 4](/en/14))
- When to use generics? If you care about what a value can do, use an interface; if only the type differs and the logic is the same, use generics. Introducing them once you've actually copy-pasted the same function two or three times is the safe bet. ([part 4](/en/14))

<Note title="Is Go object-oriented?">

Partly. Identifier case handles encapsulation, interfaces handle abstraction and polymorphism, and only inheritance is missing. "It does object orientation with interfaces and composition instead of class-based inheritance" is the accurate answer.

</Note>

- `defer`: arguments are evaluated at registration. `defer f(i)` uses `i` as it was then; if you need the value at run time, wrap it in a closure.
- `error`: you return it as a value instead of throwing it. Wrapping with `%w` lets callers identify the cause with `errors.Is/As`, but it also makes the inner error, in effect, part of your public API. Where to stop wrapping is a decision you make at design time.
- Closures: capturing the outer variable itself makes them stateful functions, at the cost that captured variables may move to the heap. The shared loop variable bug was fixed at the language level in Go 1.22 (when the `go` version in `go.mod` is 1.22 or later).
- `context`: after you cancel, the receiver still has to check `Done()` before it stops. Detach cleanup from the cancellation signal with `WithoutCancel`.

<Lab title="A pure function preserves its input, not just its result">

The copy rule applies just as directly when we design a function. A function that returns the same result for the same input and doesn't touch outside state is called pure, and keeping that promise in Go means watching how far copies reach, as we just saw. If the input is a slice, merely intending not to modify it isn't enough.

```go title="main.go · a rule extracted as a pure function"
package main

import (
	"fmt"
	"strings"
)

// Builds a new result without changing the input.
func Normalize(names []string) []string {
	out := make([]string, 0, len(names))
	for _, s := range names {
		if t := strings.TrimSpace(s); t != "" {
			out = append(out, t)
		}
	}
	return out
}

func main() {
	fmt.Println(Normalize([]string{" Go ", "", " Rust "}))
}
```

```go title="main_test.go · checking the result and that the input is preserved"
package main

import (
	"reflect"
	"testing"
)

func TestNormalizePreservesInput(t *testing.T) {
	cases := []struct {
		name  string
		input []string
		want  []string
	}{
		{"trim and drop", []string{" Go ", "", " Rust "}, []string{"Go", "Rust"}},
		{"blanks only", []string{" ", "\t"}, []string{}},
		{"nil input", nil, []string{}},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			before := append([]string(nil), tc.input...)
			got := Normalize(tc.input)
			if !reflect.DeepEqual(got, tc.want) {
				t.Fatalf("got=%v, want=%v", got, tc.want)
			}
			if len(got) > 0 {
				got[0] = "changed result only" // modify the return value
			}
			if !reflect.DeepEqual(tc.input, before) {
				t.Fatalf("input was modified: %v", tc.input) // the input must stay as it was
			}
		})
	}
}
```

## Decide copy versus share by ownership and lifetime

So how do you decide between passing a value and a pointer? <mark>Ownership and lifetime, not size.</mark> If a function only reads during the call, sharing may be enough. If it keeps the data after returning or needs to modify it independently, it may need a copy. Write that promise into the function's name, comments, and input and output types. `Normalize` above says in its comment that it doesn't change its input.

That doesn't mean picking functional over object-oriented programming. What separates the two is where state lives. Object orientation bundles state and behavior inside objects and solves problems by having objects cooperate. Functional programming composes immutable data and pure functions. Go borrows a little from each: it attaches methods to types, treats functions as first-class values, and doesn't enforce immutability. So in practice, domain state lives in types and methods, and only the computations that can be explained on their own get pulled out into functions.

Seen this way, it's also clear why design patterns take the shapes they do in Go. Without inheritance or classes, heavy patterns turn into light compositions.

| Pattern | Shape in Go | Tools |
| --- | --- | --- |
| Strategy | pull the varying part into an injected interface | interfaces |
| Decorator | middleware that wraps a handler and returns it | closures + first-class functions |
| Singleton | `sync.OnceValue` | standard library |
| Builder | functional options (`WithTimeout`) | closures + variadic args |

Half of the right column is closures and first-class functions. That's where functional style actually shows up in Go: middleware chains, functional options, and, since generics, `Map` and `Filter`.

Finally, the same lens separates a library from a framework. The test is who calls whom: you call a library; a framework calls your code. `net/http` is a nice example of both. `Client` is a library you call; `Server` defines an interface called `Handler` and calls your code, framework-style. Here too, the interface is defined on the calling side.

<Note title="Two questions that tie it together">

If I pass this value, what gets copied, and who can touch that data afterward? Those two questions tie together append side effects, the value-receiver trap, the nil-interface trap, and a pure function's input preservation. Copying has a cost too, so if it really is a bottleneck, measure it with the methods above and then change the ownership promise to copy less.

</Note>

## Summary: five posts were saying the same thing

- Part 1, interfaces: the type and value slots get copied together. A filled type slot means not nil, and method sets differ between values and pointers.
- Part 2, slices, maps, strings: only the header gets copied, so passing is cheap, but the data inside is shared and a write on one side shows on the other.
- Part 3, defer, errors, closures: defer arguments are evaluated at registration, and closures hold the variable itself. Wrapping an error with `%w` makes it part of your public contract.
- Part 4, embedding: promotion only shortens names, so the embedded type's methods can't call the outer type's methods.
- Part 5, context: if the receiver never checks `Done()`, cancelling doesn't stop it.
- This post: decide how far to copy by ownership and lifetime, then measure size with `Sizeof` and cost with benchmarks.

### Wrapping up the series

While writing the five posts, I thought of them as separate topics, but folded onto one page, they came down to one idea. Go doesn't hide how things really work for the sake of convenience. A slice being a window, an interface having two slots, embedding being an anonymous field: these are structures the language puts in plain view. Most of the pitfalls came from laying intuitions picked up in other languages over those structures.

So this series had one method: go down to the level of structure to check what something really is, and see whether that single fact explains the remaining pitfalls. Writing this post added one more: <mark>when you look at a number, also write down the questions it doesn't answer.</mark>
