<Lead>
I knew about the bug where you return a nil pointer and `err != nil` comes out true. What I couldn't do was explain why it isn't nil. Tracing it, the cause turned out to be that an interface value has two slots, a type and the data. When you put a nil pointer into an `error`, the data slot is empty but the type slot gets filled.

The fix is to return a nil of type `error` directly on the success path. This post first reproduces the bug in code, then walks through the two-slot layout, method sets, where interfaces should be defined, and what calling through an interface costs. I reran the examples on Go 1.26.10.
</Lead>

<Summary>
1. Putting a nil pointer into an `error` fills the type slot, so `err == nil` is false. On the success path, return a literal `nil`.
2. An interface value is two words, (type, data). Boxing allocations and the cost of dynamic dispatch come from the same layout.
3. Pointer-receiver methods aren't in a value's method set because the value inside an interface is a copy, so changing it never reaches the original.
</Summary>

## You returned a nil pointer, so why is err != nil?

An interface value has two slots: a type slot and a value slot. The next section covers the layout in detail; for now, just remember there are two. The comparison `err == nil` checks <mark>whether both slots are empty</mark>. If the value slot is nil but the type slot is filled, the interface isn't nil.

```go title="nilerr/main.go"
type MyErr struct{ Code int }

func (e *MyErr) Error() string { return "my error" }

func validate(v int) *MyErr {
	if v > 0 {
		return nil // a real nil pointer here
	}
	return &MyErr{Code: 400}
}

func handle(v int) error {
	return validate(v) // *MyErr(nil) goes into an error, filling the type slot
}

func main() {
	err := handle(10)
	fmt.Println(err == nil)
	fmt.Println(err)
	fmt.Printf("%T %v\n", err, err.(*MyErr) == nil)
}
```

```text frame="terminal" title="Output"
$ go run ./nilerr
false
my error
*main.MyErr true
```

There's no error, yet it's treated as one. The third line shows what's inside the interface: a nil pointer of type `*MyErr`. Because `Error()` returns a string without reading any field of its receiver, it can be called on a nil pointer, so the printed message gave no hint that the interface wasn't nil.

The compiler doesn't stop this because the assignment is legal. `*MyErr` satisfies `error`, and a nil pointer is a valid value of that type. Static analysis does catch it, though. I ran the same code through staticcheck.

```text frame="terminal" title="staticcheck (bundled with golangci-lint 2.1.2)"
$ golangci-lint run --default=none --enable=staticcheck
main.go:16:6: SA4023(related information): lint.handle never returns a nil interface value (staticcheck)
main.go:21:9: SA4023(related information): the lhs of the comparison is the 1st return value of this function call (staticcheck)
main.go:22:14: SA4023: this comparison is never true (staticcheck)
```

staticcheck followed `handle` far enough to see that it can never return a nil interface, and flagged that the comparison can never be true. There are two fixes. Make the helper return `error` in the first place, or on the success path return a literal nil instead of the variable.

```go title="Return a literal nil on success"
func handle(v int) error {
	if e := validate(v); e != nil {
		return e
	}
	return nil
}
```

Return values aren't the only place this happens. Store a nil pointer in a field of type `error` and it blows up the same way later. Anywhere the static type is an interface, the type slot gets filled along with it.

## An interface value is two words

From here on it's about the runtime. An interface variable isn't a box holding the concrete value. It's a struct of two pointers; measure it with `unsafe.Sizeof` and it comes to 16 bytes on a 64-bit machine.

Here are the definitions from the Go 1.26.10 runtime source. An interface with methods keeps an itab pointer in its type slot, while a method-less interface like `any` keeps only the type information.

```go title="runtime/runtime2.go · internal/abi/iface.go (Go 1.26.10)"
// Interfaces with methods (io.Reader, error, ...)
type iface struct {
	tab  *itab          // type slot: concrete type + method table
	data unsafe.Pointer // value slot
}

// Interfaces without methods (any, interface{})
type eface struct {
	_type *_type // no method table needed, just the type
	data  unsafe.Pointer
}

type ITab struct { // the runtime's itab
	Inter *InterfaceType // which interface
	Type  *Type          // which concrete type
	Hash  uint32         // hash used by type switches
	Fun   [1]uintptr     // variable length: method function pointers
}
```

Most itabs are baked into the binary by the compiler. Only when the pair can't be known at compile time, for example when an interface value is asserted to another interface, does the runtime build one and cache it in `itabTable`.

`Fun` is a table fixed to one concrete type. In Java, an object carries its class's vtable around. In Go, the interface value carries the itab. So the same value gets a different itab when stored as an `io.Reader` than when stored as an `io.Writer`.

To check whether the type slot really gets filled, I looked inside the interface with `unsafe`, reinterpreting the interface value as a two-word struct of the same size.

```go title="dump/main.go"
	i := (*iface)(unsafe.Pointer(&err))
	fmt.Printf("%-10s tab=%p data=%p  nil? %v\n", label, i.tab, i.data, err == nil)

func words(label string, p unsafe.Pointer) {
	i := (*iface)(p)
	fmt.Printf("%-10s tab=%p data=%p\n", label, i.tab, i.data)

	var p *MyErr
	dump("① nil", nilIface)
	dump("② nil ptr", p)

	dump("④ value", &MyErr{Code: 1})

	words("Writer", unsafe.Pointer(&w))
	fmt.Printf("%-10s ptr=%p\n", "os.Stdout", os.Stdout)
}
```

## Method sets: the call works, the assignment doesn't

This was the confusion I ran into most in Go. `d.Inc()` works fine, but `var i Incer = d` won't compile. Same method.

Start with what a method really is. A Go method is a function whose first argument moved to the front. `func (c Counter) Show()` is essentially `func Show(c Counter)`. So, like every other value passed in Go, the receiver is copied. A value receiver gets a copy, and a pointer receiver gets an address.

```go title="mset/run/main.go"
type Incer interface{ Inc() }

func main() {
	d := Counter{}
	d.BadInc()
	fmt.Println(d.n)
	d.Inc() // becomes (&d).Inc()
	fmt.Println(d.n)
	var a Incer = &d
	a.Inc()
	fmt.Println(d.n)
}
```

`BadInc` increments a copy, so `d.n` stays 0, while `Inc` gets `&d` and takes it to 1, then 2. Yet putting the same `d` straight into an `Incer` doesn't compile.

The spec's rules fit in three lines.

- The method set of `T` is the methods with receiver `T`.
- The method set of `*T` is the methods with receiver `T` or `*T`, both.
- Embedding promotes methods, and the receiver kind comes along. If `Outer` embeds `Inner` by value and `Inner`'s methods have pointer receivers, only `*Outer` satisfies the interface. Embed `*Inner` instead and an `Outer` value satisfies it too.

### Why only the assignment is rejected

This took me the longest while writing. If the compiler rewrites `d.Inc()` to `(&d).Inc()` for you, I wondered, why not do the same for an interface assignment?

The Go FAQ's answer lies in what an interface holds. When you store `d` in an interface, the value slot gets a copy of `d`. If `var i Incer = d` were allowed, `i.Inc()` would increment the copy inside the interface and leave `d` untouched. The change would never reach the caller, so the language rejects the assignment up front.

### Values without an address

The automatic `&` on method calls has a condition too. The spec reads `x.m()` as `(&x).m()` only when `x` is addressable. The variable `d` has an address, so `d.Inc()` compiles and the change stays in `d`. Here is what the spec counts as addressable.

<Compare>
<Side title="Addressable" tone="good">

- Variables
- Pointer dereferences `*p`
- Slice indexing `s[i]`
- Fields of an addressable struct, elements of an addressable array

</Side>
<Side title="Not addressable" tone="bad">

- Map elements `m[k]`
- Function results `f()`
- String indexing `s[i]`
- Constants, composite literals `Counter{}`

</Side>
</Compare>

Map elements are the classic case, and the reason is the data structure. As a map grows, it moves entries to new places. If you handed out an address and the map later moved the entry while growing, that address would point at the wrong thing.

A composite literal like `Counter{}` has no address either, which is why the third line fails the same way (`&Counter{}` is an exception the spec carves out). To call a pointer method on a map element, either take it out, change it, and put it back, or store pointers from the start.

```go title="mset/mapfix/main.go"
// take it out, change it, put it back
tmp := m["a"]
tmp.Inc()
m["a"] = tmp

// store pointers from the start (large elements or frequent updates)
mp := map[string]*Counter{"a": {}}
mp["a"].Inc() // the map already holds an address
```

### Choosing a value or pointer receiver

Once the theory is clear, the choice is simple. The Go FAQ treats choosing a receiver as the same question as choosing whether a function argument should be a value or a pointer.

| Situation | Choice and why |
| --- | --- |
| You modify fields | Pointer. A value receiver only changes the copy |
| The struct is large | Pointer. Every call copies the whole thing |
| It contains `sync.Mutex` or `sync.WaitGroup` | Always pointer. A copied lock doesn't synchronize anything |
| A small, immutable value type | Value. Only where copying is natural, like times or coordinates |
| Within one type | Be consistent. Mixing splits the method sets and muddles which interfaces it satisfies |

The third row hurts most in practice. Take a `sync.Mutex` through a value receiver and the lock itself is copied, so each call locks a different lock. The code runs, the tests pass, and nothing is actually synchronized: the most miserable kind of bug to find. Fortunately, `go vet` catches this one.

```go title="vet/main.go"
type Safe struct {
	mu sync.Mutex
	n  int
}

func (s Safe) Bad()   { s.mu.Lock(); defer s.mu.Unlock(); s.n++ } // copies the lock and n
func (s *Safe) Good() { s.mu.Lock(); defer s.mu.Unlock(); s.n++ } // locks the original
```

```text frame="terminal" title="go vet"
$ go vet ./vet
vet/main.go:10:9: Bad passes lock by value: lab/vet.Safe contains sync.Mutex
```

One more in the same vein. A value-receiver method that modifies fields shows no race even when many goroutines call it. I had 8 goroutines call `BadInc` 1,000 times each and ran it with `-race`; it printed `n = 0` without any race report. Each goroutine only touches its own copy, so nothing ever writes to the original, and the original is never updated. Instead of a race you get a silent no-op, which tends to be found later.

## Interfaces belong to the user

In Java, to use an interface the implementation has to declare `implements Saver`. Declaring it means importing that interface, which means the implementation has to know about the contract. This is called nominal typing: types are the same only if their names are.

Go is the opposite. If the method signatures match, the interface is satisfied automatically, with no declaration. That's structural typing: types are the same if their shapes are. The difference changes which way dependencies point between packages.

The two halves differ by a single arrow. In practice, that arrow shows up like this.

| What follows | What it means |
| --- | --- |
| Retroactive | A type in someone else's published package satisfies the interface you just defined |
| Small interfaces | The user defines it, so it lists only the methods it needs |
| Easy mocks | A three-line struct in the test file is enough |
| Light implementations | No imports exist just for interfaces |

```go title="The contract lives in the consumer package"
// Consumer package: all it needs is the ability to save
type Saver interface{ Save(v string) error }

func Run(s Saver) error { return s.Save("data") }

// Provider package: knows nothing about Saver, no import
type FileStore struct{ dir string }

func (f *FileStore) Save(v string) error { /* ... */ return nil }
func (f *FileStore) Open(p string) error { /* unrelated to Saver */ return nil }

// Test: a mock in three lines
type mockStore struct{ got string }

func (m *mockStore) Save(v string) error { m.got = v; return nil }
```

Go's code review guide says the same thing.

> Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values.

[Go Code Review Comments · Interfaces](https://go.dev/wiki/CodeReviewComments#interfaces)

If you habitually put `type Store interface` inside the `store` package, you end up rebuilding Java's dependency structure in Go. The same page adds that implementing packages should return concrete types, so that new methods can be added to implementations without extensive refactoring. It's the same idea as the idiom people shorten to "Accept interfaces, return structs." The nil trap from section 1 was one more reason for me to return concrete types: return an interface and that trap comes along.

### Keep them small

The Go Proverbs include "The bigger the interface, the weaker the abstraction." At first I took it as a matter of taste, but after seeing the dependency structure above, the question "why include methods I don't use?" came up on its own once the consumer was the one defining the interface.

| | Large interface (12 methods) | Small interface (1–2) |
| --- | --- | --- |
| Cost to implement | All 12 to satisfy it | Only what's needed |
| Test mocks | Stubs for methods you don't use | Three lines |
| Blast radius of a change | Add one method and every implementation and mock breaks | Only that consumer |
| What the signature says | "I need this giant thing" | "I only read" |

The standard library shows the conclusion directly. `io.Reader`, `io.Writer`, and `io.Closer` each have one method. When you need a combination, you compose with interface embedding instead of building a big new interface.

```go title="The standard library's way: snap small ones together"
type Reader interface{ Read(p []byte) (n int, err error) }
type Writer interface{ Write(p []byte) (n int, err error) }
type ReadWriter interface{ Reader; Writer } // composed by embedding
```

### Where to put a satisfaction assertion

Implicit implementation isn't free. The first cost is that nothing in the code tells you which interfaces a type satisfies. In Java you read the class declaration; in Go you search the whole project. That's where the experience of deleting one method during a refactor and breaking some distant package comes from.

The second cost is accidental satisfaction. If the name and signature match, a type satisfies an interface even when the intent is completely different. The compiler can't tell a `Close()` that flushes a cache from a `Close()` that drops a connection.

The idiomatic remedy for the first cost is this one line. It's everywhere, but the first time I saw it I had no idea what it did.

```go title="Interface satisfaction assertion"
var _ Saver = (*FileStore)(nil)

// How to read it:
//   (*FileStore)(nil)  a nil pointer of type *FileStore (no value needed)
//   var _ Saver = ...  try assigning it to Saver; compile error if it can't
//   assigned to _      leaves no variable and costs nothing at run time
```

<Lab title="Where you put the assertion changes where the error appears and what gets imported">

To see what this line prevents, I deliberately misspelled the implementation's method as `Sava`. The module has three packages: the consumer `app`, the implementation `store`, and `cmd/server`, which wires them together.

```go title="store/store.go: Save misspelled as Sava"
func (f *FileStore) Sava(v string) error { return nil }
```

Without an assertion, `store` builds fine and the error shows up in `main`, where the two are wired together.

```text frame="terminal" title="Without an assertion"
$ go build ./...
# shop/cmd/server
cmd/server/main.go:9:14: cannot use &store.FileStore{} (value of type *store.FileStore) as app.Saver value in argument to app.Run: *store.FileStore does not implement app.Saver (missing method Save)
```

Put the assertion inside the `store` package (`store/assert.go`) and the error appears in `store` right away. The catch is that `store` now has to import `app`. The arrow we removed in Figure 6 comes back.

```text frame="terminal" title="Inside store"
$ go build ./store
# shop/store
store/assert.go:5:19: cannot use (*FileStore)(nil) (value of type *FileStore) as app.Saver value in variable declaration: *FileStore does not implement app.Saver (missing method Save)
$ go list -deps ./store | grep shop
shop/app
shop/store
```

Put it in the external test package (`store_test`) instead and `go build` passes while `go vet` and `go test` catch it. Since the import belongs to a test file, `app` stayed out of the dependency list of `store`.

```text frame="terminal" title="In store_test.go"
$ go build ./store && go vet ./store
vet: store/store_test.go:8:19: cannot use (*store.FileStore)(nil) (value of type *store.FileStore) as app.Saver value in variable declaration: *store.FileStore does not implement app.Saver (missing method Save)
$ go list -deps ./store | grep shop
shop/store
```

| Assertion in | Error shows up in | store imports |
| --- | --- | --- |
| Nowhere | `cmd/server` | nothing |
| `store/assert.go` | `store` | `app` |
| `store/store_test.go` | `go vet`, `go test` | nothing |

</Lab>

So an assertion on the implementation side fits best for contracts the implementation already knows about, like `io.Writer` or `http.Handler`. For an interface the consumer defined, the wiring code catches a mismatch at compile time anyway, so I'd only add one in an external test when I want to know right away while editing the implementation.

## What calling through an interface costs

Finally, I measured how the two-word layout shows up in performance, to know what an interface costs on a hot path.

| Cost | What it means |
| --- | --- |
| Indirect call | Read `itab.Fun[n]` and jump. When I [summed the areas of 1,000 rectangles](/en/8), each element took 0.28 ns with a concrete type and 1.77 ns through an interface |
| Blocked inlining | Without knowing the target, the compiler can't inline, and the escape analysis, constant propagation, and bounds-check elimination that would follow are blocked too. This can cost more than the call itself |
| Boxing | When an interface holding a non-pointer value escapes the function, the value is copied to the heap (`runtime.convT*`). Integers 0–255 point into a static table in the runtime and don't allocate |
| Remedies | When the compiler can figure out the concrete type, it turns the call into a direct one (devirtualization). Since Go 1.21, PGO rewrites calls to the type the profile saw most often |

<Lab title="Some values allocate just by going into an interface">

I benchmarked storing values into a package-level `sink any`, which is a case where the stored value escapes the function.

```go title="box/box_test.go"
type Point struct{ X, Y int }

var sink any
var n7, n1000 = 7, 1000

func BenchmarkInt7(b *testing.B) {
	for b.Loop() {

	}
}
func BenchmarkInt1000(b *testing.B) {
	for b.Loop() {
		sink = n1000
	}
}
func BenchmarkPoint(b *testing.B) {
	for b.Loop() {
		sink = Point{n7, n1000}
	}
}
func BenchmarkPtr(b *testing.B) {

		sink = p
	}
}
```

```text frame="terminal" title="Output"
$ go test -run x -bench . -benchmem ./box
BenchmarkInt7-10       	712599123	         1.708 ns/op	       0 B/op	       0 allocs/op
BenchmarkInt1000-10    	236220782	         5.130 ns/op	       8 B/op	       1 allocs/op
```

The pointer and the 7 didn't allocate, while 1000 allocated 8 bytes per call and `Point` 16 bytes. When the interface stays inside one function, the compiler can see more. I used `-m` to see whether the compiler figures out the concrete type.

```go title="devirt/shape.go"
type Shape interface{ Area() float64 }

type Rect struct{ W, H float64 }

func (r Rect) Area() float64 { return r.W * r.H }

type Circle struct{ R float64 }

func (c Circle) Area() float64 { return 3.14159 * c.R * c.R }

// the concrete type is visible inside the function
func One() float64 {
	var s Shape = Rect{2, 3}
	return s.Area()
}

// the concrete type comes in from outside
func Total(ss []Shape) float64 {
	var t float64
	for _, s := range ss {
		t += s.Area()
	}
	return t
}
```

```text frame="terminal" title="go build -gcflags=-m (excerpt)"
$ go build -gcflags=-m ./devirt
devirt/shape.go:16:15: devirtualizing s.Area to Rect
devirt/shape.go:16:15: inlining call to Rect.Area
devirt/shape.go:15:20: Rect{...} does not escape
```

In `One`, where the concrete type is visible, the call became a direct call and `Rect.Area` was inlined. The `Rect{...}` stored in the interface didn't go to the heap either. The compiler says nothing about `s.Area()` in `Total`, where the shapes come in through a slice. That call still goes through the itab.

Next I checked whether PGO changes `Total`. I took a CPU profile of a benchmark that sums 1,000 shapes, nine `Rect`s for every `Circle`, and rebuilt with that profile. While `Area` was a single multiplication, it barely showed up in the profile, and the compiler declined with `no hot callee`. So I put 16 divisions inside `Area` to make it show up and tried again.

```text frame="terminal" title="PGO build (-gcflags=-m excerpt)"
$ go test -pgo=cpu.pprof -gcflags=-m -run x -bench XXX ./pgo
pgo/shape.go:29:14: PGO devirtualizing interface call s.Area to Rect.Area
pgo/shape.go:29:14: inlining call to Rect.Area
```

The call was rewritten to `Rect.Area` and inlined, yet the median of six benchmark runs was 6.00 µs without PGO and 5.99 µs with it. In this example the 16 divisions per element take most of the time, so whatever the indirect call cost seems to vanish into measurement noise. The Go 1.21 release notes put the gain from PGO at 2–7% for a representative set of programs.

</Lab>

<Note title="Wouldn't generics be faster?">
In [my measurements for the static typing post](/en/8), generics over a value type took 0.73 ns per element, faster than the interface at 1.77 ns. That doesn't mean the Go team recommends generics over interfaces. The Go blog's "When To Use Generics" says that if all you do with a value is call a method on it, you should use an interface type, not a type parameter, and that a type parameter will generally not be faster than an interface. That earlier result came from a specific shape: a value type with a tiny method.
</Note>

Code where nanoseconds matter is a small part of the whole, and `pprof` tells you which part. Avoid interfaces from the start and you lose the seam where a test would plug in a mock.

## Wrap-up

| What we saw | Why |
| --- | --- |
| `err == nil` is false | Storing a nil pointer fills the type slot |
| `var b Incer = d` won't compile | The value inside an interface is a copy |
| `m["a"].Inc()` won't compile | Map elements aren't addressable |
| `store` imports `app` | The assertion went into the implementation package |
| 8 bytes allocated per `sink = n1000` | A non-pointer value escaped the function |

What I newly learned while putting this together was that the nil trap, method sets, and boxing allocations all come from the same two slots. When something is confusing, start by asking what goes into the two slots that make `unsafe.Sizeof` return 16. Corrections are welcome.
