<Lead>
When I listed the Go bugs I run into most, all three had the same shape: what I thought I was holding wasn't what I was actually holding. A slice is a window, not data. A map doesn't guarantee addresses. A string isn't a character array. So I opened up the layout of each one.

The short answer to the title is that a slice is a window onto the original array, and when cap has room, append writes straight into that array instead of making a new one. This post starts from the slice header and moves through passing slices to functions, append, memory leaks, maps, and strings. I reran every example on Go 1.26.10.
</Lead>

<Summary>
1. A slice is a three-word window, `{ptr, len, cap}`, onto a backing array. append side effects, aliasing, and memory leaks all follow from that one sentence.
2. A map's two unfriendly traits, random iteration order and instant death on concurrent writes, aren't bugs. Both come from the same choice of failing fast over silent corruption.
3. A string is an immutable bundle of UTF-8 bytes. `len`, indexing, and concatenation all defy the "array of characters" intuition.
</Summary>

## Arrays and slices: a value or a window

Go arrays aren't like arrays in other languages. They're value types, and the length is part of the type. `[5]int` and `[4]int` are different types, so you can't pass one where the other is expected. Assigning an array copies every element.

So in practice you rarely use arrays directly. You use slices instead, and a slice doesn't hold data. It's <mark>a window onto part of a backing array</mark>. The whole window is one pointer and two integers: a three-word header.

`b := a[1:3]` looks at two cells starting from [1], so its len is 2, and cap runs from the starting cell to the end of the array, so it is 4. Measuring variable sizes with `unsafe.Sizeof` puts the difference between arrays and slices in numbers.

```go title="sizes/main.go"
var arr [5]int
var s []int
var str string
var m map[string]int
fmt.Println("[5]int:", unsafe.Sizeof(arr))
fmt.Println("[]int:", unsafe.Sizeof(s))
fmt.Println("string:", unsafe.Sizeof(str))
fmt.Println("map:", unsafe.Sizeof(m))
```

```text frame="terminal" title="Output"
$ go run ./sizes
[5]int: 40
[]int: 24
string: 16
map: 8
```

The array takes 40 bytes for its five elements, while a slice is 24 bytes no matter how many elements it has. A string is two words, pointer and length, so 16 bytes, and a map variable is a single pointer, so 8 bytes.

### Two things that tripped me up

Even after drawing that picture, I spent a long time confused. Looking back, I had two questions, and both came from the wrong mental model that a slice is an upgraded array.

**① Is a slice just a `[4]int` with len and cap attached?** No. It's closer to the opposite. Arrays and slices are completely different types, and a slice isn't an array with extra fields. It's a separate little struct that points at an array. An array is the data itself; a slice is more like a note saying where to find the data.

```go title="An array variable and a slice variable"
// array: the variable is the data. There's no pointer involved
var arr [4]int = [4]int{1, 2, 3, 4} // arr is the memory for 4 ints itself

// one slice literal actually creates two things
s := []int{1, 2, 3, 4}
//  ① an underlying array somewhere holding {1,2,3,4}
//  ② in s, a {ptr, len, cap} header pointing at that array
```

It's true that there's always an array behind a slice. Even without an array literal, as in `make([]int, 4)`, an array gets created inside. You just don't see it, and the slice still isn't an extension of it.

**② So is the array the `ptr`?** The array isn't ptr; it's what ptr points to. That sounds subtle, but miss it and the memory leak later on won't make sense.

<Note title="ptr versus the array">

The `ptr` in the header isn't the array. It's an 8-byte field holding the array's starting address. The array is a separate block of memory that actually lives at that address, and it's a single allocation unit. In C terms, `ptr` is an `int*` and the array is the `int[N]` it points to. You can make as many headers as you like, but there's one array. Once that clicked, the aliasing and leaks below made sense all at once.

</Note>

## Passing to a function: by value or by reference?

This comes up in interviews a lot, and answering with just one of the two is half wrong. To be precise, <mark>the header is copied by value, and the data is shared.</mark> That produces an asymmetry.

```go title="pass/main.go"
func modify(s []int) {
	s[0] = 99        // visible: same backing array
	s = append(s, 4) // not visible: only the copied header's len changes
}

// so a function that appends returns the slice
func appendTo(s []int, v int) []int { return append(s, v) }

func main() {
	s := make([]int, 3, 4)
	modify(s)
	fmt.Println(s, len(s))
	fmt.Println(s[:4]) // stretch len out to cap and look
	s = appendTo(s, 5)
	fmt.Println(s, len(s))
}
```

```text frame="terminal" title="Output"
$ go run ./pass
[99 0 0] 3
[99 0 0 4]
[99 0 0 5] 4
```

The first line is that asymmetry. The element write shows up because it's the same array, while the len of 4 that append set stayed in the copied header inside the function. The second line stretches the same `s` out to its cap of 4, and the 4 that append wrote had not vanished at all; it was sitting in slot [3] of the array. The caller just couldn't see it because its len was 3. That's also why `appendTo` overwrote the same slot with 5 on the third line.

Having `append` return its result looked awkward to me, but with the header being a value type, there was no other option. It's also why `strings.Builder` and `bytes.Buffer` are designed with pointer-receiver methods. Maps are different. As measured above, a map variable is a single pointer, so entries added inside a function show up for the caller too.

## The two paths of append: clobbering the original or breaking the link

Here's the real story behind "sometimes append changes the original and sometimes it doesn't." `append` does two completely different things depending on <mark>whether cap has room</mark>. And you can't tell which from the code alone.

```go title="appendx/main.go"
a := []int{1, 2, 3, 4, 5}
b := a[1:3] // cap extends to the end of the array
fmt.Println(len(b), cap(b))
b = append(b, 99)
fmt.Println(a)

a = []int{1, 2, 3, 4, 5}
c := a[1:3:3] // full slice expression: cap limited to 3-1 = 2
fmt.Println(len(c), cap(c))
c = append(c, 77) // over cap, copied to a new array
fmt.Println(a, c)
c[0] = 0
fmt.Println(a, c)
```

```text frame="terminal" title="Output"
$ go run ./appendx
2 4
[1 2 3 99 5]
2 2
[1 2 3 4 5] [2 3 77]
[1 2 3 4 5] [0 3 77]
```

On the second line, the 99 appended to `b` overwrote the 4 in `a`. `c` had its cap capped at 2 by the third index, so append moved it to a new array, which is why setting `c[0]` to 0 on the last line left `a` alone.

There are three ways to defend against it. Pick by situation.

| Approach | When | What it does |
| --- | --- | --- |
| Cut cap: `a[l:h:h]` | Handing a slice to someone else | Forces the next append to make a new array |
| Detach with `copy` | Keeping it around long | Copies just what you need into a new slice and fully breaks the reference |
| Preallocate: `make([]T, 0, n)` | You know the size | Eliminates reallocation and copying altogether |

I also had "cap doubles" memorized, and that's no longer true. Since Go 1.18, the threshold dropped from 1024 to 256, and above it growth tapers smoothly from 2x toward 1.25x, to avoid wasting double the memory on large slices.

<Lab title="Does cap really double?">

Starting from cap 256, I appended one element at a time and printed cap whenever it changed.

```go title="grow/main.go"
s := make([]int, 0, 256)
last := cap(s)
fmt.Print(last)
for i := 0; i < 5000; i++ {
	s = append(s, i)
	if cap(s) != last {
		last = cap(s)
		fmt.Print(" → ", last)
	}
}
```

```text frame="terminal" title="Output"
$ go run ./grow
256 → 512 → 848 → 1280 → 1792 → 2560 → 3408 → 5120
```

After 512 came 848, not 1024. The formula past 256 (`newcap += (newcap + 3*256) >> 2`) gives 832, but 832 slots (6,656 bytes) got rounded up to the allocator's 6,784-byte size class, which holds 848. The uneven ratios, like 1.40x followed by 1.43x, come from the same rounding. That's why code should never assume an exact cap.

## The memory leak from reslicing

This is where the window nature causes trouble most quietly. A slice header references the entire backing array. So if you keep just 3 bytes cut from a 10 MB response, as far as the GC is concerned the 10 MB is still a live object.

Why the whole thing? As we saw, the array is one allocation unit. A 10 MB block on the heap has no notion of "keep the first 3 bytes and give back the rest." A `len` of 3 doesn't mean the data shrank to 3 bytes. It only means the window narrowed to the first 3 bytes of the block. As long as any pointer to that block is alive, the GC can't touch any of it.

I checked this with `runtime.AddCleanup`. Each element prints its name when reclaimed; I trimmed one off with each function and ran the GC.

```go title="pop/main.go"
type Item struct {
	name string
	buf  [1 << 20]byte // 1 MB
}

func track(name string) *Item {
	it := &Item{name: name}
	runtime.AddCleanup(it, func(n string) { fmt.Println("reclaimed:", n) }, name)
	return it
}

func main() {
	a := popBad([]*Item{track("a1"), track("a2")})
	b := popGood([]*Item{track("b1"), track("b2")})
	runtime.GC()
	time.Sleep(100 * time.Millisecond) // cleanups run on a separate goroutine
	runtime.KeepAlive(a) // a and b are still in use
	runtime.KeepAlive(b)
}
```

```text frame="terminal" title="Output"
$ go run ./pop

```

Only b2, nilled out before trimming, was reclaimed. a2, trimmed by `popBad`, survived the GC because its pointer was still sitting past len.

Deleting from the middle works the same way. Since Go 1.22, `slices.Delete` zeroes the vacated tail for you. Deleting [1:3] from `[1 2 3 4 5]` and peeking with `c[:5]` gave `[1 4 5 0 0]`. Use it instead of rolling your own.

<Lab title="Confirming the leak with heap stats and pprof">

I measured whether it really doesn't shrink, using `runtime.ReadMemStats`, comparing two ways to keep 3 bytes from a 10 MB array.

```go title="leak/main.go"
func heap() uint64 {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.HeapAlloc
}

func mb(n uint64) string { return fmt.Sprintf("%.2f MB", float64(n)/(1<<20)) }

func main() {
	fmt.Println("start:", mb(heap()))
	big := make([]byte, 10<<20) // 10 MB

	leak := big[:3] // reslice
	big = nil
	fmt.Println("reslice:", mb(heap()))

	safe := make([]byte, 3) // detach with copy
	copy(safe, leak)
	leak = nil
	fmt.Println("copy:", mb(heap()))
}
```

```text frame="terminal" title="Output"
$ go run ./leak
start: 0.20 MB
reslice: 10.20 MB
copy: 0.20 MB
```

At first I thought `big = nil` would be enough, but the heap didn't budge. Of course: `leak` was holding the same block. It's reclaimed only when every pointer to that block is gone. The 10 MB disappeared only after detaching with `copy` and then setting `leak = nil`.

What mattered more than the numbers was how hard this is to find with a profiler. I split it into `fetch`, which reads a 10 MB response with `io.ReadAll`, and `keep`, which puts the first 3 bytes in a cache, and took a heap profile.

```go title="readall/main.go"
func fetch() []byte {
	body, _ := io.ReadAll(bytes.NewReader(make([]byte, 10<<20))) // 10 MB response
	return body
}

func keep(id string, body []byte) {
	cache[id] = body[:3] // cache only the first 3 bytes
}

func handle(id string) {
	body := fetch()
	keep(id, body)
}
```

```text frame="terminal" title="go tool pprof (excerpt)"
$ go tool pprof -top -inuse_space readall.bin heap.pprof

         0     0%   100%    10240kB 90.90%  main.fetch (inline)
         0     0%   100%    10240kB 90.90%  main.handle
```

All 10 MB landed on `io.ReadAll`, and the stack goes only as far as `fetch` and `handle`. The function that actually holds the sliver, keep, appears nowhere. A heap profile shows where memory was allocated, not who is holding it now. So I made it a rule: copy any slice you keep for long.

## nil slice vs empty slice

The two behave the same in almost every way. They differ in only two places, and those two places happen to be API boundaries.

```go title="nilempty/main.go"
type Resp struct {
	Items []int `json:"items"`
}

func main() {
	var a []int
	b := []int{}
	fmt.Println(a == nil, unsafe.SliceData(a) == nil)
	fmt.Println(b == nil, unsafe.SliceData(b) == nil)
	ja, _ := json.Marshal(Resp{a})
	jb, _ := json.Marshal(Resp{b})
	fmt.Println(string(ja), string(jb))
}
```

```text frame="terminal" title="Output"
$ go run ./nilempty
true true
false false
{"items":null} {"items":[]}
```

| | `var s []int` (nil) | `s := []int{}` (empty) |
| --- | --- | --- |
| len / cap | 0 / 0 | 0 / 0 |
| append, range | Same behavior | Same behavior |
| Heap allocation | None | None (only ptr is non-nil) |
| `s == nil` | true | false |
| JSON encoding | `null` | `[]` |

Go Code Review Comments recommends `var s []T`. It also points out the exception: building JSON responses. When there are no results, `null` goes out and `.map()` blows up on the frontend.

<Note title="Don't build contracts on nil versus empty">

The line the same guide adds matters more: when designing interfaces, don't distinguish between a nil slice and a zero-length slice. The moment a function contract says "nil if missing, empty if there are none," every caller reads it differently and subtle bugs follow. If you need the distinction, signal it with a separate value, like `(value, bool)`.

</Note>

The key's hash is split in two: the low 7 bits (h2) go into the group's control byte, and the remaining upper 57 bits (h1) decide which table and which group to start at. A lookup compares all 8 bytes of the control word at once and compares keys only in slots whose h2 matches. A table holds at most 1024 slots, and growth enlarges one table at a time, so even in a big map a single insert moves at most one table's worth of entries.

More important than performance, this structure explains why maps are so unfriendly. Both of their most-complained-about traits are deliberate.

### ① Iteration order changes every time

The runtime picks the starting point of iteration at random on purpose. A hash table has no defined order anyway, but left alone, you'd get situations where the order happens to be the same every time, and developers would start relying on it. Then one day, with slightly different data, it breaks in production. Randomization forces that bug to surface during development. If you need order, extract the keys and sort them.

```go title="maporder/main.go"
m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}
for i := 0; i < 3; i++ {
	for k := range m {
		fmt.Print(k, " ")
	}
	fmt.Println()
}
```

```text frame="terminal" title="Output"
$ go run ./maporder
a b c d e
c d e a b
a b c d e
```

Three runs gave two orders. Every line is `a b c d e` rotated, so the output itself shows that the runtime randomizes only the starting point rather than shuffling the entries.

### ② A detected concurrent write kills the process

And it's a fatal error, not a panic. I missed this when I learned it from flashcards, and the difference is big. `recover` can't catch it, deferred functions don't run, and the process ends right there.

```go title="mapfatal/main.go"
func main() {
	defer fmt.Println("main defer") // does this run?
	m := map[int]int{}
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			defer func() {
				if r := recover(); r != nil {
					fmt.Println("recovered:", r)
				}
			}()
			for j := 0; j < 1000; j++ {
				m[i*1000+j] = j
			}
		}(i)
	}
	wg.Wait()
}
```

```text frame="terminal" title="Output"
$ go run ./mapfatal
fatal error: concurrent map writes

goroutine 21 [running]:
internal/runtime/maps.fatal({0x10466776c?, 0x0?})
…
exit status 2
```

I ran it three times and it ended like this every time; neither the recovered line nor the main defer line was printed. Make one goroutine write while another reads, and you get `fatal error: concurrent map read and map write` instead.

It goes this far because if the structure breaks while a table is growing, the result is memory corruption you can't trace. Dying on the spot with a stack trace beats quietly returning wrong values or stomping on someone else's memory.

That detection is best effort, not a guarantee, though. The Go 1.6 release notes call it lightweight, best-effort detection. If the timing is off it can slip by silently, so you still need `-race`.

### So what do you use in practice?

| Approach | When | Cost |
| --- | --- | --- |
| Wrap with `sync.RWMutex` | The default. Start here when in doubt | Contention when many goroutines pile onto one lock |
| Sharding | When contention actually shows up in a profile | Iterating everything and counting size get awkward |
| `sync.Map` | Caches written once and read many times, or goroutines working on different keys | Values are `any`, so no type safety, and writes allocate |

```go title="A map wrapped in an RWMutex"
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func (s *SafeMap) Get(k string) (int, bool) {
	s.mu.RLock() // many readers at once
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}

func (s *SafeMap) Set(k string, v int) {
	s.mu.Lock() // one writer at a time
	defer s.mu.Unlock()
	s.m[k] = v
}
```

The first version of this post said `sync.Map` is often slower for mixed reads and writes. Then I saw a line in the Go 1.24 release notes saying the `sync.Map` implementation had changed, with writes in particular getting faster, so I measured again. Finally, two lesser-known traps. You can't take the address of a map element (`&m[k]` is a compile error, covered in [the previous post](/en/11)), and `delete` doesn't shrink memory. It empties or marks the slot and leaves the table as is. I filled a map with a million entries and then deleted them all.

```go title="mapdel/main.go (excerpt)"
m := map[int][64]byte{}
for i := 0; i < 1_000_000; i++ {
	m[i] = [64]byte{}
}
fmt.Println("1M entries:", heap(), len(m))
for i := 0; i < 1_000_000; i++ {
	delete(m, i)
}
fmt.Println("all deleted:", heap(), len(m))

m[1] = [64]byte{}
n := make(map[int][64]byte, len(m)) // move only the live entries
for k, v := range m {
	n[k] = v
}
m = n
fmt.Println("moved to a new map:", heap(), len(m))
```

```text frame="terminal" title="Output"
$ go run ./mapdel
1M entries: 160.1 MB 1000000
all deleted: 160.1 MB 0
moved to a new map: 0.2 MB 1
```

After deleting everything, the heap was still at 160 MB, and it dropped to 0.2 MB only after the live entries moved to a new map. If you have a map that balloons once and then empties out, building a new map like this is the only fix.

```go title="str/main.go"
s := "한글Go"
fmt.Println(len(s))                    // number of bytes
fmt.Println(utf8.RuneCountInString(s)) // number of code points
fmt.Println(s[0])                      // a single byte
for i, r := range s {                  // only range walks by rune
	fmt.Print(i, " ", string(r), " / ")
}
fmt.Println()
for i, r := range "a\xffb" { // with invalid UTF-8 mixed in
	fmt.Printf("%d %U  ", i, r)
}
```

```text frame="terminal" title="Output"
4
237
```

On the fourth line, i skips through 0, 3, 6, 7, which shows that range walks by rune while i itself is the byte offset where each rune starts. When invalid UTF-8 is mixed in, as on the fifth line, range yields U+FFFD for that single byte and moves on to the next, so it never loops forever.

### The cost of immutability: += is O(N²)

Because strings are immutable, changing one means creating a new one. Concatenating with `+=` in a loop copies everything built so far into a new buffer on every iteration. After N iterations, total copying is proportional to N².

<Compare>
<Side title="Concatenating with +=" tone="bad">

```go
// copies everything so far, every time
var s string
for _, w := range words {
	s += w
}
```

</Side>
<Side title="strings.Builder" tone="good">

```go
// appends into a single buffer
var b strings.Builder
b.Grow(totalLen) // no reallocation if you know the size
for _, w := range words {
	b.WriteString(w)
}
s := b.String() // handed over without a copy
```

</Side>
</Compare>

For simple joining, `strings.Join(words, "")` reads better. It allocates once internally. I measured all three with 1,000 four-byte words.

```text frame="terminal" title="go test -bench . -benchmem"
$ go test -run x -bench . -benchmem ./strbench
BenchmarkPlusEq-10       6447    179312 ns/op   2137579 B/op   999 allocs/op
BenchmarkBuilder-10    395104      3013 ns/op      4096 B/op     1 allocs/op
BenchmarkJoin-10       220131      5147 ns/op      4096 B/op     1 allocs/op
```

The `+=` version allocated 999 times per run and used 2.1 MB. The result is 4 KB, so it copied more than 500 times that. The first word is appended to an empty string and used as is without allocating, which is why it was 999 rather than 1,000. Builder and Join each allocated once.

### Converting between string and []byte copies, with exceptions

Strings are immutable and `[]byte` is mutable, so converting between them copies by default. Otherwise you could change a string by modifying the `[]byte`. Repeat this conversion on a hot path and invisible allocations pile up.

In a few places, though, the compiler can prove the result of the conversion doesn't outlive the expression, and it skips the copy.

```go title="Where the copy is skipped, and where it isn't"
b := []byte("key")

v := m[string(b)]         // map lookup: copy skipped
if string(b) == "key" {}  // comparison: copy skipped

s := string(b)            // stored in a variable: copied (it outlives the expression)

// if you truly must avoid the copy (Go 1.20+), only when you're sure
s = unsafe.String(unsafe.SliceData(b), len(b))
// modify b afterward and s changes too = the immutability contract is broken
```

Measuring with a 64-byte `b` and `testing.AllocsPerRun`, the map lookup and the comparison allocated zero times, and storing the conversion in a variable allocated once. Which spots get the optimization widens a little with each compiler version. On a hot path, don't guess. Check allocs/op with `go test -bench . -benchmem`.

## Test environment and limits

I reran every example on this Mac (Apple M5, 10 cores, darwin/arm64) with Go 1.26.10. The output of the character-count lab in the first version didn't match what the code actually prints, so I replaced it with fresh output, and I rewrote the sentence saying `sync.Map` is often slower for mixed reads and writes based on new measurements. Heap numbers and map iteration order vary a little from run to run.

| What I checked | What it tells us | What it doesn't |
| --- | --- | --- |
| Header sizes · passing · append | Sizes on 64-bit and how these examples behave | Sizes on 32-bit platforms |
| cap growth | The cap sequence for `[]int` on Go 1.26.10 | The sequence for other element sizes or versions; a new size-class table changes the numbers |
| Heap stats · cleanups · pprof | Bytes left, elements reclaimed, and profile stacks in these examples | Whether a real service with different GC timing shows the same numbers |
| Map fatal error · delete | Caught in all three runs; heap size after deleting | How often detection misses a race |
| RWMutex map · `sync.Map` | Times on 10 cores, 10,000 keys, 1/10/50% writes | Sharded maps, other key and core counts |
| String allocations · character counts | Allocation counts and byte/rune counts in these examples | Where other compiler versions skip the copy |

## Wrap-up

| What we saw | Why |
| --- | --- |
| append inside `modify` was invisible to the caller | The header is copied; the array is shared |
| `b = append(b, 99)` changed `a` | With room in cap, append writes into the same array |
| A 3-byte sliver pinned 10 MB | A slice references its entire array |
| recover never ran on a concurrent map write | It's a fatal error, not a panic |
| A fully deleted map still took 160 MB | Maps don't shrink when you delete |
| `len("한글Go")` was 8 | A string is UTF-8 bytes |

So I cut cap with `a[l:h:h]` on slices I hand to someone else, and I detach slivers I keep around with `copy`.

Lined up side by side, the three data structures had one thing in common: Go doesn't hide the reality for convenience. Slices don't hide that they're windows, maps don't pretend to guarantee element addresses, and strings don't pretend to be character arrays. It felt unfriendly at first, but had they hidden it, I think I'd have paid the price at a much worse moment.
