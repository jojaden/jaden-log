<Lead>
Part three of the DB series is about design. Normalization decides how to split tables, and the ORM question decides where business logic lives. This time I loaded a million comments and 200,000 orders into MySQL 8.4 and measured what each choice buys and what it costs.
</Lead>

<Summary>
1. Normalization keeps each fact in one place, which prevents update, insert, and delete anomalies. On a table with duplication, MySQL rejected only the insert anomaly with an error.
2. Denormalize only for a bottleneck you've measured. A precomputed comment count cut the top-20-by-comments query from 256 ms to 0.18 ms, but the latest-20 page only went from 0.58 ms to 0.18 ms.
3. Keeping duplicated data in sync is the application's job. Add to a counter inside the database, as in `comment_count + 1`, and if the comment table has a foreign key, bump the counter first.
4. Keep logic in the application by default. In a bulk batch, what won was set-based SQL, not the procedure. Changing 99,057 orders took 24.9 s row by row from the app, 5.0 s with a procedure cursor, and 2.8 s as one UPDATE sent from the app.
</Summary>

<Note title="Who this is for">
I wrote this for someone who knows the normal-form definitions but has never measured when it's fine to break them, or what you take on when you do. Sections 1 and 2 cover normalization, section 3 denormalization and keeping a counter in sync, and section 4 ORMs and stored procedures. If you already run denormalized columns in production, you can start at section 3.
</Note>

## Why normalize: three anomalies that duplication causes

Start with one unnormalized table. All the course enrollment data goes in a single table.

| Student | Name | Course | Title | Prof. | Grade |
| --- | --- | --- | --- | --- | --- |
| 1001 | Jiho Kim | CS101 | Intro to DB | Prof. Park | A |
| 1001 | Jiho Kim | CS202 | Operating Systems | Prof. Lee | B+ |
| 1002 | Seoyeon Lee | CS101 | Intro to DB | Prof. Park | A- |

The fact that Prof. Park teaches Intro to DB is stored once for every student in the course. That duplication causes three kinds of trouble.

- **Update anomaly**: when a course title changes, every row for that course has to change. Miss one and the data contradicts itself.
- **Insert anomaly**: a new course with no students yet has no way in. student_id is part of the key, so it can't be left empty.
- **Delete anomaly**: when the last student drops the course, the course information disappears with them.

<Lab title="The duplicated table only rejected the insert anomaly">

I created the table above as `enrollment` (keyed on student_id and course_id) and tried all three in order.

```text frame="terminal" title="Output · MySQL 8.4.13 (table borders and timings removed)"
mysql> UPDATE enrollment SET course_name = 'Databases'
    ->  WHERE student_id = 1001 AND course_id = 'CS101';
Query OK, 1 row affected
mysql> SELECT DISTINCT course_id, course_name
    ->   FROM enrollment WHERE course_id = 'CS101';
CS101   Databases
CS101   Intro to DB

mysql> INSERT INTO enrollment (course_id, course_name, professor)
    -> VALUES ('CS303', 'Networks', 'Prof. Choi');
ERROR 1364 (HY000): Field 'student_id' doesn't have a default value

mysql> DELETE FROM enrollment
    ->  WHERE student_id = 1001 AND course_id = 'CS202';
Query OK, 1 row affected
mysql> SELECT course_name, professor FROM enrollment
    ->  WHERE course_id = 'CS202';
Empty set
```

The UPDATE that changed one row went straight in, and CS101 now has two titles. The course with no students couldn't be added. Key columns are NOT NULL, so in strict mode (the 8.4 default) MySQL rejects an INSERT that leaves one empty with error 1364. Deleting the last student also deleted the fact that Prof. Lee teaches Operating Systems. Of the three, the database flagged only one.

</Lab>

Normalization breaks that duplication apart along functional dependencies so that <mark>each fact is stored in exactly one place</mark>. You split tables along "if you know X, Y is determined (X → Y)."

## First, second, and third normal form

### 1NF: one value per cell

Every column holds an atomic value. The moment a contact cell holds several numbers joined by commas, like `010-1000-4242, 010-9000-4242`, you've broken it. Repeated values become rows or move to their own table.

<Lab title="A comma-joined cell scans everything, index or not">

I gave 100,000 members two phone numbers each, then built one table that puts both in a single comma-joined cell and one that gives each number its own row. Both have an index on the phone column.

```sql title="Two tables holding the same numbers"
-- comma-joined in one cell (breaks 1NF)
CREATE TABLE member_flat (
  id INT PRIMARY KEY,
  phones VARCHAR(100),  -- '010-1000-4242, 010-9000-4242'
  INDEX idx_phones (phones));

-- one row per number
CREATE TABLE member_phone (
  member_id INT,
  phone VARCHAR(20),
  PRIMARY KEY (member_id, phone),
  INDEX idx_phone (phone));
```

```text frame="terminal" title="Output · four EXPLAIN columns shown"
mysql> EXPLAIN SELECT id FROM member_flat
    ->  WHERE phones LIKE '%010-9000-4242%';
type: index   key: idx_phones   rows: 99994
Extra: Using where; Using index
mysql> SELECT id FROM member_flat
    ->  WHERE phones LIKE '%010-9000-4242%';
4242
1 row in set (0.08 sec)

mysql> EXPLAIN SELECT member_id FROM member_phone
    ->  WHERE phone = '010-9000-4242';
type: ref     key: idx_phone    rows: 1
Extra: Using index
mysql> SELECT member_id FROM member_phone
    ->  WHERE phone = '010-9000-4242';
4242
1 row in set (0.00 sec)
```

In the comma-joined cell the second number sits in the middle of the string, so the index can't seek to it. Since the query only selects `id`, MySQL read the index instead of the table (`Using index`), which is why the type is `index` and not `ALL`. `type: index` means MySQL read the whole index from start to finish, an estimated 99,994 rows in 0.08 seconds. With one row per number it read a single row through `ref`.[^json]

</Lab>

### 2NF: remove columns that hang on part of the key

The key of the table above is the composite (student_id, course_id). But the student's name is determined by student_id alone, and the title and professor by course_id alone. That's a partial dependency. Columns that depend on only part of the key move to their own tables.

### 3NF: break chains between non-key columns

Say we add the professor's department to course. Two professors can share a name, so we refer to them by professor_id. Now course_id determines professor_id, and professor_id determines the professor's name and department. That's a transitive dependency, running from the key through a non-key column.

When a professor changes departments, every course row they teach has to change, and the update anomaly is back. When a non-key column determines another non-key column, split that out too.

```text title="After splitting for 3NF"
course    (course_id, title, professor_id)
professor (professor_id, name, department)
```

<Note title="The one-liner to remember">

Every column must depend on the key, the whole key (2NF), and nothing but the key (3NF). That's how William Kent summed up second and third normal form in 1983. BCNF and 4NF go further, but in practice third normal form is the baseline for schema design.

</Note>

## Denormalization: buying duplication back, knowingly

Normalization sends its bill at read time. The more you split tables, the more JOINs you need. Rendering one order list screen takes a five-table join, and when that becomes the bottleneck in a busy service, that's when denormalization comes out.

- **Duplicated columns**: copy the product name into the order. Strictly, the product's name and price at order time are a different fact from its current values, so copying them is often the right model anyway.
- **Aggregate columns**: keep a `comment_count` on each post so you can drop the COUNT and the join.
- **Merged and summary tables**: combine tables that are always read together, or keep a separate table for statistics.

<Lab title="The aggregate column only won big on sort by comments">

I loaded 10,000 posts and a million comments, skewed toward the early posts so that each post has between 30 and 10,054 comments. `comment` has an index on `post_id`, and `post.comment_count` has its own index. I ran the queries behind two pages both ways, 11 times each.

```sql title="Two ways to pick the 20 most-commented posts"
-- count on the fly
SELECT p.id, p.title, COUNT(c.id) AS cnt
FROM post p JOIN comment c ON c.post_id = p.id
GROUP BY p.id ORDER BY cnt DESC LIMIT 20;

-- read the precomputed column
SELECT id, title, comment_count
FROM post ORDER BY comment_count DESC LIMIT 20;
```

```text frame="terminal" title="Output · median of 11"
$ ./normlab -en read
    0.58 ms  latest 20 · JOIN+COUNT
    0.18 ms  latest 20 · comment_count
  256.02 ms  top 20 by comments · JOIN+COUNT
    0.18 ms  top 20 by comments · comment_count
```

The latest 20 posts only needed their own comments counted through the index, which took 0.58 ms against 0.18 ms for the column. Ranking by comment count meant counting all million comments per post, which took 256 ms; the column did it in 0.18 ms. The same column was worth very different amounts depending on the page.

</Lab>

### Keeping it in sync is now the application's job

The price is exactly what normalization was protecting you from. With duplication, every change has to touch several places, and <mark>keeping them in sync is now the application's job</mark>. Both statements go in one transaction for the atomicity reasons from [part two](/en/9). Even inside a transaction, though, the count drifted depending on how the counter was incremented.

<Lab title="Adding to the counter in the app versus in the database">

Two sessions each posted 100 comments on the same post. For the counter experiment I used separate `cpost` and `ccomment` tables, apart from the big ones. Each comment is one transaction, and only the way the counter is updated changes between the three runs.

```sql title="Read and add in the app"
START TRANSACTION;
INSERT INTO ccomment (post_id, body) VALUES (42, '...');
SELECT comment_count FROM cpost WHERE id = 42;    -- the app gets 5
UPDATE cpost SET comment_count = 6 WHERE id = 42; -- the app sends 5 + 1
COMMIT;
```

```text frame="terminal" title="Output · two sessions, 100 comments each, REPEATABLE READ"
$ ./normlab -en lost app
comments 200 · comment_count 100 · deadlocks 0  read, add in the app
$ ./normlab -en lost atomic
comments 200 · comment_count 200 · deadlocks 0  comment_count + 1
$ ./normlab -en lost lock
comments 200 · comment_count 200 · deadlocks 0  read FOR UPDATE, add
```

Reading and adding in the app left 200 comments with a `comment_count` of 100. Six runs, six times 100. Each commit spends about 16 ms on fsync, so the two sessions seem to have run in near lockstep and collided every time.

</Lab>

B's UPDATE waits for A's commit because A holds the row lock. But B is sending 6, a value the app already computed, so after waiting it still writes 6. Send `comment_count + 1` instead and the database reads the latest committed row and adds to that. It's the same reason the REPEATABLE READ UPDATE in [part two](/en/9) changed a row its snapshot never had. Reading with `FOR UPDATE` also got the count right, at the cost of one more round trip.

```sql title="Add inside the database"
START TRANSACTION;
INSERT INTO ccomment (post_id, body) VALUES (42, '...');
UPDATE cpost SET comment_count = comment_count + 1 WHERE id = 42;
COMMIT;  -- if only one of them lands, the count drifts, so one transaction
```

### With a foreign key, the order matters too

I added a foreign key on `ccomment.post_id` and ran the same experiment again. This time even `comment_count + 1` deadlocked.

<Lab title="With a foreign key, the counter UPDATE deadlocks">

```text frame="terminal" title="Output · foreign key ccomment.post_id → cpost.id"
$ ./normlab -en lost app fk
comments 200 · comment_count 200 · deadlocks 149  read, add in the app · foreign key
$ ./normlab -en lost atomic fk
comments 200 · comment_count 200 · deadlocks 11  comment_count + 1 · foreign key
$ ./normlab -en lost first fk
comments 200 · comment_count 200 · deadlocks 0  counter first, INSERT second · foreign key
```

On a deadlock, one side rolls back and posts the same comment again. Over five runs, `comment_count + 1` deadlocked between 11 and 23 times, and read-and-add in the app between 147 and 162 times. The count came out right, but only after that many rollbacks and retries. Bumping the counter first and inserting second gave zero deadlocks in all four runs.

```text frame="terminal" title="Locks taken by one INSERT · performance_schema.data_locks"
mysql> INSERT INTO ccomment (post_id, body) VALUES (42, 'x');
mysql> SELECT object_name, lock_type, lock_mode, lock_data
    ->   FROM performance_schema.data_locks;
ccomment   TABLE    IX              NULL
cpost      TABLE    IS              NULL
cpost      RECORD   S,REC_NOT_GAP   42
```

</Lab>

An INSERT that checks a foreign key takes a shared (S) lock on the parent row, `cpost` 42 here. If both sessions hold that S lock and both wait for an exclusive (X) lock to UPDATE, each waits on the other and they deadlock. With the UPDATE first, only the session that gets the X lock first goes ahead and the other waits. Since that session already holds the X lock, its INSERT's check doesn't block either.

```sql title="With a foreign key · bump the counter first"
START TRANSACTION;
UPDATE cpost SET comment_count = comment_count + 1 WHERE id = 42;
INSERT INTO ccomment (post_id, body) VALUES (42, '...');
COMMIT;
```

Design has an order too. Design normalized first, then denormalize only where you've measured a bottleneck. Once you denormalize, decide every path that changes that column, as above.

## ORM vs stored procedures: where should logic live?

The last design question. Business logic can live in application code (through an ORM) or inside the database as stored procedures.

<Compare>
<Side title="ORM (JPA, GORM, etc.)">

- You think in objects and the SQL is generated
- Version control, tests, and code review fit straight into the application pipeline
- Switching databases is comparatively easy
- But if you don't know the SQL it generates, you fall into **traps like N+1**, and complex queries hit its limits

</Side>
<Side title="Stored procedures">

- The logic runs inside the database
- **Processing without moving data**, and fewer network round trips
- But version control, testing, and debugging are harder, and you're tied to one DBMS
- **CPU load piles up on the database**, the most expensive resource and the hardest to scale out

</Side>
</Compare>

There was a reason procedure-heavy development was common in enterprise and banking systems. When networks were slow and application servers were weak, doing everything in the database was faster. Today it's the other way around. <mark>Application servers are cheap to scale horizontally, and databases are expensive.</mark> So the default is to keep logic in the application. I measured the classic trap on each side.

<Lab title="A GORM loop sent 21 queries for 20 posts">

I read the latest 20 posts and their comments with GORM, once reading each post's comments inside a loop and once with `Preload`.

```go title="main.go · reading in a loop vs Preload"
var posts []Post
db.Order("id DESC").Limit(20).Find(&posts)
for i := range posts { // one query per post
	db.Where("post_id = ?", posts[i].ID).Find(&posts[i].Comments)
}

db.Preload("Comments").Order("id DESC").Limit(20).Find(&posts)
```

The loop sends one extra query per post, 21 in all, while `Preload` batches the post ids into an `IN` and sends 2. Even on the same server, with a 0.095 ms round trip, that was 13.90 ms against 8.42 ms. The log is from the first run and the times are the median of the 11 runs after it; I didn't check why the per-query times in the log came out so much longer than the median. </Lab>

At least with GORM the loop is visible in the code. With a lazy-loading ORM like JPA, calling `post.getComments()` is what sends the query, so the queries inside the loop never show up in the code. The Hibernate documentation calls N+1 selects the most common cause of poorly performing data access code in Java programs. Using an ORM doesn't mean you can skip SQL. You need to read the SQL it generates in the logs and be able to fix it when it looks wrong.

<Lab title="The same batch, run four ways">

Out of 200,000 orders, I set the status of the 99,057 placed before June 30, 2025 to `archived`. All four runs use one transaction and one commit, and the procedure updates one row at a time through a cursor.

```sql title="archive_old · one row at a time through a cursor"
CREATE PROCEDURE archive_old(IN cutoff DATETIME)
BEGIN
  DECLARE done INT DEFAULT 0;
  DECLARE v INT;
  DECLARE cur CURSOR FOR
    SELECT id FROM orders WHERE created_at < cutoff AND status = 'done';
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;
  OPEN cur;
  l: LOOP
    FETCH cur INTO v;
    IF done THEN LEAVE l; END IF;
    UPDATE orders SET status = 'archived' WHERE id = v;
  END LOOP;
  CLOSE cur;
END
```

```text frame="terminal" title="Output · median of 3, statements sent by the app"
$ ./normlab -en batch
target: 99057 rows
 24.90 s   99058 statements  app · one UPDATE per row
  2.94 s     101 statements  app · IN with 1,000 ids
  5.01 s       1 statements  procedure · cursor, row by row
  2.79 s       1 statements  app · one UPDATE statement
```

Sending one row at a time from the app meant 99,058 statements and 24.9 seconds. Running the same row-by-row loop inside the database with a procedure cursor brought it down to 5.0 seconds. The fastest, though, was one UPDATE sent from the app (2.8 seconds), and batching 1,000 ids per statement (2.9 seconds) also beat the procedure.

</Lab>

The procedure was faster because the round trips disappeared. The single UPDATE removed both the round trips and the row-by-row work. And a set-based statement doesn't haul data out to the application either. So for a bulk batch, first check whether it fits in one statement, or a few batched ones. Procedures still win in some cases.

- **Batch jobs** that apply step-by-step processing, hard to express as one statement, to many rows. Even row by row, the round trips from the app go away.
- Cases where many statements belong in one transaction and **the number of round trips decides performance**.
- Legacy environments where several systems share one database and **rules have to be enforced at the database level**.

## Lab setup and limits

The tests ran on MySQL 8.4.13 with default settings, in a podman container on the same Rocky Linux 8.10 server (4 cores) as [part one](/en/7) and [part two](/en/9). The isolation level is REPEATABLE READ, the buffer pool is 128 MB, and `sql_mode` is the default with strict mode on. The anomalies and 1NF ran in the `mysql` client; everything else ran from a Go program on the same server (go-sql-driver/mysql 1.8.1, GORM 1.31.2). With the app and database on one server, a `SELECT 1` round trip took 0.095 ms. With the app on another server the round trip grows, so the approaches that send many statements should slow down further.

| What I checked | What it shows | What it doesn't |
| --- | --- | --- |
| Anomalies | What MySQL blocks and what it lets through | Other databases |
| Comment counts | COUNT vs aggregate column over a million rows | Data larger than the buffer pool, heavy concurrency |
| Counter updates | Lost updates, foreign keys and deadlocks | Throughput with dozens of sessions |
| N+1 | Query count and time on one server | Time across a network. JPA wasn't tested |
| Four batches | Time by number of statements sent | Batches with complex logic, an app on another server |

## Wrap-up

| Situation | What happened | What to do |
| --- | --- | --- |
| Everything in one table | Many places to fix, facts you can't insert, facts that vanish on delete | Normalize to 3NF |
| Several values in one cell | A full scan even with an index | Split into rows or a table |
| Sort by comments is slow | A million comments counted every time | Measure, then add an aggregate column |
| Counter added in the app | Concurrent comments go missing from the count | Add in the database with `comment_count + 1` |
| Foreign key on the child | The INSERT's S lock collides with the UPDATE | Bump the counter first |
| Related data in an ORM loop | One query per post | Batch with `Preload` or a JOIN |
| Bulk batch | Row by row costs one statement per row | Send one statement, or batches |
