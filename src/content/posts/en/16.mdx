Validation was dying on timeouts. Within 30 minutes I had an answer, "it's N+1, batch it," and it was only half right. Reaching the final design took two changes of direction, and since the process taught me more than the code, I'm writing it down.

<Summary>
1. I counted calls and never looked at the cost per call. The two multiply, so if you don't know which one dominates, you fix the wrong thing.
2. Batching was necessary but not sufficient. The real question wasn't how to batch but when to sync.
3. Optimization doesn't only change performance; it changes failure modes too. If you're trading scattered partial failures for one all-or-nothing failure, you should know it and sign off on it.
</Summary>

## The situation, and the first fork

There's a feature where users bundle several resources into one plan and save it. Right before saving, a validation step checks that those resources actually exist, and with enough items in the plan, that step timed out. Small plans were fine; big ones died.

There were two broad ways to fix it, and this was the project's first trade-off.

<Compare>
<Side title="Go asynchronous">

- Gain: timeouts disappear at the root, and it's simple to build
- Loss: the user who hit save doesn't get a result right away. Polling or notifications become new state to manage

</Side>
<Side title="Stay synchronous, cut latency">

- Gain: the screen flow stays the same. Hit save and you immediately know what's wrong
- Loss: you have to actually find the root cause, and if the improvement falls short, it blows up again

</Side>
</Compare>

I chose the second. The reason was the product, not performance. This validation is part of a screen flow that tells you what's wrong before you save. Going async would mean users hit save and only later hear that it didn't work, which removes the whole reason for validating up front.

<Note title="Settle the constraint first">

Looking back, this decision became the constraint on everything that followed. Pinning down "stay synchronous" forced "then latency really has to drop," and left no room to fudge it. <mark>Settling the constraint first actually made the design go faster</mark>, and this time I felt that firsthand.

</Note>

## The first answer: counting calls

Opening the validation code, I found it calling an external service once per resource. A classic shape.

```go title="Every call in the validation code looked like this"
for _, id := range instanceIDs {
	if _, err := resourceService.GetInstance(ctx, id, WithSync(true)); err != nil {
		return err
	}
}
```

The count came out like this.

```text title="Number of calls"
N        number of instances
V        volumes attached to each instance
M        networks used by each instance

calls = N  +  N×V  +  2×N×M  +  (distinct lookups for other kinds)
                        └ two IP/MAC duplicate checks per network

N=50, V=2, M=1  →  50 + 100 + 100 + α  ≈  300 calls in series
```

On top of that, the duplicate checks had no cache at all and went out every time. So far, textbook N+1. "Batch it" was the natural conclusion, and that's exactly what I proposed.

## Turn ①: the problem wasn't the number of calls

Just as I was about to design the batching, something caught. I had counted the calls but never checked how expensive one call was. I followed the code into the external service.

```text title="Following WithSync(true)"
GetInstance(id, WithSync(true))
  └─ syncOne(id, kindInstance)
       ├─ newSession(clusterID)
       │    ├─ look up cluster info + decrypt credentials
       │    └─ authenticate to the cloud platform, get a token   // external round trip
       ├─ fetch one resource                                    // external round trip
       └─ session.Close()                                       // close the session
```

`WithSync(true)` wasn't the cache-refresh flag I had vaguely assumed. Every call opened and closed a new auth session, and because the flag forced it, there was no deduplication either. In other words, <mark>validating one resource = an auth round trip + an API round trip + closing the session</mark>. Stack that 300 times in series and of course it times out.

<Note title="Decide what you're reducing first">

Call count and cost per call multiply. Had I gone straight to batching on the call count alone, the cost term would have stayed and I'd have ended up asking why it wasn't faster after batching. If you don't pin down what you're trying to reduce before performance work, you reduce whatever is easiest and stop there.

</Note>

## The answer was already in the repo

As I started designing the batching, I found the pattern already in the same package. The read path, which handles the same data, had been doing it this way for a while.

```go title="The pattern the read path already used"
collectRequired() // ① walk the plan and collect only the needed IDs. Zero external calls
fetchByKind()     // ② one list call per kind, in parallel with errgroup
lookup(byID)      // ③ decide using an in-memory map. Zero external calls
```

Only the validation path had been left on the old approach. So the plan became: reuse this instead of building something new. Along the way I found one more thing, and it turned out to matter a lot.

| Route | How it works | Cost |
| --- | --- | --- |
| List API | reads stored data | cheap |
| Single-item check API | opens an auth session, asks the outside, closes it, every time | one auth session |

There were two APIs that could serve the duplicate check, with wildly different costs, and only validation was taking the expensive one. The read path was already on the cheap one. Code review doesn't catch this. It only shows up when someone who knows both APIs answer the same question compares them.

## Turn ②: batching was a trap too

Reading the rest of the batch code I'd planned to reuse, I realized my estimate of the improvement was wrong.

```go title="Inside the bulk search API"
if req.Sync {
	syncAll(clusterID, kindInstanceList) // resyncs the whole cluster's list
}
return readByIDs(req.IDs) // only then reads the requested IDs
```

The bulk lookup's sync flag didn't sync just the requested IDs; it resynced the entire cluster's list. And the caller was splitting IDs into fixed-size chunks.

<Compare>
<Side title="What I expected">

- Send 50 IDs in chunks of 5, so 10 calls
- Calls drop from 300 to 10
- Cost per call stays the same, so a 30x improvement

</Side>
<Side title="What actually happens" tone="bad">

- Each of the 10 chunks syncs the whole cluster's list
- That's 10 full syncs
- Fewer calls, but each one costs more. I couldn't even tell on paper whether it was a net win or a net loss

</Side>
</Compare>

Batching was necessary but not sufficient. This is where the design's axis shifted. <mark>The real question wasn't how to batch the calls, but when to sync.</mark> The problem was that sync time and lookup time were glued together, and they had to be separated.

## Splitting "fetch only what we need" three ways

During the discussion, someone suggested just loading the resources the plan has. Fair enough, but as I listened, it read three different ways. If people carry on designing with different readings of the same sentence, things drift far apart later. So I split it first.

| Reading | Meaning | Verdict |
| --- | --- | --- |
| ① By kind | skip syncing resource kinds the plan doesn't use | adopted |
| ② By item | sync only the 20 IDs the plan references | impossible |
| ③ By field | fetch only the fields validation actually uses and skip assembling the rest | adopted |

② turned out to be impossible. The unit of syncing was either a whole kind or a single item, and splitting by item takes you right back to N+1. Given how the external list API works, "just these 20" wasn't a valid request. Wanting it didn't make it possible; the units the lower system offered constrained the design.

③ was bigger than I expected. The bulk search assembled every linked resource for each instance and made extra lookups per network: roughly nine DB queries per instance. And validation used none of that data.

So I decided to do both ① and ③. Fixing only one makes the other the new ceiling; cut the kinds and the field assembly still blocks you. The single sync in the figure above is, in the end, a sync over only the kinds the plan actually uses.

The catch was that ③ required deciding which fields validation actually uses. So I reread the validation code from the top, and that's where I found the biggest thing in the whole project.

## The biggest find: validation was throwing the response away

I went through every validation function, scattered by resource kind, and without exception they looked like this.

```go title="Each resource kind had its own validation function, all in this shape"
func validateVolume(ctx context.Context, id string) error {
	_, err := resourceService.GetVolume(ctx, id)
	return err // discard the response, look only at err
}

func validateNetwork(ctx context.Context, id string) error {
	_, err := resourceService.GetNetwork(ctx, id)
	return err // same here
}

// … all ten-odd kinds were identical
```

Every response went to `_`, and only `err` was checked. There were two exceptions, and they boiled down to whether a count was zero and whether something existed.

<mark>All validation needed, 100% of the time, was whether the thing exists.</mark> The detailed lookups had never been needed. Once I saw that, everything before it fell into place: we had been authenticating 300 times to build data nobody used.

That also settled ③. No fields were needed at all, just one bit: exists or doesn't. But the existing lookup APIs only returned fully assembled objects, so there was no way to ask that question. It meant adding a lightweight existence-only lookup to the external service, and that comes back later as a deploy-order problem.

<Note title="The question I should have asked first">

I wish this had come earlier. "What does this code actually need?" should have been the first question when the optimization started. I started with "how do I fetch this faster?" and only got to "does it need to fetch this at all?" at step three.

</Note>

## Arguing against "just merge them": two consumers, two policies

Since the read path and validation path did similar work, someone proposed lifting the loading into one place both could share. No more duplication, one place to maintain; it was tempting. But I had to argue against it.

| Consumer | Needs | If missing |
| --- | --- | --- |
| Validation | existence only | fail-hard: reject the request |
| Read path | status values too (for warnings) | fail-soft: log a warning and carry on |

They needed different data and had opposite failure policies. Merging the fetch wholesale would make validation pull in detailed data it doesn't need, undoing the slimming we had just achieved.

That doesn't mean nothing was worth sharing. What really deserved sharing was the collection logic that extracts which resources a plan references, the part where a change to the plan's structure should be fixed in exactly one place. <mark>The seam was between collecting and fetching, not between one fetch and another.</mark>

And this is where the biggest risk in the design was. The read path's logic is fail-soft. If that policy leaked through the shared layer into validation, resources that don't exist would pass validation. Breaking correctness while fixing performance is the worst possible outcome.

<Compare>
<Side title="The shared layer owns a policy" tone="bad">

- The shared layer carries the read path's policy (fail-soft) as-is
- That's fine for the read path
- In validation, missing resources slip through

</Side>
<Side title="The shared layer only holds errors" tone="good">

- The shared layer just collects errors
- The read path decides whether they become warnings
- Validation decides whether to reject

</Side>
</Compare>

<Note title="What may be merged, and what must not">

The shared layer only holds errors and owns no policy; each consumer makes its own call. When merging code, "what to fetch" can be merged. "What to do when it's missing" must never be. That's domain policy, and it differs per consumer.

</Note>

## Optimization changes failure modes

Consolidating syncing into once per request left an uncomfortable question: what if that one sync fails?

Checking the existing behavior, a failed sync just logged and carried on with stale data. So even today, validation was best effort, not a real-time guarantee. The issue wasn't the policy; it was <mark>the blast radius of a failure</mark>.

After some thought, I kept allowing stale data. There were three reasons, in decreasing weight.

1. **No regression.** It matches current behavior; this change doesn't introduce a new risk.
2. **Availability comes first.** A temporary outage in an external system blocking all saves would be worse.
3. **It was never achievable anyway.** A resource can be deleted right after passing validation. Validation as a real-time guarantee was impossible from the start.

The third was decisive. There's always a gap between validating and actually using a resource, and state can change in between. Once I accepted this TOCTOU (time-of-check to time-of-use) gap, the picture changed: the real safety net is rechecking at execution time, not validating at save time. I had been giving validation more meaning than it could carry.

Instead, I decided to surface failures rather than swallow them quietly, and I recorded the decision in an ADR, because it's hard to reverse, looks odd without context, and is a genuine trade-off. When someone later asks why we proceed even when this fails, the answer can't be missing from the codebase.

## Why I chose not to add a fallback

Adding the lightweight lookup API to the external service created a deploy order. What if the other side is still on the old version? The natural proposal was a safe fallback: if the new API isn't there, use the old path.

<Compare>
<Side title="Add a fallback" tone="bad">

You keep the very code that's timing out today alive forever. Dead code can simply be deleted, but a fallback is slow code that runs only occasionally, which is worse: it's effectively untested, and it's hard to track which environments take that path.

</Side>
<Side title="Don't" tone="good">

You have to respect the deploy order. In return, the code that needed fixing is definitely gone.

</Side>
</Compare>

I chose not to. The deciding factor was that the interface definitions are pinned as a module, so the build already enforces the order. What's left is runtime compatibility, and I judged that to be a job for the deploy procedure, not for code.

A fallback looks like a safety net at first glance, but often it postpones a problem instead of solving it, especially when the fallback is the exact bug you're trying to fix.

## Being honest about the numbers

The final design's expected effect came out like this.

| Per request | Now | After |
| --- | --- | --- |
| External auth sessions | about 300 | 1 |
| Service-to-service round trips | about 300 | 2 |

It looks convincing, but <mark>this is arithmetic built on an assumed time per call, not a measurement.</mark> So instrumentation went in as the very first task. You can't capture a baseline after the fix; at that point you'll never be able to say how much better it got.

On this project I got the math wrong twice: once by not looking at cost per call, and once by not looking inside the bulk API. There's only one way to avoid a third time: measure.

## Summary

- **Call count and cost per call multiply.** Optimize without knowing which dominates and you'll only cut whatever is easiest.
- **The answer may already be in the repo, but you still have to read it.** This time the answer had its own trap.
- **Several routes to the same information can cost very differently.** Comparison starts with knowing two APIs answer the same question.
- **Two consumers means two sets of requirements.** "What to fetch" can be merged; "what to do when it's missing" can't.
- **Pin down where a performance fix could break correctness, up front.** This time it was a leaking fail-soft policy.
- **Optimization changes failure modes.** If you're trading scattered partial failures for one all-or-nothing failure, know it and sign off on it.
- **Don't quote estimates as if they were measurements.** And capture the baseline before you fix anything.

The biggest lesson is this. Within the first 30 minutes I had "it's N+1, batch it," and it was only half right. If that answer had been a little less plausible, I would have looked longer. The most dangerous moment is when your first answer looks like the right one.
