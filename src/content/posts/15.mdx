<Lead>
`ctx`를 첫 인자로 받아서 넘기는 것까지는 하고 있었다. 그런데 취소하면 고루틴이 정말 멈추는지는 확인해 본 적이 없었다. 면접에서 그 질문에 말이 막힌 뒤 context를 처음부터 다시 봤다. 취소는 멈추라는 신호를 보낼 뿐이고, 실제로 멈추는 건 받는 쪽이었다.

이 글은 context의 모양과 트리, 취소가 전해지는 방식, 시간 예산, 함정 넷, 1.20 이후에 생긴 API 순서로 가고, 예제는 모두 Go 1.26.10에서 다시 돌려 확인했다.
</Lead>

<Summary>
1. 취소는 협조 요청이다. Go에는 고루틴을 밖에서 죽이는 방법이 없어서, 받는 쪽이 `Done()`을 직접 확인해야 멈춘다.
2. context는 트리다. 부모가 취소되면 자식이 전부 따라 취소되고, deadline은 짧아지기만 한다. 이게 서비스 체인의 시간 예산이 된다.
3. 함정 넷은 전부 수명의 문제다. `cancel` 미호출, 정리 로직 동반 사망, `WithValue` 남용, 구조체 필드 저장.
</Summary>

<Note title="누구를 위한 글인가">
`ctx`를 첫 인자로 받고 `defer cancel()`도 쓰지만, 취소가 실제로 무엇을 멈추는지와 `cancel`을 빼먹으면 무엇이 남는지는 돌려 본 적 없는 사람을 기준으로 썼다. 1\~3절은 context의 모양과 취소가 전해지는 방식, 4절은 시간 예산, 5절은 함정 넷, 6절은 1.20 이후에 생긴 API다. 감싼 에러를 `errors.Is`로 찾는 방법은 [3편](/13)에서 다뤘다.
</Note>

## 왜 필요한가: 유령 작업

요청 하나가 들어오면 서버는 그 안에서 여러 갈래로 뻗어 DB를 치고, 외부 API를 부르고, 파일을 읽고, 그 각각이 또 고루틴을 띄운다. 그런데 클라이언트가 3초 만에 연결을 끊어 버리면?

알려 줄 수단이 없으면 서버는 아무도 기다리지 않는 결과를 계속 만든다. 이게 유령 작업이다. 평소엔 티가 안 나다가, 장애로 응답이 느려져 클라이언트들이 타임아웃으로 끊기 시작하면 <mark>버려진 작업이 쌓여 자원을 다 먹고 연쇄 장애로 번진다.</mark> context는 그 상황에서 그만해도 된다는 신호를 호출 체인 전체에 전파하는 표준 수단이다.

정체는 의외로 단순하다. 메서드 네 개짜리 인터페이스다.

```go title="context.Context"
type Context interface {
	Deadline() (deadline time.Time, ok bool) // 언제까지인가
	Done() <-chan struct{}                   // 끝났음을 알리는 채널 (닫히면 신호)
	Err() error                              // 왜 끝났나 (Canceled / DeadlineExceeded)
	Value(key any) any                       // 요청 범위 값
}
```

쓰는 법은 만드는 함수 넷과 읽는 방법 둘이면 거의 끝난다.

| 만들기 | 언제 |
| --- | --- |
| `Background()` | 트리의 뿌리. main, 초기화, 테스트, 그리고 들어오는 요청의 최상단 |
| `WithCancel` | 내가 원할 때 직접 끊고 싶을 때 |
| `WithTimeout` / `WithDeadline` | 시간 상한을 걸 때. 실무에서 가장 많이 쓴다 |
| `WithValue` | 요청 ID, 트레이스 같은 요청 범위 메타데이터만 (뒤에서 자세히) |

| 읽기 | 무엇을 |
| --- | --- |
| `select` + `ctx.Done()` | 끝났는지 감시한다 |
| `ctx.Err()` | 끝난 이유. `Canceled`인가 `DeadlineExceeded`인가 |

중요한 건 이들이 트리를 만든다는 점이다. `WithXxx`는 부모를 받아 파생 context를 만들고, <mark>취소는 위에서 아래로만 흐른다.</mark>

## 취소는 협조 요청이다: 멈추는 건 받는 쪽

면접에서 context로 취소하면 고루틴이 죽느냐는 질문을 받고 말이 막힌 적이 있다. 답은 아니오다.

<mark>Go에는 고루틴을 밖에서 강제 종료하는 방법이 아예 없다.</mark> 스레드를 kill하는 API도, 인터럽트도 없다. 그래서 `cancel()`은 채널을 닫아 그만해도 된다고 알리기만 하고, 실제로 멈추는 건 받는 쪽의 몫이다. 공식 문서도 `CancelFunc`가 작업이 멈추기를 기다리지 않는다고 못 박는다.

<Compare>
<Side title="Done()을 보는 루프" tone="good">

```go
for _, vm := range vms {
	select {
	case <-ctx.Done():
		return ctx.Err()
	default:
	}
	copyDisk(ctx, vm)
}
```

다음 반복에서 빠져나온다.

</Side>
<Side title="Done()을 안 보는 루프" tone="bad">

```go
for _, vm := range vms {
	copyDisk(vm)
}
```

신호가 와도 확인하지 않으니 끝까지 돈다. 이게 유령 작업이다.

</Side>
</Compare>

<Lab title="cancel()은 기다리지 않았고, 안 보는 루프는 끝까지 돌았다">

두 루프를 그대로 돌려 봤다. 항목은 10개이고 하나에 100ms가 걸리며, `checks`는 항목마다 `Done()`을 확인하고 `ignores`는 `ctx`를 받기만 한다. 250ms 뒤에 `cancel()`을 부르고, `cancel()`이 돌아오는 데 걸린 시간과 처리한 항목 수를 찍었다.

```go title="coop/main.go"
func run(name string, loop func(context.Context) int) {
	ctx, cancel := context.WithCancel(context.Background())
	start := time.Now()
	done := make(chan int)
	go func() { done <- loop(ctx) }()

	time.Sleep(250 * time.Millisecond)
	t := time.Now()
	cancel()
	took := time.Since(t)
	n := <-done
	fmt.Printf("%s: cancel() 반환 %v, %d개 처리, %v\n", name,
		took.Round(time.Microsecond), n, time.Since(start).Round(10*time.Millisecond))
}

func main() {
	run("보는 루프", checks)
	run("안 보는 루프", ignores)
}
```

```text frame="terminal" title="실행 결과"
$ go run ./coop
보는 루프: cancel() 반환 62µs, 3개 처리, 300ms
안 보는 루프: cancel() 반환 4µs, 10개 처리, 1.01s
```

보는 루프는 세 번째 항목을 마치고 네 번째 앞에서 멈췄지만, 안 보는 루프는 취소한 뒤에도 10개를 다 처리했다. `cancel()`은 두 번 모두 수십 µs 안에 돌아왔고(네 번 돌려 3µs에서 62µs 사이), 루프가 멈추기를 기다리지 않는다는 문서 그대로였다.

</Lab>

취소했는데 왜 안 멈추냐는 질문의 답은 대부분 Done()을 안 보는 쪽 코드다. 그래서 취소 체크를 어디에 넣느냐가 실제 설계 포인트가 되고, 원칙은 오래 걸리는 일을 시작하기 직전이다.

```go title="오래 걸리는 일 직전에 확인한다"
func migrate(ctx context.Context, vms []VM) error {
	for _, vm := range vms {
		select {
		case <-ctx.Done():
			return ctx.Err() // Canceled 또는 DeadlineExceeded
		default: // default가 있으니 막히지 않고 지나간다
		}
		if err := copyDisk(ctx, vm); err != nil { // 하위에도 그대로 넘긴다
			return err
		}
	}
	return nil
}
```

다행히 표준 라이브러리는 알아서 봐 준다. `net/http`나 `database/sql`처럼 ctx를 받는 API는 안에서 `Done()`을 감시하다가 취소되면 중단하고 에러를 돌려준다. 내가 직접 체크를 넣어야 하는 건 내가 짠 긴 루프와 CPU를 오래 쓰는 작업이다.

서버가 `ctx`를 넘기고 있는데도 취소 뒤에 부하가 안 줄어든다면, 체인 어딘가에 `Done()`을 안 보는 구간이 있을 가능성이 크다. 나는 이럴 때 오래 도는 루프부터 찾는다.

## Done()이 브로드캐스트가 되는 이유

여기서 궁금해진 게 있었다. 고루틴이 100개인데 취소 신호를 어떻게 100개 전부에게 동시에 보낼까. 채널에 값을 보내면 하나만 받아 가는데.

답은 값을 보내지 않는다는 것이다. context는 채널을 닫는다. <mark>닫힌 채널에서 수신하면 기다리던 모두가 즉시 제로값을 받고 깨어난다.</mark> 채널 하나로 몇 명에게든 알릴 수 있는 셈이다.

```go title="broadcast/main.go"
var woke atomic.Int32

	go func() {
		<-ch
		woke.Add(1)
	}()
}
```

## 시간 예산: deadline은 짧아지기만 한다

context에서 가장 늦게 이해한 게 이거였다. `WithTimeout`을 몇 초 뒤에 끊는 장치로만 알았는데, 실제로는 요청 전체에 시간 예산을 배정하고 그 예산을 체인이 나눠 쓰게 하는 장치였다.

<mark>파생 context의 deadline은 부모보다 늦어질 수 없다.</mark> 부모가 3초 뒤에 끝나는데 자식이 10초를 걸어도 실제 상한은 여전히 3초다. 아래로 내려갈수록 남은 시간이 줄어들기만 한다.

<Lab title="10초를 건 자식의 deadline은 부모와 같았다">

3초짜리 부모에서 10초짜리 자식을 만들고 두 deadline의 차를 찍은 다음, 자식만 취소했다.

```go title="deadline/main.go"
parent, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()
child, cancel2 := context.WithTimeout(parent, 10*time.Second)

pd, _ := parent.Deadline()
cd, _ := child.Deadline()
fmt.Println("자식 deadline - 부모 deadline:", cd.Sub(pd))
fmt.Println("자식에게 남은 시간:", time.Until(cd).Round(100*time.Millisecond))

cancel2() // 자식만 취소한다
fmt.Println("자식 Err:", child.Err())
fmt.Println("부모 Err:", parent.Err())
```

```text frame="terminal" title="실행 결과"
$ go run ./deadline
자식 deadline - 부모 deadline: 0s
자식에게 남은 시간: 3s
자식 Err: context canceled
부모 Err: <nil>
```

자식의 deadline은 부모와 똑같았다. 10초를 달라고 했는데도 그렇게 된 건, 부모 deadline이 더 이르면 `WithDeadline`이 타이머를 새로 만들지 않고 `WithCancel`로 돌려주기 때문이다. 자식을 취소한 뒤에도 부모의 `Err()`는 `nil`이었다.

## 함정 넷: 전부 수명의 문제

앞의 둘은 context의 수명을 끝내지 않거나 너무 일찍 끝내는 문제고, 뒤의 둘은 호출 하나만큼 사는 ctx를 그보다 오래 사는 곳에 두는 문제다.

### ① cancel을 안 부르면 샌다

`defer cancel()`을 관용구로 외워 쓰다가, 안 부르면 정확히 무엇이 새는지는 몰랐다. 공식 문서가 짧게 답해 준다. `cancel`을 부르면 세 가지가 일어난다.

1. 자식과 그 자식들을 취소한다.
2. 부모가 자식을 가리키던 참조를 끊는다.
3. 관련 타이머를 멈춘다.

안 부르면 이 셋이 일어나지 않는다. 문서는 부모가 취소될 때까지 자식이 샌다고 적는다. 오래 사는 부모에서 `WithCancel`로 파생했다면 그 시점은 서버가 내려갈 때다. <mark>한 요청에서는 티가 안 나고, 초당 수천 요청에서 드러난다.</mark>

<Lab title="cancel을 버린 자식 10만 개가 11.5MB를 붙잡았다">

서버만큼 오래 사는 부모를 하나 두고 `WithCancel`로 자식 10만 개를 만들되, 한 번은 바로 `cancel`을 부르고 한 번은 버렸다. `heapMB`는 GC를 두 번 돌리고 살아 있는 힙 크기를 재는 작은 함수다.

```go title="leak/main.go"
parent, stop := context.WithCancel(context.Background()) // 서버만큼 오래 사는 부모
base := heapMB()

for range 100_000 {
	_, cancel := context.WithCancel(parent)
	cancel()
}
fmt.Printf("cancel 부름:    +%.1f MB\n", heapMB()-base)

for range 100_000 {
	context.WithCancel(parent) // cancel을 버린다
}
fmt.Printf("cancel 안 부름: +%.1f MB\n", heapMB()-base)

stop() // 부모를 취소한다
fmt.Printf("부모 취소 뒤:   +%.1f MB\n", heapMB()-base)
```

```text frame="terminal" title="실행 결과"
$ go run ./leak
cancel 부름:    +0.0 MB
cancel 안 부름: +11.5 MB
부모 취소 뒤:   +0.0 MB
```

코드 어디에서도 자식을 쓰지 않는데 GC가 거둬 가지 못한 건 부모가 자식 목록에 참조를 쥐고 있어서다. 자식 하나에 115바이트쯤이었고, 부모를 취소하자 다시 0이 됐다.

</Lab>

타임아웃이 이미 지났다면 어떨까. 타이머가 울리면 context가 스스로 취소되면서 부모 참조도 함께 끊으니, 그때는 `cancel`이 할 일이 거의 없다. 문제는 일이 일찍 끝난 경우다. 2초 만에 끝났어도 `cancel`을 안 부르면 남은 1초 동안 타이머와 참조가 그대로 남는다. 어느 쪽이든 만든 직후 `defer cancel()`이면 신경 쓸 일이 없다.

<Lab title="cancel을 빼먹으면 go vet이 잡는다">

한 분기에서만 `cancel`을 부르는 코드를 일부러 만들어 `go vet`을 돌려 봤다.

```go title="leak.go"
func leak(ctx context.Context) {
	ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
	if ctx == nil {
		cancel()
		return
	}
}
```

```text frame="terminal" title="실행 결과"
$ go vet ./...
leak.go:9:2: the cancel function is not used on all paths (possible context leak)
leak.go:14:1: this return statement may be reached without using the cancel var defined on line 9
```

모든 경로에서 `cancel`이 불리는지 검사하고 빠지는 return 위치까지 알려 주니, CI에 `go vet`을 넣어 두면 이 함정은 사람이 기억할 필요가 없다.

</Lab>

### ② 취소되면 정리 로직도 같이 죽는다

이건 실제로 겪고 나서야 알았다. 작업이 실패해서 롤백을 하는데, 롤백 코드에도 같은 `ctx`를 넘기고 있었다. 이미 취소된 ctx다. 롤백이 시작하자마자 취소돼서, 지워야 할 스냅샷이 스토리지에 그대로 남아 비용이 계속 나갔다. 에러 로그도 `context canceled`뿐이라 원인이 정리 실패라는 걸 알아채기 어려웠다.

논리적으로는 당연한 일이었다. 취소 신호는 이 요청과 관련된 모든 작업을 멈추라는 뜻이고, 정리 작업도 그 안에 들어간다. 그래서 <mark>정리는 취소 신호에서 명시적으로 떼어 내야 한다.</mark>

<Compare>
<Side title="같은 ctx로 정리한다" tone="bad">

```go
func rollback(ctx context.Context, id string) {
	deleteSnapshot(ctx, id) // context canceled
}
```

정리가 시작하자마자 죽는다. 지워야 할 자원이 계속 과금된다.

</Side>
<Side title="떼어 내고 상한은 새로 준다" tone="good">

```go
func rollback(ctx context.Context, id string) {
	cctx := context.WithoutCancel(ctx)
	cctx, cancel := context.WithTimeout(cctx, 30*time.Second)
	defer cancel()
	deleteSnapshot(cctx, id)
}
```

정리는 반드시 수행되고, 그렇다고 영원히 매달리지도 않는다 (Go 1.21+).

</Side>
</Compare>

`WithoutCancel`은 값은 그대로 물려주면서 취소만 끊어 준다. 요청 ID나 트레이스 정보를 유지한 채 정리 작업의 로그를 남길 수 있다는 점이 좋다. 다만 deadline도 함께 사라지므로 새 타임아웃을 반드시 걸어야 하고, 안 그러면 이번엔 정리가 영원히 안 끝나는 반대 문제가 생긴다.

### ③④ WithValue 남용과 구조체 필드 저장

나머지 둘은 쓰지 말아야 할 곳에 쓰는 문제다. 공식 문서가 규칙을 명확히 적어 둬서, 헷갈릴 때 그대로 따르면 된다.

| 규칙 | 이유 |
| --- | --- |
| 구조체 안에 넣지 않는다 | ctx는 객체의 수명이 아니라 호출 하나의 수명에 묶인다. 필드에 박아 두면 언제 취소되는지 알 수 없다 |
| 첫 번째 인자로, 이름은 `ctx` | 문서가 정한 관례라 읽는 사람도 린터도 그 자리를 기대한다 |
| nil을 넘기지 않는다 | 무엇을 넣을지 모르겠으면 `context.TODO()`를 넘긴다. 나중에 고칠 자리라는 표시가 된다 |
| Value는 요청 범위 데이터만 | 함수의 선택적 파라미터를 넘기는 용도가 아니다 |
| 키는 비공개 타입으로 | `string` 같은 기본 타입을 쓰면 다른 패키지와 키가 충돌한다 |

넷째 줄이 실무에서 가장 자주 어긋난다. `WithValue`가 편해 보여서 필수 파라미터를 여기에 숨기기 시작하면, 함수 시그니처만 봐서는 무엇이 필요한지 알 수 없고 타입 안전성도 사라진다. 값이 빠져 있어도 컴파일은 통과하고, 꺼내는 쪽의 타입 단언에서 실행 중에 panic이 난다.

```go title="필수 값은 인자로, 키는 비공개 타입으로"
// 나쁨: 필수 파라미터를 ctx에 숨긴다. 시그니처가 아무것도 말해 주지 않는다
func createOrder(ctx context.Context) error {
	userID := ctx.Value("userID").(string) // 없으면 런타임 panic
	// ...
}

// 좋음: 필수는 인자로, ctx에는 요청 범위 메타데이터만
func createOrder(ctx context.Context, userID string) error { /* ... */ }

// 키는 반드시 비공개 타입으로
type traceIDKey struct{} // 다른 패키지는 이 타입을 만들 수 없다

func WithTraceID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, traceIDKey{}, id)
}
func TraceIDFrom(ctx context.Context) (string, bool) { // 타입 안전한 접근자를 같이 둔다
	id, ok := ctx.Value(traceIDKey{}).(string)
	return id, ok
}

// 구조체 필드가 아니라 메서드 인자로
type Server struct{ ctx context.Context }          // 나쁨
func (s *Server) Handle(ctx context.Context) error // 좋음
```

<Lab title="string 키에서는 다른 패키지의 값이 나왔다">

패키지 `a`와 `b`가 둘 다 `"id"`라는 `string` 키로 값을 넣게 했는데, `a`는 사용자 ID를 넣고 나중에 `b`가 요청 ID를 넣는다. 마지막 두 줄은 아무도 넣지 않은 값을 타입 단언으로 꺼낸다.

```go title="value/main/main.go"
ctx := a.WithUser(context.Background(), "user-7")
ctx = b.WithRequest(ctx, "req-42")
fmt.Println("a 패키지가 꺼낸 사용자:", a.User(ctx))

defer func() { fmt.Println("panic:", recover()) }()
userID := context.Background().Value("userID").(string)
fmt.Println(userID)
```

```text frame="terminal" title="실행 결과"
$ go run ./value/main
a 패키지가 꺼낸 사용자: req-42
panic: interface conversion: interface {} is nil, not string
```

`a`가 넣은 `user-7` 대신 `b`의 `req-42`가 나왔다. 두 키가 같은 `string` 값이라 같은 키로 본 것이다. 아무도 넣지 않은 값은 `nil`이라 `.(string)`에서 panic이 났는데, 두 실수 모두 컴파일도 `go vet`도 아무 말 없이 통과했다.

</Lab>

## 알아 두면 좋은 최신 API

context 패키지는 조용히 계속 커졌다. 특히 왜 취소됐는지 알 수 없던 문제가 1.20에서 풀렸는데, 이걸 모르고 `context canceled`라는 의미 없는 로그만 보고 있었다.

- `WithCancelCause`, `Cause` (1.20): 취소에 이유를 실어 보낸다. 디버깅이 훨씬 쉬워진다.
- `WithoutCancel` (1.21): 정리, 감사 로그처럼 취소돼도 끝내야 하는 작업을 떼어 낸다.
- `AfterFunc` (1.21): ctx가 끝나면 함수를 실행한다. `Done()`을 지켜보는 고루틴을 직접 띄우지 않아도 된다.
- `WithTimeoutCause`, `WithDeadlineCause` (1.21): 타임아웃에도 이유를 붙인다. 어느 단계에서 예산이 터졌는지 알 수 있다.

```go title="cause/main.go"
ctx, cancel := context.WithCancelCause(parent)
cancel(fmt.Errorf("업스트림 5xx 연속 발생: %w", err)) // err는 마지막 502 응답
fmt.Println(ctx.Err(), "|", context.Cause(ctx))

tctx, cancel2 := context.WithTimeoutCause(parent, 10*time.Millisecond,
	errors.New("재고 조회 예산 10ms 초과"))
defer cancel2()
<-tctx.Done()
fmt.Println(tctx.Err(), "|", context.Cause(tctx))
```

```text frame="terminal" title="실행 결과"
$ go run ./cause
context canceled | 업스트림 5xx 연속 발생: 502
context deadline exceeded | 재고 조회 예산 10ms 초과
```

`Err()`는 언제나 `context canceled`나 `context deadline exceeded` 둘 중 하나라 쓸모가 적었다. 필요했던 정보는 `Cause()` 쪽에 있다.

여러 작업 중 하나라도 실패하면 전부 취소하는 패턴은 `errgroup`이 감싸 준다.

```go title="errgroup: 첫 에러가 나면 나머지를 취소한다"
g, gctx := errgroup.WithContext(ctx)
g.Go(func() error { return fetchUser(gctx) })
g.Go(func() error { return fetchOrders(gctx) })
if err := g.Wait(); err != nil { // 첫 에러가 나면 gctx가 자동으로 취소된다
	return err
}
```

`fetchUser`는 50ms 만에 실패하고, `fetchOrders`는 2초 걸리면서 `gctx.Done()`을 지켜보게 해서 돌려 봤다.

```text frame="terminal" title="실행 결과"
$ go run ./group
fetchOrders: 50ms 뒤 멈춤 (context canceled)
Wait: fetchUser: 503, 50ms 걸림
```

2초짜리 fetchOrders가 50ms에 멈췄고 `Wait`는 첫 에러를 돌려줬는데, 여기서도 멈춘 건 `gctx.Done()`을 지켜보던 받는 쪽이었다.

에러를 판별할 때는 [3편](/13)에서 본 방식이 그대로 쓰여서, 감싸진 에러 안에서도 원인을 찾도록 `==` 대신 `errors.Is`를 쓴다.

```go title="원인별로 다르게 처리한다"
if errors.Is(err, context.DeadlineExceeded) {
	return status(504) // 시간 초과
}
if errors.Is(err, context.Canceled) {
	return // 클라이언트가 이미 떠났다. 응답할 필요도 없다
}
```

`ctx.Err()`를 `%w`로 한 번 감싸기만 해도 `==` 비교는 바로 `false`가 되고, 원인을 찾아내는 건 `errors.Is`뿐이었다.

```text frame="terminal" title="실행 결과"
$ go run ./iswrap
재고 조회: context deadline exceeded
err == context.DeadlineExceeded: false
errors.Is(err, context.DeadlineExceeded): true
```

## 실습 환경과 한계

예제는 모두 이 맥(Apple M5, 10코어, darwin/arm64)에서 Go 1.26.10으로 다시 돌렸고, errgroup은 `golang.org/x/sync` v0.23.0을 썼다. 처음 올린 글과 달라진 곳이 둘 있다. `go vet` 출력은 실제로 돌려 보니 파일 경로 앞에 `./`가 붙지 않아 그대로 옮겼다. `cancel`을 안 부를 때 언제까지 새는지 적은 문서 문장은 Go 1.24에서 바뀌었는데, 1.23까지 '부모가 취소되거나 타이머가 울릴 때까지'였던 것이 지금은 '부모가 취소될 때까지'로 줄어서 본문도 지금 문장으로 고쳤다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| 두 루프와 `cancel()` | 확인하지 않는 루프가 끝까지 도는 것, `cancel()`이 기다리지 않는 것 | 다른 기기에서의 µs 값 |
| 값 보내기와 채널 닫기 | 깨어난 고루틴 수 1과 100 | 없다. 명세가 정한 동작이다 |
| 자식 deadline · 체인 예산 | 한 프로세스 안에서 남은 시간 | gRPC로 프로세스를 넘을 때. 문서로만 확인했다 |
| HTTP 요청 ctx | HTTP/1.1에서 연결이 끊긴 뒤 핸들러 ctx가 취소되는 시점 | HTTP/2나 프록시를 거칠 때의 시점 |
| `cancel`을 버린 자식 10만 개 | 이 맥에서 붙잡힌 힙 11.5MB | 다른 버전·아키텍처의 바이트 수 |
| `WithoutCancel` · `Cause` · errgroup | 남는 값, 출력 문자열, 멈춘 시점 | 다른 버전의 메시지 형식 |
| `string` 키 · 타입 단언 | 값이 덮이는 것과 panic 메시지 | staticcheck 같은 다른 린터의 경고. 돌려 보지 않았다 |

## 정리

| 이 글에서 본 것 | 원인 |
| --- | --- |
| `Done()`을 안 보는 루프가 취소 뒤에도 10개를 다 처리했다 | 취소는 채널을 닫는 신호일 뿐 고루틴을 멈추지 않는다 |
| `cancel()`은 수십 µs 안에 돌아왔다 | `CancelFunc`는 작업이 멈추기를 기다리지 않는다 |
| 값 하나에 1개, 채널을 닫자 100개가 깨어났다 | 닫힌 채널의 수신은 기다리던 모두에게 바로 돌아온다 |
| 10초를 건 자식의 deadline이 부모와 같았다 | deadline은 부모보다 늦어질 수 없다 |
| 클라이언트가 끊자 핸들러 ctx가 200ms 만에 취소됐다 | `net/http`는 연결이 닫히면 요청 ctx를 취소한다 |
| `cancel`을 버린 자식 10만 개가 11.5MB를 붙잡았다 | 부모가 자식 목록에 참조를 쥔다 |
| 취소된 ctx로 한 정리가 바로 실패했다 | 정리도 같은 요청의 작업이라 함께 취소된다 |
| `"id"` 키로 넣은 값이 다른 패키지 값으로 바뀌었다 | 기본 타입 키는 패키지 사이에서 겹친다 |

그래서 긴 루프에는 `Done()` 확인을 넣고, context를 만들면 바로 `defer cancel()`을 쓰고, 정리 작업은 `WithoutCancel`과 새 타임아웃으로 떼어 내고, 키는 비공개 타입으로 둔다.

### 다섯 편을 쓰고 나서

돌아보니 각 편의 함정이 같은 모양이었다. 인터페이스 값이 두 칸이라는 것, 슬라이스가 배열을 들여다보는 창이라는 것, defer와 클로저가 무엇을 언제 붙잡는지, 임베딩의 승격이 호출을 되돌리지 않는다는 것, 그리고 취소가 명령이 아닌 신호라는 것. 다섯 번 모두 그게 실제로 무엇인지를 착각했을 때 함정에 빠졌다. 이 이야기는 [정리 편](/20)에서 두 축으로 다시 묶었다.
