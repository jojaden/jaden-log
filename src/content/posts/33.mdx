<Lead>
이름을 IP로 바꿨으니 이제 그 IP로 연결을 연다. `http.Client`가 연결을 알아서 다시 쓴다는 것까지는 알고 있었는데, 그게 얼마나 차이 나는지는 재 본 적이 없었다. 지연 프록시를 끼워 재 보니 HTTPS 첫 요청은 TLS 1.2에서 <C k="num">155ms</C>, 같은 연결을 다시 쓰면 <C k="num">50ms</C>였고, 연결을 매번 새로 열면 서버 쪽에 TIME_WAIT가 거의 요청 수만큼 쌓였다. 응답 Body를 읽지 않고 닫으면 연결을 버린다는 것도 세어 봤는데, Go 1.27부터는 작은 응답이면 결과가 달라져 있었다.
</Lead>

</Note>

## TCP는 세 번 주고받아 연결한다

지난 편에서 이름을 IP로 바꿨으니, 이번 정거장은 그 IP로 실제 연결을 여는 단계다. 연결을 열 때는 두 가지를 준비한다. 데이터를 빠짐없이 순서대로 실어 나르는 통로(TCP)와, 그 통로로 오가는 내용을 남이 못 읽게 잠그면서 상대가 진짜인지 확인하는 장치(TLS)다.

먼저 TCP부터 보자. 인터넷은 데이터를 작은 조각(패킷)으로 나눠 보내는데, 가는 길에 조각이 사라지거나 순서가 바뀔 수 있다. TCP는 <mark>사라진 조각은 다시 보내고, 받은 조각은 보낸 순서대로 맞춰 주는 프로토콜</mark>이다. UDP는 보내기만 하고 뒷일은 책임지지 않는다.

전화로 치면 “여보세요?”, “네, 여보세요”, “네”를 주고받은 뒤에 통화를 시작하는 것과 같다. 다만 TCP가 확인하는 건 목소리가 아니라 시작 번호다.

왜 하필 세 번일까? TCP는 보내는 바이트마다 번호(시퀀스 번호, 그림 1의 1\~4)를 붙여 무엇이 빠졌는지 안다. 그래서 양쪽은 시작 번호를 알려 주고 확인받아야 하는데, 각자 보내고 확인받는 네 번 가운데 가운데 두 개를 한 패킷(SYN-ACK)에 합쳐서 세 번이 된다.

## 끊을 때는 네 번, 먼저 끊은 쪽이 남는다

끊을 때는 네 번 주고받는다. FIN은 “나는 보낼 게 끝났다”는 뜻이다. TCP 연결은 양쪽이 서로에게 보내는 길이 따로 있어서, FIN을 방향마다 따로 보내야 한다. 한쪽이 FIN을 보내도 상대는 아직 보낼 데이터가 남아 있을 수 있으니, 상대는 ACK부터 보내고 자기 데이터를 다 보낸 뒤에 FIN을 보낸다.

먼저 끊은 쪽은 마지막 ACK를 보낸 뒤에도 바로 사라지지 않고 TIME_WAIT 상태로 2MSL 동안 남는다.[^msl] 리눅스에서는 이 시간이 60초로 고정돼 있다. 표준 커널에는 이 값을 바꾸는 sysctl도 없다. 이름이 비슷한 `net.ipv4.tcp_fin_timeout`은 상대의 FIN을 기다리는 FIN_WAIT_2 상태의 시간이라 TIME_WAIT와는 관계가 없다.

## TIME_WAIT는 누구에게 쌓이나

<Lab title="연결을 매번 새로 열면 서버 쪽에 TIME_WAIT가 쌓인다">

같은 프로그램 안의 Go HTTP 서버에 요청을 100번, keep-alive를 끄고 한 번, 켜고 한 번 보냈다. TIME_WAIT는 <C k="path">/proc/net/tcp</C>에서 상태 `06`인 줄을 로컬 포트로 서버·클라이언트 쪽을 나눠 세고, 30초, 59초, 65초에 다시 셌다. 리눅스 컨테이너 안이라 다른 프로그램의 소켓은 섞이지 않는다.

```go title="tcplab/tw/main.go"
package main

import (
	"fmt"
	"io"
	"net"
	"net/http"
	"os"
	"strconv"
	"strings"
	"time"
)

// /proc/net/tcp 에서 TIME_WAIT(상태 06) 소켓을 서버 쪽·클라이언트 쪽으로 나눠 센다.
func timeWait(serverPort int) (server, client int) {
	b, _ := os.ReadFile("/proc/net/tcp")
	for _, l := range strings.Split(string(b), "\n")[1:] {
		f := strings.Fields(l)
		if len(f) < 4 || f[3] != "06" {
			continue
		}
		local, _ := strconv.ParseInt(f[1][strings.Index(f[1], ":")+1:], 16, 32)
		if int(local) == serverPort {
			server++
		} else {
			client++
		}
	}
	return
}

func main() {
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	port := ln.Addr().(*net.TCPAddr).Port
	go http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		io.WriteString(w, "ok")
	}))

	var start time.Time
	for _, keepAlive := range []bool{false, true} {
		tr := &http.Transport{DisableKeepAlives: !keepAlive}
		c := &http.Client{Transport: tr}
		s0, c0 := timeWait(port)
		for i := 0; i < 100; i++ {
			resp, err := c.Get("http://" + ln.Addr().String())
			if err != nil {
				panic(err)
			}
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
		}
		if !keepAlive {
			start = time.Now() // keep-alive를 끈 100번이 끝난 시각
		}
		tr.CloseIdleConnections() // 재사용하던 연결은 여기서 클라이언트가 닫는다
		time.Sleep(200 * time.Millisecond)
		s1, c1 := timeWait(port)
		fmt.Printf("keep-alive %-5v 요청 100번 → TIME_WAIT 서버 쪽 +%d, 클라이언트 쪽 +%d\n",
			keepAlive, s1-s0, c1-c0)
	}

	// 서버 쪽 TIME_WAIT가 언제 사라지는지 본다
	for _, sec := range []int{30, 59, 65} {
		time.Sleep(time.Until(start.Add(time.Duration(sec) * time.Second)))
		s, _ := timeWait(port)
		fmt.Printf("%2d초 뒤 서버 쪽 TIME_WAIT %d개\n", sec, s)
	}
}
```

비대칭키는 잠그는 키와 여는 키가 달라 처음 만난 상대와도 안전하게 시작할 수 있지만 느리고, 대칭키는 같은 키로 잠그고 열어 빠르지만 같은 키를 먼저 나눠 가져야 한다. 그래서 TLS는 처음 핸드셰이크에서만 비대칭키로 서버를 확인하고 이번 연결에서만 쓸 키(세션 키)를 맞춘 뒤, 그다음부터는 그 세션 키로 빠른 대칭키 암호를 쓴다.

<Lab title="CA를 모르거나 이름이 다르면 핸드셰이크에서 끊긴다">

사설 CA가 `api.example.internal`에 서명한 인증서로 TLS 서버를 띄우고, 클라이언트 설정만 세 가지로 바꿔 붙어 봤다(`certs.New`는 글 끝 실습 환경 절에 있다).

```go title="tcplab/trust/main.go"
package main

import (
	"crypto/tls"
	"fmt"
	"net"

	"tcplab/certs"
)

// 같은 서버에 세 가지 클라이언트 설정으로 붙어 본다.
func main() {
	cert, pool := certs.New("api.example.internal")
	ln, _ := tls.Listen("tcp", "127.0.0.1:0", &tls.Config{Certificates: []tls.Certificate{cert}})
	go func() {
		for {
			c, err := ln.Accept()
			if err != nil {
				return
			}
			go func(c net.Conn) { c.(*tls.Conn).Handshake(); c.Close() }(c)
		}
	}()

	cases := []struct {
		desc string
		cfg  *tls.Config
	}{
		{"CA를 모르는 클라이언트", &tls.Config{ServerName: "api.example.internal"}},
		{"CA는 알지만 다른 이름으로 접속", &tls.Config{ServerName: "db.example.internal", RootCAs: pool}},
		{"CA도 알고 이름도 맞음", &tls.Config{ServerName: "api.example.internal", RootCAs: pool}},
	}
	for _, c := range cases {
		conn, err := tls.Dial("tcp", ln.Addr().String(), c.cfg)
		if err != nil {
			fmt.Printf("✕ %s\n   %v\n", c.desc, err)
			continue
		}
		st := conn.ConnectionState()
		fmt.Printf("✓ %s\n   %s · %s\n", c.desc, tls.VersionName(st.Version), tls.CipherSuiteName(st.CipherSuite))
		conn.Close()
	}
}
```

<C k="err">certificate signed by unknown authority</C>는 클라이언트가 그 CA를 모른다는 뜻이라 신뢰할 CA를 추가해야 하고, <C k="err">certificate is valid for …, not …</C>는 CA는 믿지만 인증서의 이름과 접속한 이름이 다르다는 뜻이다. 세 번째는 TLS 1.3과 `TLS_AES_128_GCM_SHA256`으로 맺어졌다.

첫 번째 에러를 `InsecureSkipVerify: true`로 넘기면 연결은 되지만, 서버가 진짜인지 확인하는 일을 통째로 끄게 된다. 사설 CA라면 위 실습처럼 그 CA를 `RootCAs`에 넣는다.

왕복(RTT)은 보낸 패킷이 상대에게 닿고 답이 돌아오기까지 걸리는 시간이다. 새 연결로 HTTPS 요청을 하나 보내면 TCP 핸드셰이크에 한 번, TLS 핸드셰이크에 TLS 1.3은 한 번, TLS 1.2는 두 번, 요청과 응답에 한 번 왕복한다. 이미 열린 연결을 다시 쓰면 요청과 응답 한 번뿐이다.

왕복 한 번이 50ms라면 TLS 1.2 새 연결은 첫 응답까지 200ms, 다시 쓰는 연결은 50ms다. 연결을 새로 열 때마다 HTTP 칸 앞의 칸만큼 기다리니, 요청이 많을수록 차이가 커진다.

TLS 1.3이 왕복을 하나 덜 쓰는 건 첫 메시지 덕분이다. 키 교환에는 그림 9의 공개값 A와 B가 필요한데, TLS에서는 이걸 키 공유값이라고 부른다. TLS 1.2의 클라이언트는 서버가 어떤 키 교환 방식을 골랐는지 들은 뒤에야 자기 키 공유값을 보낸다. TLS 1.3의 클라이언트는 서버가 고를 만한 방식을 짐작해서 첫 메시지에 자기 키 공유값을 미리 실어 보낸다.[^hrr] 그래서 서버는 첫 답장에 자기 키 공유값과 인증서, Finished(지금까지 주고받은 핸드셰이크가 바뀌지 않았는지 확인하는 메시지)를 한 번에 싣고, 클라이언트는 그 답장을 받자마자 세션 키를 계산해 요청을 보낸다.

<Lab title="지연 프록시로 왕복 횟수를 재 봤다">

같은 컴퓨터 안에서는 왕복이 너무 짧아, 바이트를 한 방향에 <C k="num">25ms</C>씩 늦추는 프록시를 끼워 왕복 한 번을 <C k="num">50ms</C>로 만들었다. 단계별 시간은 `httptrace`(단계마다 알려 주는 표준 패키지)로 쟀고, 프록시 코드는 글 끝 실습 환경 절에 있다.

```go title="tcplab/rtt/main.go"
package main

import (
	"context"
	"crypto/tls"
	"fmt"
	"io"
	"net/http"
	"net/http/httptrace"
	"time"

	"tcplab/certs"
)

// TLS 1.2와 1.3에서 요청을 두 번씩 보내며 연결·핸드셰이크·전체 시간을 잰다. 지연 프록시는 proxy.go
func main() {
	cert, pool := certs.New("api.example.internal")
	ln, _ := tls.Listen("tcp", "127.0.0.1:0", &tls.Config{Certificates: []tls.Certificate{cert}})
	go http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { io.WriteString(w, "ok") }))
	addr := proxy(ln.Addr().String())

	for _, v := range []uint16{tls.VersionTLS12, tls.VersionTLS13} {
		tr := &http.Transport{TLSClientConfig: &tls.Config{
			ServerName: "api.example.internal", RootCAs: pool, MinVersion: v, MaxVersion: v,
		}}
		client := &http.Client{Transport: tr}
		for i := 1; i <= 2; i++ {
			var start, connDone, tlsDone time.Time
			trace := &httptrace.ClientTrace{
				ConnectDone:      func(string, string, error) { connDone = time.Now() },
				TLSHandshakeDone: func(tls.ConnectionState, error) { tlsDone = time.Now() },
			}
			req, _ := http.NewRequestWithContext(httptrace.WithClientTrace(context.Background(), trace),
				"GET", "https://"+addr, nil)
			start = time.Now()
			resp, err := client.Do(req)
			if err != nil {
				panic(err)
			}
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			total := time.Since(start)
			if connDone.IsZero() { // 재사용한 연결 — 연결·핸드셰이크 없음
				fmt.Printf("%s 요청 %d: 연결 재사용                        전체 %3dms\n",
					tls.VersionName(v), i, total.Milliseconds())
				continue
			}
			fmt.Printf("%s 요청 %d: TCP 연결 %2dms · TLS 핸드셰이크 %3dms · 전체 %3dms\n",
				tls.VersionName(v), i, connDone.Sub(start).Milliseconds(),
				tlsDone.Sub(connDone).Milliseconds(), total.Milliseconds())
		}
		tr.CloseIdleConnections()
	}
}
```

## 흐름 제어와 혼잡 제어는 누구를 지키나

연결이 열린 뒤에도 TCP는 보내는 속도를 계속 조절한다. 장치가 두 가지인데 이름이 비슷해서 자주 헷갈리니, 지키는 대상으로 나눠 보자.

흐름 제어는 받는 쪽을 지킨다. 받는 쪽이 버퍼에 남은 자리(수신 윈도우)를 계속 알려 주고, 보내는 쪽은 그 이상 보내지 않는다. 받는 프로그램이 느리게 읽으면 윈도우가 줄어 보내는 쪽도 느려진다.

혼잡 제어는 네트워크를 지킨다. 보내는 쪽이 길이 얼마나 막혔는지 짐작해서 한 번에 보낼 양(혼잡 윈도우)을 정한다. 처음엔 작게 시작해 왕복마다 두 배쯤 늘리고(slow start), 패킷이 사라지면 길이 막혔다고 보고 크게 줄였다가 다시 늘린다. 리눅스의 기본 방식은 CUBIC이다.

새 연결은 혼잡 윈도우도 작게(리눅스는 패킷 10개) 시작하고, 다시 쓰는 연결은 늘려 둔 윈도우를 이어 쓴다. 다만 리눅스는 연결이 RTO(최소 200ms)보다 오래 쉬면 윈도우를 줄이고, 오래 쉴수록 처음 크기까지 되돌린다(`net.ipv4.tcp_slow_start_after_idle` 기본값 1). 그래서 몇 초에 한 번 쓰는 연결은 핸드셰이크만 아낀다.

작은 데이터를 모았다 보내는 Nagle 알고리즘과 지연 ACK가 만나면 작은 요청이 수십 ms씩 늦어질 수 있어 대화형 프로토콜은 `TCP_NODELAY`를 켜는데, Go는 TCP 연결마다 이미 켜 둔다(`SetNoDelay` 기본값 `true`).

그래서 호출마다 `&http.Client{}`만 새로 만드는 건 괜찮다. Transport를 비워 두면 기본 Transport의 풀을 같이 쓰니, 맥에서 따로 100번 보내 보니 새 연결은 1개였다. `&http.Transport{}`까지 새로 만들면 100개였다. 풀을 같이 쓰더라도 두 가지를 놓치면 연결을 새로 연다. 직접 세어 봤다.

<Lab title="Body를 안 읽거나 동시 요청이 많으면 연결을 새로 연다">

64KB 응답을 주는 서버에 요청 100번을 보내면서, 새로 연 TCP 연결 수를 `httptrace`의 `ConnectDone`으로 셌다. `/big`은 1MB를 준다. 같은 코드를 Go 1.26.10과 Go 1.27.0으로 돌렸다.

```go title="tcplab/reuse/main.go"
package main

import (
	"context"
	"fmt"
	"io"
	"net"
	"net/http"
	"net/http/httptrace"
	"runtime"
	"strings"
	"sync"
	"sync/atomic"
)

// 요청 100번(동시 n개씩)을 보내는 동안 새로 연 TCP 연결 수를 센다.
func run(c *http.Client, url string, parallel int, drain bool) int64 {
	var opened atomic.Int64
	trace := &httptrace.ClientTrace{ConnectDone: func(string, string, error) { opened.Add(1) }}
	ctx := httptrace.WithClientTrace(context.Background(), trace)
	for round := 0; round < 100/parallel; round++ {
		var wg sync.WaitGroup
		for i := 0; i < parallel; i++ {
			wg.Add(1)
			go func() {
				defer wg.Done()
				req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
				resp, err := c.Do(req)
				if err != nil {
					panic(err)
				}
				if drain {
					io.Copy(io.Discard, resp.Body) // 끝까지 읽고
				}
				resp.Body.Close() // 닫는다
			}()
		}
		wg.Wait()
	}
	return opened.Load()
}

func main() {
	small := strings.Repeat("x", 64*1024) // 64KB 응답
	big := strings.Repeat("x", 1<<20)     // 1MB 응답
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	go http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path == "/big" {
			io.WriteString(w, big)
			return
		}
		io.WriteString(w, small)
	}))
	url := "http://" + ln.Addr().String()

	fresh := func(maxIdle int) *http.Client {
		return &http.Client{Transport: &http.Transport{MaxIdleConnsPerHost: maxIdle}}
	}
	fmt.Println(runtime.Version())
	fmt.Printf("순차, Body 끝까지 읽고 닫음             → 새 연결 %3d개\n", run(fresh(0), url, 1, true))
	fmt.Printf("순차, 64KB Body 안 읽고 닫기만 함       → 새 연결 %3d개\n", run(fresh(0), url, 1, false))
	fmt.Printf("순차, 1MB Body 안 읽고 닫기만 함        → 새 연결 %3d개\n", run(fresh(0), url+"/big", 1, false))
	fmt.Printf("동시 10개, MaxIdleConnsPerHost 기본(2)  → 새 연결 %3d개\n", run(fresh(0), url, 10, true))
	fmt.Printf("동시 10개, MaxIdleConnsPerHost 10       → 새 연결 %3d개\n", run(fresh(10), url, 10, true))
}
```

```go title="client.go"
var client = newClient()

func newClient() *http.Client {
	// 기본 Transport를 복사해 타임아웃·프록시 설정을 이어받는다
	t := http.DefaultTransport.(*http.Transport).Clone()
	t.MaxIdleConnsPerHost = 10 // 동시 요청 수에 맞춘다
	return &http.Client{Transport: t, Timeout: 10 * time.Second}
}

func call(url string) error {
	resp, err := client.Get(url)
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	_, err = io.Copy(io.Discard, resp.Body) // 큰 응답도 연결을 남긴다
	return err
}
```

좋은 쪽은 `http.DefaultTransport`를 `Clone()`해서 필요한 값만 바꿨다. `&http.Transport{}`를 새로 만들면 기본 Transport에 있던 연결 타임아웃(30초), `IdleConnTimeout`(쉬는 연결을 닫기까지의 시간, 90초), 프록시 설정이 빠지기 때문이다.

Body를 끝까지 읽는 줄은 Go 1.27부터는 작은 응답이면 없어도 된다. 1.26 이하를 쓰거나 응답이 256KB를 넘을 수 있으면 남겨 둔다. 다만 아주 큰 응답을 버리려고 끝까지 받는 것보다 연결을 버리는 쪽이 쌀 때도 있다.

## 실습 환경과 한계

실습은 실습 서버(Rocky Linux 8.10, 커널 4.18, x86_64, 4 vCPU)에서 podman 4.9.4 컨테이너 안에 Go 1.27.0과 Go 1.26.10으로 빌드한 바이너리를 넣어 돌렸다. 컨테이너마다 네트워크 네임스페이스가 따로라서 다른 프로세스의 소켓이 TIME_WAIT 수에 섞이지 않는다. 두 버전의 결과는 64KB Body를 읽지 않고 닫는 줄(1.26.10은 100개, 1.27.0은 2\~10개) 하나만 달랐다. 지연 프록시 실습은 Go 1.27.0으로 72번 돌렸고, 중앙값이 TLS 1.2 첫 요청 157ms, TLS 1.3 첫 요청 106ms, 재사용 51ms였다. 인증서 실습을 이 맥(Apple M5)에서 돌리면 CA를 모를 때의 문구가 `certificate is not trusted`로 나온다. 맥의 Go는 시스템 인증서 검증기를 쓰기 때문이다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| TIME_WAIT 실습 | 먼저 끊은 쪽에 남고 60초 남짓 뒤 사라진다 | 다른 커널에서 사라지는 시점. 4.18 커널에서만 셌다 |
| 인증서 실습 | CA를 모를 때와 이름이 다를 때의 에러 | 중간 인증서가 빠지거나 만료된 경우 |
| 지연 프록시 | TLS 1.2는 왕복 둘, 1.3은 하나, 재사용은 0 | TCP 핸드셰이크 왕복. 프록시가 늦추지 못해 계산으로 더했다 |
| 재사용 실습 | 새 연결이 생기는 조건과 Go 1.27의 대신 읽기 | HTTP/2. 연결 하나에 요청을 여러 개 싣는다 |
| 흐름·혼잡 제어 | 문서에 적힌 동작 | 실제 윈도우 크기. 재지 않았다 |

실습용 CA와 인증서를 만드는 코드, 그리고 지연 프록시 코드는 아래가 전부다.

```go title="tcplab/certs/certs.go"
// Package certs 는 실습용 사설 CA와 서버 인증서를 메모리에서 만든다.
package certs

import (
	"crypto/ecdsa"
	"crypto/elliptic"
	"crypto/rand"
	"crypto/tls"
	"crypto/x509"
	"crypto/x509/pkix"
	"math/big"
	"time"
)

// New 는 서버용 인증서(name 에 대해 서명됨)와, 그 인증서를 믿게 해 주는 CA 풀을 돌려준다.
func New(name string) (tls.Certificate, *x509.CertPool) {
	caKey, _ := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	caTpl := &x509.Certificate{
		SerialNumber:          big.NewInt(1),
		Subject:               pkix.Name{CommonName: "lab CA"},
		NotBefore:             time.Now().Add(-time.Hour),
		NotAfter:              time.Now().Add(time.Hour),
		IsCA:                  true,
		KeyUsage:              x509.KeyUsageCertSign,
		BasicConstraintsValid: true,
	}
	caDER, _ := x509.CreateCertificate(rand.Reader, caTpl, caTpl, &caKey.PublicKey, caKey)
	ca, _ := x509.ParseCertificate(caDER)

	key, _ := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	tpl := &x509.Certificate{
		SerialNumber: big.NewInt(2),
		Subject:      pkix.Name{CommonName: name},
		DNSNames:     []string{name},
		NotBefore:    time.Now().Add(-time.Hour),
		NotAfter:     time.Now().Add(time.Hour),
		KeyUsage:     x509.KeyUsageDigitalSignature,
		ExtKeyUsage:  []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth},
	}
	der, _ := x509.CreateCertificate(rand.Reader, tpl, ca, &key.PublicKey, caKey) // CA가 서명
	pool := x509.NewCertPool()
	pool.AddCert(ca)
	return tls.Certificate{Certificate: [][]byte{der}, PrivateKey: key}, pool
}
```

```go title="tcplab/rtt/proxy.go"
package main

import (
	"net"
	"time"
)

const oneWay = 25 * time.Millisecond // 한 방향 25ms → 왕복(RTT) 50ms

// delayPipe 는 src 에서 읽은 덩어리를 oneWay 만큼 늦춰서 dst 에 쓴다. 순서는 지킨다.
func delayPipe(dst, src net.Conn) {
	type chunk struct {
		at time.Time
		b  []byte
	}
	q := make(chan chunk, 1024)
	go func() {
		for c := range q {
			time.Sleep(time.Until(c.at))
			dst.Write(c.b)
		}
		dst.Close()
	}()
	buf := make([]byte, 32*1024)
	for {
		n, err := src.Read(buf)
		if n > 0 {
			q <- chunk{time.Now().Add(oneWay), append([]byte(nil), buf[:n]...)}
		}
		if err != nil {
			close(q)
			return
		}
	}
}

// 지연 프록시: 클라이언트와 서버 사이에서 오가는 모든 바이트를 늦춘다.
func proxy(upstream string) string {
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	go func() {
		for {
			c, err := ln.Accept()
			if err != nil {
				return
			}
			u, _ := net.Dial("tcp", upstream)
			go delayPipe(u, c)
			go delayPipe(c, u)
		}
	}()
	return ln.Addr().String()
}
```

## 정리

- TCP는 세 번 주고받아 연결하고 네 번 주고받아 끊는다. 먼저 끊은 쪽이 TIME_WAIT로 60초 남는다.
- 서버에 TIME_WAIT가 쌓이면 서버가 먼저 끊고 있다는 뜻이다. keep-alive를 끈 클라이언트가 흔한 원인이다.
- TLS는 인증서로 서버를 확인하고, 양쪽이 각자 계산한 세션 키로 본 통신을 암호화한다.
- 새 연결의 첫 응답까지 왕복이 TLS 1.3은 세 번, 1.2는 네 번이고, 다시 쓰는 연결은 한 번이다. 1.3은 첫 메시지에 키 공유값을 실어서 한 번을 줄였다.
- Go에서는 Transport 하나를 같이 쓰고 동시 요청 수만큼 `MaxIdleConnsPerHost`를 올린다. Go 1.27부터 작은 응답은 `Close()`가 대신 읽어 주지만, 1MB 응답은 여전히 연결을 버렸다.

연결을 열었으니, 다음 정거장은 그 연결로 요청을 보내는 단계다. 이번 재사용 실습은 모두 HTTP/1.1이었다. HTTP/2는 연결 하나에 요청 여러 개를 동시에 실어서 `MaxIdleConnsPerHost` 같은 숫자가 다르게 움직일 텐데, 다음 편에서 HTTP/1.1이 연결 하나에서 요청을 어떻게 줄 세우는지와 함께 직접 재 보려고 한다.
