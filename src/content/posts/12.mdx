<Lead>
Go에서 자주 만나는 버그 목록을 적어 보니 셋 다 같은 모양이었다. 내가 들고 있다고 생각한 것과 실제로 들고 있는 것이 다르다. 슬라이스는 데이터가 아니라 창이고, map 요소는 주소를 얻을 수 없고, string은 문자 배열이 아니다. 세 자료구조의 레이아웃을 하나씩 열어 봤다.

append가 원본을 바꾸는 건, 슬라이스가 원본 배열을 함께 보는 창이고 cap에 여유가 있으면 append가 새 배열을 만들지 않고 그 배열에 그대로 쓰기 때문이다. 이 글은 슬라이스 헤더에서 시작해 함수 전달, append, 메모리 누수, map, string 순서로 간다. 예제는 Go 1.26.10에서 다시 돌려 확인했다.
</Lead>

<Summary>
1. 슬라이스는 백킹 배열을 보는 `{ptr, len, cap}` 3워드 창이다. append 부작용, 공유, 메모리 누수가 전부 이 한 문장에서 나온다.
2. map의 두 가지 불친절(순회 순서가 매번 다름, 동시 쓰기에 바로 죽음)은 둘 다 조용히 망가지느니 그 자리에서 실패하는 쪽을 택한 설계에서 나온다.
3. string은 불변 UTF-8 바이트 뭉치다. `len`도 인덱싱도 연결도 문자 배열이라는 직관과 어긋난다.
</Summary>

<Note title="누구를 위한 글인가">
Go로 슬라이스와 맵을 매일 쓰지만, 그 값이 메모리에서 어떤 모양인지는 따로 들여다본 적 없는 사람을 기준으로 썼다. 1\~2절은 슬라이스 헤더와 함수 전달, 3절은 append, 4\~5절은 재슬라이싱 누수와 nil 슬라이스, 6절은 map, 7절은 string이다. 인터페이스 값의 두 칸은 [지난 글](/11)에서 다뤘다.
</Note>

## 배열과 슬라이스: 값이냐 창이냐

Go의 배열은 다른 언어의 배열과 다르다. 값 타입이고, 길이가 타입의 일부다. `[5]int`와 `[4]int`는 서로 다른 타입이라 같은 함수에 넘길 수도 없다. 대입하면 원소가 통째로 복사된다.

그래서 실무에서 배열을 직접 쓸 일은 거의 없다. 대신 슬라이스를 쓰는데, 슬라이스는 데이터를 가진 게 아니라 <mark>뒤에 있는 배열(백킹 배열)의 일부를 들여다보는 창</mark>이다. 창의 정체는 포인터 하나와 정수 두 개, 즉 3워드짜리 헤더가 전부다.

`b := a[1:3]`은 [1]부터 두 칸을 보니 len이 2이고, cap은 시작 칸부터 배열 끝까지라 4다. 변수 크기를 `unsafe.Sizeof`로 재 보면 배열과 슬라이스의 차이가 숫자로 나온다.

```go title="sizes/main.go"
var arr [5]int
var s []int
var str string
var m map[string]int
fmt.Println("[5]int:", unsafe.Sizeof(arr))
fmt.Println("[]int:", unsafe.Sizeof(s))
fmt.Println("string:", unsafe.Sizeof(str))
fmt.Println("map:", unsafe.Sizeof(m))
```

```text frame="terminal" title="실행 결과"
$ go run ./sizes
[5]int: 40
[]int: 24
string: 16
map: 8
```

배열은 원소 다섯 개만큼 40바이트인데, 슬라이스는 원소가 몇 개든 24바이트이고, string은 포인터와 길이 2워드라 16바이트, map 변수는 포인터 하나라 8바이트다.

### 여기서 막혔던 두 가지

그림을 그려 놓고도 한참을 더 헤맸다. 정리하고 보니 질문이 두 개였는데, 둘 다 "슬라이스는 배열의 업그레이드판"이라는 잘못된 그림에서 나온 것이었다.

**① 배열 `[4]int` 뒤에 len과 cap을 붙이면 슬라이스인가?** 아니다. 오히려 정반대에 가깝다. 배열과 슬라이스는 완전히 다른 타입이고, 슬라이스는 배열을 가리키는 별도의 작은 구조체다. 배열은 그 자체가 데이터 덩어리이고, 슬라이스는 그 데이터가 어디 있는지 적어 둔 작은 헤더다.

```go title="배열 변수와 슬라이스 변수"
// 배열: 변수 자체가 데이터다. 가리키는 포인터 같은 건 없다
var arr [4]int = [4]int{1, 2, 3, 4} // arr = int 4개 크기의 메모리 그 자체

// 슬라이스 리터럴 한 줄이 실제로는 두 가지를 만든다
s := []int{1, 2, 3, 4}
//  ① 어딘가에 {1,2,3,4}를 담을 밑바탕 배열을 만들고
//  ② s에는 그 배열을 가리키는 {ptr, len, cap} 헤더를 담는다
```

슬라이스 뒤에는 항상 배열이 있다는 말은 맞다. `make([]int, 4)`처럼 배열 리터럴 없이 만들어도 안에서는 똑같이 배열이 생긴다. 그 배열이 눈에 안 보일 뿐이고, 슬라이스가 그 배열의 확장형인 건 아니다.

**② 그럼 배열이 곧 `ptr`인가?** 배열은 ptr이 가리키는 대상이다. 미묘해 보이지만 이 차이를 놓치면 뒤에 나올 메모리 누수가 이해되지 않는다.

<Note title="ptr과 배열">

헤더 안의 `ptr`은 배열의 시작 주소를 담은 8바이트 필드다. 배열은 그 주소에 실제로 있는 별도의 메모리 블록이고, 통째로 하나의 할당 단위다. C로 치면 `ptr`은 `int*`, 배열은 그 포인터가 가리키는 `int[N]`이다. 헤더는 몇 개든 만들 수 있고, 그 헤더들이 모두 같은 배열 하나를 가리킨다. 이걸 붙잡고 나서야 뒤에 나오는 공유와 누수가 한 번에 풀렸다.

</Note>

## 함수에 넘기면 값 전달인가 참조 전달인가

```go title="pass/main.go"
func modify(s []int) {
	s[0] = 99        // 보인다: 같은 백킹 배열
	s = append(s, 4) // 안 보인다: 복사본 헤더의 len만 바뀐다
}

// 그래서 append하는 함수는 슬라이스를 반환한다
func appendTo(s []int, v int) []int { return append(s, v) }

func main() {
	s := make([]int, 3, 4)
	modify(s)
	fmt.Println(s, len(s))
	fmt.Println(s[:4]) // len을 cap까지 늘려서 본다
	s = appendTo(s, 5)
	fmt.Println(s, len(s))
}
```

```text frame="terminal" title="실행 결과"
$ go run ./pass
[99 0 0] 3
[99 0 0 4]
[99 0 0 5] 4
```

첫 줄이 그 비대칭이다. 원소 수정은 같은 배열이라 보이고, append가 늘린 len 4는 함수 안 복사본 헤더에만 남았다. 둘째 줄은 같은 `s`를 cap 4까지 늘려 본 것이다. append가 쓴 4는 배열의 [3] 자리에 그대로 들어가 있었고, 호출한 쪽의 len이 3이라 보이지 않았을 뿐이다. 셋째 줄에서 `appendTo`가 같은 자리에 5를 덮어쓴 것도 같은 이유다.

`append`가 결과를 반환하는 시그니처라 불편해 보였는데, 헤더가 값 타입이니 다른 선택지가 없었다. `strings.Builder`나 `bytes.Buffer`가 포인터 리시버 메서드로 설계된 것도 같은 이유다. map은 사정이 다르다. 앞에서 잰 것처럼 map 변수는 포인터 하나라서, 함수 안에서 넣은 항목이 호출한 쪽에도 그대로 보인다.

## append의 두 갈래: 원본 훼손과 연결 끊김

append했는데 원본이 바뀌기도 하고 안 바뀌기도 한다는 증상의 정체가 여기 있다. `append`는 <mark>cap에 여유가 있느냐 없느냐</mark>에 따라 완전히 다른 두 가지 동작을 한다. 그리고 어느 쪽인지는 코드만 봐서는 알 수 없다.

```go title="appendx/main.go"
a := []int{1, 2, 3, 4, 5}
b := a[1:3] // cap은 배열 끝까지 물려받는다
fmt.Println(len(b), cap(b))
b = append(b, 99)
fmt.Println(a)

a = []int{1, 2, 3, 4, 5}
c := a[1:3:3] // full slice expression: cap을 3-1 = 2로 제한
fmt.Println(len(c), cap(c))
c = append(c, 77) // cap 초과, 새 배열로 복사
fmt.Println(a, c)
c[0] = 0
fmt.Println(a, c)
```

```text frame="terminal" title="실행 결과"
$ go run ./appendx

[1 2 3 99 5]
2 2
[1 2 3 4 5] [2 3 77]
[1 2 3 4 5] [0 3 77]
```

둘째 줄에서 `b`에 붙인 99가 `a`의 4 자리를 덮었다. `c`는 세 번째 인덱스로 cap을 2로 막아 둬서 append할 때 새 배열로 옮겨 갔고, 마지막 줄에서 `c[0]`을 0으로 바꿔도 `a`는 그대로였다.

| `copy`로 떼어 내기 | 오래 보관할 때 | 필요한 부분만 새 슬라이스로 떠서 원본 참조를 완전히 끊는다 |
| 미리 잡기 `make([]T, 0, n)` | 크기를 알 때 | 재할당과 복사를 아예 없앤다 |

cap이 늘어나는 규칙도 두 배라고 외우고 있었는데, 지금은 아니다. Go 1.18부터 기준점이 1024에서 256으로 낮아졌고, 그 위로는 늘리는 폭이 두 배에서 1.25배 쪽으로 완만하게 줄어든다. 큰 슬라이스에서 메모리를 두 배씩 낭비하지 않으려는 조정이다.

<Lab title="cap은 정말 두 배로 늘까">

cap 256에서 시작해 하나씩 append하면서 cap이 바뀔 때마다 찍었다.

```go title="grow/main.go"
s := make([]int, 0, 256)
last := cap(s)
fmt.Print(last)
for i := 0; i < 5000; i++ {
	s = append(s, i)
	if cap(s) != last {
		last = cap(s)
		fmt.Print(" → ", last)
	}
}
```

```text frame="terminal" title="실행 결과"
$ go run ./grow
256 → 512 → 848 → 1280 → 1792 → 2560 → 3408 → 5120
```

512를 두 배 하면 1024인데, 실제로 512 다음은 848이었다. 256을 넘은 뒤의 공식(`newcap += (newcap + 3*256) >> 2`)대로면 832인데, 832칸(6,656바이트)이 할당기가 메모리를 나눠 주는 정해진 크기(크기 등급) 가운데 가까운 6,784바이트로 올림되어 848칸이 됐다. 1.40배 다음에 1.43배가 오는 것처럼 비율이 고르지 않은 것도 이 올림 때문이다. cap을 정확한 숫자로 가정하는 코드를 쓰면 안 되는 이유다.

</Lab>

## 재슬라이싱이 만드는 메모리 누수

창이라는 성질이 가장 조용하게 사고를 내는 곳이다. 슬라이스 헤더는 백킹 배열 전체를 참조한다. 그러니 10MB짜리 응답에서 3바이트만 잘라 보관해도, GC 입장에서는 10MB가 여전히 살아 있는 객체다.

왜 하필 전체냐면 앞에서 본 것처럼 배열이 통째로 하나의 할당 단위이기 때문이다. 힙에 잡힌 10MB 블록에서 앞의 3바이트만 남기고 뒤는 돌려주는 방법은 없다. `len`이 3이라는 건 데이터가 3바이트로 줄었다는 뜻이 아니라 이 블록의 앞 3바이트만 보겠다고 창을 좁혔다는 뜻일 뿐이다. 그 블록을 향하는 포인터가 하나라도 살아 있으면 GC는 블록 전체를 건드리지 못한다.

슬라이스로 생기는 누수가 하나 더 있다. 포인터를 담은 슬라이스에서 원소를 잘라 내면, 잘려 나간 자리의 포인터가 `len` 밖에 그대로 남아 있다. 눈에는 안 보이는데 GC는 여전히 그 객체를 살려 둔다.

<Compare>
<Side title="잘라 내기만 한다" tone="bad">

```go
func popBad(s []*Item) []*Item {
	// s[len(s)-1]이 여전히 Item을 붙잡고 있다
	return s[:len(s)-1]
}
```

</Side>
<Side title="nil을 넣고 자른다" tone="good">

```go
func popGood(s []*Item) []*Item {
	s[len(s)-1] = nil // 참조를 먼저 끊고
	return s[:len(s)-1]
}
```

</Side>
</Compare>

정말 그런지 `runtime.AddCleanup`으로 확인하려고, 원소가 회수되면 이름을 찍게 해 두고 두 함수로 하나씩 잘라 낸 뒤 GC를 돌렸다.

```go title="pop/main.go"
type Item struct {
	name string
	buf  [1 << 20]byte // 1MB
}

func track(name string) *Item {
	it := &Item{name: name}
	runtime.AddCleanup(it, func(n string) { fmt.Println("회수:", n) }, name)
	return it
}

func main() {
	a := popBad([]*Item{track("a1"), track("a2")})
	b := popGood([]*Item{track("b1"), track("b2")})
	runtime.GC()
	time.Sleep(100 * time.Millisecond) // cleanup은 따로 도는 고루틴에서 불린다
	runtime.KeepAlive(a) // a와 b는 아직 쓰는 중이다
	runtime.KeepAlive(b)
}
```

```text frame="terminal" title="실행 결과"
$ go run ./pop
회수: b2
```

nil을 넣고 자른 b2만 회수됐다. `popBad`로 잘라 낸 a2는 len 밖에 남은 포인터 때문에 GC를 돌린 뒤에도 살아 있었다.

중간 삭제도 같은 원리다. Go 1.22부터 `slices.Delete`는 줄어든 뒤쪽 자리를 0으로 지워 주는데, `[1 2 3 4 5]`에서 [1:3]을 지우고 `c[:5]`로 들여다보니 `[1 4 5 0 0]`이었다. 직접 구현하지 말고 이걸 쓰면 된다.

<Lab title="누수를 힙 통계와 pprof로 확인하기">

정말 안 줄어드는지 `runtime.ReadMemStats`로, 10MB 배열에서 3바이트만 남기는 두 가지 방식을 비교해 봤다.

```go title="leak/main.go"
func heap() uint64 {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.HeapAlloc
}

func mb(n uint64) string { return fmt.Sprintf("%.2f MB", float64(n)/(1<<20)) }

func main() {
	fmt.Println("시작:", mb(heap()))
	big := make([]byte, 10<<20) // 10MB

	leak := big[:3] // 재슬라이싱
	big = nil
	fmt.Println("재슬라이싱:", mb(heap()))

	safe := make([]byte, 3) // copy로 떼어 내기
	copy(safe, leak)
	leak = nil
	fmt.Println("copy:", mb(heap()))
}
```

```text frame="terminal" title="실행 결과"
$ go run ./leak
시작: 0.20 MB
재슬라이싱: 10.20 MB
copy: 0.20 MB
```

처음엔 `big = nil`만 하면 될 줄 알았는데 힙이 꿈쩍도 안 했다. `leak`이 같은 블록을 붙잡고 있으니 당연했다. 그 블록을 향하는 포인터가 전부 사라져야 회수된다. `copy`로 떼어 낸 뒤 `leak = nil`까지 하고 나서야 10MB가 사라졌다.

숫자보다 중요한 건 이걸 프로파일러로 찾기가 얼마나 어려운가였다. 10MB 응답을 `io.ReadAll`로 읽는 `fetch`와, 그 앞 3바이트를 캐시에 넣는 `keep`을 따로 두고 힙 프로파일을 떠 봤다.

```go title="readall/main.go"
func fetch() []byte {
	body, _ := io.ReadAll(bytes.NewReader(make([]byte, 10<<20))) // 10MB 응답
	return body
}

func keep(id string, body []byte) {
	cache[id] = body[:3] // 앞 3바이트만 캐시에 넣는다
}

func handle(id string) {
	body := fetch()
	keep(id, body)
}
```

```text frame="terminal" title="go tool pprof (일부)"
$ go tool pprof -top -inuse_space readall.bin heap.pprof
      flat  flat%   sum%        cum   cum%
   10240kB 90.90% 90.90%    10240kB 90.90%  io.ReadAll
         0     0%   100%    10240kB 90.90%  main.fetch (inline)
         0     0%   100%    10240kB 90.90%  main.handle
```

10MB는 전부 `io.ReadAll`에 잡혔고, 스택에는 `fetch`와 `handle`까지만 있다. 정작 조각을 붙잡은 `keep`은 어디에도 없다. 힙 프로파일은 메모리를 할당한 자리를 보여 줄 뿐, 지금 누가 붙잡고 있는지는 보여 주지 않는다. 그래서 슬라이스를 오래 보관할 때는 copy한다는 걸 규칙으로 굳혔다.

</Lab>

## nil 슬라이스 vs 빈 슬라이스

둘은 거의 모든 면에서 똑같이 동작한다. 딱 두 군데에서만 갈리는데, 둘 다 다른 코드와 값을 주고받는 자리다.

```go title="nilempty/main.go"
type Resp struct {
	Items []int `json:"items"`
}

func main() {
	var a []int
	b := []int{}
	fmt.Println(a == nil, unsafe.SliceData(a) == nil)
	fmt.Println(b == nil, unsafe.SliceData(b) == nil)
	ja, _ := json.Marshal(Resp{a})
	jb, _ := json.Marshal(Resp{b})
	fmt.Println(string(ja), string(jb))
}
```

```text frame="terminal" title="실행 결과"
$ go run ./nilempty
true true
false false
{"items":null} {"items":[]}
```

| | `var s []int` (nil) | `s := []int{}` (빈) |
| --- | --- | --- |
| len / cap | 0 / 0 | 0 / 0 |
| append, range | 똑같이 동작 | 똑같이 동작 |
| 힙 할당 | 없음 | 없음 (ptr만 nil이 아닌 주소) |
| `s == nil` | true | false |
| JSON 직렬화 | `null` | `[]` |

Go 코드 리뷰 가이드(Go Code Review Comments)는 `var s []T` 쪽을 권하면서도, JSON 응답을 만들 때는 예외라고 짚어 둔다. 결과가 없을 때 `null`이 나가면 프런트엔드에서 `.map()`이 터지기 때문이다.

<Note title="nil과 빈 슬라이스를 구별하는 계약은 만들지 않는다">

같은 가이드가 덧붙이는 문장이 더 중요하다. 인터페이스를 설계할 때 nil 슬라이스와 길이 0 슬라이스를 구별하지 말라는 것이다. 함수 계약에 "없으면 nil, 비었으면 빈 슬라이스" 같은 규칙을 넣는 순간 호출자마다 다르게 해석해서 미묘한 버그가 생긴다. 구별이 필요하다면 `(값, bool)`처럼 별도의 값으로 신호를 주는 게 맞다.

</Note>

키의 해시를 둘로 나눠, 하위 7비트(h2)는 그룹의 컨트롤 바이트에 넣고 나머지 상위 57비트(h1)로 어느 테이블과 어느 그룹부터 볼지 정한다. 찾을 때는 컨트롤 워드 8바이트를 한 번에 비교해서, h2가 같은 칸만 키를 비교한다. 테이블 하나는 최대 1024슬롯이고 커질 때도 테이블 하나씩만 키워서, 큰 맵에서도 삽입 한 번이 옮기는 양이 1024슬롯 안으로 묶인다.

성능보다 중요한 건, 이 구조가 map이 왜 그렇게 불친절한지를 설명해 준다는 점이다. 자주 욕먹는 두 가지 성질은 둘 다 의도된 설계다.

### ① 순회 순서가 매번 다르다

런타임이 순회 시작 지점을 일부러 무작위로 잡는다. 해시 테이블이라 원래도 순서가 정해져 있지 않지만, 그냥 두면 어쩌다 항상 같은 순서가 나오는 상황이 생기고 개발자는 거기에 기대게 되고, 그러면 데이터가 조금 달라진 어느 날 운영에서 터진다. 무작위화는 그 버그를 개발 단계에서 억지로 깨뜨리는 장치다. 순서가 필요하면 키를 뽑아 정렬한다.

```go title="maporder/main.go"
m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}
for i := 0; i < 3; i++ {
	for k := range m {
		fmt.Print(k, " ")
	}
	fmt.Println()
}
```

```text frame="terminal" title="실행 결과"
$ go run ./maporder
a b c d e
c d e a b
a b c d e
```

세 번 돌렸는데 순서가 두 가지였다. 줄마다 `a b c d e`를 돌려 놓은 꼴이라, 원소를 섞지 않고 시작 지점만 무작위로 잡는다는 게 출력에도 보인다.

### ② 동시 쓰기를 감지하면 즉시 죽는다

그리고 이건 panic이 아니라 fatal error다. 카드로 외웠을 때 놓쳤던 부분인데, 차이가 크다. `recover`로 잡을 수 없고, `defer`도 실행되지 않고, 프로세스가 그 자리에서 끝난다.

```go title="mapfatal/main.go"
func main() {
	defer fmt.Println("main의 defer") // 실행될까?
	m := map[int]int{}
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			defer func() {
				if r := recover(); r != nil {
					fmt.Println("복구:", r)
				}
			}()
			for j := 0; j < 1000; j++ {
				m[i*1000+j] = j
			}
		}(i)
	}
	wg.Wait()
}
```

```text frame="terminal" title="실행 결과"
$ go run ./mapfatal
fatal error: concurrent map writes

goroutine 22 [running]:
internal/runtime/maps.fatal({0x104ce376c?, 0x0?})
…
exit status 2
```

세 번 돌려 세 번 모두 이렇게 끝났고, 복구 줄도 main의 defer 줄도 찍히지 않았다. 맵은 동시에 읽고 쓰면 안전할까? 한 고루틴은 쓰고 다른 고루틴은 읽게 바꾸면 `fatal error: concurrent map read and map write`가 나온다.

이렇게까지 하는 이유는, 테이블을 키우는 도중에 구조가 깨지면 추적할 수 없는 메모리 손상이 되기 때문이다. 잘못된 값을 조용히 돌려주거나 남의 메모리를 밟는 것보다, 그 자리에서 스택 트레이스를 남기고 죽는 편이 낫다는 판단이다.

다만 Go 1.6 릴리스 노트에 가벼운 best-effort 감지라고 적혀 있듯, 이 감지가 늘 잡아 주지는 않는다. 타이밍이 어긋나면 잡히지 않고 조용히 지나갈 수도 있어서 `-race`가 여전히 필요하다.

### 그래서 실무에서는 무엇을 쓰나

| 방식 | 언제 | 대가 |
| --- | --- | --- |
| `sync.RWMutex`로 감싸기 | 기본값. 고민되면 여기서 시작 | 락 하나에 고루틴이 몰리면 경합이 생긴다 |
| 샤딩 | 경합이 실제로 프로파일에 잡힐 때 | 전체 순회와 크기 계산이 번거롭다 |
| `sync.Map` | 한 번 쓰고 여러 번 읽는 캐시, 고루틴마다 다른 키를 쓸 때 | 값이 `any`라 타입 안전성이 없고, 쓸 때마다 할당이 생긴다 |

```go title="RWMutex로 감싼 맵"
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func (s *SafeMap) Get(k string) (int, bool) {
	s.mu.RLock() // 읽기는 여럿이 동시에
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}

func (s *SafeMap) Set(k string, v int) {
	s.mu.Lock() // 쓰기는 혼자
	defer s.mu.Unlock()
	s.m[k] = v
}
```

<Lab title="RWMutex 맵과 sync.Map을 같이 재 봤다">

처음 글에는 `sync.Map`이 읽기와 쓰기가 섞이면 오히려 느린 경우가 많다고 적었는데, Go 1.24 릴리스 노트에 `sync.Map` 구현이 바뀌어 특히 쓰기가 빨라졌다는 줄이 있어서 다시 쟀다. 고루틴 10개가 키 1만 개 가운데 하나를 무작위로 골라 읽거나 쓰게 하고, 쓰기 비율을 1%, 10%, 50%로 바꿨다.

```go title="syncmap/m_test.go (일부)"
b.RunParallel(func(pb *testing.PB) {
	r := rand.New(rand.NewPCG(rand.Uint64(), 1))
	for pb.Next() {
		k := names[r.IntN(keys)] // 키 1만 개 중 하나
		if r.IntN(100) < writePct {
			set(k) // RWMutex 맵의 Set, 또는 sync.Map.Store
		} else {
			get(k) // RWMutex 맵의 Get, 또는 sync.Map.Load
		}
	}
})
```

| 쓰기 비율 | RWMutex 맵 | `sync.Map` |
| --- | --- | --- |
| 1% | 67.2 ns/op | 6.8 ns/op |
| 10% | 49.7 ns/op | 9.5 ns/op |
| 50% | 80.8 ns/op | 27.3 ns/op, 32 B/op |

세 번씩 돌린 중앙값이다. 쓰기가 절반이어도 `sync.Map`이 세 배쯤 빨랐지만, 쓰기가 섞이면 할당이 생겼다. 락 하나에 고루틴 10개가 몰리는 조건이라 RWMutex 쪽이 불리했고 샤딩한 맵과는 비교하지 않았다. 그래도 기본값은 RWMutex 맵으로 둔다. `sync.Map` 문서도 타입 안전성과, 맵과 함께 지켜야 할 다른 불변식을 이유로 대부분의 코드는 일반 맵에 락을 따로 걸라고 한다.

</Lab>

마지막으로 잘 알려지지 않은 함정 두 개. 맵 요소의 주소는 얻을 수 없고(`&m[k]`는 컴파일 에러다. [지난 글](/11)에서 다뤘다), `delete`를 해도 메모리는 줄지 않는다. 슬롯을 비우거나 삭제 표시만 하고 테이블은 그대로 둔다. 100만 개를 넣었다가 전부 지워 봤다.

```go title="mapdel/main.go (일부)"
m := map[int][64]byte{}
for i := 0; i < 1_000_000; i++ {
	m[i] = [64]byte{}
}
fmt.Println("100만 개:", heap(), len(m))
for i := 0; i < 1_000_000; i++ {
	delete(m, i)
}
fmt.Println("전부 delete:", heap(), len(m))

m[1] = [64]byte{}
n := make(map[int][64]byte, len(m)) // 살아 있는 항목만 새 맵으로
for k, v := range m {
	n[k] = v
}
m = n
fmt.Println("새 맵으로 옮기기:", heap(), len(m))
```

```text frame="terminal" title="실행 결과"
$ go run ./mapdel
100만 개: 160.2 MB 1000000
전부 delete: 160.2 MB 0
새 맵으로 옮기기: 0.2 MB 1
```

전부 delete해도 160MB 그대로였고, 살아 있는 항목만 새 맵으로 옮긴 뒤에야 0.2MB로 줄었다. 한 번 크게 부풀었다가 비워지는 맵이 있다면 이렇게 새 맵을 만들어 옮기는 수밖에 없다.

```go title="str/main.go"
	fmt.Print(i, " ", string(r), " / ")
```

문자열을 rune 단위로 돌려면 어떻게 할까? 넷째 줄에서 i가 0, 3, 6, 7로 건너뛰는 게 range가 rune 단위로 돈다는 뜻이고, i 자체는 그 rune이 시작하는 바이트 위치다. 다섯째 줄처럼 잘못된 UTF-8이 섞이면 range는 그 바이트 하나를 U+FFFD로 내놓고 다음 바이트로 넘어가서, 무한 루프는 생기지 않는다.

### 불변이라서 생기는 비용: +=는 O(N²)이다

string은 불변이라 고치려면 새 문자열을 만들어야 한다. 루프에서 `+=`로 이어 붙이면 반복마다 지금까지 만든 전체를 새 버퍼에 복사한다. N번 반복하면 총 복사량이 N²에 비례한다.

<Compare>
<Side title="+=로 이어 붙이기" tone="bad">

```go
// 반복마다 지금까지 전체를 복사
var s string
for _, w := range words {
	s += w
}
```

</Side>
<Side title="strings.Builder" tone="good">

```go
// 버퍼 하나에 이어 쓴다
var b strings.Builder
b.Grow(totalLen) // 크기를 알면 재할당도 없다
for _, w := range words {
	b.WriteString(w)
}
s := b.String() // 복사 없이 넘긴다
```

</Side>
</Compare>

단순히 이어 붙이는 거라면 `strings.Join(words, "")`가 더 읽기 쉽다. 안에서 한 번에 할당한다. 4바이트 단어 1,000개로 세 방식을 재 봤다.

```text frame="terminal" title="go test -bench . -benchmem"
$ go test -run x -bench . -benchmem ./strbench
BenchmarkPlusEq-10       6447    179312 ns/op   2137579 B/op   999 allocs/op
BenchmarkBuilder-10    395104      3013 ns/op      4096 B/op     1 allocs/op
BenchmarkJoin-10       220131      5147 ns/op      4096 B/op     1 allocs/op
```

`+=`는 한 번에 999번 할당하며 2.1MB를 썼다. 결과는 4KB인데 그 500배 넘게 복사했다. 첫 단어는 빈 문자열에 붙이는 거라 할당 없이 그대로 쓰여서 1,000번이 아니라 999번이었다. Builder와 Join은 한 번만 할당했다.

### string과 []byte 변환은 복사다, 단 예외가 있다

string은 불변이고 `[]byte`는 가변이다. 그래서 서로 바꿀 때 기본적으로 복사가 일어난다. 그러지 않으면 `[]byte`를 고쳐서 string을 바꿀 수 있게 되기 때문이다. 자주 도는 코드에서 이 변환을 반복하면 눈에 안 보이는 할당이 쌓인다.

다만 변환한 값이 그 식 밖으로 나가지 않는다고 컴파일러가 알 수 있는 몇 가지 자리에서는 복사를 생략한다.

```go title="복사가 생략되는 자리와 아닌 자리"
b := []byte("key")

v := m[string(b)]         // 맵 조회: 복사 생략
if string(b) == "key" {}  // 비교: 복사 생략

s := string(b)            // 변수에 담으면 복사 (살아남으니 당연하다)

// 정말 복사를 없애야 한다면 (Go 1.20+), 확신이 있을 때만
s = unsafe.String(unsafe.SliceData(b), len(b))
// 이후 b를 고치면 s도 바뀐다 = 불변성 계약이 깨진다
```

64바이트짜리 `b`로 `testing.AllocsPerRun`을 재 보니 맵 조회와 비교는 할당이 0번, 변수에 담는 변환은 1번이었다. 어느 자리가 생략되는지는 컴파일러 버전마다 조금씩 넓어진다. 핫 패스라면 짐작하지 말고 `go test -bench . -benchmem`의 allocs/op로 확인한다.

<Lab title="글자 수에 답이 세 개 있다">

## 실습 환경과 한계

예제는 모두 이 맥(Apple M5, 10코어, darwin/arm64)에서 Go 1.26.10으로 다시 돌렸다. 처음 올린 글의 글자 수 실습은 출력이 실제와 달라서 새로 찍은 값으로 바꿨고, `sync.Map`이 읽기와 쓰기가 섞이면 느린 경우가 많다는 문장은 다시 잰 결과로 고쳤다. 힙 숫자와 맵 순회 순서는 실행할 때마다 조금씩 달라진다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| 헤더 크기 · 함수 전달 · append | 64비트에서 크기와 이 예제의 동작 | 32비트 플랫폼에서의 크기 |
| cap 증가 | Go 1.26.10에서 `[]int`의 cap 순서 | 원소 크기나 버전이 다를 때의 순서. 크기 등급 표가 바뀌면 숫자도 바뀐다 |
| 힙 통계 · cleanup · pprof | 이 예제에서 남은 바이트, 회수된 원소, 프로파일 스택 | GC 시점이 다른 실제 서비스에서 같은 숫자가 나오는지 |
| 맵 fatal error · delete | 세 번 모두 잡힌 것, 지운 뒤 힙 크기 | 감지가 경합을 놓치는 빈도 |
| RWMutex 맵 · `sync.Map` | 10코어, 키 1만 개, 쓰기 1·10·50%의 시간 | 샤딩한 맵, 키 수와 코어 수가 다를 때 |
| 문자열 할당 · 글자 수 | 이 예제의 할당 수와 바이트·rune 수 | 다른 버전 컴파일러가 복사를 생략하는 자리 |

## 정리

| 이 글에서 본 것 | 원인 |
| --- | --- |
| `modify` 안의 append가 호출한 쪽에 안 보였다 | 헤더는 복사되고 배열은 공유된다 |
| `b = append(b, 99)`가 `a`를 바꿨다 | cap에 여유가 있으면 같은 배열에 쓴다 |
| 3바이트 조각이 10MB를 붙잡았다 | 슬라이스는 배열 전체를 참조한다 |
| 맵 동시 쓰기에 recover가 돌지 않았다 | panic이 아니라 fatal error다 |
| 전부 delete한 맵이 160MB 그대로였다 | 맵은 지워도 줄어들지 않는다 |
| `len("한글Go")`가 8이었다 | string은 UTF-8 바이트다 |

그래서 남에게 넘기는 슬라이스는 `a[l:h:h]`로 cap을 자르고, 오래 보관할 조각은 `copy`로 떼어 낸다.

세 자료구조를 나란히 놓고 보니 공통점이 하나 보였다. 셋 다 속을 감추지 않는다. 슬라이스가 배열을 들여다보는 창이라는 것도, map 요소의 주소를 얻을 수 없다는 것도, string이 바이트라는 것도 코드에 그대로 드러난다. 처음엔 불친절해 보였는데, 숨겼다면 그 대가를 훨씬 나쁜 때에 치렀을 것 같다.
