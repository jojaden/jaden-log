<Lead>
nil 포인터를 반환했는데 `err != nil`이 참이 되는 사고가 있다는 건 알고 있었다. 그런데 왜 nil이 아닌지는 설명하지 못했다. 따라가 보니 원인은 인터페이스 값이 타입과 데이터, 두 칸으로 되어 있다는 데 있었다. nil 포인터를 `error`에 담으면 데이터 칸은 비어 있어도 타입 칸이 채워진다.

고치는 방법은 성공 경로에서 `error` 타입의 nil을 직접 반환하는 것이다. 이 글은 그 현상을 코드로 먼저 확인하고, 두 칸 구조와 메서드셋, 인터페이스를 어디에 정의할지, 인터페이스를 거칠 때 드는 비용 순서로 간다. 예제는 Go 1.26.10에서 다시 돌려 확인했다.
</Lead>

<Summary>
1. nil 포인터를 `error`에 담으면 타입 칸이 채워져서 `err == nil`이 거짓이 된다. 성공 경로에서는 리터럴 `nil`을 돌려준다.
2. 인터페이스 값은 (타입, 데이터) 두 워드다. 박싱 할당과 동적 디스패치 비용도 이 구조에서 나온다.
3. 포인터 리시버 메서드가 값의 메서드셋에 없는 건, 인터페이스에 담긴 값이 복사본이라 고쳐도 원본에 닿지 않기 때문이다.
</Summary>

<Note title="누구를 위한 글인가">
Go로 코드를 짜며 인터페이스를 매일 쓰지만, 인터페이스 값이 런타임에 어떤 모양인지는 따로 들여다본 적 없는 사람을 기준으로 썼다. 1절은 nil 함정, 2절은 두 칸 구조, 3절은 메서드셋과 리시버, 4절은 인터페이스를 둘 자리, 5절은 인터페이스를 거칠 때 드는 비용이다. 임베딩으로 메서드가 승격되는 이야기는 [4편](/14)에서 따로 다룬다.
</Note>

## nil 포인터를 반환했는데 왜 err != nil인가

인터페이스 값은 타입 칸과 값 칸, 두 칸으로 되어 있다. 구조는 다음 절에서 자세히 보고, 여기서는 칸이 두 개라는 것만 기억하면 된다. `err == nil` 비교는 <mark>두 칸이 모두 비었는지</mark>를 본다. 값 칸이 nil이어도 타입 칸이 차 있으면 nil이 아니다.

```go title="nilerr/main.go"
type MyErr struct{ Code int }

func (e *MyErr) Error() string { return "my error" }

func validate(v int) *MyErr {
	if v > 0 {
		return nil // 여기서는 진짜 nil 포인터
	}
	return &MyErr{Code: 400}
}

func handle(v int) error {
	return validate(v) // *MyErr(nil)이 error에 담기면서 타입 칸이 찬다
}

func main() {
	err := handle(10)
	fmt.Println(err == nil)
	fmt.Println(err)
	fmt.Printf("%T %v\n", err, err.(*MyErr) == nil)
}
```

```text frame="terminal" title="실행 결과"
$ go run ./nilerr
false
my error
*main.MyErr true
```

에러가 없는데 에러로 취급된다. 셋째 줄을 보면 인터페이스 안에 든 건 `*MyErr` 타입의 nil 포인터다. `Error()`가 수신자의 필드를 읽지 않고 문자열만 돌려주기 때문에 nil 포인터로도 호출이 되고, 그래서 출력 문자열만 봐서는 인터페이스가 nil인지 알 수 없었다.

`*MyErr`는 `error`를 만족하고 nil 포인터도 그 타입의 유효한 값이라서, 컴파일러 입장에서는 막을 이유가 없는 대입이다. 대신 정적 분석은 이걸 잡는다. 같은 코드를 staticcheck로 검사해 봤다.

```text frame="terminal" title="staticcheck (golangci-lint 2.1.2에 들어 있는 것)"

main.go:21:9: SA4023(related information): the lhs of the comparison is the 1st return value of this function call (staticcheck)
main.go:22:14: SA4023: this comparison is never true (staticcheck)
```

staticcheck는 `handle`이 nil 인터페이스를 돌려줄 수 없다는 것까지 따라가서, `err == nil` 비교가 절대 참이 될 수 없다고 짚었다. 고치는 방법은 둘이다. 헬퍼의 반환 타입을 처음부터 `error`로 두거나, 성공 경로에서는 변수 대신 리터럴 `nil`을 돌려준다.

```go title="성공 경로는 리터럴 nil"
func handle(v int) error {
	if e := validate(v); e != nil {
		return e
	}
	return nil
}
```

반환값만 그런 게 아니다. `error` 타입 필드에 nil 포인터를 넣어 두면 나중에 똑같이 터진다. 인터페이스 타입인 자리라면 어디든 타입 칸이 같이 채워진다.

## 인터페이스 값은 두 워드다

Go 1.26.10 런타임 소스의 정의를 옮기면 이렇다. 메서드가 있는 인터페이스는 타입 칸에 itab 포인터를 두고, `any`처럼 메서드가 없는 인터페이스는 타입 정보만 둔다.

```go title="runtime/runtime2.go · internal/abi/iface.go (Go 1.26.10)"
// 메서드가 있는 인터페이스 (io.Reader, error, ...)
type iface struct {
	tab  *itab          // 타입 칸: 구체 타입 + 메서드 테이블
	data unsafe.Pointer // 값 칸
}

// 메서드가 없는 인터페이스 (any, interface{})
type eface struct {
	_type *_type // 메서드 테이블이 필요 없으니 타입 정보만
	data  unsafe.Pointer
}

type ITab struct { // 런타임의 itab
	Inter *InterfaceType // 어떤 인터페이스인가
	Type  *Type          // 어떤 구체 타입인가
	Hash  uint32         // 타입 스위치가 쓰는 해시
	Fun   [1]uintptr     // 가변 길이: 메서드 함수 포인터 배열
}
```

itab은 대부분 컴파일러가 바이너리에 미리 넣어 두고, 쌍을 컴파일할 때 알 수 없는 경우, 예를 들어 인터페이스 값을 다른 인터페이스로 단언할 때만 런타임이 itab을 만들어 `itabTable`에 캐시한다.

`Fun`은 구체 타입 하나에 고정된 테이블인데, Java의 vtable은 객체가 자기 클래스의 테이블을 들고 다니는 반면 Go의 itab은 인터페이스 값 쪽이 들고 있다. 그래서 같은 값이라도 `io.Reader`로 담을 때와 `io.Writer`로 담을 때 서로 다른 itab이 붙는다.

<Lab title="nil 포인터를 담아도 tab은 정상 값과 같다">

타입 칸이 채워진다는 말이 진짜인지 `unsafe`로 인터페이스 내부를 들여다봤는데, 방법은 인터페이스 값을 같은 크기의 2워드 구조체로 다시 해석하는 것이다.

```go title="dump/main.go"
type iface struct{ tab, data unsafe.Pointer }

func dump(label string, err error) {
	i := (*iface)(unsafe.Pointer(&err))
	fmt.Printf("%-10s tab=%p data=%p  nil? %v\n", label, i.tab, i.data, err == nil)
}

func words(label string, p unsafe.Pointer) {
	i := (*iface)(p)
	fmt.Printf("%-10s tab=%p data=%p\n", label, i.tab, i.data)
}

func main() {
	var nilIface error
	var p *MyErr
	dump("① nil", nilIface)
	dump("② nil ptr", p)
	dump("③ value", &MyErr{})
	dump("④ value", &MyErr{Code: 1})
	fmt.Println("sizeof error:", unsafe.Sizeof(nilIface))

	var r io.Reader = os.Stdout
	var w io.Writer = os.Stdout
	words("Reader", unsafe.Pointer(&r))
	words("Writer", unsafe.Pointer(&w))
	fmt.Printf("%-10s ptr=%p\n", "os.Stdout", os.Stdout)
}
```

## 메서드셋: 호출은 되는데 대입은 안 된다

Go를 쓰면서 가장 자주 만난 혼란은 `d.Inc()`는 잘 되는데 `var i Incer = d`는 컴파일 에러가 나는 것이었다. 같은 메서드인데 말이다.

먼저 메서드의 정체부터 보자. Go의 메서드는 첫 번째 인자가 앞으로 나온 함수다. `func (c Counter) Show()`는 사실상 `func Show(c Counter)`다. 그러니 리시버도 Go의 다른 값 전달과 똑같이 복사되어서, 값 리시버는 복사본을, 포인터 리시버는 주소를 받는다.

```go title="mset/run/main.go"
type Counter struct{ n int }

func (c Counter) Show() int { return c.n } // 값: 복사본을 받는다
func (c Counter) BadInc()   { c.n++ }      // 복사본만 늘린다
func (c *Counter) Inc()     { c.n++ }      // 포인터: 원본을 고친다

type Incer interface{ Inc() }

func main() {
	d := Counter{}
	d.BadInc()
	fmt.Println(d.n)
	d.Inc() // (&d).Inc()로 바뀐다
	fmt.Println(d.n)
	var a Incer = &d
	a.Inc()
	fmt.Println(d.n)
}
```

```text frame="terminal" title="실행 결과"
$ go run ./mset/run
0
1
2
```

`BadInc`는 복사본을 늘려서 `d.n`이 0 그대로고, `Inc`는 `&d`를 받아 1, 2로 늘렸는데, 같은 `d`를 `Incer`에 바로 담으면 컴파일이 안 된다.

```text frame="terminal" title="var b Incer = d"
$ go build ./mset/assign
# lab/mset/assign
mset/assign/main.go:12:16: cannot use d (variable of struct type Counter) as Incer value in variable declaration: Counter does not implement Incer (method Inc has pointer receiver)
```

스펙의 규칙은 세 줄이다.

- `T`의 메서드셋은 리시버가 `T`인 메서드다.
- `*T`의 메서드셋은 리시버가 `T`이거나 `*T`인 메서드, 둘 다다.
- 임베딩하면 메서드가 승격되는데 리시버 종류도 따라와서, `Outer`에 `Inner`를 값으로 임베드했는데 `Inner`의 메서드가 포인터 리시버라면, 인터페이스를 만족하는 건 `*Outer`뿐이다. `*Inner`로 임베드하면 `Outer` 값도 만족한다.

### 왜 대입만 막나

이 글을 쓰면서 가장 오래 걸린 곳이다. `d.Inc()`를 알아서 `(&d).Inc()`로 바꿔 줄 거라면 인터페이스 대입도 알아서 해 주면 되지 않나 싶었다.

Go FAQ의 답은 인터페이스에 담기는 값에 있는데, 인터페이스에 `d`를 담으면 값 칸에는 `d`의 복사본이 들어간다. `var i Incer = d`가 허용된다면 `i.Inc()`가 늘리는 건 인터페이스 안의 복사본이고, `d`는 그대로다. 고친 내용이 호출한 쪽에 닿지 않는 호출이라 언어가 대입부터 막는다.

복사본이 들어간다는 건 값 리시버만 있는 `fmt.Stringer`로 확인할 수 있다. 대입한 뒤에 원본을 바꿔도 인터페이스 쪽은 대입할 때의 값을 들고 있다.

```go title="copy/main.go"
type Counter struct{ n int }

func (c Counter) String() string { return fmt.Sprint("n=", c.n) }

func main() {
	d := Counter{n: 1}
	var s fmt.Stringer = d // 인터페이스에는 d의 복사본이 들어간다
	d.n = 99
	fmt.Println(d.n, s.String())
}
```

```text frame="terminal" title="실행 결과"
$ go run ./copy
99 n=1
```

### 주소를 얻을 수 없는 값

메서드 호출에서 `&`를 붙여 주는 데도 조건이 있어서, 스펙은 `x`가 주소를 얻을 수 있는 값일 때만 `x.m()`을 `(&x).m()`으로 읽는다. 변수 `d`는 주소가 있으니 `d.Inc()`가 통과하고, 고친 내용도 `d`에 그대로 남는다. 스펙이 주소를 얻을 수 있다고 정한 값은 이렇다.

<Compare>
<Side title="주소를 얻을 수 있다" tone="good">

- 변수
- 포인터 역참조 `*p`
- 슬라이스 인덱싱 `s[i]`
- 주소를 얻을 수 있는 구조체의 필드, 배열의 원소

</Side>
<Side title="주소를 얻을 수 없다" tone="bad">

- 맵 요소 `m[k]`
- 함수 반환값 `f()`
- 문자열 인덱싱 `s[i]`
- 상수, 복합 리터럴 `Counter{}`

</Side>
</Compare>

맵 요소가 대표적인데, 이유는 맵이 원소가 늘어나면 항목을 새 자리로 옮기는 자료구조라는 데 있다. 주소를 내줬는데 맵이 커지며 원소를 옮기면, 그 주소는 엉뚱한 곳을 가리키게 된다.

### 값 리시버와 포인터 리시버 고르기

이론이 정리되면 선택은 단순해진다. Go FAQ도 리시버를 값으로 둘지 포인터로 둘지를 함수 인자를 값으로 받을지 포인터로 받을지와 같은 질문으로 본다.

| 상황 | 선택과 이유 |
| --- | --- |
| 필드를 고친다 | 포인터. 값 리시버는 복사본만 고친다 |
| 구조체가 크다 | 포인터. 호출할 때마다 통째로 복사된다 |
| `sync.Mutex`, `sync.WaitGroup`을 품는다 | 무조건 포인터. 락이 복사되면 동기화가 무력해진다 |
| 작고 바뀌지 않는 값 타입 | 값. 시각이나 좌표처럼 복사가 자연스러운 것만 |
| 한 타입 안에서 | 통일. 섞으면 메서드셋이 갈려 인터페이스 만족 여부가 헷갈린다 |

세 번째 줄이 실무에서 가장 아프다. `sync.Mutex`를 값 리시버로 받으면 락 자체가 복사되어 서로 다른 락을 잠그게 된다. 코드는 멀쩡히 돌고 테스트도 통과하는데 동기화만 안 되는, 가장 찾기 싫은 형태의 버그다. 다행히 이건 `go vet`이 잡는다.

```go title="vet/main.go"
type Safe struct {
	mu sync.Mutex
	n  int
}

func (s Safe) Bad()   { s.mu.Lock(); defer s.mu.Unlock(); s.n++ } // 락도 n도 복사본
func (s *Safe) Good() { s.mu.Lock(); defer s.mu.Unlock(); s.n++ } // 원본을 잠근다
```

```text frame="terminal" title="go vet"
$ go vet ./vet
vet/main.go:10:9: Bad passes lock by value: lab/vet.Safe contains sync.Mutex
```

비슷한 결로 하나 더 있다. 값 리시버 메서드에서 필드를 고치는 코드는 고루틴 여러 개가 불러도 경합이 보이지 않는다. 고루틴 8개가 `BadInc`를 1,000번씩 부르게 하고 `-race`를 켜고 돌렸더니, 경합 보고 없이 `n = 0`이 찍혔다. 각 고루틴이 자기 복사본만 만지니 원본에 쓰는 곳이 없고, 원본은 한 번도 갱신되지 않는다. 경합 대신 조용히 아무 일도 안 하는 셈이라 오히려 발견이 늦다.

## 인터페이스는 쓰는 쪽에 둔다

Java에서 인터페이스를 쓰려면 구현체가 `implements Saver`라고 선언해야 한다. 선언한다는 건 그 인터페이스를 import한다는 뜻이고, 곧 구현체가 계약을 알아야 한다는 뜻이다. 이걸 명목적 타이핑(nominal typing)이라고 부른다. 이름이 같아야 같은 타입이다.

Go는 반대다. 메서드 시그니처만 맞으면 선언 없이 자동으로 만족하는 구조적 타이핑(structural typing)이라, 모양이 같으면 같은 타입이다. 이 차이가 패키지 사이의 의존 방향을 바꾼다.

화살표 하나가 사라진 게 이 그림의 전부다. 그 결과는 실무에서 이렇게 나타난다.

| 따라오는 것 | 내용 |
| --- | --- |
| 소급 적용 | 이미 배포된 남의 패키지 타입도 방금 정의한 인터페이스를 만족한다 |
| 작은 인터페이스 | 쓰는 쪽이 정의하니 필요한 메서드만 적는다 |
| 쉬운 목 | 테스트 파일 안의 세 줄짜리 구조체면 된다 |
| 가벼운 구현체 패키지 | 인터페이스 때문에 생기는 import가 없다 |

```go title="계약은 소비자 패키지에"
// 소비자 패키지: 저장만 할 수 있으면 된다
type Saver interface{ Save(v string) error }

func Run(s Saver) error { return s.Save("data") }

// 제공자 패키지: Saver를 모른다. import도 없다
type FileStore struct{ dir string }

func (f *FileStore) Save(v string) error { /* ... */ return nil }
func (f *FileStore) Open(p string) error { /* Saver와 상관없는 메서드 */ return nil }

// 테스트: 목은 세 줄이면 끝
type mockStore struct{ got string }

func (m *mockStore) Save(v string) error { m.got = v; return nil }
```

Go 코드 리뷰 가이드도 같은 말을 한다.

> Go 인터페이스는 대개 그 인터페이스 타입의 값을 쓰는 패키지에 두고, 그 값을 구현하는 패키지에는 두지 않는다.

[Go Code Review Comments · Interfaces](https://go.dev/wiki/CodeReviewComments#interfaces)

습관처럼 `store` 패키지 안에 `type Store interface`를 같이 넣어 두면, Go로 쓰면서 Java의 의존 구조를 그대로 재현하게 된다. 같은 문서는 구현하는 패키지가 구체 타입을 돌려줘야 구현체에 메서드를 더할 때 크게 고칠 일이 없다고 덧붙인다. 흔히 'Accept interfaces, return structs'라고 줄여 부르는 관용구와 같은 이야기다. 반환을 인터페이스로 하면 1절의 nil 함정까지 딸려 온다는 것도 구체 타입을 돌려줄 이유였다.

### 작게 쪼갠다

Go 속담(Go Proverbs)에 'The bigger the interface, the weaker the abstraction'이라는 줄이 있다. 처음엔 취향 문제인 줄 알았는데, 앞의 의존 구조를 보고 나니 쓰는 쪽이 정의하는 순간 안 쓰는 메서드를 왜 넣느냐는 질문이 저절로 생겼다.

| 기준 | 큰 인터페이스 (메서드 12개) | 작은 인터페이스 (1~2개) |
| --- | --- | --- |
| 구현 비용 | 12개를 전부 구현해야 만족 | 필요한 것만 |
| 테스트 목 | 안 쓰는 메서드까지 스텁 작성 | 세 줄 |
| 변경 파급 | 메서드 하나 추가에 모든 구현체와 목이 깨진다 | 그 소비자만 |
| 시그니처가 말하는 것 | 이 거대한 무언가가 필요하다 | 나는 읽기만 한다 |

표준 라이브러리가 그 결론을 그대로 보여 주는데, `io.Reader`, `io.Writer`, `io.Closer`는 전부 메서드가 하나다. 조합이 필요하면 큰 인터페이스를 새로 만드는 대신 인터페이스 임베딩으로 합성한다.

```go title="표준 라이브러리의 조합 방식: 작은 걸 붙인다"
type Reader interface{ Read(p []byte) (n int, err error) }
type Writer interface{ Write(p []byte) (n int, err error) }
type ReadWriter interface{ Reader; Writer } // 임베딩으로 합성
```

### 만족 어서션은 어디에 두나

암묵적 구현은 공짜가 아니다. 첫 번째 대가는 이 타입이 어떤 인터페이스를 만족하는지가 코드에 드러나지 않는다는 것이다. Java라면 클래스 선언 줄만 보면 되는데, Go는 프로젝트 전체를 뒤져야 안다. 리팩터링하다가 메서드 하나를 지웠는데 멀리 있는 다른 패키지가 깨지는 경험이 여기서 나온다.

두 번째 대가는 우연한 만족이다. 이름과 시그니처만 같으면 의도가 전혀 달라도 인터페이스를 충족해서, 캐시를 비우는 `Close()`와 커넥션을 끊는 `Close()`를 컴파일러는 구분하지 못한다.

첫 번째 대가에 대한 관용적 처방이 이 한 줄인데, 널리 쓰이는 코드인데도 처음 봤을 땐 뭘 하는 건지 몰랐다.

```go title="인터페이스 만족 어서션"
var _ Saver = (*FileStore)(nil)

// 읽는 법:
//   (*FileStore)(nil)  *FileStore 타입의 nil 포인터를 만든다 (값은 필요 없다)
//   var _ Saver = ...  Saver에 대입해 본다. 못 하면 컴파일 에러
//   _ 에 담으니         변수도 안 남고 런타임 비용도 없다
```

<Lab title="어서션을 두는 자리에 따라 에러가 나는 곳과 import가 달라진다">

이 한 줄이 무엇을 막아 주는지 보려고, 구현체의 메서드 이름을 일부러 `Sava`로 틀리게 써 봤다. 소비자 `app`, 구현체 `store`, 둘을 잇는 `cmd/server` 세 패키지로 된 모듈이다.

```go title="store/store.go: Save를 Sava로 오타"
func (f *FileStore) Sava(v string) error { return nil }
```

어서션이 없으면 `store`는 멀쩡히 빌드되고, 에러는 둘을 잇는 `main`에서 난다.

```text frame="terminal" title="어서션이 없을 때"
$ go build ./...
# shop/cmd/server
cmd/server/main.go:9:14: cannot use &store.FileStore{} (value of type *store.FileStore) as app.Saver value in argument to app.Run: *store.FileStore does not implement app.Saver (missing method Save)
```

어서션을 `store` 패키지 안(`store/assert.go`)에 두면 에러가 `store`에서 바로 난다. 대신 `store`가 `app`을 import해야 해서, 그림 6에서 지운 화살표가 다시 생긴다.

```text frame="terminal" title="store 안에 둘 때"
$ go build ./store
# shop/store
store/assert.go:5:19: cannot use (*FileStore)(nil) (value of type *FileStore) as app.Saver value in variable declaration: *FileStore does not implement app.Saver (missing method Save)
$ go list -deps ./store | grep shop
shop/app
shop/store
```

외부 테스트 패키지(`store_test`)에 두면 `go build`는 통과하고 `go vet`과 `go test`가 잡는다. 테스트 파일의 import라서 `store`의 의존 목록에 `app`이 들어가지 않았다.

```text frame="terminal" title="store_test.go에 둘 때"
$ go build ./store && go vet ./store
vet: store/store_test.go:8:19: cannot use (*store.FileStore)(nil) (value of type *store.FileStore) as app.Saver value in variable declaration: *store.FileStore does not implement app.Saver (missing method Save)
$ go list -deps ./store | grep shop
shop/store
```

| --- | --- | --- |
| 없음 | `cmd/server` | 없음 |
| `store/assert.go` | `store` | `app` |
| `store/store_test.go` | `go vet`, `go test` | 없음 |

| 드는 것 | 내용 |
| --- | --- |
| 간접 호출 | `itab.Fun[n]`을 읽어서 점프한다. [정적 타입 글](/8)에서 사각형 1,000개의 넓이 합을 쟀을 때 원소 하나에 구체 타입은 0.28ns, 인터페이스는 1.77ns였다 |
| 인라이닝 차단 | 호출 대상을 모르면 인라이닝을 못 하고, 그 뒤에 따라오는 escape analysis, 상수 전파, 경계 검사 제거까지 막힌다. 호출 자체보다 이쪽 손해가 클 수 있다 |
| 박싱 할당 | 포인터가 아닌 값을 담은 인터페이스가 함수 밖으로 나가면 값의 복사본을 힙에 만든다(`runtime.convT*`). 0~255 정수는 런타임의 정적 테이블을 가리켜서 할당이 없다 |
| 구제책 | 컴파일러가 구체 타입을 알아내면 직접 호출로 바꾼다(devirtualize). Go 1.21부터는 PGO가 프로파일에서 가장 많이 불린 타입으로 호출을 바꿔 준다 |

<Lab title="인터페이스에 담기만 해도 할당이 생기는 값이 있다">

담은 값이 함수 밖으로 나가는 경우를 보려고, 패키지 변수 `sink any`에 값을 담는 벤치마크를 돌렸다.

```go title="box/box_test.go"
type Point struct{ X, Y int }

var sink any
var n7, n1000 = 7, 1000

func BenchmarkInt7(b *testing.B) {
	for b.Loop() {
		sink = n7
	}
}
func BenchmarkInt1000(b *testing.B) {
	for b.Loop() {
		sink = n1000
	}
}
func BenchmarkPoint(b *testing.B) {
	for b.Loop() {
		sink = Point{n7, n1000}
	}
}
func BenchmarkPtr(b *testing.B) {
	p := &Point{1, 2}
	for b.Loop() {
		sink = p
	}
}
```

```text frame="terminal" title="실행 결과"
$ go test -run x -bench . -benchmem ./box
BenchmarkInt7-10       	712599123	         1.708 ns/op	       0 B/op	       0 allocs/op
BenchmarkInt1000-10    	236220782	         5.130 ns/op	       8 B/op	       1 allocs/op
BenchmarkPoint-10      	166294120	         7.244 ns/op	      16 B/op	       1 allocs/op
BenchmarkPtr-10        	726752438	         1.674 ns/op	       0 B/op	       0 allocs/op
```

포인터와 7은 할당이 없었고, 1000은 호출마다 8바이트를, `Point`는 16바이트를 할당했다. 함수 안에서만 쓰는 인터페이스라면 사정이 달라서, 컴파일러가 구체 타입을 알아내는지 `-m`으로 봤다.

```go title="devirt/shape.go"
type Shape interface{ Area() float64 }

type Rect struct{ W, H float64 }

func (r Rect) Area() float64 { return r.W * r.H }

type Circle struct{ R float64 }

func (c Circle) Area() float64 { return 3.14159 * c.R * c.R }

// 구체 타입이 함수 안에서 보인다
func One() float64 {
	var s Shape = Rect{2, 3}
	return s.Area()
}

// 구체 타입이 밖에서 들어온다
func Total(ss []Shape) float64 {
	var t float64
	for _, s := range ss {
		t += s.Area()
	}
	return t
}
```

```text frame="terminal" title="go build -gcflags=-m (일부)"
$ go build -gcflags=-m ./devirt
devirt/shape.go:16:15: devirtualizing s.Area to Rect
devirt/shape.go:16:15: inlining call to Rect.Area
devirt/shape.go:15:20: Rect{...} does not escape
```

구체 타입이 함수 안에서 보이는 `One`은 직접 호출로 바뀌고 `Rect.Area`가 인라이닝됐다. 인터페이스에 담은 `Rect{...}`도 힙으로 가지 않았다. 슬라이스로 밖에서 들어오는 `Total`의 `s.Area()`에는 아무 말이 없다. 여기는 itab을 거쳐 부른다.

PGO를 켜면 `Total`도 바뀌는지 보려고, `Rect` 9개에 `Circle` 1개 꼴로 섞은 1,000개를 합하는 벤치마크로 CPU 프로파일을 뜨고, 그 프로파일로 다시 빌드했다. `Area`가 곱셈 하나일 때는 프로파일에 `Area`가 거의 잡히지 않아서 컴파일러가 `no hot callee`라며 바꾸지 않았다. 그래서 `Area` 안에 나눗셈 16번을 넣어 프로파일에 잡히게 하고 다시 했다.

```text frame="terminal" title="PGO 빌드 (-gcflags=-m 일부)"
$ go test -pgo=cpu.pprof -gcflags=-m -run x -bench XXX ./pgo
pgo/shape.go:29:14: PGO devirtualizing interface call s.Area to Rect.Area
pgo/shape.go:29:14: inlining call to Rect.Area
```

호출이 `Rect.Area`로 바뀌고 인라이닝까지 됐는데, 벤치마크를 6번씩 돌린 중앙값은 PGO 없이 6.00µs, PGO로 5.99µs였다. 이 예제는 원소마다 나눗셈 16번이 시간 대부분을 차지해서, 간접 호출을 없앤 몫이 측정 오차 안에 묻힌 것으로 보인다. Go 1.21 릴리스 노트도 PGO를 켰을 때 대표 프로그램들의 개선 폭을 2~7%로 적었다.

</Lab>

<Note title="제네릭으로 바꾸면 빨라지나">
[정적 타입 글](/8)에서 잰 결과로는 값 타입을 받는 제네릭이 원소당 0.73ns로 인터페이스(1.77ns)보다 빨랐다. 그렇다고 Go 팀이 인터페이스 대신 제네릭을 권하지는 않는다. Go 블로그의 'When To Use Generics'는 값에 메서드를 부르기만 할 거라면 타입 매개변수 대신 인터페이스를 쓰라고 하고, 타입 매개변수가 대체로 인터페이스보다 빠르지도 않다고 적었다. 그 결과는 값 타입에 작은 메서드라는 모양에서 나온 것이다.
</Note>

## 실습 환경과 한계

예제는 모두 이 맥(Apple M5, 10코어, darwin/arm64)에서 Go 1.26.10으로 다시 돌렸다. staticcheck는 이 맥에 설치된 golangci-lint 2.1.2(Go 1.23.11로 빌드)에 들어 있는 것을 썼고, 그래서 nil 함정 예제만 Go 1.23 모듈로 따로 검사했다. 처음 올린 글의 덤프와 `go vet` 출력은 측정 환경 기록이 없어서 새로 찍은 값으로 바꿨다. 덤프의 주소 값은 실행할 때마다 달라진다.

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
| --- | --- | --- |
| nil 함정 · SA4023 | 이 예제의 동작과 경고 | 여러 함수를 거치거나 필드에 담긴 경우 staticcheck가 어디까지 따라가는지 |
| 두 칸 덤프 · nm | darwin/arm64에서 tab과 data에 든 값 | 다른 버전의 내부 배치. `unsafe`로 읽은 구조는 버전마다 바뀔 수 있다 |
| 컴파일 에러 · go vet · -race | Go 1.26.10의 판정과 문구 | 다른 버전의 문구 |
| 만족 어서션 | 세 자리에서 에러가 나는 곳과 import | 큰 저장소의 빌드·테스트 시간에 미치는 영향 |
| 박싱 · devirtualize · PGO | 이 예제의 할당 수, 컴파일러 결정, 시간 | 실제 서비스에서 인터페이스 호출이 차지하는 몫과 PGO 이득 |

## 정리

| 이 글에서 본 것 | 원인 |
| --- | --- |
| `err == nil`이 거짓 | nil 포인터를 담으면 타입 칸이 찬다 |
| `var b Incer = d`가 컴파일 에러 | 인터페이스에 담긴 값은 복사본이다 |
| `m["a"].Inc()`가 컴파일 에러 | 맵 요소는 주소를 얻을 수 없다 |
| `store`가 `app`을 import | 만족 어서션을 구현체 패키지에 뒀다 |
| `sink = n1000`마다 8바이트 할당 | 포인터가 아닌 값이 함수 밖으로 나갔다 |

nil 함정, 메서드셋, 박싱 할당이 모두 같은 두 칸에서 나온다는 점이 정리하면서 새롭게 알게 된 부분이었다. 헷갈릴 때는 `unsafe.Sizeof`가 16인 그 두 칸에 무엇이 들어가는지부터 따져 보면 된다.
