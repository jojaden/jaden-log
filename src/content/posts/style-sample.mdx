<Lead>
이 글은 테마를 확인하려고 만든 샘플이다. 실제 글을 옮기기 전에, 티스토리에서 인라인 스타일로 쓰던 요소가 MDX 컴포넌트로 바뀌었을 때 다크 본문에서 어떻게 보이는지 한 화면에서 본다.
</Lead>

<Summary>
1. `sync.Pool` 은 짧게 쓰고 버리는 버퍼를 다시 써서 요청당 할당을 줄인다.
2. `Put` 으로 돌려준 뒤의 버퍼와 그 `Bytes()` 는 다른 요청의 것이 될 수 있다.
3. 크게 늘어난 버퍼는 돌려주지 않아야 풀 전체가 커지지 않는다.
</Summary>

## 버퍼를 왜 재사용하나

요청마다 `bytes.Buffer` 를 새로 만들면 힙 할당이 그만큼 늘고, GC 가 치울 일도 늘어난다. 측정해 보니 요청 1만 건에 할당이 <C k="num">10,000회</C>, 풀을 쓰면 <C k="num">37회</C>였다. 설정 파일 경로는 <C k="path">/etc/app/config.yaml</C>, 실패하면 <C k="err">OOMKilled</C> 가 찍힌다.

```go title="pool.go"
var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func render(w io.Writer, v any) error {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset()
	defer bufPool.Put(buf)

	if err := json.NewEncoder(buf).Encode(v); err != nil {
		return err
	}
	_, err := w.Write(buf.Bytes())
	return err
}
```

<Lab title="Put 뒤에 읽은 Bytes()가 바뀌는지 확인하기">

두 고루틴이 같은 풀을 쓰게 하고, `Put` 뒤에 들고 있던 슬라이스를 다시 출력해 본다.

```go title="main.go"
b := buf.Bytes()
bufPool.Put(buf)

other := bufPool.Get().(*bytes.Buffer)
other.Reset()
other.WriteString("overwritten")

fmt.Printf("%s\n", b)
```

```text frame="terminal" title="예상 출력"
overwr
```

</Lab>

## 무엇을 알 수 있고 무엇은 알 수 없나

| 확인한 것 | 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| `-benchmem` 할당 수 | 풀을 쓰면 요청당 할당이 줄어든다 | 실제 서비스 지연이 얼마나 줄지 |
| `GODEBUG=gctrace=1` | GC 주기가 길어진다 | 메모리 상한에 닿는 시점 |
| 위 실습 | Put 뒤 슬라이스는 안전하지 않다 | 경합이 실제로 얼마나 자주 나는지 |

## 큰 버퍼는 돌려주지 않는다

한 번 크게 늘어난 버퍼를 풀에 넣으면 그 크기가 계속 남는다. 처음엔 무조건 돌려줬다가, 일정 크기를 넘으면 버리도록 고쳤다.

```go title="pool.go" del={2} ins={3-6}
func putBuf(buf *bytes.Buffer) {
	bufPool.Put(buf)
	const max = 64 << 10
	if buf.Cap() <= max {
		bufPool.Put(buf)
	}
}
```

## GC 와의 관계

풀에 든 객체는 GC 주기마다 한 단계씩 비워진다[^victim]. 그래서 풀은 캐시가 아니라 잠깐 쓰고 돌려주는 자리다.

[^victim]: Go 1.13부터 풀에는 victim 캐시가 있다. GC 한 번에 바로 사라지지 않고 victim 으로 옮겨졌다가, 다음 GC 에서 비워진다.

> 풀은 오래 보관하는 곳이 아니다. 다음 GC 두 번 안에 사라질 수 있다고 보고 쓴다.

## 다른 방법과 비교

<Compare>
<Side title="요청마다 새로 만들기" tone="bad">

```go
buf := new(bytes.Buffer)
json.NewEncoder(buf).Encode(v)
```

요청 수만큼 할당이 쌓이고 GC 가 그만큼 자주 돈다.

</Side>
<Side title="풀에서 꺼내 쓰기" tone="good">

```go
buf := bufPool.Get().(*bytes.Buffer)
buf.Reset()
defer bufPool.Put(buf)
```

할당은 줄지만 `Put` 뒤의 버퍼는 건드리지 않는다.

</Side>
</Compare>

풀이 늘 답은 아니다. 상황마다 더 단순한 방법이 있다.

<Carousel label="풀 대신 쓸 수 있는 방법">
<Slide title="고정 크기">

크기가 정해져 있으면 배열을 스택에 두는 편이 낫다. 탈출 분석에 걸리지 않으면 힙 할당 자체가 없다.

```go
var buf [512]byte
n := copy(buf[:], src)
```

</Slide>
<Slide title="요청이 적을 때">

초당 요청이 몇 건이면 풀을 안 쓰는 편이 단순하다. 할당 비용보다 `Put` 을 잊는 버그가 더 비싸다.

```go
buf := new(bytes.Buffer)
```

</Slide>
<Slide title="크기가 제각각일 때">

크기 차이가 크면 크기별로 풀을 나눈다. 작은 요청이 큰 버퍼를 물고 있지 않게 된다.

```go
var pools = [...]sync.Pool{ /* 1KB, 16KB, 256KB */ }
```

</Slide>
</Carousel>

## 숫자 하나와 핵심 구절

글 전체가 숫자 하나로 요약될 때는 `<Big>`을 글당 하나만 쓴다.

<Big value="0 B/op" label="풀을 쓴 뒤 요청당 힙 할당 (샘플 글의 예시 수치)" />

결론 문단에서 한 문장만 살릴 때는 `<Key>`로 문단을 흐리게 두고 굵게 쓴 구절만 밝힌다.

<Key>
풀은 요청마다 버퍼를 새로 만드는 비용을 줄여 준다. 대신 **`Put`으로 돌려준 버퍼는 그 순간부터 다른 요청의 것이다.** 슬라이스로 들고 있던 내용도 마찬가지다.
</Key>

## 정리

<Note title="이 글에서 확인한 것">

`sync.Pool` 은 할당을 줄이지만, `Put` 한 뒤의 버퍼와 그 슬라이스는 더 이상 내 것이 아니다. 큰 버퍼는 돌려주지 않고, 풀은 GC 에 비워진다는 전제로 쓴다.

</Note>
